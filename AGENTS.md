# Как работать в этом репозитории

Events Bot для AI Qadam. Несущий стек — [Qadam Flow](https://github.com/aiqadam/qadam-flow),
инстанс <https://app.flow.aiqadam.org>.

## Главное правило

> **0 кода. Всё на Qadam Flow, максимум — Code steps внутри флоу.**

Прежде чем предложить «давайте напишем небольшой сервис / скрипт / кастомный qadam» —
перечитайте [ADR-0001](docs/adr/0001-qadam-flow-as-carrier-stack.md). Это решение принято
с открытыми глазами, включая его цену. Обходить его «по мелочи» нельзя: два-три таких
обхода — и у проекта снова свой деплой.

Что допустимо:

- флоу и subflow-«функции» (`subflows` qadam);
- **Code steps** — только чистые функции: ни сетевых вызовов, ни записи в БД внутри.
  HTTP делает `http`/`telegram-bot` qadam, запись — `tables`;
- core-qadam'ы: `tables`, `crypto`, `store`, `schedule`, `webhook`, `http`, `csv`, `qrcode`, `delay`;
- статические страницы Mini App — **ровно три**: `ticket`, `scan`, `manage`
  (исключение ADR-0001, расширенное с одной страницы до трёх
  [ADR-0017](docs/adr/0017-screen-not-message.md)). Четвёртая — только новым ADR.

Криптографию руками не пишем: HMAC — `crypto` qadam (`hmac-signature`),
Code step рядом только кодирует и сравнивает. **Исключение** (с 2026-09-09,
[ADR-0010](docs/adr/0010-unsandboxed-code-step-for-crypto.md)): в `fn-verify-init-data`
и `fn-sign-qr` HMAC разрешено считать внутри Code step через builtin `node:crypto` —
это узкое решение владельца проекта ради устранения секрета в логах прогонов
(ADR-0005), а не общее снятие запрета. Новых мест для «своей крипты» это не
открывает; npm-пакеты по-прежнему не разрешены без отдельного решения.

`docs/MINIAPP-UX.md` — такая же дельта про среду, в которой живёт Mini App
(навигация, жизненный цикл WebView, Safe Area).

## Роли агентов

Роль агента — не файл харнесса, а **канон в репозитории**: протокол работы
выполняется в любом харнессе, а конфигурация прав у каждого своя. Канонов два:

- **[docs/agents/dev-agent.md](docs/agents/dev-agent.md)** — владелец пакета:
  взял пакет → довёл → `на проверке` → запустил независимое ревью;
- **[docs/agents/review-agent.md](docs/agents/review-agent.md)** — независимый
  ревьюер: проверил живой проект → написал вердикт → ничего не чинил.

Адаптеры харнессов (`.opencode/agent/`, `.claude/agents/`) — тонкие: только
frontmatter прав и указатель на канон, процедур в них нет. Согласованность
адаптеров и правил держит `tools/check-agents.py` (офлайн, pre-commit и CI).
Устройство и цена решения — [docs/agents/README.md](docs/agents/README.md),
[ADR-0029](docs/adr/0029-agent-roles-canon-and-adapters.md).

## Документы — источник правды

- **ТЗ не переписывается по ходу реализации.** Наткнулись на противоречие или
  невозможность — отдельным коммитом правите `docs/SPEC.md` со ссылкой на ADR
  или добавляете вопрос в OPEN-QUESTIONS. Молча реализовать «как удобнее» нельзя.
- Архитектурное решение — новый файл в `docs/adr/`, старый не редактируется задним числом.
- Закрытый вопрос в OPEN-QUESTIONS не удаляется, а помечается ответом.

## Инварианты, которые ломают чаще всего

Проверяйте их явно — каждый уже описан в ТЗ, и каждый легко потерять:

1. **Права контролёра проверяются по конкретному `event_id`** (STF-2).
   «Пользователь вообще где-то staff» — баг: любой участник отметит соседа.
2. **`telegram_id` — единственный ключ** (DAT-1). `username` меняется и может
   отсутствовать; ни связей, ни проверок прав по нему.
3. **Согласие на рассылку отдельно от согласия на обработку данных** (PAR-1, PAR-2).
   `consent_marketing` не проставляется как побочный эффект и по умолчанию `false`.
4. **Все даты в UTC, показ в Asia/Tashkent** (OWN-3). Ввод owner'а — ташкентский.
5. **Идемпотентность** (IDM-1…IDM-4): регистрация, чекин, напоминания, `update_id`.
   Повторный чекин показывает исходное время, а не переписывает его.
6. **`sig` в QR-payload — последние 10 символов, не `split('-')`**: base64url содержит дефис
   ([SECURITY.md](docs/SECURITY.md#ловушка-парсинга)).
7. **I18N-2 приостановлено, а не выполняется.** С
   [ADR-0014](docs/adr/0014-russian-only-until-platform-i18n.md) (W24) тексты
   лежат во входах CODE-шагов на русском, `i18n-sync` не построен, чтений
   `strings` в живых флоу нет. Инвариант на сегодня другой: текст
   **сгенерирован из `i18n/ru.json`**, а не набран руками, и форма ответа шага
   совпадает с эталоном `catalog/snippets/ru-texts.md`. Прежнее требование
   («ни одной строки литералом») вернётся пакетом
   [W25](docs/BACKLOG.md#w25-возврат-i18n-на-платформенном-механизме).
8. **Рассылка: 25 msg/s, `retry_after` на 429, `blocked_bot` на 403,
   кнопка «отписаться», обязательный тест себе** (OWN-10…OWN-13).
9. **Единственные команды — `/start` и `/start <payload>` из диплинка;
   дальше только карточки и Mini App**
   ([ADR-0025](docs/adr/0025-start-only-commands-ban.md), решение владельца
   2026-09-15). Новых команд не заводить — даже служебных: новый сценарий,
   не помещающийся в кнопку, становится экраном. Незнакомая команда карточкой
   меню отвечает, но не исполняется. Живые проверки — `curl` на `/sync`,
   а не команды: `initData` для них человек получает, открыв Mini App кнопкой
   из карточки. Правило держит детерминированная проверка
   `tools/check-commands.py` (хук + CI); существующие маршруты команд сняты
   пакетом [W40](docs/BACKLOG.md#w40-убрать-команды-кроме-start).

## Лимиты платформы

Из исходников (`server/api/src/app/helper/system/system.ts`):

- `FLOW_TIMEOUT_SECONDS = 600` — рассылка бьётся на чанки с курсором;
- `TRIGGER_TIMEOUT_SECONDS = 60` — `checkin-api` обязан быть коротким;
- `TRIGGER_HOOKS_TIMEOUT_SECONDS = 180`.

Проверено прогоном на инстансе 2026-09-08 — не догадки, а факты:

- **Песочница Code step (факт от 2026-09-08, устарел для `pro-data-tech-qa`):** чистый
  ECMAScript + полный `Intl`. Нет `node:crypto`, `fetch`, `Buffer`, `btoa`, `TextEncoder`,
  `crypto.subtle`, npm-зависимостей, `process`. `Intl` с `Asia/Tashkent` и локалью
  `uz-UZ` работает.
  **Обновление 2026-09-09** (тикет инфры `T-0161`, `AP_EXECUTION_MODE=UNSANDBOXED`):
  на этом же инстансе `node:crypto`, `Buffer`, `TextEncoder`, `crypto.subtle`, `process`,
  `require` — все определены и работают (HMAC-SHA256 посчитан прогоном за 6 мс).
  npm-пакеты технически разрешены (`ALLOW_NPM_PACKAGES_IN_CODE_STEP`), но ни один не
  проверен и не согласован — не использовать без отдельного решения. Это настройка
  инстанса, не проекта: обратима, привязка задокументирована в
  [ADR-0010](docs/adr/0010-unsandboxed-code-step-for-crypto.md).
- **Tables (проверено прогонами 2026-09-12):** фильтры и проекция **fail-closed** —
  нечитаемая форма `filters`, несуществующее поле в фильтре и несуществующий
  externalId колонки в `columns` **валят шаг**, а не отдают таблицу целиком.
  Fail-open из [#382](https://github.com/aiqadam/qadam-flow/issues/382) не
  воспроизводится. Практическое следствие: переименование колонки не превратит
  проекцию в тихую утечку — прогон упадёт.
  **Очистить DATE-поле нечем** ([Q30](docs/OPEN-QUESTIONS.md#q30)): пустая строка
  отвергается валидатором, «оставить пустым» у `values` значит «не менять».
  **Проверено 2026-09-13 (W26): то же самое верно и для `TEXT`-полей** — пустая
  строка через `tables-update-record`/`tables-upsert-records` не перезаписывает
  прежнее значение ни там, ни там. «Очистка» поля требует сентинела
  (например, `-`), а не пустой строки.
- **Tables:** уникальных индексов нет, типы полей — только
  `TEXT` / `NUMBER` / `DATE` / `STATIC_DROPDOWN` (boolean хранится как dropdown
  `true`/`false`, JSON — как текст). **`tables-upsert-records`** матчит ключ на
  своей стороне, а не в БД, так что уникальность им не обеспечивается и
  ADR-0003 в силе. **Проверено прогоном 2026-09-13 (W26)** — первое
  использование в проекте: `ap_run_action` insert-then-upsert на `users` дал
  тот же `record id` во второй раз, значение обновилось, дублей нет. С этого
  пакета используется как основной способ записи в обработчиках-касаниях:
  избегает ROUTER'а с последующим схождением веток (ветки в этом движке не
  сходятся, см. `catalog/flows/reg-start.md`).
- **Store:** нет ни put-if-absent, ни TTL.
- **Цена шага (замер 2026-09-13, после двух платформенных фиксов):** ROUTER —
  0,03 мс; CODE-шаг — **2–5 мс** (у HMAC-шагов 12–20 мс — это их собственная
  работа); чтение/запись `tables`, `store`, ответ вебхука — **25–70 мс**;
  отправка сообщения Bot API — **0,7–0,9 с**.
  Первое обращение к каждому qadam'у и первый CODE-шаг в прогоне дороже
  остальных (прогрев), дальше почти бесплатно.
  **Так было не всегда, и старые замеры в документах это отражают.** До
  2026-09-13 PIECE-шаг стоил 344–636 мс
  ([#417](https://github.com/aiqadam/qadam-flow/issues/417), незакэшированный
  обход 238 папок), а CODE-шаг ~75 мс
  ([#412](https://github.com/aiqadam/qadam-flow/issues/412) item 2, спавн
  процесса). Оба починены. Если увидите такие числа снова — проверяйте, не
  откатили ли фиксы, это единственное известное объяснение.
  **Практический вывод:** единственная дорогая статья теперь — **отправка
  сообщений**, и она не лечится внутри платформы. Меньше сообщений = быстрее
  ([ADR-0013](docs/adr/0013-fewer-messages-on-start.md)). Экономить на
  количестве шагов почти бессмысленно; см.
  [ADR-0009](docs/adr/0009-hot-path-latency-budget-and-order.md), раздел
  «Вывод, который стоит унести дальше».
- **Первый прогон после публикации флоу не показателен для замеров.**
  Мемоизация из #417 живёт в процессе воркера, поэтому после
  `ap_lock_and_publish` кэш холодный и первое обращение к каждому qadam'у снова
  платит обход. Замер W24: сразу после публикации трёх флоу визард дал 21,9 с,
  через четыре минуты на прогретом — **9,5 с**. Мерить только по прогретому,
  иначе получите «регрессию», которой нет.
- **Атомарных примитивов нет вообще** — идемпотентность строится по
  [ADR-0003](docs/adr/0003-idempotency-without-atomicity.md), а не на гарантиях БД.
  Обещать exactly-once в этом проекте нельзя.
- **Telegram:** доставка апдейтов — **long-polling, не вебхук** (проверено 2026-09-12,
  W19: `getWebhookInfo` отдаёт `url: ""`, а POST на `/api/v1/webhooks/<tg-router>`
  отвечает `409 «receives events by polling»`). Эксклюзивность на бот-токен
  сохраняется — у `getUpdates` она такая же, как у вебхука, — поэтому бот у events
  по-прежнему **отдельный**. Флоу с триггером `@aiqadam/qadam-webhook`
  (`checkin-api`, `my-qr-api`) это не затронуло: их ingress работает.

## Доступ к инстансу (MCP)

В репозитории зарегистрирован проектный MCP-сервер `qadam-flow`
(`.mcp.json` → `https://app.flow.aiqadam.org/mcp`).

**Авторизация — OAuth, статического токена нет.** Эндпоинт отвечает 401 с
`WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/mcp"`,
клиент проходит стандартный OAuth-флоу MCP через браузер
(`packages/server/api/src/app/mcp/oauth/mcp-oauth.controller.ts`).

Поэтому в `.mcp.json` **не должно быть** секции `headers` с `Authorization`:
заданный вручную заголовок отключает OAuth-фолбэк, и подключение падает с 401.
Секретов для MCP в репозитории не нужно вовсе.

Проектный MCP-сервер требует одобрения при первом запуске сессии
(`/mcp` → `Authenticate`). Проект выбирается на экране согласия — так же
подключается второе окружение (`events-prod`) отдельным сервером.

Отличие от `qadam-flow-project-template`: там `.mcp.json` в `.gitignore`,
у нас он **закоммичен**. Причина — в нашем файле нет ни токенов, ни заголовков:
OAuth-токены Claude Code хранит у себя, а закоммиченный файл избавляет каждого
агента от ручной регистрации сервера.

## Модель работы: пишем через MCP, читаем чем угодно

- **MCP** — строить и менять flows (`ap_build_flow`, `ap_add_step`, `ap_update_step`, …);
- **UI** — проект, connections, variables;
- **REST, только `GET`** — смотреть то, чего не отдаёт MCP;
- **git** — `catalog/*.md` (зачем и на чём ломается) и `flows/*.json`
  (что именно настроено).

**`GET` к REST API разрешён всем ролям и по любым эндпоинтам**
([ADR-0018](docs/adr/0018-rest-read-for-everyone.md), отменяет ADR-0006).
Это нужно потому, что `ap_flow_structure` не отдаёт `settings.input`
PIECE-шагов — URL, cron-выражения, таймзоны, `parse_mode` и порядок аргументов
`hmac-signature` через MCP не увидеть вообще, и владелец пакета не может
проверить собственную работу.

**`POST` / `PATCH` / `DELETE` — по-прежнему никому и никогда.** Сборка, правка
и публикация только через MCP: запись мимо MCP обходит `ap_validate_flow`
(единственная автопроверка вместо тестов) и делает расхождение каталога
с проектом вероятным — это уже случалось (`event-wizard` мимо процесса,
[Q34](docs/OPEN-QUESTIONS.md#q34)).

**Ключ платформы не коммитится** — переменная окружения, подставляется так,
чтобы не попасть ни в вывод, ни в историю оболочки.

Выгрузка `flows/*.json` в репозиторий **разрешена и разблокирована**:
[Q38](docs/OPEN-QUESTIONS.md#q38) закрыт 2026-09-13 — платформа отдаёт
`{{variables['...']}}` и `{{connections[...]}}` строками, как написано,
фактических значений в шаблоне нет. Выгрузка — `tools/export-flows.sh`
(REST `GET`, пакет [W29](docs/BACKLOG.md#w29-экспорт-flowsjson-в-репозиторий)).
Без ключа платформы — `ap_export_flow` через MCP **сразу после
`ap_lock_and_publish`** и `tools/export-flow-mcp.py` (снимок беднее: без
`auth` в шагах и без пустых строк `exampleData`; в манифесте `source: "mcp"`).
Источник правды — репозиторий; каждое изменение инстанса записывается в
таблицу `migrations` ([ADR-0021](docs/adr/0021-repo-is-source-of-truth-migrations-table.md),
дополняет [Q44](docs/OPEN-QUESTIONS.md#q44)).

**Проверка перед каждым коммитом экспорта остаётся обязательной:** проверено
текущее поведение платформы, а не гарантия на будущее — сериализация шаблона
может измениться с версией образа. Значение секрета в экспорте не
откатывается удалением файла.

### Правило синхронизации каталога (главное)

После **любого** изменения flow через MCP:

1. `ap_flow_structure` (+ `ap_read_step_code` для CODE-шагов) — снять актуальную структуру;
2. обновить `catalog/flows/<flow>.md` по формату `catalog/flows/_TEMPLATE.md`;
3. при изменениях таблиц/переменных/связей — обновить `catalog/tables/`,
   `catalog/variables.md`, `catalog/overview.md`;
4. коммит: feature-ветка → PR, не напрямую в `main`.

Каталог и живой проект должны совпадать. Каталог, описывающий то, чего в проекте
нет, хуже пустого: по нему принимают решения.

### Каталог — инструкция, а не дневник

`catalog/` отвечает на один вопрос: **что здесь есть и как оно устроено сейчас**.
Не «как это нашли», не «когда это узнали», не «какой прогон это подтвердил».
Карточка флоу читается как рецепт: шаги, назначение каждого, от чего зависит,
на какие грабли настроен (если наступить на них снова — сломается то же самое).

Практически это значит:

- **Без дат и номеров прогонов в тексте карточки.** «Проверено прогоном
  `xY7z...` 2026-09-13» — это факт про работу над пакетом, а не про флоу;
  его место — журнал пакета (`docs/work/WNN-*.md`). В карточке остаётся
  единственный итог: что это работает и (если нетривиально) чем это
  доказывается по существу («различающим прогоном: не-владелец → отказ,
  владелец → успех»), без ссылки на конкретный запуск.
- **Без глагольной истории обнаружения.** Не «нашли, что X, когда пытались
  сделать Y» — просто «X: <причина, если не очевидна>». Читателю карточки
  не нужно знать, как агент дошёл до факта, ему нужен сам факт.
- **Платформенные факты общего действия (гочи, поведение MCP-примитивов)
  живут в AGENTS.md/ARCHITECTURE.md**, а не размножаются пересказом в каждой
  карточке, которая на них наткнулась. В карточке — короткая ссылка на
  гочу и то, как именно она проявляется в этом флоу.
- **Что удалить при следующей правке карточки, если увидели** — фразы вида
  «раньше было по-другому», «до очистки инстанса», «в отличие от старой
  версии»: это тоже история, а не текущее состояние. Карточка не обязана
  объяснять, чем текущее решение лучше прошлого — только что оно из себя
  представляет.

Журналу (`docs/work/`) — ровно наоборот: там как раз нужны даты, номера
прогонов, путь к решению и тупики. Если факт стоит сохранить и как историю
работы, и как знание о системе — он пишется **дважды в разных тональностях**,
не одной строкой со ссылкой между.

## Где что фиксируется

Три разные вещи в трёх разных местах — путать их нельзя:

| Что | Где | Когда обновляется |
| --- | --- | --- |
| **Состояние системы** — что реально построено | `catalog/` | после каждого изменения флоу |
| **Состояние работ** — кто что взял, что готово | `docs/work/WNN-*.md` + `docs/STATUS.md` | при взятии пакета, по ходу, при закрытии |
| **Решения и нерешённое** | `docs/adr/`, `docs/OPEN-QUESTIONS.md` | как только возникли |

Взятие пакета = коммит, меняющий **свою строку** в `STATUS.md` на `в работе`,
плюс созданный журнал по [шаблону](docs/work/_TEMPLATE.md). Запушить сразу:
отбитый push означает, что пакет уже взят кем-то другим.

У журнала один писатель — владелец пакета, поэтому параллельные агенты не конфликтуют.
Правила — [docs/work/README.md](docs/work/README.md).

**Не ставить `готов`, если сделана часть пакета.** Ставится `заблокирован` с указанием,
чего не хватает: половина, помеченная готовой, всплывёт на приёмке и обойдётся дороже.

### Сдать пакет самому себе нельзя

Обязательный шаг перед статусом `готов` — **независимое ревью**:

```
в работе → на проверке → (замечания) → в работе → на проверке → готов
```

Доведя пакет, владелец ставит `на проверке` и **запускает отдельного
агента-ревьюера с чистым контекстом**, передав ему номер пакета,
[чек-лист ревьюера](docs/work/REVIEW-CHECKLIST.md) и чек-лист пакета из BACKLOG.

- ревьюер проверяет **живой проект через MCP**, а не только диф: каталог — это
  утверждение о реальности, ревью сверяет его с реальностью;
- в чек-листе есть отдельный блок **AppSec**: авторизация и IDOR, криптография,
  инъекции (включая разметку Telegram и формулы в CSV), утечки, устойчивость;
- ревьюер **ничего не чинит сам** — пишет замечания, чинит владелец,
  затем пакет уходит на **повторное** ревью;
- `готов` — только после вердикта «замечаний нет».

Причина проста: юнит-тестов в этом проекте нет, это цена «0 кода». Агент,
только что собравший флоу, видит в нём задуманное, а не сделанное. Свежий
контекст — единственная замена тестам, которая у нас есть.

## Артефакты

- `catalog/` — агентский каталог: живое состояние flows, таблиц, переменных;
- `docs/work/` — журналы пакетов работ, `docs/STATUS.md` — индекс;
- `i18n/{ru,uz,en}.json` — строки; таблица `strings` на инстансе — рабочая копия,
  репозиторий — источник правды;
- `miniapp/` — статическая страница сканера (GitHub Pages).

Секретов в репозитории нет и не будет: bot token — connection платформы,
`QR_SIGNING_KEY` — project Variable, оба задаются в UI.

## Gotchas Qadam Flow

Из шаблона проекта, проверять при сборке шагов:

1. В qadam'ах ключи `values` — это `externalId`; внутренний `id` — только в CODE-шагах.
2. HTTP qadam требует `headers: {}` и `queryParams: {}` даже пустыми.
3. Действия Tables называются `tables-find-records`, `tables-create-records` и т.д.
4. Ссылки на шаги — всегда через `['output']`: `{{trigger['output'].field}}`,
   `{{step_1['output'].id}}`.
5. AI-провайдеры платформенные, connections проектные.
6. Вебхук с синхронным ответом — суффикс `/sync`:
   `POST /api/v1/webhooks/<flowId>/sync`.
7. **Значение пропа `flow` у `callFlow` — объект, а не строка.** Нужен
   `{"externalId": "...", "exampleData": {...}}` в точности той формы, которую
   отдаёт `ap_resolve_property_options` для пропа `flow`; строка с externalId
   проходит валидацию, но валит прогон `{"message":"Please select a flow"}`.
   Это продолжение урока Q20: там же выяснилось, что объект нужен и при
   *резолве* пропов через `ap_get_piece_props`. Проверено 2026-09-12 (W19),
   ценой сломанного на несколько минут входа по deep link.
7a. **`flowProps` у `callFlow` резолвится в единственное поле `payload`
   (`OBJECT`), не в плоские именованные поля callee** — найдено 2026-09-13
   (W26), ломает конвенцию, задокументированную в
   [catalog/flows/README.md](catalog/flows/README.md) и работавшую в W2–W22.
   Без обёртки `{"payload": {...}}` вызов проходит `ap_validate_flow` и
   формально успешен, но callee получает пустые поля — тихий отказ
   (`chat_id is empty` у отправки сообщения внутри вызванного флоу), а не
   ошибка самого `callFlow`. Callee по-прежнему читает поля плоско —
   `{{trigger['output'].data.<field>}}`, платформа разворачивает `payload`
   обратно на его стороне. Проверено различающим прогоном на `tg-router` →
   `reg-start`/`fn-parse-start`. **Обязательно для каждого нового `callFlow`.**
8. Переменная проекта — только `{{variables['NAME']}}`. Короткая форма `{{NAME}}`
   молча даёт **пустую строку**, а не ошибку; несуществующее имя валит прогон
   `INTERNAL_ERROR` без списка шагов
   ([ARCHITECTURE](docs/ARCHITECTURE.md#переменные-проекта-в-шаблонах--проверено-на-инстансе-2026-09-08)).
9. **Текущий элемент `LOOP_ON_ITEMS` — `{{loopStepName['output'].item}}`,
   не `{{loopStepName['output']}}` (голый) и не `{{loopStepName.currentItem}}`.**
   Найдено 2026-09-13 (W26, `event-wizard-publish`): обе неверные формы
   проходят `ap_validate_flow` и даже проходят прогон с **нулевыми**
   итерациями цикла — падают `INTERNAL_ERROR` без детализации по шагам
   только когда в цикле реально есть ≥1 элемент. Тестировать `LOOP_ON_ITEMS`
   с заведомо непустым списком, иначе баг синтаксиса маскируется.
10. **`ap_add_step` с `ROUTER` через `stepLocationRelativeToParent: AFTER` на
    шаг, у которого уже есть следующий шаг, не гейтит существующее продолжение.**
    Найдено 2026-09-13 (W26, попытка исправить `checkin-api`): вставка ROUTER'а
    между `step_1` и уже существовавшим `step_2` создаёт новые ветки (`ap_add_branch`),
    но старое ребро `step_1 → step_2` остаётся отдельным, безусловным путём —
    прогоном подтверждено, что при несовпавшем условии **обе** цепочки
    выполняются одновременно (и новая ветка, и старое продолжение), а не одна
    вместо другой. `ap_validate_flow` при этом ругается на «empty branch»,
    что и есть единственная видимая подсказка о проблеме. ROUTER, вставленный
    таким способом, не подходит для ретрофита gate-логики в уже собранный
    линейный флоу — так ROUTER настраивают только при сборке с нуля
    (`ap_build_flow`) или когда ветвление добавляется сразу после шага,
    у которого ещё нет ребёнка. Откат — `ap_delete_step` на созданный ROUTER
    восстанавливает исходную цепочку (проверено на `checkin-api`, черновик
    не публиковался).
11. **`ap_test_flow` может выполнить прогон с сохранённым sample-входом, а не
    с переданным `triggerTestData`.** Найдено 2026-09-14 (ревью W31, прогон
    `jXsJUpOnf1ETZaNBCm8kr`): заведомо невалидный `initData` в аргументе — а
    прогон прошёл ветку `valid` с прежним телом и **записал в таблицу и
    отправил сообщение**. У флоу с побочными эффектами негативные проверки
    делать только `curl`'ом на опубликованный `/sync`; `ap_test_flow` — когда
    сохранённый sample-вход безвреден. Доказывающие временные флоу не удалять
    до вердикта ревью — `ap_get_run` по их прогонам после удаления отвечает
    «not found».
12. **`ap_update_step` с частичным `input` заменяет вложенный объект целиком,
    а не мержит подключи.** Найдено 2026-09-15 (W37, `manage-api` step_7):
    `"texts": {"<один ключ>": ...}` стёр остальные 35 ключей карты — поймал
    `tools/check-texts.py` (120 сверенных пар → 85). Подключевой мерж работает
    только у DYNAMIC-пропов (`flowProps` у `callFlow`). Обновляя `texts`,
    `fields`, `values` и другие вложенные объекты, присылайте **всю карту**;
    после правки — экспорт и `check-texts.py`, карта ключей восстанавливается
    из git-версии `flows/*.json`.

## Safety rules

**Никогда:**

- не менять ничего в Qadam Flow через REST API: `POST`/`PATCH`/`DELETE` —
  никогда и никому, сборка и публикация только через MCP
  ([ADR-0018](docs/adr/0018-rest-read-for-everyone.md)). `GET` разрешён всем;
- не коммитить платформенный API-ключ: он передаётся ревьюеру переменной
  окружения и подставляется так, чтобы не попасть ни в вывод, ни в историю;
- не коммитить секреты: connections и variables задаются исключительно в UI;
- не удалять flows и таблицы, не отразив это в каталоге;
- не пушить напрямую в `main` — только через PR.

**Всегда:**

- после изменения flow обновлять `catalog/*.md`;
- `ap_validate_flow` перед публикацией;
- если не уверен — остановиться и спросить.

## Проверка работы

Юнит-тестов в привычном виде нет — это плата за «0 кода». Готовность пакета работ
определяется его чек-листом в [BACKLOG.md](docs/BACKLOG.md), а не ощущением «вроде работает».
Три сценария проверяются всегда, потому что ломаются чаще всего:

1. участник пытается отметить участника → отказ;
2. рассылка прервана на середине → продолжается с курсора, никому не шлёт дважды;
3. один `update_id` доставлен дважды → одна реакция.

Проверки, которые запускаются сами, а не по памяти:

| Проверка | Когда | Требует |
| --- | --- | --- |
| `tools/check-export-secrets.sh` | pre-commit при изменении `flows/`/`i18n/ru.json` + CI на PR | — (офлайн) |
| `tools/check-texts.py` (тексты = `i18n/ru.json`) | pre-commit при изменении `flows/`/`i18n/ru.json` + CI на PR | — (офлайн) |
| `tools/check-commands.py` (команд, кроме `/start`, нет) | pre-commit при изменении `flows/`/`i18n/ru.json` + CI на PR | — (офлайн) |
| `tools/check-migrations.py` (манифест ↔ инстанс ↔ `migrations`) | после каждого изменения инстанса через MCP, на ревью, на приёмке W15 | ключ платформы, сеть |

Pre-commit хук: `.githooks/pre-commit`, активация на машине —
`git config core.hooksPath .githooks` (один раз). Хук блокирует коммит,
если в экспорте секрет или тексты разошлись с `ru.json` — обходить
`--no-verify` нельзя: и то, и другое в истории git не откатывается.
CI (`.github/workflows/checks.yml`) гоняет те же офлайн-проверки на PR,
без секретов. Сетевая `check-migrations.py` в хук и CI не входит —
коммит не должен зависеть от доступности инстанса.
