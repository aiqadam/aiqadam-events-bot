# Безопасность и подписи

Проверяется на ревью каждого пакета — блок AppSec в
[чек-листе ревьюера](work/REVIEW-CHECKLIST.md#4-appsec).

## Бюджет deep link

Telegram: `start`-параметр — **до 64 символов**, алфавит **`A-Za-z0-9_-`** (PAR-6).
Всё, что мы кладём в ссылку, обязано влезать. Отсюда жёсткие правила:

- `events.id` — slug в алфавите **`A-Za-z0-9_`**, длина ≤ 12. **Дефис запрещён**:
  он у нас разделитель.
- `utm` — тот же алфавит `A-Za-z0-9_`, длина ≤ 32, дефис запрещён по той же причине.

| Ссылка | Формат | Худший случай |
| --- | --- | --- |
| Регистрация (OWN-6) | `e<id>-<utm>` | 1 + 12 + 1 + 32 = **46** |
| QR участника (PAR-6) | `c<eventId>-<userId>-<sig>` | 1 + 12 + 1 + 16 + 1 + 10 = **41** |
| Инвайт staff (OWN-14) | `s<eventId>-<token>` | 1 + 12 + 1 + 22 = **36** |

`fn-parse-start` обязан отбивать payload длиннее 64 символов и с символами вне алфавита
до всякой другой логики.

### Ловушка парсинга

`sig` — **base64url**, а в его алфавит входит `-`. Значит, `c<eventId>-<userId>-<sig>`
**нельзя разбирать простым `split('-')`**: подпись сама может содержать дефисы,
и разбор поедет.

Правило: `sig` — это **последние ровно 10 символов** payload. Остальное разбирается слева.
То же для `s<eventId>-<token>`: токен — всё после **первого** дефиса.

## Подпись QR (PAR-6)

```
msg = "c:" + eventId + ":" + userId          // канонический вид, фиксирован
raw = HMAC-SHA256(key = QR_SIGNING_KEY, data = msg)
sig = base64url(raw).slice(0, 10)            // без padding
```

- `QR_SIGNING_KEY` — **отдельный секрет**, не токен бота. Живёт в **project Variable**
  и читается только как `{{variables['QR_SIGNING_KEY']}}` (см. «Секреты» ниже).
  Раньше здесь было написано «в connection платформы» — это противоречило таблице
  секретов в этом же файле и реализации; исправлено по ревью W2.
- HMAC считает **`crypto` qadam (`hmac-signature`)**: `method = sha256`,
  `outputEncoding = base64`. Code step получает готовый base64 и переводит его
  в base64url чистыми строковыми операциями: `+`→`-`, `/`→`_`, отрезать `=`, взять 10.
- Своей реализации HMAC быть не может даже при желании: в песочнице Code step нет
  ни `node:crypto`, ни `crypto.subtle`, ни `Buffer`, ни npm
  ([ARCHITECTURE.md](ARCHITECTURE.md#песочница-code-step--проверено-на-инстансе-2026-09-08)).
  **С 2026-09-09 на `pro-data-tech-qa` это больше не физика** (см. обновление в том же
  разделе ARCHITECTURE.md) — владелец проекта разрешил узкое исключение для этой
  цепочки, [ADR-0010](adr/0010-unsandboxed-code-step-for-crypto.md). Реализация
  (слияние `step_2`+`step_3` в один CODE-шаг) — отдельный пакет работ, ещё не начат;
  текст выше описывает **текущее** состояние живого `fn-sign-qr`.
- Сравнение — **constant-time** (посимвольный XOR-аккумулятор, без раннего выхода).
- `userId` в `msg` — тот же `telegram_id` строкой, что и в БД.

**Что даёт обрезка до 10 символов.** 10 символов base64url ≈ 60 бит.
Подобрать подпись офлайн нереалистично, но это и не единственный барьер: чекин
всё равно требует валидного `initData` контролёра, его членства в `event_staff`
этого ивента и существующей регистрации. Подпись отсекает подделку payload'а,
а не заменяет авторизацию.

**Срока жизни у подписи нет** — QR действителен, пока существует ивент.
Это осознанно: участник получает QR при регистрации и открывает его на входе,
возможно, без сети. Ротация `QR_SIGNING_KEY` инвалидирует все выданные QR разом,
поэтому ротация = перевыпуск и рассылка новых кодов.

## Валидация `initData` (STF-2)

Стандартный алгоритм Telegram, без самодеятельности:

```
secret_key = HMAC-SHA256(key = "WebAppData", data = <bot_token>)
data_check_string = поля initData кроме hash,
                    в виде key=value, отсортированы по key, склеены "\n"
expected = hex(HMAC-SHA256(key = secret_key, data = data_check_string))
valid = constant_time_equal(expected, initData.hash)
```

Плюс проверка `auth_date`.

**Как это собирается из `crypto` qadam'а** (ключ второго HMAC — двоичный результат первого):

1. `hmac-signature`: `secretKey = "WebAppData"`, `secretKeyEncoding = utf-8`,
   `method = sha256`, `text = <bot_token>`, `outputEncoding = **hex**`;
2. `hmac-signature`: `secretKey = <hex из шага 1>`, `secretKeyEncoding = **hex**`,
   `method = sha256`, `text = <data_check_string>`, `outputEncoding = hex`;
3. Code step: constant-time сравнение результата с `initData.hash`.

Именно ради шага 2 нужен `secretKeyEncoding` — он есть в qadam'е, так что цепочка
собирается штатно, без единой строчки своей криптографии.

**Практическое замечание про `auth_date`:** сканер контролёра открыт весь вечер,
а `initData` выдаётся один раз при открытии Mini App и не обновляется сам.
Слишком строгое окно (5–15 минут) уронит чекин в разгар входа.
Берём **24 часа** и на просроченном `initData` отвечаем кодом, по которому
страница просит переоткрыть Mini App, — а не молча ломаемся.

`telegram_id` контролёра берётся **только** из проверенного `initData`,
никогда из тела запроса.

## Логи прогонов — тоже секрет ([ADR-0005](adr/0005-secrets-visible-in-run-logs.md))

Цена, которую нельзя не назвать. Платформа логирует входы и выходы **каждого**
шага прогона, и читает их любой, у кого есть доступ к проекту (UI или MCP
`ap_get_run`). Для цепочки выше это значит:

| Что оказывается в логе | Где | Чем это плохо |
| --- | --- | --- |
| `secret_key = HMAC("WebAppData", bot_token)` | вывод шага 1 | этим ключом подделывается `hash` для **любого** `telegram_id` — обход STF-2 целиком, мимо `event_staff` |
| сам bot token | входы шага 1 (`text`) | доступ к боту |
| `phone`, имена, `username` участников | вывод любого `find-records` по `users` | персональные данные (DAT-2) в логах |

**Проверено на ревью W2 (2026-09-08):** ревьюер прочитал производный ключ через
`ap_get_run` и посчитал им валидный `hash`. Это не гипотеза.

Исправить внутри платформы было нечем на момент принятия (2026-09-08): ключ
второго HMAC обязан быть выходом первого, считать HMAC в Code step было не из
чего, проекции колонок у `tables` qadam нет. **Первое условие с 2026-09-09
больше не физика** — `node:crypto` доступен на этом инстансе, и владелец
проекта разрешил слить оба HMAC-шага в один CODE-шаг для `fn-verify-init-data`
и `fn-sign-qr`, чтобы производный ключ/полный дайджест перестали быть выводом
шага ([ADR-0010](adr/0010-unsandboxed-code-step-for-crypto.md)). Это закрывает
только первую строку таблицы выше; вторая (bot token во входах шага) и третья
(ПД без проекции колонок) остаются в силе — ADR-0010 это явно называет.
Реализация — отдельный, ещё не начатый пакет работ. До него актуальны обе
цепочки в виде, описанном выше. Поэтому:

- **доступ к проекту = доступ к bot token и к ПД участников.** Роль «только чтение»
  здесь ничего не защищает — чтения логов достаточно;
- **логи прогонов не выносятся из платформы**: прогон, приложенный к баг-репорту,
  это утёкший токен;
- **компрометация логов = ротация bot token** через BotFather;
- `events-prod` — свой бот и свой `QR_SIGNING_KEY`, чтобы dev-логи не открывали бой;
- **шаг не тянет больше строк, чем ему нужно**: проекции колонок нет, но фильтр есть.
  Полная выгрузка `users` в шаг — дефект. Остаточный риск (ПД найденных строк
  всё равно в логе) — [Q17](OPEN-QUESTIONS.md#q17).

## Двойная проверка контролёра

Валидный `initData` означает «это настоящий пользователь Telegram», и ничего больше.
Второй проверкой обязательно идёт:

```
event_staff WHERE event_id = <eventId запроса> AND telegram_id = <из initData>
            AND revoked_at IS NULL
```

Без привязки к конкретному `event_id` любой участник, открывший Mini App,
отметит соседа. Проверка «пользователь вообще где-то staff» — **баг**.

## Инвайт-токены staff (OWN-14)

- Токен — **22 случайных символа** из `crypto / generate-password`
  (`characterSet = alphanumeric`, `length = 22`). Это `A-Za-z0-9`, подмножество
  алфавита deep link, ≈131 бит энтропии. Генератора случайных байт в Code step нет,
  поэтому источник случайности — только этот qadam.
- В БД лежит **только `sha256(token)`** (`staff_invites.token_hash`).
  Утечка таблицы не даёт работающих ссылок.
- Одноразовость — `used_at`; TTL — `expires_at = created_at + 24ч`.
  Проверяются **оба** условия плюс существование записи.
- Отзыв прав — `event_staff.revoked_at`. Проверка идёт на каждый скан,
  поэтому отзыв действует немедленно, без «протухания сессии».

## Согласия и персональные данные

- `consent_pdn` — обязательный шаг (PAR-1), без него строки в `registrations` нет.
- `consent_marketing` — отдельное, необязательное, по умолчанию `false` (PAR-2).
  Не выставляется как побочный эффект чего-либо. Отказ не мешает регистрации.
- Телефон — только из `request_contact` (DAT-2). Ручного ввода нет: номер от Telegram
  подтверждён, набранный руками — нет.
- Отписка (OWN-13) снимает только `consent_marketing`; регистрации и `consent_pdn` не трогает.
- Экспорт (OWN-8) содержит персональные данные. Кто и когда выгружал — стоит логировать;
  доступ к экспорту — только owner ивента.

## Секреты

| Секрет | Где | Ротация |
| --- | --- | --- |
| Bot token | **connection** `events-bot` (auth qadam'а Telegram Bot) | через BotFather; ломает `initData` до переоткрытия Mini App |
| `QR_SIGNING_KEY` | **project Variable**, `{{variables['QR_SIGNING_KEY']}}` | инвалидирует все выданные QR — только с перевыпуском |

Разница не косметическая: connection — это auth конкретного qadam'а, а ключ подписи
QR не принадлежит никакому qadam'у и нужен шагам `crypto`. Его место — Variables.

В репозитории секретов нет и не будет: конфигурация задаётся в UI платформы,
в git попадают только **имена** переменных ([catalog/variables.md](../catalog/variables.md)).

Но «нет в репозитории» ≠ «защищено»: в логах прогонов и токен, и производный
от него ключ лежат открытым текстом — см. раздел выше и
[ADR-0005](adr/0005-secrets-visible-in-run-logs.md).
