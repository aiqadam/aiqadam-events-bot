## Цель

Владелец уточнил после W58: онбординг (согласие + профиль) обязан
запускаться на **первое** обращение к боту, независимо от того, пришло оно
по диплинку события или голым `/start`, и одинаково для всех ролей
(гость/staff/owner). Решение и его границы — [ADR-0034](../adr/0034-onboarding-any-first-touch.md).

### Как проверено (и чем это ревью ограничено)

У этой сессии **нет рабочего доступа к MCP-инструментам платформы и нет
ключа REST API** (тот же вывод, теми же командами, что и в круге 2 W58,
см. подробности там): `mcp__qadam-flow__ap_*` не появились среди
вызываемых функций, `claude mcp get qadam-flow` показывает «⏸ Pending
approval (run `claude` to approve)» — подключение требует интерактивного
OAuth, которое субагент выполнить не может; `tools/export-flows.sh` не
нашёл ключ ни в `QADAM_API_KEY`, ни в Keychain. Из-за этого пункты
протокола 1/3 (живой прогон `menu`→`reg-profile`→`reg-consent-mkt` через
`ap_test_flow` с обёрткой `{"data": {...}}` и чтение `users` через
`ap_find_records` после записи) **не выполнены** — это ограничение среды,
не находка про пакет.

Сделано вместо этого — реконструкция полного графа шагов всех трёх флоу
пакета из `flows/*.json` этой ветки (побайтовый разбор JSON, с обходом
`nextAction`/`children`/`continueOnFailureBranches`; последнее не входит
в очевидный обход дерева и без него часть шагов `reg-profile` не находится
вовсе):

1. **Гейт `menu` стоит раньше чтения ролей**: `menu/step_1` (`tables-find-
   records users`, только `telegram_id`+`profile_completed_at`) →
   `step_2` (CODE, `needsOnboard`) → `step_3` (ROUTER). Ветка
   `has_profile` ведёт на `step_8` (`staff`) → `step_9` (`event_staff`) →
   `step_10` (`events`) — чтения ролей физически недостижимы из ветки
   `needs_onboard`, которая уходит сразу на `step_4` (карточка
   онбординга). Соответствует ADR-0034 п.2 («гейт один на все роли,
   роли читаются только после»).
2. **`finish_no_event` не пишет `registrations`**: цепочка
   `reg-profile/step_35 → 36 → 37 → (38/39/40 фолбэк)` использует
   `table_id = xHhYjhwqKdONkrYJGcBsz` (`users`, сверено с
   `catalog/tables/users.md`) на обоих upsert-шагах (`step_35`:
   профиль+`consent_pdn`, `step_36`: сессия `await_marketing`) — ни один
   шаг цепочки не обращается к `table_id = SM8tMxfQuQCHRDdAiNJyQ`
   (`registrations`, сверено с `catalog/tables/registrations.md`), в
   отличие от параллельных веток `finish`/`finish_lite`
   (`step_23`/`step_29`, тот же `table_id` регистраций). Разводит ветки
   `reg-profile/step_4` (CODE «render ob card»): `writeKind =
   'finish_no_event'` только когда `action === 'finish' && eventId ===
   ''` — прочитал код целиком, логика соответствует описанию ADR-0034 п.3.
3. **`reg-consent-mkt` разводит билет/каталог по `hasEvent`**:
   `step_5` вычисляет `hasEvent = eventId !== ''` (тот же `eventId`,
   что пришёл в `draft` из `reg-profile`, не из тела запроса и не из
   `callback_data`) и по нему выбирает и заголовок карточки
   (`reg.done.header` / `profile.saved.header`), и `reply_markup`
   второго сообщения (`web_app` на `#/ticket?event_id=…` или на
   `#/events`). Ветка без события не создаёт побочных обращений к
   `registrations` — `step_3`/`step_4`/`step_6` этого флоу трогают
   только `users`/`events`/`sessions`.
4. **`esc()` в `menu/step_4`** (новая копия эталона, добавленная этим
   пакетом) — побайтово равна `catalog/snippets/markdown-v2.md` (один
   `\-`, без регресса на двойной `\\-`).
5. Офлайн-чекеры на актуальном экспорте: `check-texts.py i18n/ru.json
   flows/*.json` — 25 флоу, 218 пар, 0 расхождений (совпадает с числом
   в журнале); `check-commands.py` — 0 нарушений, самопроверка ok;
   `check-export-secrets.sh` — чисто.
6. `docs/SPEC.md` (PAR-8) сверен с ADR-0034 — формулировка «первое
   касание бота, не только первый диплинк», гейт `profile_completed_at`,
   финал без события в каталог — согласована с кодом и с самим ADR.

#### Замечания

1. **важно** Голый `/start` во время незавершённого онбординга по
   диплинку теряет событие. `tg-router/step_10` при
   `command==='start' && parsedKind===''` безусловно ставит
   `route='menu'` **до** проверки активной сессии, а `menu` в ветке
   `needs_onboard` нигде не читает `sessions` и `step_7` делает upsert
   сессии по `telegram_id` с `draft.eventId=''` — черновик диплинка
   затирается. Дальше любой `ob:*` (в т.ч. кнопка исходной карточки)
   уходит в `reg-profile` с пустым `eventId` и завершается
   `finish_no_event`: профиль сохранится, **регистрации на событие не
   будет**. Это расходится с ADR-0034 п.4 («онбординг с диплинком
   заканчивается реальной регистрацией») в сценарии, который прогонами
   пакета не покрыт. Живым прогоном не воспроизводил (ревьюер проект не

   `tg-router`; предложение: не перетирать активную сессию
   `scenario='registration'` с непустым `eventId` либо назвать это
   поведение в ADR/журнале.
2. **важно** Журнал не содержит обязательной сверки нового финала без

## Сверка с прототипом (ADR-0027 п.3a)
