# W59. Онбординг — на первое /start вообще, не только на диплинк (ADR-0034)

- **Статус**: на проверке
- **Владелец**: агент
- **Волна**: вне BACKLOG — прямое решение владельца в чате (продолжение W58)
- **Зависит от**: W58 (без него онбординг по диплинку не работал вообще)
- **Начат**: 2026-09-20 · **Закрыт**: —

## Цель

Владелец уточнил после W58: онбординг (согласие + профиль) обязан
запускаться на **первое** обращение к боту, независимо от того, пришло оно
по диплинку события или голым `/start`, и одинаково для всех ролей
(гость/staff/owner). Решение и его границы — [ADR-0034](../adr/0034-onboarding-any-first-touch.md).

## Как проверено

Живыми прогонами через `ap_test_flow` (с `data`-обёрткой, гоча CLAUDE.md
№13) на инстансе `events-dev`, с последующим чтением таблиц (`ap_find_records`),
не только по ответу шага:

1. `menu` с `telegramId` без строки в `users` → ветка `needs_onboard`,
   why-карточка отправлена, сессия `ob_consent` с `draft.eventId === ''`.
2. `menu` с `telegramId` владельца (профиль уже заполнен W58) → ветка
   `has_profile`, прежнее меню без изменений (роль `guest`, т.к. таблица
   `staff` сейчас пуста — не связано с этим пакетом).
3. `reg-profile`: `ob:allgood` на сессии с `eventId: ''` → `writeKind:
   'finish_no_event'`, `users` получил все шесть профильных полей плюс
   `consent_pdn`, `registrations` не тронута (в отличие от `finish` с
   событием — сверено прогоном W58).
4. `reg-consent-mkt`: `reg:mkt:yes` на той же сессии → заголовок карточки
   «Профиль сохранён» (не «Вы зарегистрированы»), второе сообщение —
   кнопка `web_app` на `#/events` вместо билета.
5. `tools/check-texts.py`/`check-commands.py` — чисто на обновлённом
   экспорте (218 пар, 0 расхождений; 0 команд).

Диагностическая строка `users`/`sessions` (`telegram_id: 888888888`) и её
сообщения удалены после проверки.

## Журнал

- **2026-09-20** — Владелец уточнил после W58: триггер онбординга — любое
  первое `/start`, не только диплинк; одинаково для всех ролей; финал без
  события — кнопка в Mini App с каталогом. Три развилки закрыты прямым
  ответом владельца (см. AskUserQuestion в диалоге), ADR написан до кода.
- **2026-09-20** — Ретрофит ROUTER в уже собранный `menu` уткнулся бы в
  гочу CLAUDE.md №10 (`ap_add_step` ROUTER через `AFTER` на шаг с
  существующим продолжением не гейтит старую цепочку). Пересобрал `menu`
  с нуля: удалил `step_1`…`step_5` с хвоста (`ap_delete_step`, по одному,
  от листьев к корню — так предсказуемо, в отличие от каскада), отстроил
  чтение профиля → CODE-гейт → ROUTER с нуля, внутри веток — прежнее меню
  (без изменений) и новая цепочка онбординга без события.
- **2026-09-20** — Для `reg-profile` ретрофит не понадобился: `step_5` уже
  был ROUTER (из W50/W58), добавление восьмой ветки — штатная операция
  `ap_add_branch`, а не риск, задокументированный в гоче №10 (там речь про
  превращение линейной цепочки в router, не про добавление ветки к уже
  существующему).
- **2026-09-20** — `reg-consent-mkt` обошёлся вовсе без структурных правок:
  ветвление по `hasEvent` целиком внутри CODE-шага (`step_5`), передаётся
  дальше готовым объектом `ticketReplyMarkup` в уже существующее поле
  `reply_markup` шага `step_9` — правка только `input`, ни одного нового
  шага.
