# W17. Inline execution mode для `callFlow` на горячем пути

- **Статус**: в работе
- **Владелец**: агент W17
- **Волна**: 5
- **Зависит от**: W8, W5, W16
- **Начат**: 2026-09-11 · **Закрыт**: —

## Цель

Применить `executionMode: "inline"` (upstream [qadam-flow#363](https://github.com/aiqadam/qadam-flow/issues/363),
раскатано на инстансе) к синхронным `callFlow`-цепочкам горячего пути
(`checkin-api`, `registration`, `fn-event-card`) и перемерить латентность
тем же методом, что [Q22](../OPEN-QUESTIONS.md#q22)/W16 — before/after на
опубликованной версии. Подробности и чек-лист — [BACKLOG.md#w17](../BACKLOG.md#w17-inline-execution-mode-для-callflow-на-горячем-пути).

## Журнал

- **2026-09-11** — пакет взят. Контекст: команда qadam-flow закрыла
  [issue #363](https://github.com/aiqadam/qadam-flow/issues/363) и раскатала
  `executionMode: "inline"` на `callFlow` (PR upstream #365, milestone v2.0.0).
  Это прямой ответ на [Q22](../OPEN-QUESTIONS.md#q22) — «пауза» между хопами
  была объявлена платформой фиксированной архитектурной стоимостью синхронного
  `callFlow` (до 3 циклов BullMQ-джобы + снапшот/resume), inline её убирает,
  исполняя ребёнка в engine-процессе родителя без джобы/снапшота/waitpoint.
  Из финального комментария в issue — жёсткое ограничение: inline-ребёнок
  никогда не должен паузиться (Delay/Human Input/вложенный `queue`-`callFlow`
  с ожиданием). Ни один subflow горячего пути такого не делает — все чистые
  CODE/tables-цепочки, проверено по каталогу перед стартом.
- **2026-09-11** — `ap_get_piece_props` подтвердил схему (`executionMode`,
  `STATIC_DROPDOWN`, дефолт `queue`). `ap_update_step` с частичным `input`
  (только `{executionMode: "inline"}`) подтверждённо **мержит**, а не заменяет
  весь input шага — после первой правки (`fn-event-card` `step_4`)
  `ap_validate_flow` показал только старую известную issue про
  `{{variables...}}`, остальные поля (`flow`/`mode`/`flowProps`/`waitForResponse`)
  сохранились.
- **2026-09-11** — `fn-event-card` (4 шага), `checkin-api` (10 шагов),
  `registration` (22 шага) переведены на `inline` и опубликованы по очереди.
  В `registration` `step_43` на первой попытке `ap_update_step` дал
  `step_validity: invalid` при валидации — повторный идентичный вызов прошёл
  чисто; похоже на транзиент платформы, а не системную проблему (остальные 21
  шаг того же флоу прошли с первого раза).
- **2026-09-11** — after-прогоны на `fn-event-card`/`registration` сняты и
  сравнены с эталоном (см. «Как проверено»); ADR-0009 и Q22 обновлены числами.
  Владелец пакета решил не строить синтетическую fixture-цепочку (`initData`+QR
  через временный флоу с `crypto : hmac-signature`) для `checkin-api` —
  проверит вживую сам. Регресс-прогоны STF-2/IDM-2 тоже оставлены владельцу.
  Статус пакета остаётся **в работе**, не `на проверке` — чек-лист не пройден
  целиком.
- **2026-09-11 — регрессия найдена и исправлена живым прогоном владельца.**
  Владелец гонял `registration` вживую (`return_void_0` регистрируется через
  реальный `/start edemo`). Прогон `vJTyTL3qX0klGVpOXN7EK` упал на `step_44`
  (`send_text_message`) с `400 Bad Request: message text is empty`: `step_43`
  («перевод reg.done», `callFlow → fn-t`) вернул `texts: {}, keys: []` —
  **пустой список ключей**, хотя должен был запросить `key: "reg.done"`.
  Причина — та самая транзиентная история из первой сессии: `step_43` — единственный
  из 22 переведённых на `inline` шагов, которому потребовалась **вторая** попытка
  `ap_update_step` (первая дала `step_validity: invalid`). Вторая попытка передавала
  только `{executionMode: "inline"}` и `ap_validate_flow` после неё показал `valid`,
  но, как выяснилось, при этом молча очистилось `flowProps.payload` (сам `key`/`vars`
  для `fn-t`) — структурная валидация это не ловит, потому что схема `callFlow`
  не проверяет содержимое `flowProps` рантаймом. **Читать `flowProps.payload` через
  MCP нельзя** ([ARCHITECTURE.md](../ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2),
  ADR-0006), поэтому восстановить исходный `payload` пришлось не чтением, а
  реконструкцией по документации `registration.md` (`reg.done`, `{title}` из
  `{{step_39['output'].eventTitle}}`, `lang` из `{{step_1['output'].lang}}`) и
  проверкой на изолированном `fn-t` (`ap_test_flow` с теми же `key`/`vars` —
  прогон `whJ80F7sZI0m7WXbRLCCG`, `text: "Вы зарегистрированы на «AI Qadam Demo
  Meetup»."`, корректно). `ap_update_step` с восстановленным `flowProps.payload`
  + `executionMode: "inline"`, `ap_validate_flow` чист, опубликовано.
  **Гипотеза «риск только у step_43, у которого была повторная попытка»
  оказалась неверной** — см. следующую запись.
- **2026-09-11 — второй битый шаг, гипотеза «риск только у step_43» опровергнута,
  полный аудит всех 36 переведённых шагов.** Владелец продолжил живой прогон
  (`/start` → `pdn_yes`) — прогон `vJTyTL3qX0klGVpOXN7EK`(2-й) упал на `step_47`
  с той же `400 message text is empty`: `step_46` («перевод: согласие на
  рассылку») тоже отдал `texts: {}, keys: []`. **`step_46` при сборке прошёл
  `ap_update_step` с первой попытки** — не было даже сигнала `step_validity:
  invalid`, который «поймал» `step_43`. Значит потеря `flowProps.payload` —
  **не следствие ретрая**, а более общий риск частичного `ap_update_step` на
  DYNAMIC-поле `flowProps` в mode `advanced`: из 8 стихийно проверенных вживую
  шагов (по мере прохождения визарда) 2 оказались битыми (25%) без видимого
  паттерна, отличающего сломанные от целых.
  Решение — **не ждать, пока проверит живой прогон**, а аудировать все 36
  переведённых шагов сразу: для каждого callFlow-шага реконструирован
  `flowProps.payload` по контракту вызываемого subflow'а (`catalog/flows/fn-*.md`)
  и по факту связей, прочитанному из CODE-шагов через `ap_read_step_code`
  (там, где имя поля не задокументировано явно — например, `step_39` дал
  точное имя `eventTitle`, `step_7` — `regDeadlineAt`, `step_11` (`checkin-api`)
  подтвердил, что `parse`/`verify`/`reg` приходят из `step_8`/`step_9`/`step_10`
  с полями `eventId`/`userId`/`sig`/`registered`/`checkedIn`/`checkedInAt`).
  Все текстовые ключи (`reg.*`, `checkin.*`) сверены с `i18n/ru.json` и разом
  прогнаны через `fn-t`/`fn-fmt-time` изолированно (`ap_test_flow`, прогоны
  `y9XV7rUoHNbZD3Z2JqXFG` — 14 ключей `registration` разом, `text`/`missing: []`
  для каждого; `boSbkQ7uKuyJy1SCSvzse` — 8 ключей `checkin.*` разом, тоже чисто)
  **до**, а не после публикации. Обновлены и переопубликованы оба флоу:
  `registration` (`step_10`, `step_11`, `step_13`, `step_14`, `step_16`,
  `step_17`, `step_57`, `step_59`, `step_62`, `step_68`, `step_70`, `step_72`,
  `step_73`, `step_74` — 14 шагов) и `checkin-api` (`step_2`, `step_8`,
  `step_9`, `step_10`, `step_19`, `step_29`, `step_30`, `step_31`, `step_32`,
  `step_33` — все 10 шагов, ни один из которых ещё не проверялся живым
  прогоном). `fn-event-card` не тронут повторно — все 4 его шага уже
  подтверждены живыми данными несколько раз (карточка приходит с правильным
  текстом на всех прогонах `registration`).
  `ap_validate_flow` чист на обоих флоу (кроме двух старых `{{variables...}}`
  false positive). **Не проверено этим агентом**: полное прохождение
  `registration` вживую до конца (`existing`/IDM-1, `declined`) и ни один живой
  скан `checkin-api` — оба флоу переопубликованы «по построению и изолированной
  сверке ключей», а не «доказаны сквозным прогоном». Следующему, кто продолжит
  пакет (включая самого владельца вживую), стоит трактовать этот аудит как
  снижение риска, а не как замену независимого ревью и сквозных прогонов —
  чек-лист пакета по-прежнему не закрыт.
- **2026-09-11 — живой скан `checkin-api` состоялся, аудит подтверждён.**
  Владелец сбросил регистрацию `return_void_0`, довёл её заново через живой
  `/start` (после хотфикса `step_46` — прошло чисто), затем отправил
  `binali_beelab` (реальный стафф `demo` в `event_staff`) сообщение с
  `web_app`-кнопкой на сканер (`ap_run_action`, разово, без сборки флоу —
  автоматической выдачи ссылки на сканер стаффу в проекте ещё нет, W10/W11).
  `binali_beelab` отсканировал QR — прогон `Dv6ccs06vqwdHeXBH6bVE`,
  `SUCCEEDED`, 10,0 с, исход `ok`, `checked_in_at` записан. Все 10
  переведённых на `inline` шагов `checkin-api` (включая пять аудированных
  ранее без живой проверки) отработали корректно с первого реального
  прогона — аудит от предыдущей записи подтверждён, а не опровергнут.
  Числа записаны в ADR-0009/Q22.

### Замечания

## Хвосты и блокеры

- `checkin-api`: after-замер и позитивный контроль STF-2 сделаны живым сканом
  (`Dv6ccs06vqwdHeXBH6bVE`, 10,0 с, `isStaff: true`) — остались **три
  отрицательных** различающих прогона STF-2 (не-стафф, стафф чужого `event_id`,
  отозванный стафф — все должны дать `403`), не повторены после W17.
- `registration`: ветки `declined` и `existing`/IDM-1 (повторный `/start`)
  не пройдены живым прогоном ни разу — payload реконструирован по документации
  и сверен изолированно через `fn-t`/`fn-fmt-time`, но сквозного подтверждения
  (как для `start`→`new`→`pdn_yes`→`mkt_*` веток) нет.
- **Найдены и исправлены две регрессии живыми прогонами владельца** (`step_43`,
  `step_46` — пустой `flowProps.payload` после `ap_update_step`), после чего
  весь пакет из 36 переведённых callFlow-шагов **аудирован и переопубликован**
  (14 доп. шагов `registration`, все 10 шагов `checkin-api`) — см. журнал
  2026-09-11. Причина потери `flowProps.payload` **не выяснена окончательно**:
  затронуло и шаг с ретраем (`step_43`), и шаг без него (`step_46`), явного
  паттерна нет. Это open-item для отдельного разбора (возможно, стоит вопроса
  апстриму платформы), не блокер конкретно этого пакета — но означает, что
  **любой будущий частичный `ap_update_step` на DYNAMIC-поле `flowProps`**
  (не только `executionMode`) заслуживает последующей проверки прогоном,
  а не доверия к зелёному `ap_validate_flow`.
- Независимое ревью не запускалось — статус `на проверке` рано ставить, пока
  открыты пункты выше.
