# W64. Стресс-тест ёмкости: 500 гостей × 10 ивентов

- **Статус**: диагностика завершена (вне BACKLOG, кода не построено)
- **Владелец**: агент
- **Волна**: вне волн (задание владельца, 2026-09-21)
- **Зависит от**: —
- **Начат**: 2026-09-21 · **Закрыт**: 2026-09-22

## Цель

Ответить на вопрос владельца замером, а не догадкой: переживёт ли система
500 гостей на каждый из 10 ивентов (5000 действий) в одном окне. Побочно —
независимая перепроверка [Q33](../OPEN-QUESTIONS.md#q33) (задержка
диспетчеризации).

Итог сведён в [Q61](../OPEN-QUESTIONS.md#q61), платформенная часть — апстриму:
[qadam-flow#509](https://github.com/aiqadam/qadam-flow/issues/509) (молчаливые
потери под нагрузкой) и [#510](https://github.com/aiqadam/qadam-flow/issues/510)
(задержка до старта и неработающий `TRIGGER_TIMEOUT_SECONDS` на этой стадии).

## Как проверено

Два захода на `events-dev`. Первый — изолированный, без записи в боевые таблицы;
второй — настоящий сквозной путь через боевые `checkin-api`/`registrations`.

### Заход 1 — слой данных и диспетчеризация

Временная таблица-зеркало `zz-stress-reg` (поля `event_id`/`telegram_id`/
`status`/`registered_at`), 5000 строк (10 ивентов × 500).

- Засев 5000 строк батчами по 50: **22,4 с**, 0 ошибок.
- Зонд с теми же чтениями, что у боевых флоу (`event_id eq … limit 200` и
  `event_id in (10) + status=registered limit 500`): прогон **0,5 с** на оба
  чтения (700 строк), тёплый end-to-end **~0,7 с**. Слой данных на 5000 строк
  не деградирует — это не узкое место.
- Диспетчеризация (тот же зонд, публичный `events-api`):

  | Нагрузка | min | med | max | ошибки |
  |---|---|---|---|---|
  | зонд, 1 (тёплый) | 0,69 с | — | 0,73 с | 0 |
  | зонд, 20 параллельно | 2,90 с | ~4,3 с | 6,73 с | 0 |
  | зонд, 50 параллельно | 2,31 с | — | 15,90 с | 0 |
  | `events-api`, 30 параллельно | 1,06 с | 2,72 с | 6,47 с | 0 |

  Платформа не отдаёт `429`/`5xx`, но ставит прогоны в очередь: задержка растёт
  почти линейно от конкурентности.

### Заход 2 — настоящий E2E через боевые `checkin-api`

Синтетические гости не могут пройти `initData`-гейт своими силами: `checkin-api`
и `reg-api` проверяют `initData` по `BOT_TOKEN` (`fn-hmac-init-data`), а QR —
по `QR_SIGNING_KEY`; оба секрета — project Variables, снаружи не читаются.
Подпись сделана «монетным» флоу `zz-mint`: HMAC считался в Code step по
`{{variables['BOT_TOKEN']}}`/`{{variables['QR_SIGNING_KEY']}}` (**цену — секрет
во входе шага и, вероятно, в логе прогона — владелец принял явно**;
[ADR-0005](../adr/0005-secrets-visible-in-run-logs.md)/[ADR-0010](../adr/0010-unsandboxed-code-step-for-crypto.md)
по умолчанию этого не разрешают). Форматы сверены с живым кодом
`fn-hmac-init-data`, `fn-sign-qr`, `fn-parse-start`; корректность подписи
подтверждена различающим откликом: `reg-api` с подделанным `initData` ответил
`outcome:"mine"`, а не `401`.

Засеяно **5000 регистраций** (10 ивентов × 500) + **10 `event_staff`** в боевые
таблицы за 17 с. Затем **5000 синхронных вызовов боевого `checkin-api`**,
конкурентность 40.

| Метрика | Значение |
|---|---|
| Прогонов / wall | 5000 / **1611 с (26,9 мин)** |
| Пропускная | **3,1 прогона/с** |
| HTTP `200 ok` | **2684 (53,7%)** |
| HTTP `204` (пустое тело) | 1833 (36,7%) |
| HTTP `502` | 483 (9,7%) |
| Латентность min/med/p95/max | 0,29 / 2,75 / **30,95** / 40,45 с |
| Записалось в БД (счётчик `checkin-counter-api`) | **2688** `checked_in` — ровно там, где `200` |

`users` не засевались намеренно (в горячем пути читается `first_name`; без
строки вердикт — «участник без имени — отмечен», `status: ok`). Чтение `users`
при этом всё равно исполнялось.

**2312 сканов (46%) потеряны** — без вердикта и без записи; ни один `204`/`502`
не «дошёл потом» (проверено по БД после завершения).

## Журнал

- **2026-09-21** — блокер на входе: `TELEGRAM_BOT_TOKEN` в окружении агента —
  это `binali_picode_bot`, не бот событий (`aiqadam_events_dev_bot`), поэтому
  локально `initData` не подписать. Развилка предложена владельцу; выбран
  вариант с «монетным» флоу (подпись настоящая, риск логов принят).
- **2026-09-21** — грабли, знакомые по каталогу, повторились в новом коде:
  ключи `values` — `externalId` (первый сид упал с `Table with externalId … not
  found`, потому что `ap_create_table` возвращает внутренний `id`, а qadam
  ищет по `externalId`); `table_id` в шаге — тоже `externalId`, не `id`.
- **2026-09-21** — `users` не засевались осознанно: это вдвое сокращает объём
  записей и чистку, а горячий путь всё равно читает таблицу (возвращая пусто).
  Цена — «участник без имени» в вердикте; на `status: ok` это не влияет.
- **2026-09-22** — чистка сделана не руками, а временным флоу
  `zz-clean-regs` (`tables-find-records` `limit 500` → `tables-delete-record`
  массивом id, повтор): 10 вызовов удалили 5000 регистраций, 10 строк
  `event_staff` — точечно через MCP. Ни один временный артефакт не остался.
- **2026-09-22** — апстрим перепроверил замер и **опроверг** вывод «молчаливые
  потери диспетчера»: прогоны не терялись, а падали на гонке чтения-после-записи
  строки прогона (`The parent run could not be verified.`), а `204` — срез
  30-секундного `AP_WEBHOOK_TIMEOUT_SECONDS`. Причина разобрана и исправлена
  [PR #511](https://github.com/aiqadam/qadam-flow/pull/511) (мерж `046adc8`).
  Итог исправлен в [Q61](../OPEN-QUESTIONS.md#q61) и [Q33](../OPEN-QUESTIONS.md#q33);
  перезамер — ниже.

## Перезамер после фикса платформы (2026-09-22)

Платформа исправила обе поломки, давшие 46% потерь ([PR #511](https://github.com/aiqadam/qadam-flow/pull/511),
мерж `046adc8`): гонку чтения-после-записи строки прогона (инлайновый `callFlow`
первого шага не находил родителя) и молчаливый `204` на упавшем прогоне.

Тот же бурст 5000 синхронных вызовов при конкурентности 40 воспроизведён на
временном стенд-ине пути `checkin-api`: 4 инлайновых `callFlow` (initData, parse,
verify-qr, find-registration) + чтение временной таблицы + guarded-запись + ответ.
**Секреты не использовались**: вместо `BOT_TOKEN`/`QR_SIGNING_KEY` — фейковые
константы (шаги и крипта те же, ключ не настоящий), поэтому, в отличие от захода 2,
в логи прогонов секрет не попал.

| Метрика | До фикса (заход 2) | После фикса |
|---|---|---|
| HTTP `200 ok` | 2684 (53,7%) | **5000 (100%)** |
| `204` / `502` | 1833 / 483 (46%) | **0 / 0** |
| Пропускная | 3,1 прогона/с | 4,0 прогона/с |
| min / med / p95 / max | 0,29 / 2,75 / 30,95 / 40,45 с | 6,3 / 9,8 / 12,1 / 18,2 с |
| Записалось в БД | 2688 | **5000** (`checked_in_at not_exists` → 0) |

Вторая половина фикса проверена отдельным временным флоу с намеренным падением
на шаге: ответ `500 {message, runId}` за ~0,5 с вместо пустого `204` через 30 с.

Вывод: **потерь нет** — причина 46% была не в ёмкости диспетчера. Потолок
~3–4 прогона/с остался: это время в очереди **до** старта, отдельный
backpressure-вопрос ([Q61](../OPEN-QUESTIONS.md#q61)); апстрим-тикеты #509/#510
не закрыты.

Временные артефакты (флоу `zz-race-probe`, `zz-fail-probe`, `zz-seed`; таблица
`zz-stress-reg`) удалены, живой проект — как до теста.

## Хвосты

- **Точка перегиба не измерена.** Замерены крайние режимы (1 параллельный и
  40/50); между ними — не мерили. «Одни двери и 300 гостей» безопасны по
  краевым замерам (последовательный поток ~1 с/скан, потолок не достигается),
  но утверждение «до N дверей безопасно» пока без прямого прогона.
- **Секреты.** Вариант с «монетным» флоу оставил `BOT_TOKEN`/`QR_SIGNING_KEY`
  в истории прогонов (флоу удалены, логи прогонов удалить нельзя). На `dev`
  принято владельцем; на `prod` этот приём повторять нельзя. Перезамер
  2026-09-22 прошёл без секретов (фейковые ключи) — этот путь предпочтителен
  для любой будущей проверки.
- **Проектные лимиты чтений** на 500/ивент дают тихую неверность (не ошибку):
  `reg-api/step_7` `limit 200` (занятость/`no_seats`), `reminders/step_1,3`
  `limit 500`, `lifecycle/step_4`, `checkin-counter-api/step_4`. Сведены и
  вынесены на решение в [Q61](../OPEN-QUESTIONS.md#q61).
- **Один инстанс, один день.** Потолок ~3 прогона/с — замер `events-dev`, а не
  паспорт платформы; потолок может быть общим на инстанс и зависеть от чужих
  прогонов.
