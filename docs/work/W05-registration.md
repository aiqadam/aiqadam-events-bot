## Цель

Флоу `registration` ([FLOWS.md](../FLOWS.md#registration--регистрация-участника)):
участник переходит по `/start e<id>-<utm>`, получает карточку ивента и место
(с учётом овербукинга), даёт обязательное согласие на обработку данных,
опционально — согласие на рассылку и телефон, получает QR.

## Как проверено

  ссылка на Я.Карты, запись `sessions` (`await_pdn`), вопрос согласия с

## Журнал

- **2026-09-09, начало пакета** — Q20 (`callFlow` с данными через MCP)
  переоткрыт и закрыт **до** сборки: причина была в форме `input.flow` при
  резолве `ap_get_piece_props` (нужен объект с `exampleData`, а не строка), а
  не в платформе. Подробности — [ARCHITECTURE](../ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2),
  блок «Опровергнуто»; тот же текст также лежит в отдельной ветке `docs/q20-callflow-payload`
  (PR #14), которая на момент старта W5 ещё не была смержена — правки
  ARCHITECTURE.md/OPEN-QUESTIONS.md/STATUS.md в этом пакете дублируют то же
  содержимое, чтобы ветка `w5-registration` была самодостаточной; при мерже
  обеих веток возможен git-конфликт в этих файлах — это ожидаемо, не ошибка.
- **Хранение состояния диалога** — переиспользована существующая таблица
  `sessions` (заведена под owner-визарды в DATA-MODEL.md, `event_create`/
  `event_edit`/`broadcast`), добавлено значение `scenario = 'registration'`.
  Новой таблицы заводить не пришлось — `scenario` не dropdown, а `TEXT`,
  ограничений на набор значений в БД нет (см. `sessions.md`).
- **`tg-router` менялся минимально** — по конвенции пакета (`ap_add_branch`
  на существующий `step_14`, без переделки остального роутера): одна ветка
  для `start_payload` → `fn-parse-start` → вложенный router по `kind`
  (`e` → `registration`, иначе — старый fallback-лог), вторая ветка — для
  продолжения визарда по `session.scenario = 'registration'`. Оба вызова
  `registration` — `waitForResponse: false`: `registration` — тяжёлая цепочка
  вложенных `callFlow` (сравнимо с `fn-event-card`, ~13 с в одиночку),
  роутеру, синхронно обслуживающему вебхук бота, незачем её ждать.
- **QR-доставка не заработала** — не из-за ошибки конфигурации, а видимо
  из-за платформенного ограничения. Опробовано два независимых пути (см.
  [Q21](../OPEN-QUESTIONS.md#q21) и блок в ARCHITECTURE.md): FILE-проп
  `send_media.media.photo` не резолвит ссылку на файл предыдущего шага
  (либо роняет значение, либо пишет саму строку-URL как «файл»); прямой
  `custom_api_call` на `/sendPhoto`/`/sendDocument` с этим URL реально уходит
  в Bot API, но Telegram не может скачать файл по ссылке инстанса
  (`"failed to get HTTP URL content"`, одинаково для фото и документа).
  Потрачено ~8 конфигураций на разбор, прежде чем остановиться и
  задокументировать как блокер — дальше перебирать не стал, по прямому
  указанию не тратить часы на угадывание форм, если блокер похож на
  платформенный (по опыту Q20 — именно так и оказалось один раз, но не в
  этот).
- **`sendVenue`** пришлось собирать через `custom_api_call` — у
  `@aiqadam/qadam-telegram-bot` нет отдельного action'а, есть только
  `send_location` (без `title`/`address`).
- **Капасити считается прямым `tables-find-records` по `registrations`**
  (`status = registered`, `limit 500`), не через `fn-find-registration` —
  тот отвечает за одну пару `(event_id, telegram_id)`, а не за агрегатное
  число участников события.
- **`answer_callback_query` везде `continueOnFailure: true`** — не только
  ради тестируемости (фиктивный `callback_query_id` в `ap_test_flow` всегда
  даёт `"query is too old..."`), но и как осознанное решение для прода:
  неотвеченный (просроченный) callback не должен ронять остальную бизнес-логику.
- **Q21 переоткрыт перед тем, как звать пользователя за решением — и решён
  архитектурно, не обходом.** Прежде чем предлагать внешний object storage
  (S3/R2, вариант, который рассматривался), проверил на изолированной паре
  тестовых флоу: платформенный `http`-qadam с `body_type: raw` на деле шлёт
  `JSON.stringify` строки, а не сырые байты; FILE-проп (`fieldType: file`) не
  резолвит base64/data-URI ни у `send_media`, ни у `http`-qadam'а — та же
  стена, что и в оригинальной находке Q21, только уже без Telegram и без
  внешнего сервиса вовсе. Значит смена стораджа не решает проблему — решение
  [ADR-0007](../adr/0007-qr-rendered-in-miniapp.md): QR не отправляется файлом
  никуда, а рендерится клиентским JS в `miniapp/ticket.html` из подписанного
  `payload`, который отдаёт новый флоу `my-qr-api`. Удалены ставшие ненужными
  шаги генерации картинки (`text_to_qrcode`) из обеих веток `registration` —
  подпись (`fn-sign-qr`) осталась, она нужна для `payload` и для fallback-ссылки.
- **Новые ключи i18n (`reg.qr.open_miniapp`, `reg.qr.button`) добавлены в
  `i18n/*.json`, но таблица `strings` их ещё не содержит** — `i18n-sync`
  синхронизируется по cron из `main`, а эта ветка (`w5-registration`) в `main`
  ещё не смержена. До прогона `i18n-sync` **после мержа** `fn-t` возвращает сам
  ключ вместо перевода (документированное поведение фолбэка, не баг) — это
  видно и в прогонах ниже (`"text":"reg.qr.open_miniapp"`). Тот же
  пост-мерж-ритуал, что уже был у W3 (`i18n-sync`) — обязательный шаг после
  мержа этого PR, не отдельная задача.
