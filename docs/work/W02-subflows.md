## Чек-лист готовности

- [x] `fn-parse-start` корректно разбирает `c…`-payload, где **`sig` содержит дефис**
      (последние 10 символов — подпись, не `split('-')`)
- [x] отбивается payload длиннее 64 символов и с символами вне `A-Za-z0-9_-`
- [x] `fn-sign-qr` использует `crypto` qadam (`sha256`, `outputEncoding = base64`),

- [x] `fn-verify-init-data` собран цепочкой из двух `hmac-signature`,
      где ключ второго — hex-вывод первого
- [x] `fn-find-registration` при нескольких строках на `(event_id, telegram_id)`
      возвращает самую раннюю (ADR-0003)
- [x] `fn-verify-qr` и `fn-verify-init-data` сравнивают **constant-time**
- [x] `fn-verify-init-data` **сверен с независимой реализацией** HMAC и отвергает
      подделанный `hash`, подменённый `user` и просроченный `auth_date`
- [ ] прогон на `initData` **от живого клиента Telegram** — **не сделан**, критерий

      агент синтезировать её не может, а MCP не отдаёт inputs PIECE-шагов, поэтому
      ориентацию аргументов первого HMAC чтением не подтвердить
- [x] `fn-fmt-time` отдаёт ташкентское время для UTC-входа (OWN-3)
- [x] `catalog/` совпадает с живым проектом
- [ ] пройдено независимое ревью, вердикт «замечаний нет»

## Как проверено

Все прогоны — `ap_test_flow` на инстансе; отрицательные сценарии прогонялись
как отдельные запуски, а не читались глазами по коду.

### `fn-parse-start`

- `cmeetup01-555000111-x6-XmQ2T8R` — **реальная** подпись из `fn-sign-qr`, в которой
  есть дефис → `eventId=meetup01`, `userId=555000111`, `sig=x6-XmQ2T8R`.
  Наивный `split('-')` дал бы `sig="x6"` — ловушка воспроизведена, а не постулирована.
- `cmeetup01-123456789-Ab-cd_efGhXXXX…` (65 символов) → `too_long`.
- `emeetup01-tg ads!` → `bad_charset`.
- `emeetup01-tg_ads_2026` → `kind=e`, `utm=tg_ads_2026`.
- `smeetup01-Ab3kZ9qLm2Xy7Pw1Rt5Nc0` → `kind=s`, токен 22 символа.
- `cmeetup01-abc-Ab-cd_efGh` → `bad_user_id`; `cmeetup01-123456789-Abcd_efGh`
  (подпись 9 символов) → `bad_qr_payload`; `""` → `empty`.

### `fn-sign-qr`

- `meetup01` + `123456789` → base64 `NBqSKT4StU…CHf0=` → `sig=NBqSKT4StU`,
  `payload=cmeetup01-123456789-NBqSKT4StU`.
- `555000111` → base64 `x6+XmQ2T8R…` → base64url `x6-XmQ2T8R…`: видно, что
  конвертация `+`→`-` реально срабатывает, а не «должна».
- Пустой `eventId` → прогон **падает** на первом шаге с `fn-sign-qr: bad eventId`.
  Так и задумано: подпись от `c::` опаснее падения.
- **Ключ не пустой.** HMAC-SHA256 с пустым ключом от `c:meetup01:123456789` даёт
  `hXO+doL7M4yot0XfX6zoJrukAfHxavZuiZ8csDvmspw=` (посчитано вне платформы),
  инстанс вернул `NBqSKT4StUDQQa8yVXWZqarAYGLe3OEynv6mcR6CHf0=`. Расходятся →
  `{{variables['QR_SIGNING_KEY']}}` подставился. Без этой сверки «успешный прогон»
  ничего не доказывает: опечатка в имени переменной тоже даёт успешный прогон.

### `fn-verify-qr`

- Валидная подпись с дефисом → `valid: true`.
- Последний символ подписи изменён (`…T8Q`) → `bad_signature`.
- Подпись пользователя `555000111` предъявлена за `123456789` → `bad_signature`
  (подпись привязана к паре, а не только к ивенту).
- `sig = "'; DROP TABLE"` → `bad_input`, прогон не падает; лишний HMAC от заглушки
  посчитан — цена одного пути исполнения.

### `fn-verify-init-data`

Оговорка честности: `initData` **от живого клиента Telegram у агента нет**, и после
ревью соответствующий пункт чек-листа снят, а критерий перенесён в W8
([Q16](../OPEN-QUESTIONS.md#q16)). Что проверено — ниже; чего этим **не** доказано:
что в `text` шага 2 стоит именно токен. MCP не отдаёт inputs PIECE-шагов, поэтому
подтвердить это можно только глазами в UI или первым живым `initData`.

1. **Алгоритм сверен с внешней реализацией.** Для `data_check_string`
   `auth_date=1789047720\nquery_id=AAF\nuser={"id":555000111,"first_name":"Test"}`
   шаг 3 вернул `632d6a78…59e9`; независимый расчёт HMAC-SHA256 с ключом из шага 1
   дал ровно то же значение. Значит цепочка — телеграмовская, включая трактовку
   hex-ключа второго HMAC как двоичного.
2. **Подпись делает сам бот-токен.** Шаг 2 вернул значение, отличное от
   HMAC(`WebAppData`, `""`) = `e2a4475b…dee1`, то есть `{{connections['…']}}`
   раскрылся в непустой токен.
2а. **Семантика аргументов qadam'а проверена прямо**, а не выведена из документации:
   `ap_run_action` с `secretKey = "WebAppData"`, `text = "PROBE-W2"`
   (прогон `SySnRsY42NKUDcjijmOE9`) дал `5a2b099b…3e8b`, что равно
   HMAC(key=`WebAppData`, msg=`PROBE-W2`) и **не** равно обратной ориентации
   `4469d2c2…67cc`. Значит `secretKey` — это ключ, `text` — сообщение.
   Это половина того, что закрывал бы живой `initData`; вторая половина (что
   в `text` стоит токен) остаётся за [Q16](../OPEN-QUESTIONS.md#q16).
3. **Положительный сценарий.** `initData` с корректным `hash` (посчитан ключом,
   который выдал шаг 2 — тем же токеном бота) и свежим `auth_date` → `valid: true`,
   `telegramId: 555000111`, `ageSeconds: 40`.
4. **Подделанный `hash`** (`0000…`) → `valid: false`, `reason: bad_hash`,
   `telegramId: ''`.
5. **Подмена `user`** на `{"id":999,"first_name":"Evil"}` при валидном чужом `hash`
   → `bad_hash`, `telegramId: ''`. Именно этот сценарий и есть STF-2.
6. **Порядок полей не важен**: тот же `initData` с полями в другом порядке →
   `valid: true` (сортировка по ключу работает).
7. **Просроченный, но правильно подписанный** `initData` (`auth_date` на 27 ч раньше)
   → `hashValid: true`, `fresh: false`, `reason: expired`. Это тот код, по которому
   Mini App просит переоткрыться. После ревью тот же прогон
   (`5Lajtk7X2fFsbmV7938t7`) проверяет ещё две вещи: `telegramId: ''` и `user: null`
   при `hashValid: true` — просроченная подпись больше не отдаёт личность; и вход
   `maxAgeSeconds: 999999999` вернулся как `86400` — окно свежести не отключается
   параметром.
8. **Мусор** `not a query string at all` → `reason: malformed`, прогон не падает.

### `fn-fmt-time`

- `2026-09-10T14:00:00Z`, `ru` → `10 сентября 2026 г. в 19:00` (UTC+5 — верно).
- `2026-09-10T13:42:00Z`, `ru`, `format=time` → `18:42` — ровно та строка,
  что стоит примером в ТЗ («уже отмечен в 18:42»).
- `2026-09-10T14:00:00` (**без зоны**), `uz` → `10-sentabr, 2026, 19:00`:
  дополнение `Z` работает, узбекская локаль на месте.
- `2026-09-10T13:42:00+05:00`, `lang=de` → `13:42`, `lang` вернулся `ru` (фолбэк).
- `not-a-date` → `valid: false`, `error: bad_date`.
- Переход суток (добавлено по ревью, `buOGxNqxounjPqYwJKyU0`):
  `2026-09-10T19:30:00Z` → `11 сентября 2026 г. в 00:30`.

### `fn-find-registration`

Фикстура: три строки на `(meetup01, 555000111)` — `registered` (рег. 01.09, чекин 13:42),
`cancelled` (03.09), `registered` (05.09, чекин 13:55) — плюс строка другого
пользователя и строка другого ивента.

- → `duplicates: 3`, `recordId` = строка от 01.09, `registration.source = first_link`,
  `checkedInAt = 13:42` (**самый ранний**, не последний — IDM-2), чужие строки
  не попали.
- Пустой `eventId` → выборка пуста (`inputOk: false`), а не «все регистрации юзера».
- Существующая пара без регистрации → `found: false`, `inputOk: true`.
- После ревью — отдельная фикстура на неоднозначный статус: ранняя строка
  `cancelled`, поздний дубль `registered` (`SmIR5pihNT4ykYHIc3cLQ`) →
  `registered: false`, `cancelled: true`, `statuses: ["cancelled","registered"]`,
  `anyRegistered: true`, `checkedInAt` по-прежнему 13:42.

## Журнал

- **2026-09-08** — пакет взят, ветка `w02-subflows`.
- **2026-09-08** — **главный сюрприз дня: вход subflow'а лежит не там, где кажется.**
  `ap_test_flow` с плоскими `triggerTestData` проходил, а первый реальный вызов через
  `callFlow` упал: `callFlow` передаёт `{ data: <payload>, callbackUrl: … }`, то есть
  ссылка `{{trigger['output'].eventId}}` даёт `undefined`. Пришлось переписать
  ссылки во всех уже собранных флоу на `{{trigger['output'].data.*}}` и перепубликовать.
  Ответ `callFlow` тоже завёрнут: `{ status, data: <тело respond> }` — из-за этого
  `fn-verify-qr` сначала вернул `no_expected_sig` при валидной подписи.
  Оба факта записаны в [flows/README.md](../../catalog/flows/README.md), чтобы
  следующие пакеты не платили за них второй раз.
- **2026-09-08** — вложенный subflow исполняется в **PRODUCTION**, даже когда
  вызывающий гоняется в TESTING: ошибка внутри callee не видна в отчёте теста,
  только по ссылке на его собственный run.
- **2026-09-08** — callee обязан быть published + ENABLED, иначе его нет в dropdown'е
  `flow`. Отсюда порядок сборки: сначала листья (`fn-t`, `fn-fmt-time`, `fn-sign-qr`),
  потом вызывающие.
- **2026-09-08** — вместо ROUTER'а везде выбран **один путь исполнения**: невалидный
  вход нормализуется в Code step, а отказ выдаёт последний Code step. Причина не
  в лени: ветка — это место, где проверку можно случайно обойти, и на канвасе это
  не видно. Цена — лишний HMAC на мусорном входе в `fn-verify-qr`.
- **2026-09-08** — пустой фильтр в `tables-find-records` пришлось закрывать
  сентинелами. `event_id eq ""` вернул бы чужие строки; фильтр `in` по пустому списку
  вообще валит шаг (`requires at least one value`), а строка из пробела обрезается —
  поэтому `!no-key`.
- **2026-09-08** — **столкновение с параллельным пакетом W3.** Для проверки `fn-t`
  и `fn-event-card` были вставлены собственные строки `event.card.*`; прогон показал
  чужие значения — W3 к этому моменту залил в `strings` реальный набор ключей
  (573 строки). Свои фикстуры удалены (это территория W3), а `fn-event-card`
  переписан под **фактические** ключи W3 (`header`, `description`, `when`, `ends`,
  `where`, `deadline`, `map_link`). Побочный вывод: дубли `(key, lang)` `fn-t`
  переживает — берёт первую непустую строку.
- **2026-09-08** — из-за того, что W3 использует `{when}` сразу в трёх ключах
  с разным смыслом, в контракт `fn-t` добавлено поле `varsByKey` (подстановки
  для конкретного ключа, перекрывают общие `vars`). Расширение аддитивное: вызовы
  с одним `vars` не сломались.
- **2026-09-08** — `ap_validate_flow` считает `{{variables['NAME']}}` битой ссылкой.
  Ложное срабатывание (прогон подставляет значение), но полезный урок наоборот:
  валидатор **не** поймает опечатку в имени переменной, потому что опечатка даёт
  пустую строку. Единственная надёжная проверка — сверка результата с контрольным
  значением, посчитанным вне платформы.
- **2026-09-08** — `ap_delete_records` работает в пределах одной таблицы за вызов:
  список из 12 id по трём таблицам удалил только 7 строк, остальное потребовало
  отдельных вызовов. Если чистить фикстуры «одним списком» — часть останется.
- **2026-09-08** — `ap_test_step` на шаге в середине цепочки не всегда переигрывает
  предшественников: предыдущие шаги вернули `{}`, и шаг посчитал мусор.
  Для сквозных проверок использовался только `ap_test_flow`.

- **2026-09-08 (после ревью)** — **`ap_run_action` оказался недооценённым инструментом.**
  Одиночное действие можно прогнать без флоу, и именно так закрылись две вещи,
  которые иначе требовали бы пробного флоу: семантика аргументов
  `crypto / hmac-signature` (замечание 1) и поведение фильтров `tables-find-records`
  по `DATE` ([Q15](../OPEN-QUESTIONS.md#q15)). Стоило вспомнить о нём в начале
  пакета, а не в конце.
- **2026-09-08 (после ревью)** — **замечание про ПД оказалось важнее, чем про скорость.**
  В хвостах у меня было написано «`users` читается целиком, это медленно»;
  ревьюер увидел то же место и назвал главное: в лог прогона уезжают телефоны
  всех пользователей. Исправление вышло дешёвым и улучшило заодно скорость:
  вместо одной выборки без фильтров — две фильтрованные (`blocked_bot eq true`,
  `consent_marketing eq true`), множества ровно те же. Урок на будущее:
  «шагу нужно три поля из двенадцати» — это не про производительность.
- **2026-09-08 (после ревью)** — закрыт [Q15](../OPEN-QUESTIONS.md#q15), который висел
  на W2 с пакета W1. Форма `filters` у qadam'а выяснилась при сборке
  (`{"filters": {"filters": [{"field": {"id", "type", "name"}, "operator", "value"}]}}`),
  и с правильной формой видно: `eq` по `DATE` работает, `lt` — нет, `gt` по `NUMBER` —
  работает. То есть вариант «разобраться с формой фильтра и не менять схему» отпадает,
  остаётся фильтрация в Code step. Числовых дублей `*_ms` в схему не добавляли.
- **2026-09-08 (после ревью)** — цена «секреты в платформе» названа отдельным
  решением: [ADR-0005](../adr/0005-secrets-visible-in-run-logs.md). Ревьюер прочитал
  производный ключ Telegram через `ap_get_run` и посчитал им валидный `hash` —
  то есть доступ к логам проекта равен обходу STF-2. Чинить в флоу нечего
  (цепочка иначе не собирается), но молчать об этом было нельзя.
- **2026-09-08 (после ревью)** — факты платформы переехали из каталога
  в `docs/ARCHITECTURE.md`. Замечание справедливое: `catalog/` по CLAUDE.md — это
  «состояние системы», а проверенные свойства платформы читают вторым пунктом
  порядка чтения. Первые два факта (вход в `.data`, ответ `callFlow`) стоили мне
  переписывания всех девяти флоу — в каталоге их следующий пакет просто не нашёл бы.

A. **важно** — **`fn-event-card` не возвращает `owner_id`, а каталог утверждает, что
   возвращает.** В `catalog/flows/fn-event-card.md`, в абзаце, дописанном как
   исправление замечания 9: «`status` и `owner_id` возвращаются наружу именно для

   авторизации**, и закрыто оно документацией — «гейт обязанность вызывающего».

   по этому контракту, сравнит `undefined` и молча пропустит или молча откажет.

   абзаца и написать прямо, что для проверки владельца вызывающий читает `events`

#### Отдельно: законно ли считать пакет готовым при незакрытом живом `initData`

**Законно. Это не самозачёт.** Проверял это отдельно, потому что «правка документа
вместо работы» — самый дешёвый способ закрыть неудобный критерий.

За:

1. **Невозможность настоящая, а не удобная.** Подтвердил механику сам:
   `ap_flow_structure` не показывает inputs PIECE-шагов, `ap_read_step_code`
   работает только по CODE, `ap_get_run` отдаёт outputs без inputs. Токен
   доступен только шаблоном `{{connections[…]}}` внутри шага и наружу не читается —
   значит агент не может ни синтезировать `initData`, ни прочитать конфигурацию
   шага 2.
2. **Порядок соблюдён буквально.** Критерий правлен **отдельным** коммитом
   `3863e72`, и он предшествует коммиту исправлений `d2f3e23` — документ правился
   до, а не задним числом под уже поставленную галочку. Галочка в журнале
   так и стоит `[ ]`.
3. **Критерий не исчез, а переехал с адресом.** В чек-листе W8 он записан явно
   («прогон на `initData` от живого клиента Telegram — переехал сюда из W2»),
   а Q16 назван блокером приёмки STF-2 в W8 и перечисляет три способа закрытия.
   Q15 в этом же файле показывает, что владелец умеет и закрывать вопросы,
   а не только заводить.
4. **Компенсация не бумажная.** Половину дыры действительно закрыли, и я
   воспроизвёл это независимо: ориентация аргументов qadam'а доказана, цепочка
   двух HMAC совпала побайтово, трактовка hex-ключа как двоичного подтверждена.
   Остаётся ровно один непроверяемый чтением факт — что в `text` шага 2 стоит
   токен, а не `WebAppData`; при зеркальной конфигурации все прогоны выглядели
   бы точно так же.

Оговорка, которую надо держать в голове: перенос критерия **задокументирован,
но ничем не обеспечен**. Если W8 упрётся в то же самое, критерий поедет дальше
тем же приёмом и уже с прецедентом. Поэтому у Q16 должен остаться самый дешёвый
из трёх способов — пять минут человека с открытым Mini App, — и закрывать его
стоит **до** W8, а не внутри него. И ещё дешевле: способ 3 (посмотреть шаг
в UI) закрывает ориентацию хоть сегодня и Telegram не требует вообще; на ревью
он мне недоступен, потому что UI мне не дан, — владельцу доступен.

#### Что проверить не смог

- **inputs PIECE-шагов** — MCP их не отдаёт (сам этот факт записан в ARCHITECTURE

  `consent_marketing eq true` заданы именно так», «в `text` шага 2

## Хвосты и блокеры

1. **Живой `initData` не проверен** — единственный незакрытый пункт чек-листа.
   Критерий перенесён в W8 отдельным коммитом, вопрос заведён как
   [Q16](../OPEN-QUESTIONS.md#q16). Закрывается пятью минутами человека (открыть
   Mini App у `@aiqadam_events_dev_bot` и скопировать `Telegram.WebApp.initData`)
   либо первым сквозным прогоном W7/W8. **Блокирует приёмку STF-2 в W8**, не W4/W5.
2. **W3 не хватает трёх ключей i18n**, которые уже запрашивает `fn-event-card`:
   `event.card.btn_map`, `event.card.btn_register`, `event.card.not_found`.
   Пока их нет — кнопок в карточке нет, а при `found: false` в `text` уходит сырой
   ключ, поэтому **до появления ключей `fn-event-card` нельзя ставить
   в пользовательский путь** (записано в контракт). Флоу править не нужно: ключи
   появятся в `strings` — кнопки появятся сами. Свои значения W2 не заводил
   сознательно: `i18n/*.json` — территория W3, а строка мимо репозитория живёт
   до следующего `i18n-sync`. Передано владельцу W3.
3. **`fn-resolve-segment`: ПД найденных строк всё равно в логе.** Полная выгрузка
   `users` убрана (две фильтрованные выборки вместо одной), но проекции колонок
   у `tables` qadam нет — у тех строк, что попали в выборку, логируются все поля,
   включая `phone`. Принятый риск: [Q17](../OPEN-QUESTIONS.md#q17),
   [ADR-0005](../adr/0005-secrets-visible-in-run-logs.md). Вариант «вынести `phone`
   в отдельную таблицу» стоит рассматривать не раньше, чем телефоны реально начнут
   собирать. Объём выборок **на больших таблицах не проверен** — перемерить до W14
   вместе с [Q13](../OPEN-QUESTIONS.md#q13), теперь уже и на размер лога прогона.
4. **`fn-event-card` — 12–13 с на прогон** при ~2,8 с суммы шагов: остальное —
   ≈2,5 с на каждый из четырёх вложенных `callFlow`. Правило записано
   в ARCHITECTURE: в синхронный вебхук не больше трёх уровней `callFlow`,
   `fn-event-card` в синхронный путь не включать. Для `checkin-api` карточка
   не нужна, но бюджет W5 (`fn-verify-init-data` + `fn-verify-qr` → `fn-sign-qr`
   + `fn-find-registration` ≈ те же 10–12 с при таймауте 60 с) надо замерить
   сквозным прогоном, а не считать по бумаге.
5. Sample data у триггеров `fn-find-registration`, `fn-resolve-segment` и
   `fn-event-card` ссылается на удалённые фикстуры (`meetup01`, `555000111`).
   На исполнение это не влияет — это только пример схемы в редакторе.
