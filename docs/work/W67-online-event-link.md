# W67. Онлайн-событие: ссылка на трансляцию вместо QR

- **Статус**: готов
- **Владелец**: агент
- **Волна**: Phase 3 ([#119](https://github.com/aiqadam/aiqadam-events-bot/issues/119))
- **Зависит от**: решение владельца по полю `events.online_url` (получено 2026-09-29)
- **Начат**: 2026-09-29 · **Закрыт**: 2026-09-29

## Цель

Для онлайн-события QR не генерируется: зарегистрированный участник получает
**ссылку на трансляцию** — в билете (`#/ticket`) и в напоминаниях 24 ч / 2 ч,
только в тот момент, когда она нужна. Публичный каталог ссылку не отдаёт.
Решение владельца 2026-09-29 (взятие пакета): «для онлайн-событий QR не должен
генерироваться, там просто должна появляться ссылка в нужный момент».

Дизайн — [ADR-0051](../../docs/adr/0051-online-event-link-instead-of-qr.md).

### Замечания

1. **блокер** — Документы утверждают реализованную очистку `address`/`lat`/`lon`
   при offline → online, которой нет. `docs/SPEC.md` OWN-1 («при ней
   `address`/`lat`/`lon` очищаются»), `docs/adr/0051-…md` п. 5 («Теперь
   `manage-api` при онлайне очищает эти колонки (`clear_columns`)»),
   `docs/DATA-MODEL.md` (`events`: «они **очищаются** (`clear_columns`)»).
   Реальность: `manage-api/step_11` — `tables-upsert-records` на пине `0.4.5`,
   `values` без `clear_columns`; `step_7` кладёт `address`/`lat`/`lon` пустыми
   строками, а пустая строка Tables = «не менять» (AGENTS.md; ADR-0044 п. 3.1).
   Журнал честно держит это хвостом (`[~]`), но SPEC/ADR/DATA-MODEL описывают
   как сделанное, а комментарий `step_7` («очистку уже стоящих значений делает
   клиент отправкой пустых полей») прямо ложен. Следствие: у события,
   переведённого офлайн → онлайн, старый адрес/точка остаются; публичный
   `events-api` и `#/ticket` продолжают их показывать, а `notify-on-change`
   сообщает зарегистрированным, что адрес убран (`rec.address === ''`).
   Либо реализовать (bump `step_11` до `tables` 0.4.6 + `clear_columns` либо
   отдельный `tables-update-record`), либо привести SPEC OWN-1 / ADR-0051 п. 5 /
   DATA-MODEL в соответствие с реальностью — до `готов`.

2. **важно** — ADR-0051 п. 2 утверждает, что для онлайна `my-qr-api` «**не**
   вызывает `fn-sign-qr`». Живьём `step_9` → `step_4` (`callFlow fn-sign-qr`)
   исполняется безусловно, до решения `step_5`; для онлайна лишь не
   возвращается `payload`. `catalog/flows/my-qr-api.md` это уже оговаривает
   верно, ADR — нет. Утечки нет (payload не отдаётся), но нормативный документ
   описывает несуществующее свойство. Поправить ADR либо, если подпись
   действительно не нужна, гейтить `step_4` по признаку онлайна.

3. **важно** — W67 не подтверждён ни одним прогоном. `ap_list_runs`
   (TESTING) по `my-qr-api`/`manage-api`/`reminders` — пусто; production-прогонов
   этих флоу после публикации 2026-09-29 нет (последние — 2026-09-28, старая
   версия); в живом `events` нет ни одного онлайн-события. Проверены только
   `ap_validate_flow` (3/3), офлайн-скрипты и сборка. Ключевое для безопасности
   поведение «ссылка только зарегистрированному» и импорт платформенных
   переводов (`$t`) в рантайме не наблюдались, отрицательные сценарии не
   прогонялись. До `готов` нужен хотя бы один живой прогон опубликованного
   `/sync`: положительный (онлайн-событие → `online:true` + `url`) и
   отрицательный (не-зарегистрированный / чужой `eventId` → отказ без ссылки).

4. **важно** — `my-qr-api/step_9` с `continueOnFailure: true` даёт тихий откат
   на QR. При сбое чтения `online_url` `step_5` получает пустой `event`, уходит
   в офлайн-ветку и возвращает подписанный `payload` (`step_4` к тому моменту
   уже подписал). Пользователь получит QR вместо ссылки, ошибка наружу не
   выходит — декларируемое «QR для онлайна не генерируется» ломается молча.
   Лечится гейтом по `{{step_9['error']}}` либо отказом от `continueOnFailure`.

5. **на будущее** — `my-qr-api/step_5` отдаёт `online_url` при `found &&
   registered`, не сверяя статус события. Для `cancelled` (и `finished`/`draft`,
   если там окажется `registered`-строка) онлайн-событие продолжит отдавать
   кнопку трансляции. Утечки нет (пользователь зарегистрирован), но семантику
   стоит решить — например, не отдавать ссылку у `cancelled`.

6. **на будущее** — в журнале нет раздела сверки с прототипом (чек-лист 3a,
   ADR-0027), хотя затронуты `#/ticket` (кнопка вместо QR-плиты) и `#/manage`
   (новое поле «Ссылка на трансляцию»; в прототипе поля трансляции нет). Дельта
   частично названа в ADR-0051, но не в журнале — добавить перечень расхождений
   с причиной.

7. **на будущее** — клиентский признак онлайна (`online`-переключатель в
   `Manage.tsx`) и серверный (непустой `online_url`) могут разойтись: черновик
   с включённым онлайном и пустой ссылкой сервер сохранит как офлайн (ошибки
   нет, `strict=false`), после перезагрузки переключатель сбросится в офлайн.
   Не ошибка, но стоит выровнять признаки.

## Хвосты и блокеры

- **Очистка `address`/`lat`/`lon` при offline → online.** Подтверждено чтением
  кода и семантики Tables (пустая строка = «не менять»), `tables-upsert-records`
  на пине 0.4.5 не содержит `clear_columns`. Фикс — отдельный шаг
  `tables-update-record` (`clear_columns`) в ветке `save` либо перепривязка
  `step_11` на `tables` 0.4.6. Следствие сейчас: у события, переведённого из
  офлайна в онлайн, в записи может остаться старый адрес (свежее онлайн-событие
  чисто).
- **Посещаемость онлайн-событий** — отдельный вопрос: без чекина не включается

- **Строгий тайм-гейт** ссылки (не раньше N часов до начала) — по умолчанию нет;

  открыть билет, напоминание) — за владельцем.
