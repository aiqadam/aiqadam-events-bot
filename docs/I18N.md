# Локализация

> **Возобновлено 2026-09-27 — [ADR-0045](adr/0045-i18n-on-platform-dollar-t.md).**
> Бот и Mini App снова говорят на **ru / uz / en**, но уже на платформенном
> механизме переводов `{{$t['ключ']}}` ([qadam-flow#420](https://github.com/aiqadam/qadam-flow/issues/420)),
> а не на своём обвесе. Флоу `i18n-sync` не воскрешён, таблица `strings`
> не читается. Механика — [ADR-0045](adr/0045-i18n-on-platform-dollar-t.md),
> требования — SPEC §6 (I18N-1, I18N-2).

Языки: **ru / uz / en** (I18N-1). Дефолт — `ru` (`project.defaultLocale`).

## Правило

**Ни одной пользовательской строки литералом** — ни в Code step, ни в поле
`sendMessage`, ни в подписи кнопки (I18N-2). Везде только ключ; во входе
CODE-шага лежит **ссылка** `{{$t['ключ']}}`, значение живёт в платформенных
переводах.

Нарушение видно сразу: если в экспорте флоу встречается кириллица или узбекская
латиница в значении `texts` (а не `{{$t['…']}}`) — это баг локализации.
Офлайн ловит `tools/check-texts.py`: значение обязано быть ссылкой на
существующий ключ `i18n/ru.json`.

## Где живут строки

Каноничный источник — файлы в этом репозитории:

```
i18n/
  ru.json   # полный набор; единственный обязательный
  uz.json
  en.json
```

Плоские ключи, точка как разделитель уровней:

```json
{
  "reg.consent_pdn.ask": "Для регистрации нужно согласие на обработку данных.",
  "checkin.ok": "{name} — отмечен"
}
```

Репозиторий — источник правды. Значения импортируются в **платформенные
переводы** проекта (MCP `ap_upsert_translations` или UI/`POST /v1/translations/import`),
откуда их достаёт движок по `$t`. Таблица `strings` на инстансе — **архив**:
она создана в W1, наполнялась старым `i18n-sync` и с 2026-09-13 не читается;
с W25 строки в неё не пишутся.

## Как строки попадают во флоу

- Вход `texts` CODE-шага: `{ "checkin.ok": "{{$t['checkin.ok']}}" }`.
- CODE-шаг читает `texts[key]` и подставляет `{…}`-плейсхолдеры — код `t()`
  не изменился со времён W24 (эталон `catalog/snippets/ru-texts.md`).
- **Отсутствующий ключ валит шаг** (`TranslationKeyNotFoundError`), а не отдаёт
  ключ-заглушку. Поэтому импорт переводов — **до** публикации флоу.
- **Пустое значение `''` — это «перевода нет»**, а не пустая строка: движок
  идёт дальше по цепочке локали.
- Значения вставляются буквально и **не пересканируются** на `{{…}}` — перевод
  не может протащить `{{connections[…].access_token}}`.

Лимиты платформы: ключ ≤255 символов, значение ≤10 КБ, ≤50 локалей на ключ,
≤5000 ключей, ≤4 МБ на всю таблицу, ≤1 МБ на импорт.

## Цепочка локали

Разрешение идёт по порядку, с базовым языком на каждом шаге (`ru-RU` → `ru`):

1. **явная скобка** — `{{$t['ключ'][выражение]}}` (динамическая локаль);
2. **локаль прогона** — `FlowVersion.localeSource`;
3. **`project.defaultLocale`**.

Локаль прогона задаётся по входному касанию:

- **`tg-router`** — единственный Telegram-триггер —
  `localeSource = {{step_1['output'].languageCode}}` (шаг нормализации достаёт
  `message.from.language_code` и `callback_query.from.language_code`). Все
  вызываемые им флоу (inline и queue) наследуют его локаль.
- **Вебхук-флоу Mini App** своего `localeSource` **не имеют**: свой перебил бы
  наследование. SPA шлёт заголовок `ap-parent-run-locale` из
  `Telegram.WebApp.initDataUnsafe.user.language_code`; платформа кладёт его в
  `inheritedRunLocale`. Значение санитизируется — это лишь предпочтение поиска.
- **Флоу без контекста** (расписания `lifecycle`/`reminders`)
  падают на `project.defaultLocale = ru`.

**`project.defaultLocale` обязан быть `ru`.** Без него цепочка локали пуста,
и любой `$t` валит шаг. Это разовая настройка UI (Settings → General →
Default locale) на каждой среде; в репозитории её не выразить.

Динамическая скобка нужна, когда один прогон пишет многим: локаль у прогона
одна, а получатели разные. `{{$t['ключ'][выражение]}}` берёт язык конкретного
получателя (например, из `users.lang`). Для `reminders`/`reg-afterword`/`bcast-run`
это хвост — сегодня они идут на `ru` дефолта.

## Плейсхолдеры

Подстановки — `{name}`, `{time}`, `{title}`. Никакой логики внутри строк.
Правила `t()` не изменились:

- `vars` — плоский объект строк, подстановка одним проходом;
- плейсхолдер, которого нет в `vars`, остаётся в тексте как есть — это заметный
  дефект, и он должен быть заметным;
- подставленное значение **не интерпретируется**: `{name}` из `vars` не может
  внести новый плейсхолдер, второго прохода нет.

## Разметка: строки — простой текст

Строки не содержат разметки Telegram, и `parse_mode` для них не выставляется.
В `{name}`, `{title}`, `{address}` приезжает пользовательский ввод, и при
включённом `Markdown`/`HTML` один символ `_` в имени ломает сообщение. Нужен
акцент — он делается структурой сообщения (отдельная строка, кнопка).

## Выбор языка

Первичное значение — `language_code` апдейта Telegram, если это `ru`/`uz`/`en`,
иначе `ru`. Отдельной команды выбора языка нет
([ADR-0025](adr/0025-start-only-commands-ban.md), команд кроме `/start` не
заводим).

Явный выбор возможен двумя путями (W114):

- **первое касание** — карточка `lang.ask` с кнопками `ru`/`uz`/`en` до согласия
  (у входа по диплинку на событие — теми же фактами события, `reg-start/step_9`;
  у «голого» `/start` — карточка без события, `menu/step_4`);
- **Mini App** — переключатель в табе «Профиль», `set_lang` через `reg-api`.

Выбор первого касания становится `users.lang` только при завершении онбординга
(`reg-profile/step_22`/`step_35` через `draft.profile.lang`); прерванный
онбординг оставляет `users.lang` пустым. Поэтому карточку языка видят не все:
у пользователя с уже заполненным профилем и пустым `users.lang` онбординг не
запускается и язык остаётся производным от Telegram (`catalog/flows/reg-start.md`).

`tg-router` не затирает сохранённый выбор языком клиента: `step_27
«effective lang»` берёт колбэк `ob:lang:<xx>` → `users.lang` → язык черновика
сессии → `language_code` Telegram, и его вывод назначен `localeSource` флоу
(наследуют вызываемые флоу). Приоритет сохраняется — выбранный язык бот
уважает и после апдейта на другом языке.

## Mini App

`miniapp/src/lib/i18n.ts` выбирает язык по `user.language_code` (ru/uz/en, иначе
ru), но **сохранённый выбор в `localStorage` перебивает** язык Telegram
(`getLang`); переключатель в табе «Профиль» меняет словарь сразу (`setLang`) и
best-effort пишет `users.lang` на сервере. Язык читается из
`initDataUnsafe.user`, а если на клиенте тот ещё не заполнен (macOS Desktop
отдаёт его позже) — из сырого `initData` (W124): холодный запуск не залипает на
дефолте `ru`. Русский словарь грузится **всегда как основа**, словарь языка — поверх:
это даёт фолбэк **по каждому ключу** — неполный `uz`/`en` покажет русскую строку,
а не сырой ключ. Пока словарь грузится, подписи пусты — сырых ключей на
первом кадре нет (W115); сырой ключ на экране — только сигнал отсутствующего
ключа после загрузки словаря.

Даты рендерит `Intl.DateTimeFormat` с таймзоной `Asia/Tashkent` (OWN-3) и локалью
пользователя. Форматы дат не хардкодятся в строках. Локаль берётся в момент
рендера, а не на импорте (W124): смена языка в «Профиле» обновляет и даты, без
перезагрузки.

## Замечания по конкретным языкам

- **uz** — латиница (`oʻ`, `gʻ` с модификатором `ʼ`, U+02BB/U+02BC). Не подменять
  их апострофом `'`: это разные символы, и поиск по строкам поедет.
- Числа и склонения («3 участника» / «5 участников») — держим формулировки,
  не требующие плюрализации, пока не появится реальная необходимость.
- **Вычитка носителем** `uz`/`en` ещё не сделана: W25 заполнил flow-ключи,
  W27 — Mini App-ключи, оба машинным переводом. Вычитка принята хвостом
  [W27](BACKLOG.md#w27-догон-переводов-uz--en) решением владельца 2026-09-27.
