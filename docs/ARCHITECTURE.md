# Архитектура: всё на Qadam Flow

> **Актуальность (2026-09-13, W22).** Ниже subflow-«функции» `fn-*` местами
> описаны как существующие. **Их больше нет** — [ADR-0012](adr/0012-end-to-end-flows-instead-of-subflow-functions.md)
> отменил их как практику, W21 убрал вызовы, W22 удалил флоу. Проверенные
> факты про subflow'ы сохранены и остаются верными: они относятся к
> единственному оставшемуся вызову `tg-router` → `registration` и к сборке
> `events-prod` с нуля. Живое состояние — [catalog/overview.md](../catalog/overview.md).


Несущий стек — [Qadam Flow](https://github.com/aiqadam/qadam-flow), форк Activepieces
(MIT-ядро, enterprise-код вырезан). Инстанс: <https://app.flow.aiqadam.org>.

## Главное ограничение

> **Цель — 0 кода. Всё на Qadam Flow, максимум — Code steps внутри флоу.**

Из этого следует, чего в проекте **нет**:

- нет отдельного бот-процесса (aiogram / grammY / что угодно ещё);
- нет кастомного qadam'а в `packages/qadams/custom/` и, значит, нет форка платформы,
  сборки, публикации и релизного цикла под нас;
- нет своего API-сервиса, своей БД, своего деплоя.

Всё, что есть: **флоу + встроенные Code steps + core-qadam'ы + Tables**.
Артефакт проекта — агентский каталог `catalog/` и схема таблиц, а не приложение.

Единственное исключение — Mini App (см. ниже): `showScanQrPopup()` физически требует
статической HTML-страницы с Telegram WebApp JS. Это ~одна страница, и она клиентская.

## Что даёт платформа

| Что | Где | Зачем нам |
| --- | --- | --- |
| **Code step** | встроен в редактор (`engine/src/lib/core/code`) | TypeScript в песочнице, npm-зависимости, вход = выход предыдущих шагов |
| **Telegram Bot** qadam | `qadams/community/telegram-bot` | 20 actions: `sendMessage`, `sendLocation`, `sendMedia`, `sendPoll`, `editMessageText`, `answerCallbackQuery`, `getChat`, … + триггер `new-message` |
| **Tables** | `qadams/core/tables` | встроенная БД: `create-records`, `find-records`, `get-record`, `update-record`, `delete-record`, `download-table` + триггеры на новую/изменённую/удалённую запись |
| **Crypto** | `qadams/core/crypto` | **`hmac-signature`**, `hash-text`, `base64-encode/decode` — подпись QR и проверка `initData` без единой строчки своего кода |
| **Subflows** | `qadams/core/subflows` | `callable-flow` (триггер) + `call-flow` + `respond` — наши переиспользуемые «функции» |
| **Webhook** | `qadams/core/webhook` | входящая точка для Mini App |
| **Schedule** | `qadams/core/schedule` | крон: напоминания, автоперевод в `finished` |
| **Store** | `qadams/core/store` | KV: дедуп `update_id`, курсор рассылки, TTL-токены |
| **CSV / QR / HTTP / Delay / Date-helper / Text-helper** | `qadams/core/*` | экспорт, генерация QR, вызовы Bot API, троттлинг, таймзоны |

Терминология: **qadam** = piece в терминах Activepieces.

## Песочница Code step — проверено на инстансе 2026-09-08

Прогон пробного флоу на <https://app.flow.aiqadam.org> дал жёсткую картину.
**Code step — это чистый ECMAScript плюс `Intl`, и больше ничего:**

| Что | Результат пробы |
| --- | --- |
| `Intl.DateTimeFormat` с `Asia/Tashkent` | ✅ `2026-09-08T14:00:00Z` → `8 сент. 2026 г., 19:00` |
| Локаль `uz-UZ` | ✅ `Sentabr` |
| `node:crypto` | ❌ `Not supported` |
| `fetch` | ❌ `undefined` |
| `Buffer` | ❌ `undefined` |
| `btoa` / `TextEncoder` / `crypto.subtle` | ❌ отсутствуют |
| npm-зависимости через `packageJson` | ❌ `require is not defined` |
| `process` | ❌ отсутствует; таймзона песочницы — UTC |

Отсюда три следствия, и все они в нашу пользу:

1. **«Code step — чистая функция» больше не соглашение, а физика.** Сети из шага нет,
   обойти правило нечем.
2. **HMAC обязан идти через `crypto` qadam** — своей реализации просто не из чего собрать.
   Ровно то, что уже записано в правилах.
3. **`fn-fmt-time` реализуется штатно**: полный ICU на месте, `Asia/Tashkent` и `uz-UZ`
   работают, ручной расчёт смещения UTC+5 не нужен.

Что это меняет в мелочах: base64url получается **строковым преобразованием** вывода
`crypto` qadam'а в base64 (`+`→`-`, `/`→`_`, срезать `=`) — без `Buffer` это единственный
путь. Случайные токены — `crypto / generate-password` (`alphanumeric`, до 256 символов).

### Обновление 2026-09-09 — `pro-data-tech-qa`, `AP_EXECUTION_MODE=UNSANDBOXED`

Факты выше датированы 2026-09-08 и **больше не действуют на этом инстансе**.
Инфра-тикет `T-0161` поставил `AP_EXECUTION_MODE=UNSANDBOXED` и
`ALLOW_NPM_PACKAGES_IN_CODE_STEP=true` — это настройка `.env` воркеров инстанса,
не проекта, и решение о ней принимала инфра-команда, а не этот репозиторий.

Перепроверено прогоном пробного флоу 2026-09-09 (создан и удалён тем же прогоном):

| Что | Результат пробы 2026-09-08 | Результат пробы 2026-09-09 |
| --- | --- | --- |
| `node:crypto` (HMAC-SHA256) | ❌ `Not supported` | ✅ работает, 6 мс |
| `Buffer` | ❌ `undefined` | ✅ работает |
| `TextEncoder` | ❌ отсутствует | ✅ работает |
| `crypto.subtle` | ❌ отсутствует | ✅ определён |
| `process` | ❌ отсутствует | ✅ определён |
| `require` | ❌ `require is not defined` | ✅ определён |
| npm-зависимость через `packageJson` | ❌ | не проверено — агент не вправе выполнять код, скачанный из внешнего реестра, независимо от разрешения владельца проекта |

Следствие №2 из раздела выше («HMAC обязан идти через `crypto` qadam — своей
реализации просто не из чего собрать») **перестало быть физикой и стало
соглашением**. Владелец проекта решил узко разрешить `node:crypto` для двух
конкретных HMAC-цепочек — [ADR-0010](adr/0010-unsandboxed-code-step-for-crypto.md).
Правило «Code step — чистая функция, без сети и записи в БД» (следствие №1)
не отменяется: сети как не было, так и нет, `fetch`/сетевые вызовы из Code step
по-прежнему запрещены соглашением проекта, а не только физикой песочницы.

Это настройка инстанса — обратима независимо от решений этого репозитория.
Флоу, которые начнут полагаться на `node:crypto` (после реализации по ADR-0010),
должны быть помечены в `catalog/flows/*.md` как зависящие от неё явно.

## Переменные проекта в шаблонах — проверено на инстансе 2026-09-08

Пробным флоу (шаг 0.5), два факта, оба неочевидные и оба кусачие:

| Выражение | Результат |
| --- | --- |
| `{{variables['MINIAPP_URL']}}` | ✅ значение переменной |
| `{{MINIAPP_URL}}` | ⚠️ **пустая строка, без ошибки** |
| `{{variables['NO_SUCH_VAR']}}` | ❌ прогон падает `INTERNAL_ERROR`, шаги не выполняются |

Первый случай опаснее второго. Опечатка в имени или короткая форма не ломает
прогон, а тихо подставляет `''`: подпись считается пустым ключом, deep link
собирается без домена, и флоу рапортует успех. Форма без `variables[...]`
в этом проекте **запрещена** — ссылка на переменную всегда через `variables`.

Второй случай, наоборот, честный: отсутствующая переменная валит прогон целиком
и в логе не остаётся даже списка шагов. Если флоу падает с `INTERNAL_ERROR`
и пустым отчётом — первым делом проверяйте имена переменных.

## Tables на практике — проверено на инстансе 2026-09-08

Заведение всех десяти таблиц (W1) дало ещё пять фактов. Каждый из них — то,
чего платформа за нас **не** делает.

| Что проверяли | Результат |
| --- | --- |
| `STATIC_DROPDOWN` со значениями `true`/`false`, пишем `"yes"` | ⚠️ записалось и прочиталось как `"yes"` — валидации нет |
| Что видно в UI как варианты флага | к `true`/`false` платформа добавляет **пустой** вариант |
| Типы на чтении | всё строками: `lat` → `"41.311081"`, `capacity` → `""` |
| `DATE` со смещением `+05:00` | ⚠️ сохранён как есть, к UTC не приводится |
| Фильтр `not_exists` по `null` и по `""` | ✅ ловит оба |
| `gt`/`lt` через MCP `ap_find_records` по полю `DATE` | ❌ пусто; по `NUMBER` — работает ([Q15](OPEN-QUESTIONS.md#q15)) |
| Три строки с одинаковым `(event_id, telegram_id)` | вставились подряд — подтверждение ADR-0003 |

Следствия:

1. **Dropdown — подсказка, а не ограничение.** Допустимость `status`, `segment`,
   `state` и флагов проверяет флоу. Значение вне списка не упадёт, а доедет до логики.
2. **Инвариант «всё в UTC» (OWN-3) держится только дисциплиной флоу.** База примет
   любую строку, включая ташкентское время со смещением, и не пожалуется.
3. **У флага три состояния**, не два: `true`, `false`, «не задано». Для `consent_marketing`
   это важно — «не задано» тоже «нет согласия» (PAR-2), но фильтром `eq false` не ищется.
4. **Числа приводит Code step.** Расчёт лимита с овербукингом (OWN-15) получает
   `capacity` строкой или пустой строкой, и `Number('')` = `0` здесь ловушка.

Отдельная ловушка на стыке с qadam'ом: у поля **два разных идентификатора** —
`externalId` для записи (`values`) и внутренний `id` для чтения (`cells`), а у таблицы
`externalId` для qadam'а и внутренний `id` для MCP-инструментов. Полные таблицы
соответствий — [catalog/tables/README.md](../catalog/tables/README.md).

## Qadam'ы `http` и `tables` на практике — проверено на инстансе 2026-09-08

Сборка `i18n-sync` (W3) дала четыре факта, каждый из которых стоил бы отладки
в более дорогом месте.

**1. Форма вывода шага `http` зависит от исхода запроса.**

| Исход | `{{step_N['output']}}` |
| --- | --- |
| 2xx | плоская: `{ status, headers, body }` |
| 4xx/5xx при `failureMode = continue_all` | обёрнутая: `{ response: { status, body }, request: {} }` |

Поэтому шаблон `{{step_1['output'].status}}` работает **только на успехе**,
а на ошибке молча отдаёт пустую строку — та же ловушка, что с короткой формой
переменной. Правильный приём: передавать в Code step **весь** вывод шага
и нормализовать обе формы внутри.

**2. `failureMode = continue_all` — штатный способ не падать на чужом сервере.**
Шаг остаётся `SUCCEEDED`, а решение принимает следующий шаг по `status`.
Для `i18n-sync` это и есть гарантия «404 на одном языке не стирает его строки».

**3. Тело JSON приходит уже разобранным**, даже когда сервер отдаёт его
с `Content-Type: text/plain` (так делает `raw.githubusercontent.com`).
Рассчитывать на это нельзя — Code step должен принимать и строку, и объект.

**4. `tables-delete-record` с пустым `records_ids` падает** —
`404 ENTITY_NOT_FOUND`. `tables-create-records` с пустым `values.values`,
наоборот, безобиден и возвращает `[]`. Отсюда приём: удаление живёт внутри
`LOOP_ON_ITEMS` по списку id — пустой список даёт ноль итераций вместо ошибки,
и router для проверки «есть ли что удалять» не нужен.

Попутно: `tables-find-records` без `limit` читает таблицу целиком (607 строк
прочитались одним вызовом), а `tables-create-records` вставляет весь массив
записей одним вызовом — 573 строки за 1,3 секунды.

## Ограничения MCP, о которые спотыкаешься при правке шагов

Тоже проверено 2026-09-08, на том же `i18n-sync`. Это не про платформу,
а про инструменты, которыми мы её правим, — и оба пункта меняют то,
как приходится работать.

**1. `ap_update_step` с полем `input` — это merge, а не replace.** Переданные
ключи перезаписываются, **не переданные остаются**. Убрать ключ из `input`
средствами MCP нельзя вообще: `null` обнуляет значение, но сам ключ никуда
не девается. Отсюда правило: переименовали вход в Code step — старый останется
висеть в конфигурации шага, и следующий читатель примет его за рабочий.
Единственный способ «почистить» — обнулить значение и **описать в каталоге**,
что вход мёртвый.

**2. Конфигурацию PIECE-шага через MCP прочитать нельзя.** `ap_flow_structure`
отдаёт тип и `configStatus`, `ap_read_step_code` — только CODE-шаги (зато вместе
с `input`). URL, `failureMode`, cron-выражение, таймзона, `table_id` PIECE-шага
не читаются ничем. Следствия:

- **владельцу пакета проверить конфигурацию нечем** — REST ему запрещён
  ([ADR-0006](adr/0006-rest-read-only-for-review.md)), поэтому он обязан
  оставлять в журнале прогон, который различает верную и неверную
  конфигурацию;
- приём, который работает: подобрать прогон, где **неверная конфигурация дала бы
  другой результат**. Для `i18n-sync` это прогон по `main` до мержа — три 404
  доказывают, что все три URL смотрят на `main`, потому что URL на feature-ветку
  отдал бы 200 и заполненный `coverage`;
- **ревьюер с 2026-09-08 конфигурацию читает** — `GET` к
  `/api/v1/flows/<flowId>/template` разрешён ему ADR-0006 именно потому, что
  в это ограничение независимо упёрлись ревью W2 и три круга W3. Но экспорт
  отдаёт **опубликованную** версию, а не draft: совпадение published с draft
  им не проверяется, и различающий прогон остаётся нужен. Два довода
  закрывают разное;
- **на практике экспорт может оказаться недоступен даже ревьюеру** — но
  не как правило, а как возможность: в W3 исходящий `curl` прошёл у ревьюера
  пятого круга и у ревьюера W2, а у ревьюера четвёртого круга был заблокирован,
  и блок 1a тогда выполнить не удалось. Пока он не выполнен, поля, видимые
  только в экспорте (`cronExpression`, `timezone`, `timeout`, `authType`,
  `filters`), держатся на одном источнике — это надо называть прямо,
  а не считать проверенным. Отсюда и практический вывод: различающий прогон
  владельцу нужен всё равно, потому что доступность экспорта средой
  не гарантирована.

**3. `callFlow` требует `externalId` флоу, которого MCP не показывает.**
`ap_list_flows` отдаёт внутренний `id`, и он **не** подходит: шаг падает
`Please select a flow` из `findFlowByExternalIdOrThrow`. `ap_resolve_property_options`
по пропу `flow` возвращает пустой список (у MCP нет нужного контекста авторизации),
и у скопированного через `ap_duplicate_flow` флоу id тоже не подходит. Значит,
**собрать `call-flow` полностью через MCP нельзя — этот шаг выбирается в UI.**
Проверить чужой subflow, ничего в нём не меняя, всё же можно: `ap_duplicate_flow`
→ `ap_lock_and_publish` → `ap_test_flow` с `triggerTestData` на копии → удалить
копию. Логика та же, оригинал не тронут (так проверялся фолбэк `fn-t` в W3).

> **Уточнение (W4, 2026-09-09):** сам выбор флоу через MCP всё же работает,
> если передать `flow` не через `ap_resolve_property_options` (пустой список
> подтверждён и здесь), а напрямую объектом `{"externalId": "<id из каталога>"}`
> в `input` шага. `ap_add_step`/`ap_build_flow` принимают это без ошибки, и
> вызов реально доходит до callee (подтверждено прогонами `fn-parse-start` в
> `PRODUCTION` при тесте `tg-router`). Значит фраза «собрать call-flow полностью
> через MCP нельзя» была не совсем точна: не проходит не выбор флоу, а передача
> данных — см. следующий пункт.

**4. `callFlow`: данные (`flowProps`) не долетают до callee ни в одной из
проверенных форм — проверено на инстансе 2026-09-09, пакет W4.**
Само название субфлоу выбирается успешно (см. уточнение выше), но что бы ни
передавалось в `flowProps`, вызываемый subflow получает `trigger['output']` без
ключа `data` вовсе (`{"callbackUrl": "..."}` и всё) — то есть **никакие** данные
не доехали. Проверено шесть разных форм на реальном шаге и на изолированном
пробном флоу (`ap_build_flow` в одну команду, чтобы исключить артефакт
`ap_add_step`/`ap_update_step`), результат одинаковый во всех случаях:

| Что пробовали | Результат |
| --- | --- |
| `flowProps: {"data": "<JSON-строка>"}` (advanced) | `data` не пришёл |
| `flowProps: {"data": {"start": "..."}}` (объект, advanced) | `data` не пришёл |
| `flowProps: {"start": "...", "data": null}` (advanced) | `data` не пришёл |
| `flowProps: {"start": "..."}` (плоско, advanced) | `data` не пришёл |
| `flowProps: {"fields": [{"key": "start", "value": "..."}]}` (simple) | `data` не пришёл |
| `flowProps: {"sampleData": {"start": "..."}}` (по аналогии с `exampleData.sampleData` callee-триггера, advanced) | `data` не пришёл |

`ap_validate_step_config` во всех случаях отвечает `valid: true` — валидатор
не проверяет реальную форму `flowProps`, так что зелёный ответ ничего не значит.
`ap_get_piece_props` для `flowProps` при любом `input.flow` отдаёт одну и ту же
общую метасхему (`disabled`/`options`/`placeholder}` — это описание самого
UI-компонента, а не полей callee), что и объясняет причину: серверу нужен тот
же недоступный MCP контекст авторизации, что и для `ap_resolve_property_options`
(см. пункт 3), только здесь он нужен ещё и для сохранения значения, а не только
для показа списка.
**Практический вывод:** передавать в вызываемый subflow **динамические** данные
(результат предыдущих шагов) через `callFlow`, собранный целиком через MCP,
сейчас нельзя. Разовые вызовы без данных (subflow сам ничего не принимает)
через MCP проходят нормально. Следующему пакету, которому нужен `callFlow`
с данными: переоткрыть этот пункт на текущем инстансе (могли поправить
платформу) прежде чем тратить время на повтор перебора форм; если не поправили —
шаг донастраивается в UI, как и выбор флоу до этого уточнения.

> **Опровергнуто (2026-09-09, переоткрытие Q20 перед W5): `callFlow` с данными
> через MCP работает — дело было не в авторизации, а в форме `input.flow`
> при вызове `ap_get_piece_props`.** Шесть форм из таблицы выше проверялись с
> `input.flow` = **строка**-`externalId` (или вовсе без него) — в этом случае
> `ap_get_piece_props` для `flowProps` действительно отдаёт общую метасхему
> `disabled`/`options`/`placeholder` вне зависимости от callee, как и описано
> выше. Но если передать `input.flow` **объектом**, как его возвращает
> `ap_resolve_property_options` для этого же пропа —
> `{"externalId": "...", "exampleData": {"sampleData": {...}}}` — схема
> резолвится верно и вскрывает настоящее динамическое подполе: `flowProps.payload`
> (тип `JSON`), а не `data`. Рабочая конфигурация шага:
> ```json
> {
>   "flow": {"externalId": "<externalId из каталога>"},
>   "mode": "advanced",
>   "flowProps": {"payload": {"key": "...", "lang": "..."}},
>   "waitForResponse": true
> }
> ```
> Проверено `ap_build_flow` → `ap_test_flow` на изолированной паре флоу
> (публикуемый callee с `returnResponse`, эхом отдающий свой `trigger['output']`)
> и на живом `fn-t`: `trigger['output']` у callee пришёл как
> `{"data": {"key": "...", "lang": "ru"}, "callbackUrl": "..."}` — то есть данные
> лежат под `.data`, как и задокументировано в разделе «Subflow'ы на практике».
> Тот же приём (полный объект `flow`, а не голая строка) нужен и для
> `returnResponse.response` — его DYNAMIC-подполе называется `response.response`,
> а не `response` напрямую. **Правило на будущее:** прежде чем объявлять
> DYNAMIC-проп платформы «недоступным через MCP», резолвить его схему через
> `ap_get_piece_props`, передав в `input` **все** уже известные соседние поля
> целиком в том виде, в котором их отдаёт `ap_resolve_property_options`
> (не переизобретать форму руками) — общая метасхема часто означает не лимит
> платформы, а недостающий контекст в `input`, а не то, что MCP этот проп не видит.
> Тестовые флоу удалены после проверки, `fn-t` и другие production-флоу не менялись.
> Пакет W5 подтвердил это на 77-шаговом `registration` и правке `tg-router` —
> все `callFlow` с данными собраны через MCP без UI-эскейпа.

## Файлы предыдущих шагов через FILE-пропы платформенных qadam'ов — не резолвятся через MCP (проверено 2026-09-09, W5)

`send_media` (`@aiqadam/qadam-telegram-bot`) и `custom_api_call` с `body_type: form_data`
имеют FILE-типизированные подпропы (`media.photo`, `data[].fileFieldValue`).
Ссылка на файл, отданный **предыдущим шагом того же флоу** (например, URL из
вывода `@aiqadam/qadam-qrcode` `text_to_qrcode`,
`https://app.flow.aiqadam.org/api/v1/files/<id>?token=...`), в эти пропы через
голый JSON **не резолвится**:

- простой строкой, `{"url": ...}`, `{"url": ..., "filename": ...}` — `send_media`
  падает `"No media defined. Provide either a file or an id."`;
- как `fieldType: "file"` в `form_data` — шаг не падает, но `_valueLength`
  отправленного multipart-поля совпадает с длиной URL-строки, а не с размером
  реального файла: платформа не скачала файл и не подставила байты, а буквально
  записала строку-URL как содержимое.

Отдельно проверено (и это не то же самое): **Telegram сам не может скачать
файл по этому URL** — `custom_api_call` на `/sendPhoto` и `/sendDocument` с
URL в JSON-теле одинаково отвечает `"Bad Request: failed to get HTTP URL content"`.
Заголовки файла — `content-type: application/octet-stream`,
`content-disposition: attachment` — не похожи на то, что Telegram готов
скачивать как медиа, но падение одинаковое и для документа, и для фото, так что
дело не только в типе контента. Причина не установлена до конца — не исключена
недоступность `app.flow.aiqadam.org` внешним серверам вообще, не только
Telegram; подробности и открытый вопрос — [OPEN-QUESTIONS Q21](OPEN-QUESTIONS.md#q21).

**Практический вывод:** передать через MCP боту файл, сгенерированный внутри
того же флоу (QR, экспорт и т.п.), сейчас нельзя ни одним проверенным способом.
Файлы, уже лежащие на серверах Telegram (`file_id`, например `photo_file_id`
ивента), это не затрагивает — `photoId`-проп `send_media` работает штатно.

### Subflow'ы вместо библиотеки

Раз своего пакета нет, переиспользование строится на `subflows`: каждая общая
операция — отдельный флоу с триггером `callable-flow`, который вызывается через
`call-flow` и отдаёт результат через `respond`.

Контракты ниже — **фактические**, уточнены по итогам сборки (W2, 2026-09-08).
Точные поля выхода и заметки по каждой функции — в
[catalog/flows/](../catalog/flows/README.md); здесь только форма.

| Subflow | Вход | Выход | Чем реализован |
| --- | --- | --- | --- |
| `fn-t` | `key` и/или `keys[]`, `lang`, `vars`, `varsByKey` | `{text, texts, resolvedLang, missing, fellBack}` | Tables `strings` + Code step (подстановка `{var}`) |
| `fn-parse-start` | `start` payload | `{valid, kind, error, eventId, userId, utm, token, sig}` | Code step (чистый парсинг) |
| `fn-sign-qr` | `eventId`, `userId` | `{sig, msg, payload}` | **crypto `hmac-signature`** + Code step (base64url + обрезка) |
| `fn-verify-qr` | `eventId`, `userId`, `sig` | `{valid, error}` | `fn-sign-qr` + Code step (constant-time сравнение) |
| `fn-verify-init-data` | `initData`, `maxAgeSeconds?` | `{valid, hashValid, fresh, reason, telegramId, user, authDate, ageSeconds}` | crypto `hmac-signature` ×2 + Code step (разбор и сортировка полей) |
| `fn-resolve-segment` | `segment`, `eventId` | `{allowed, reason, count, recipients[], opensAt}` | Tables `find-records` + Code step (фильтры, вычитание `blocked_bot`) |
| `fn-fmt-time` | ISO UTC, `lang`, `format?` | `{text, date, time, datetime, valid}` | Code step (`Intl.DateTimeFormat`) |
| `fn-event-card` | `eventId`, `lang` | текст + кнопки + venue-параметры + сырые поля ивента | Tables + `fn-t` + `fn-fmt-time` |
| `fn-find-registration` | `eventId`, `telegramId` | `{found, recordId, registration, duplicates, statuses}` | Tables `find-records` + Code step (выбор самой ранней строки, ADR-0003) |

Три контракта уточнены против первоначального замысла, и причины стоит знать:

- **`fn-verify-qr` принимает разобранные части, а не сырой payload.** Разбор — дело
  `fn-parse-start`, и в [FLOWS.md](FLOWS.md#checkin-api--основной-путь-чекина-mini-app)
  `checkin-api` вызывает обе функции подряд. Парсинг чистый и дешёвый, проверка
  подписи требует секрета — смешивать их в одной функции значит считать HMAC
  на любом мусоре из QR-сканера.
- **`fn-t` принимает список ключей и отдаёт объект, а не строку.** Карточке ивента
  нужно 7–10 ключей за раз, и вызов на каждый ключ — это 7–10 вложенных `callFlow`
  (по ~2,5 с каждый, см. ниже). `varsByKey` появился потому, что в реальном наборе
  строк (W3) `{when}` встречается в трёх разных ключах с разным значением.
- **`fn-find-registration` в первоначальной таблице отсутствовал**, хотя в
  [BACKLOG](BACKLOG.md#w2-subflow-функции) он есть с самого начала: он и есть
  «чтение `registrations` только через него» из
  [DATA-MODEL](DATA-MODEL.md#идемпотентность).

Правило: **Code step — только чистая функция.** Никаких сетевых вызовов и записей в БД
внутри Code step: HTTP делает `http`/`telegram-bot` qadam, запись — `tables`.
Так шаг остаётся отлаживаемым и переигрываемым, а в логе прогона видно каждое обращение вовне.

Второе правило: **криптографию не пишем руками.** HMAC берём из `crypto` qadam'а,
Code step рядом только кодирует/сравнивает.

#### Subflow'ы на практике — проверено на инстансе 2026-09-08 (W2)

Сборка девяти `fn-*` и три круга ревью дали тринадцать фактов.
**Первые три идут впереди, потому что каждый уже стоил дорого:** два первых —
переписывания ссылок во **всех** собранных флоу, третий — молча оставшегося
`limit: 50`, который два круга ревью считался снятым. Подробности и как это
выглядит в шагах — [catalog/flows/README.md](../catalog/flows/README.md).

| Что | Результат |
| --- | --- |
| Где лежит вход subflow'а | ⚠️ **в `trigger['output'].data`, не в корне.** `callFlow` передаёт `{ data: <payload>, callbackUrl: … }` |
| Что отдаёт `callFlow` вызывающему | `{ status: 'success', data: <тело respond> }` — поле читается как `{{step_N['output'].data.field}}` |
| `ap_update_step` и ключи `input` | ⚠️ **сливает** переданное с существующим и **удалять ключи не умеет.** Передача полного набора без ключа его не убирает; максимум — обнулить значение (`null`). Из-за этого в `fn-find-registration` полтора круга ревью жил `limit: 50`, который считался снятым |
| Callee не published / DISABLED | его нет в dropdown'е `flow` у `callFlow`: листья публикуются раньше вызывающих |
| Окружение вложенного subflow при тесте вызывающего | ⚠️ **PRODUCTION**, даже если вызывающий гоняется в TESTING: ошибка видна только по ссылке на его собственный run |
| Накладные расходы одного `callFlow` | ≈2,5 с. У `fn-event-card` сумма шагов ≈2,8 с при полном времени 13,4 с |
| `ap_validate_flow` про `{{variables['NAME']}}` | ⚠️ ложное «references … which does not exist in the flow»; и **опечатку в имени он не поймает** — та даёт пустую строку и тоже «валидна» |
| `ap_test_step` на шаге в середине цепочки | не всегда переигрывает предшественников: их выводы приходят `{}` |
| Inputs PIECE-шагов через MCP | ❌ **не отдаются** (`ap_read_step_code` — только CODE, `ap_get_run` — только outputs). Владельцу остаётся UI; ревьюеру разрешён read-only REST — [ADR-0006](adr/0006-rest-read-only-for-review.md) |
| Прогоны `ap_run_action` | ❌ **не сохраняются как flow run**: `ap_get_run` на их id отвечает «Flow run not found». Одиночное действие доказывается **контрольным значением**, а не ссылкой на прогон |
| Что доказывает прогон про конфигурацию | ⚠️ правка `input` **новую версию не создаёт**, а id версии в логе прогона не хранится. Про опубликованную конфигурацию доказателен только прогон **после блокировки версии**; всё, что внутри жизни draft'а, доказывает лишь «тогда работало» — это и есть механика, скрывшая `limit: 50` два круга |
| `lastUpdatedDate` шага и сам экспорт | ⚠️ **не доказывают неизменность.** Открытие флоу в UI пересохраняет шаги: меняются `lastUpdatedDate` и `propertySettings` при неизменных `settings.input` и коде. Экспорт отдаёт текущие записи шагов, а не снимок опубликованной версии, поэтому дифф двух экспортов даёт ложные расхождения: сравнивать надо конфигурацию, а не файлы |
| Большой вывод шага в логе | вместо значения подставляется файл (`{fileId, size, url}`, тип `FLOW_RUN_LOG_SLICE`, ссылка с подписанным токеном). Следующий шаг при этом получает данные целиком — проверено на выборке из 51 строки (71 КБ) |

Первый пункт — самая дорогая ловушка из всех найденных: `ap_test_flow` с плоскими
`triggerTestData` проходит зелёным, а реальный вызов через `callFlow` получает
`undefined`. Тест «на плоских данных» не доказывает ничего.

Практический вывод про накладные расходы: **в синхронный вебхук
(`TRIGGER_TIMEOUT_SECONDS = 60`) не закладывать больше трёх уровней `callFlow`**,
а `fn-event-card` (у неё своих два) в синхронный путь не включать вовсе.

### Флоу-маршрутизаторы

Оркестрация. Строится через MCP, а в git версионируется как **агентский каталог**
`catalog/flows/*.md` ([ADR-0004](adr/0004-catalog-instead-of-flow-export.md)).
Целевой список и разбор — [FLOWS.md](FLOWS.md).

Инвариант: **вебхук бота принадлежит ровно одному флоу** (`tg-router`), который дальше
разводит апдейты по типам и по состоянию визарда. Два флоу на один `setWebhook` не живут.

### Состояние диалогов

Никакой памяти процесса — воркеры платформы горизонтальны и рестартуются.
Шаг визарда owner'а и черновик ивента лежат в таблице `sessions`
([DATA-MODEL.md](DATA-MODEL.md)). Каждый апдейт — это «прочитать состояние → шаг → записать».

### Данные

Qadam Flow Tables — [DATA-MODEL.md](DATA-MODEL.md), живая схема с идентификаторами —
[catalog/tables/](../catalog/tables/README.md).

**Проверено 2026-09-08, и ответ неудобный:** уникальных индексов в Tables нет.
Три записи с одинаковым ключом вставились подряд без единой жалобы. Типы полей —
только `TEXT`, `NUMBER`, `DATE`, `STATIC_DROPDOWN`; ни boolean, ни JSON.
Действия qadam'а: create / update / get / find / delete / clear / download —
и **`tables-upsert-records`**, замеченный W22 (2026-09-13; когда появился —
неизвестно, раньше здесь стояло «upsert'а нет»). Уникальности он не даёт:
ключ матчится на стороне qadam'а, а не БД, поэтому другой путь записи всё равно
вставит дубль. ADR-0003 в силе. В проекте не используется и прогоном не проверен.
У `store put` нет ни режима «только если ключа нет», ни TTL.

Значит, **атомарного примитива на платформе нет вообще**, и идемпотентность
(IDM-1…IDM-4) не может опираться на БД. Как мы с этим живём —
[ADR-0003](adr/0003-idempotency-without-atomicity.md).

### Вебхуки: проверенные факты

```
POST https://app.flow.aiqadam.org/api/v1/webhooks/<flowId>/sync
```

- суффикс **`/sync`** даёт синхронный ответ — это адрес `checkin-api`;
- **preflight `OPTIONS` обрабатывает платформа сама** (204, `access-control-allow-origin: *`),
  прогон флоу на него не тратится;
- `webhook / return_response` задаёт `status`, произвольные `headers` и JSON-тело —
  коды `401`/`403` для Mini App реализуются штатно;
- у триггера `catch_webhook` есть встроенная авторизация (`none` / basic / header /
  **HMAC Signature**) — мы её не используем, потому что проверяем `initData` сами,
  но знать полезно.

### Mini App — исключение из «0 кода»

Статическая страница: `showScanQrPopup()`, экран результата, один `fetch` в webhook-флоу
`checkin-api` с `initData` в теле запроса. Без бэкенда, без сборки, без фреймворка.

Требование STF-1 «сканер не закрывается между людьми» — ограничение именно этой страницы:
результат рисуется поверх сканера, попап не переоткрывается на каждого человека.

**Хостинг: GitHub Pages из этого репозитория** (решено), каталог `miniapp/`,
адрес `https://miniapp.events.aiqadam.org/` — он же прописывается
в BotFather как Mini App URL. Деплой пушем в `main`, HTTPS из коробки.

Публикует **GitHub Actions** (`.github/workflows/pages.yml`), а не ветковый режим Pages:
ветковый умеет отдавать только корень репозитория или `/docs`, а `/docs` занят
документацией — публикация корня выложила бы документы вместо сканера. Артефактом
уходит ровно `miniapp/`, он же становится корнем сайта, поэтому адрес совпадает
с решением [Q3](OPEN-QUESTIONS.md#q3).

Домен собственный: `miniapp.events.aiqadam.org` — `CNAME` на `aiqadam.github.io`
в Cloudflare, запись **без проксирования** (серый значок). Сертификат выдаёт сам
GitHub (Let's Encrypt), и на записи под прокси он не выдаётся; Universal SSL
Cloudflare третий уровень (`*.events.aiqadam.org`) тоже не покрывает.

Порядок настройки важен, проверено 2026-09-08:

1. DNS-запись в Cloudflare;
2. Pages включается с `build_type = workflow`;
3. **сначала первый успешный деплой**, только потом домен — до сборки сайта
   назначение домена отвечает `404 The certificate does not exist yet`;
4. домен задаётся в настройках Pages (`Settings → Pages → Custom domain`).
   Файла `miniapp/CNAME` в артефакте для этого **не достаточно** — деплой с ним
   прошёл, а домен остался пустым. Файл всё равно лежит в `miniapp/`: он
   удерживает настройку от сброса при последующих деплоях;
5. сертификат выдаётся не мгновенно — минуты; до выдачи HTTPS падает на
   проверке имени, и `Enforce HTTPS` включить нельзя.

Кросс-доменный запрос со страницы в `checkin-api` **проверен боем 2026-09-08
и работает** ([Q11](OPEN-QUESTIONS.md#q11)): preflight отвечает платформа,
`Content-Type: application/json` проходит, подгонять запрос под «простой» не нужно.

### Окружения

Два проекта внутри одного инстанса: **`events-dev`** и **`events-prod`**
(решено, [Q7](OPEN-QUESTIONS.md#q7)). Разные боты, разные таблицы, разные connections.
Правки обкатываются в `events-dev`; в `events-prod` флоу **пересобирается по каталогу**
через MCP ([ADR-0004](adr/0004-catalog-instead-of-flow-export.md)), а не переносится файлом.
Прямая правка боевого флоу «на живую» особенно опасна для рассылок — там ошибка

## Цена решения — принимаем осознанно

Честный список того, что «0 кода» стоит. Это не возражения, а то, что нельзя обнаружить на проде:

1. **Рассылка на 25 msg/s** внутри Code step упирается в 600-секундный таймаут флоу и в то,
   что шаг не может сам себя перезапустить. Решение — чанки + курсор в `store`
   + `schedule`-флоу, догоняющее очередь. Разложено в [FLOWS.md](FLOWS.md#broadcast).
2. **Визард создания ивента** на канвасе — это ветвление по `sessions.step`.
   Читается хуже, чем FSM в коде; компенсируем тем, что каждый шаг однотипен.
3. **Нет юнит-тестов** в привычном виде. Проверяемость — на фикстурах прогонов
   и на чек-листах приёмки в [BACKLOG.md](BACKLOG.md).
4. **Секреты** живут в платформе, а не в `.env` репозитория: bot token — connection,
   `QR_SIGNING_KEY` — project Variable. Ротация — процедура в UI.
5. **Версионирование — через каталог, а не через выгрузку файлов.** Значит,
   автоматического отката нет и синхронность каталога держится на дисциплине
   (ADR-0004).
