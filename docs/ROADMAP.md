# Roadmap для агентов

Порядок сборки. Что именно делает каждый пакет и по какому чек-листу он принимается —
в [BACKLOG.md](BACKLOG.md); кто что взял прямо сейчас — в [STATUS.md](STATUS.md);
здесь — **последовательность, параллельность и брифинг агента**.

Проект собирается в `events-dev` (project_id `vZXlkfz60dx6kX97yICx7`).
Перенос в `events-prod` — пересборка через MCP по каталогу, а не деплой файла
([ADR-0004](adr/0004-catalog-instead-of-flow-export.md)).

> **План переписан 2026-09-15 по решению владельца.** Проект разбит на
> **v0.1** и **v0.2**: v0.1 — три опыта пользователя, доведённых до идеала;
> всё, что в них не участвует, — v0.2. Мотивация владельца: «хочу, чтобы эти
> флоу максимально вылизаны — идеальные, красивые и шустрые». Прежний план
> («волна 8 — функции, которых нет») описывал набор пакетов без общего
> вектора качества; он сохранён в истории git, брать по нему работу больше
> нельзя.

## Что такое v0.1

Три опыта. Формулировка владельца, дословно:

1. **Гость:** перешёл по ссылке → зарегистрировался → получил QR.
2. **Овнер:** нажал `/start` → выбрал действие → открылся Mini App → создал
   ивент → **сразу получил ссылку-приглашение**.
3. **Контролёр:** тупо открыл сканер → зачекинил.

Состояние по каждому:

| Опыт | Что есть | Чего не хватает |
| --- | --- | --- |
| Гость | deep link → `reg-start` одной карточкой → согласия → билет с QR (`#/ticket` + `my-qr-api`) | ничего структурного; замер и чистка — W37 |
| Овнер | `/start` → меню с «Создать ивент» (`web_app`) → `#/manage` → создание | **ссылка-приглашение после создания не показывается**; **входа в правку существующего ивента нет** — команда снята ([ADR-0025](adr/0025-start-only-commands-ban.md)), список в `#/manage` — W37; создавать ивент вправе **любой** пользователь (нет W32) |
| Контролёр | меню показывает «Сканер» для ближайшего будущего ивента → `#/scan` → луп без переоткрытия → `checkin-api` | **права контролёра выдать некем**: полный W10 (инвайт-ссылки, одноразовые токены) — v0.2, а без записи в `event_staff` сканер не открывается вовсе |

Плюс два пакета, которые вырезать из v0.1 нельзя, хотя пользователь их не
видит:

- **W35** (`migrations`) — без него у приёмки нет сверки `_manifest.json` ↔
  `migrations`, пакет крошечный;
- **W32** (права `staff` по чаптеру, окна `initData` по флоу) — безопасность: без
  него v0.1 публикуется с дырой «создать ивент вправе кто угодно», а `initData`
  из логов годен сутки. Публичный продукт с такой дырой — не v0.1.

**Явно НЕ входит в v0.1** (решение владельца 2026-09-15): списки и экспорт
(W13), рассылки (W14), lifecycle и напоминания (W12), инвайт-ссылки
(W10 полный), `dedup-report` (W12b), i18n (W25/W27). Кнопка «Мои ивенты»
в чате не появляется (она была привязана к W13) — список своих ивентов
овнер получает внутри роута `#/manage` (W37), новую страницу ради этого
никто не заводит ([ADR-0017](adr/0017-screen-not-message.md) п. 3:
четвёртой страницы нет без нового ADR).

## v0.1 — порядок работ (один агент, последовательно)

Критический путь:

```
W35 → W32 → W36 (staff-lite) → W40 (команды убраны) → W37 (полировка) → W41 (дизайн-гейт) → W15
```

1. **W35** — дозапись `migrations` за W33–W34. Крошечный, ничего не
   блокирует, но ревью всех последующих пакетов сверяет экспорт с таблицей —
   сначала восстановить базу сверки.
2. **W32** — права `staff` **по чаптеру** (создание и правка,
   [ADR-0024](adr/0024-staff-by-chapter-event-staff-checkin.md)), окна `initData`
   **по флоу** ([Q47](OPEN-QUESTIONS.md#q47), [Q49](OPEN-QUESTIONS.md#q49):
   `manage`/`ticket` 300 c, `checkin` 12 ч), афиша выведена из использования
   **временно** ([Q46](OPEN-QUESTIONS.md#q46), возврат — [Q50](OPEN-QUESTIONS.md#q50)).
   Без него овнерский опыт v0.1 небезопасен. Точка остановки: чаптер `1` и первая
   строка `staff` — шаг человека (0.8), подтверждена владельцем: `322876545`.
3. **W36** — staff-lite: овнер выдаёт и отзывает права контролёра
   по `telegram_id` внутри `#/manage/:id`. Без него контролёрский опыт
   в v0.1 мёртвый — права выдать некем, сканер никому не открывается.
4. **W40** — команды, кроме `/start`, убраны
   ([ADR-0025](adr/0025-start-only-commands-ban.md); указание владельца
   2026-09-15 «выпили сразу»): `tg-router` без командных веток, `manage-open`
   выведен из эксплуатации, незнакомая команда отвечает карточкой меню.
   Первый пакет v0.1, трогающий `tg-router`. **Переходная цена:** вход
   в правку существующего ивента появляется только с W37 — команда `/editevent`
   убрана раньше, чем собран экранный список.
5. **W37** — полировка трёх путей: сквозной прогон каждого опыта, замер
   тёплой латентности по методу [ADR-0009](adr/0009-hot-path-latency-budget-and-order.md),
   ссылка-приглашение после создания, **список своих ивентов в `#/manage`**
   (он и возвращает вход в правку), чистка лишних сообщений. **Это пакет,
   который делает v0.1 «идеальным»**, а не просто работающим.
6. **W41** — дизайн-гейт перед приёмкой ([перенесён в v0.1 решением владельца
   2026-09-15](work/W41-prototypes-e2e.md)): кликабельные моки чата и Mini App
   на фейковых данных, показ построенного v0.1, затем предложений v0.2;
   вердикт владельца по каждому экрану. Инстанс не трогает; граница —
   [ADR-0026](adr/0026-prototypes-design-artifact.md) (черновик пакета).
   Вердикт «менять» по построенному экрану рождает **отдельный** пакет правки
   до приёмки — поэтому пакет идёт до W15.
7. **W15** — приёмка. Скоуп v0.1: три опыта целиком + сценарии из
   [CLAUDE.md](../CLAUDE.md). Сценарий «рассылка прервана на середине» на
   приёмке v0.1 **не применим** (рассылок нет, W14 — v0.2) и в чек-листе
   помечается именно так, а не «пройден». До приёмки — вердикт владельца
   по экранам из W41.

Параллельность: W35 никого не трогает и может идти первым любым агентом;
W40 идёт сразу за W36 (решение владельца: команды убираются не дожидаясь W37)
и правит `tg-router` — его ветки команд убираются один раз и централизованно;
W37 затем возвращает вход в правку списком в `#/manage` и не трогает
`tg-router`. W41 не трогает инстанс вовсе и может идти параллельно любому
пакету v0.1, но в порядок поставлен перед приёмкой W15: его вердикт по
построенным экранам должен успеть превратиться в правки до приёмки.

## Брифинг агента, берущего пакет

**Готовые задания на свободные пакеты** — в [BACKLOG.md](BACKLOG.md).
Ниже — общая часть, обязательная для любого пакета.

**Прочитать перед началом:** [CLAUDE.md](../CLAUDE.md) целиком, свой пакет
в [BACKLOG.md](BACKLOG.md), релевантные разделы [FLOWS.md](FLOWS.md) и
[DATA-MODEL.md](DATA-MODEL.md), плюс [catalog/overview.md](../catalog/overview.md) —
чтобы увидеть, что уже построено. Если пакет трогает то, что видит
пользователь, — ещё [ADR-0017](adr/0017-screen-not-message.md),
[ADR-0019](adr/0019-design-system-from-brand-repo.md), [ADR-0022](adr/0022-miniapp-react-spa.md)
и `docs/VOICE.md`. Пакет с правками Mini App — ещё
`docs/MINIAPP-UX.md` (платформенные ограничения среды: навигация,
жизненный цикл WebView, Safe Area).

**Взять пакет:** проверить по [STATUS.md](STATUS.md), что он `не начат`, а его
зависимости `готов`; завести журнал `docs/work/WNN-*.md` по
[шаблону](work/_TEMPLATE.md); перевести свою строку в `в работе` и сразу запушить.
Отбитый push = пакет уже взят, делать rebase и смотреть.

**Границы.** Агент трогает только флоу своего пакета. Чужой флоу нужно поменять —
это не «заодно поправлю», а вопрос владельцу или отдельная задача. Схему таблиц
не меняет никто в одиночку: она заморожена с W1 и пережила пересборку
(исключение — новые таблицы, заведённые пакетом с правкой DATA-MODEL, как
`staff` в W32).

**Порядок работы:**

1. `ap_list_flows` / `ap_list_tables` — свериться с живым состоянием, а не с ожиданиями;
2. собрать через MCP (`ap_build_flow` или `ap_create_flow` + `ap_add_step`);
3. `ap_validate_flow`;
4. `ap_test_step` / `ap_test_flow` на фикстурах — включая **отрицательные**;
   у флоу с побочными эффектами негативные проверки — только `curl`'ом на
   опубликованный `/sync` (gotcha 11), `ap_test_flow` может выполнить прогон
   со старым sample-входом;
5. `ap_lock_and_publish` только после того, как чек-лист пакета пройден;
6. `ap_flow_structure` + `ap_read_step_code` → обновить `catalog/flows/<flow>.md`;
   **плюс обновить экспорт `flows/*.json` тем же коммитом** —
   `tools/export-flows.sh`, затем обязательно `tools/check-export-secrets.sh`
   ([ADR-0018](adr/0018-rest-read-for-everyone.md) п. 5);
7. дописать журнал, поставить статус `на проверке` и **запустить независимого
   агента-ревьюера** ([чек-лист](work/REVIEW-CHECKLIST.md));
8. исправить замечания `блокер` и `важно` → **повторное ревью**;
9. после вердикта «замечаний нет» — статус `готов`, коммит в feature-ветку → PR.

**Пакет готов**, когда выполнен его чек-лист из BACKLOG, каталог совпадает
с живым проектом **и пройдено независимое ревью**. «Вроде работает» готовностью
не является — юнит-тестов здесь нет, их заменяют чек-лист и свежий взгляд ревьюера.

Сдать пакет самому себе нельзя ни при каких обстоятельствах, включая «тут же
две строчки». Мелкие пакеты ломают инварианты не реже крупных.

**Если наткнулся на противоречие в документах** — не реализовывать «как удобнее».
Правка [SPEC.md](SPEC.md) отдельным коммитом со ссылкой на ADR либо новая запись
в [OPEN-QUESTIONS.md](OPEN-QUESTIONS.md). Это правило нарушают чаще прочих,
и каждое нарушение стоит потом дороже самой фичи.

## Риски параллельной работы

| Риск | Почему возникает | Что делаем |
| --- | --- | --- |
| Два агента правят схему таблиц | нет блокировок ни в платформе, ни в git | схема заморожена с W1; изменение — отдельная задача с правкой DATA-MODEL (новая таблица пакета — с правкой DATA-MODEL в том же PR) |
| Два агента правят `tg-router` | все новые касания добавляют в него ветки | в v0.1 роутер не трогает ни один пакет; с v0.2 — правка по одному пакету за раз, в журнале явно записывать, какие ветки добавлены |
| Каталог разъезжается с проектом | синхронизация на дисциплине, а не на автомате | «каталог обновлён» — пункт чек-листа каждого пакета; экспорт — тем же коммитом |
| Экспорт протухает | обновляется руками, как каталог | экспорт коммитится **тем же коммитом**, что правка флоу (ADR-0018 п. 5) |
| Два агента взяли один пакет | нет блокировок | взятие = запушенная строка `в работе` в STATUS.md; отбитый push вскрывает гонку |
| Агент сдаёт собственную работу | юнит-тестов нет, проверять некому | обязательное ревью независимым агентом до статуса `готов` |
| Второй флоу забирает апдейты бота | эксклюзивность на бот-токен (long-polling) | триггером бота владеет только `tg-router`; остальные — через `callFlow` |
| Тестовая рассылка уходит живым людям | сегменты считаются по реальным таблицам | в v0.1 рассылок нет вовсе; с v0.2 — гонять на списке своих аккаунтов до W15 |
| Правка боевого флоу «на живую» | dev и prod — проекты одного инстанса, перепутать легко | сверяться с `project_id` перед изменением; prod меняется только пересборкой |
| W36/W37 конфликтуют в `manage` | оба пакета правят `manage-api` и роут `#/manage` | строго последовательно: W36 → W37; W37 начинается с `ap_flow_structure` по свежему состоянию |
