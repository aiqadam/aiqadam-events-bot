## Q2. Уникальность и атомарность в Tables

**Проверено 2026-09-08 на живом инстансе. Ответ: ничего этого нет.**

| Проверка | Результат |
| --- | --- |
| Три записи с одинаковым ключом в таблице-пробе | вставились все три, ошибки нет |
| Уникальные индексы при создании таблицы | не поддерживаются |
| Типы полей | только `TEXT`, `NUMBER`, `DATE`, `STATIC_DROPDOWN` — ни boolean, ни JSON |
| Upsert в `tables` qadam | отсутствует: create / update / get / find / delete / clear |
| `store put` «только если нет» | отсутствует |
| TTL у `store` | отсутствует |
| Условный update (обновить, если поле пусто) | отсутствует, `update-record` работает по `id` |

Атомарного примитива на платформе нет вообще. Идемпотентность переписана
на «повтор безвреден + свёртка дублей при чтении + `dedup-sweep`» —
[ADR-0003](adr/0003-idempotency-without-atomicity.md).

Строгой exactly-once гарантии у нас не будет, и это записано прямо.

**Статус:** закрыт 2026-09-08.

## Q4. Отношение к существующему `aiqadam/aiqadam-telegram-bot`

В организации уже есть бот на aiogram (`aiqadam/aiqadam-telegram-bot`, «AI Qadam
Telegram bot + outbound notifier, long-poll + Redis Streams», компаньон
`ai-qadam-platform` по ADR-0034).

Вопросы:

- это **тот же бот-аккаунт** или новый? Один токен не может одновременно висеть
  на long-poll в одном сервисе и на webhook в Qadam Flow — они будут отбирать
  апдейты друг у друга;
- если бот один, кто владеет `setWebhook` и как события событийного модуля
  доезжают до Qadam Flow;
- не дублируем ли мы существующий outbound notifier своей рассылкой.

**Решено: отдельный бот-аккаунт под ивенты.** Конфликт за апдейты снимается целиком:
существующий бот остаётся на long-poll, новый работает по webhook в Qadam Flow.

Следствия:
- `setWebhook` нового бота ставит **только** флоу `tg-router`;
- у пользователя будет два бота AI Qadam — стоит развести их по назначению в описаниях
  и перелинковать друг на друга;
- `QR_SIGNING_KEY` и токен нового бота заводятся как отдельные connections
  в проектах `events-dev` и `events-prod`.

**Статус:** закрыт 2026-09-08.

## Q6. Возможности Code step

**Проверено 2026-09-08 прогоном пробного флоу.** Песочница — чистый ECMAScript плюс
полный `Intl`, и ничего больше:

| Что | Результат |
| --- | --- |
| `Intl` + `Asia/Tashkent` | ✅ `2026-09-08T14:00:00Z` → `8 сент. 2026 г., 19:00` |
| Локаль `uz-UZ` | ✅ `Sentabr` |
| `node:crypto` | ❌ `Not supported` |
| `fetch` | ❌ `undefined` |
| `Buffer`, `btoa`, `TextEncoder`, `crypto.subtle` | ❌ отсутствуют |
| npm через `packageJson` | ❌ `require is not defined` |
| `process` | ❌ отсутствует; таймзона песочницы UTC |

Следствия разнесены по документам:

- `fn-fmt-time` делается штатно, ручной расчёт UTC+5 не нужен (OWN-3);
- HMAC — только через `crypto` qadam, альтернативы физически нет;
- base64url — строковое преобразование base64-вывода qadam'а;
- случайные токены — `crypto / generate-password`;
- правило «Code step — чистая функция» обеспечено песочницей, а не дисциплиной.

**Статус:** закрыт 2026-09-08.

## Q7. Экспорт и версионирование флоу

**Решено по окружениям: два проекта в одном инстансе** — `events-dev` и `events-prod`,
с разными ботами, таблицами и connections. Правки обкатываются в dev, в prod едет
экспортированный флоу. Для рассылок это не формальность: ошибка в боевом флоу
уходит людям и не отзывается.

**Решено: агентский каталог, REST API не используем.**

Сначала я нашёл в исходниках рабочий экспорт
(`GET /api/v1/flows/<flowId>/template`, `flow.controller.ts:153`, принимает
платформенный API-ключ) и предложил скриптовать выгрузку в `flows/*.json`.
Владелец указал на `qadam-flow-project-template` — домашнюю практику,
обкатанную на BPM Hero, где принята модель **только MCP + UI**, а источник правды
в git — **агентский каталог** `catalog/*.md`.

Приняли практику. Найденный REST-эндпоинт остаётся неиспользованным сознательно —
[ADR-0004](adr/0004-catalog-instead-of-flow-export.md) фиксирует и его существование,
и причину отказа, чтобы через полгода это не выглядело упущением.

Цена решения — синхронизация каталога держится на дисциплине агента, а не на
автоматическом diff'е. Поэтому «каталог обновлён» входит в чек-лист готовности
каждого пакета работ.

### Дополнение 2026-09-08: что REST-экспорт умеет на самом деле

Отказ от REST в силе, но одно его свойство проверено прогоном, потому что упёрлись
в него трижды. Ревьюеры W2 и W3 независимо обнаружили, что **MCP не отдаёт входы
PIECE-шагов**: `ap_read_step_code` работает только для CODE, `ap_get_run` — только
для выводов. Из-за этого через MCP нельзя проверить ни URL и расписание
`i18n-sync`, ни ориентацию аргументов `hmac-signature` в `fn-verify-init-data` —
то есть ровно те места, где ошибка тихая и дорогая.

`GET /api/v1/flows/<flowId>/template` с платформенным API-ключом
(обязателен `?projectId=`) отдаёт `settings.input` каждого шага целиком. Проверено
на двух флоу:

- `i18n-sync` — `cronExpression: "0 4 * * *"`, `timezone: "Asia/Tashkent"`,
  три URL на `main`, `failureMode: "continue_all"`;
- `fn-verify-init-data / step_2` — `secretKey: "WebAppData"`,
  `text: "{{connections['<id>']}}"`, `secretKeyEncoding: "utf-8"`;
  у `step_3` ключ — `{{step_2['output']}}` с `secretKeyEncoding: "hex"`.

Секретов в экспорте нет: bot token присутствует **ссылкой на connection**, а не
значением. Для git это безопасно.

**Решено 2026-09-08: read-only REST разрешён ревьюеру** —
[ADR-0006](adr/0006-rest-read-only-for-review.md). Только `GET`, только то, чего не
отдаёт MCP, и только проверяющему: владельцу пакета REST не разрешён ни для чего,
`flows/*.json` в репозиторий не выгружаются, каталог остаётся источником правды.
ADR-0004 задним числом не правится — граница проведена новым решением.

Соблазн «выгружать флоу скриптом» закрыт по-прежнему. Разница в роли: у ревьюера
нет права ничего менять, поэтому чтение конфигурации не открывает дорогу к
скрипту заливки и своему деплою — тому, от чего защищает ADR-0004.

Цена названа в ADR-0006: конвенция «только MCP + UI» перестала быть однострочной,
и в обороте появился третий секрет — платформенный API-ключ, чья область шире
одного проекта. Ключ не коммитится, передаётся переменной окружения.

**Статус:** закрыт 2026-09-08. Основная часть — агентский каталог как источник
правды; слепое пятно ревью — ADR-0006.

## Q8. Второй чаптер

ТЗ прямо говорит: «скоро появится второй чаптер», и из-за этого роли моделируются
таблицами (DAT-3). Но не сказано, что именно чаптер значит для данных:

- у ивента появляется `chapter_id`?
- owner становится owner'ом чаптера, а не отдельных ивентов?
- сегменты рассылок режутся по чаптеру?

**Решено: `chapter_id` заводим сразу, логики пока нет.** В модель добавлены таблица
`chapters` и поле `events.chapter_id`. Права, сегменты рассылок и видимость по чаптеру
**не режутся** — это отдельное требование, когда появится.

Так второй чаптер не потребует миграции данных, а мы не выдумываем семантику
разграничения раньше, чем узнаем реальные правила.

**Осталось открытым:** что чаптер значит для прав (owner чаптера vs owner ивента)
и для сегментов рассылок.

**Подтверждено 2026-09-08: оставляем отложенным сознательно.** Решаем, когда второй
чаптер появится реально. Модель к этому готова в главном — права привязаны к ивенту,
а не к пользователю (ADR-0002), поэтому миграции не потребуется. Выдумывать семантику
разграничения раньше реальных требований — верный способ угадать неправильно.

**Статус:** частично закрыт 2026-09-08; остаток отложен намеренно.

## Q11. CORS между GitHub Pages и вебхуком

**Проверено 2026-09-08 боем** — поднял временный webhook-флоу и постучался с
`Origin: https://aiqadam.github.io`. Работает полностью:

```
OPTIONS /api/v1/webhooks/<flowId>/sync   → 204
  access-control-allow-origin: *
  access-control-allow-methods: *
  access-control-allow-headers: content-type

POST    /api/v1/webhooks/<flowId>/sync   → 200  {"ok":true}
  access-control-allow-origin: *
  + заголовки, которые вернул сам флоу
```

Важные детали:

- **preflight обрабатывает платформа**, а не флоу — прогон на `OPTIONS` не тратится;
- ответ синхронный при суффиксе **`/sync`** — это и есть адрес для `checkin-api`;
- `webhook / return_response` умеет отдавать произвольные `headers` и `status`,
  так что коды `401`/`403` из [FLOWS.md](FLOWS.md#checkin-api--основной-путь-чекина-mini-app)
  реализуемы штатно;
- подгонять запрос под «простой» не требуется: `Content-Type: application/json` проходит.

Проверка шла с `Origin: https://aiqadam.github.io`, но платформа отвечает
`access-control-allow-origin: *`, поэтому переезд страницы на собственный домен
`miniapp.events.aiqadam.org` ([Q3](#q3)) на CORS не влияет — перепроверять не нужно.

**Статус:** закрыт 2026-09-08.

## Q13. Темп рассылки и `retry_after` — **BLOCKER для W14**

Всплыло после разведки W0: в песочнице Code step нет `fetch`, поэтому отправлять
из кода нельзя. Рассылка становится циклом платформы (`LOOP_ON_ITEMS` + шаг
`telegram send_text_message` + `delay`), а не пачкой внутри одного шага.

Отсюда два неизвестных, и оба упираются в требования ТЗ:

1. **Достижимы ли 25 msg/s (OWN-11)?** У каждой итерации цикла есть накладные
   расходы платформы — запись состояния шага, переход по дереву. Если итерация
   стоит дороже 40 мс, потолок окажется ниже требуемого, и рассылка на 3000 человек
   не уложится ни в один прогон по `FLOW_TIMEOUT_SECONDS = 600`.
2. **Доступен ли `retry_after` из ответа Telegram** в объекте ошибки шага
   (`{{step['error']}}`) при `continueOnFailure`? Требование OWN-12 говорит «пауза
   ровно на `retry_after`». Если в ошибке лежит только текст без структуры, придётся
   парсить строку, а при неудаче — брать фиксированную паузу, что уже не «ровно».

**Как проверить:** временный флоу с циклом на 50 итераций и `delay 40ms`, замер
фактического времени прогона; отдельно — шаг с заведомо неверным `chat_id`,
чтобы посмотреть форму ошибки. Обе пробы дешёвые, делать до сборки W14.

**Решено заранее, что делать при отрицательном результате** (2026-09-08):
**снижаем темп до реального и правим OWN-11** отдельным коммитом в
[SPEC.md](SPEC.md), с честной записью, какой потолок даёт платформа.

Параллельные прогоны по чанкам отклонены: они дают нужный суммарный темп, но
общий лимит Telegram при этом не контролирует никто, и вместо одной управляемой
очереди получаем лавину `429`. Оставить требование невыполненным «на бумаге»
тоже нельзя — документ, расходящийся с реальностью, хуже отсутствующего.

Для митапа это малая потеря: рассылка на 500 человек при 10 msg/s — минута.

**Статус:** открыт (нужен замер), но решение по результату уже принято.

## Q14. Как одна страница сканера адресует два окружения

Всплыло при заведении `events-prod` (шаг 0.6, 2026-09-08).

`checkin-api` адресуется как `/api/v1/webhooks/<flowId>/sync`
([ARCHITECTURE.md](ARCHITECTURE.md)), и `flowId` у `events-dev` и `events-prod`
**разный**: флоу пересобирается по каталогу, а не переносится файлом
([ADR-0004](adr/0004-catalog-instead-of-flow-export.md)). При этом страница
сканера — одна, на одном домене `miniapp.events.aiqadam.org` ([Q3](#q3)),
и в ТЗ нигде не сказано, откуда она берёт адрес своего окружения.

Цена ошибки несимметрична: боевой сканер, стучащий в dev-проект, отмечает людей
в пустой таблице и рапортует успех. Молча захардкодить один `flowId` нельзя.

Варианты, все в рамках «0 кода»:

1. **Два пути в артефакте** — `/` (prod) и `/dev/`, у каждого бота в BotFather
   свой Mini App URL. Адрес окружения виден в URL, перепутать труднее всего.
2. **Query-параметр** — `?env=dev` в Mini App URL у dev-бота, карта
   `env → flowId` внутри страницы. Один файл, но параметр легко потерять.
3. **Отдельный поддомен для dev** — чище всех, но это ещё одна DNS-запись
   и второй сертификат.

Склоняюсь к (1): цена — копия файла в `miniapp/`, зато окружение видно глазами,
и prod остаётся адресом по умолчанию, который уже прописан.

**Отложен на старте W7, 2026-09-09.** `events-prod` (шаг 0.6) на момент W7
ещё не существует — он сам сдвинут в BACKLOG на волну 6 (после W15), решено
2026-09-08. Адресовать два окружения, второе из которых физически не
развёрнуто, преждевременно: `flowId` `events-prod` сегодня взять неоткуда,
любое решение будет гаданием. W7 строится на один `flowId` — `checkin-api`
в `events-dev` — зашитый обычной константой в `miniapp/index.html` (не через
переменные проекта, их в статике нет). Вопрос, как различать окружения
(варианты 1–3 выше), переоткрывается **к моменту фактического создания
`events-prod`**, а не раньше; тогда же учитывать найденное по ходу W7
ограничение GitHub Pages — автоматический TLS-сертификат выдаётся на один
кастомный домен на репозиторий, поэтому вариант 3 («отдельный поддомен»)
на практике требует **второго репозитория**, а не только DNS-записи.

**Статус:** отложен до момента создания `events-prod` (не раньше волны 6).

## Q15. Как выбирать строки по диапазону дат

Всплыло при заведении таблиц (W1, 2026-09-08).

Через MCP `ap_find_records` операторы `gt`/`lt` **работают только по `NUMBER`**:

| Фильтр | Результат |
| --- | --- |
| `overbook_pct gt 10` (NUMBER, значение 40) | ✅ строка найдена |
| `starts_at lt 2026-09-11T00:00:00Z` (DATE, значение 2026-09-10T09:00:00Z) | ❌ пусто |
| то же со значением `2026-09-01` и с epoch-ms | ❌ пусто |
| `title gt A` (TEXT) | ❌ пусто |
| `starts_at eq 2026-09-10T09:00:00Z` | ✅ строка найдена |

Похоже, диапазонное сравнение приводит значение к числу, и всё нечисловое
превращается в `NaN`. Проверить то же на **qadam'е** `tables-find-records`
(а флоу ходят именно через него) в W1 не удалось: `filters` — DYNAMIC-проп,
и обе угаданные формы (`fieldName`/`field_id`) были молча проигнорированы —
действие вернуло все строки. Молчаливое игнорирование неизвестной формы фильтра
опаснее ошибки, и это само по себе стоит запомнить.

Кого касается:

- **W12** (lifecycle) — «ивенты, у которых `ends_at` уже прошёл»;
- **W12** (напоминания) — «ивенты в окне ближайших N часов»;
- **W10** — «инвайт не просрочен» (`expires_at`);
- **W6/W13** — «предстоящие» против «прошедших» ивентов.

Варианты:

1. **Фильтровать в Code step.** Тянем строки по `status`/`event_id` (`eq` работает)
   и сравниваем даты в шаге. Ивентов десятки — объём не проблема. Цена: сканы
   растут вместе с историей, для `registrations` так делать уже нельзя.
2. **Числовой дубль поля** — `starts_at_ms`, `ends_at_ms`, `expires_at_ms` типа
   `NUMBER`, по ним диапазонные фильтры точно работают. Цена: два поля с одним
   смыслом, которые обязаны обновляться вместе, — классический источник расхождения.
3. **Разобраться с формой `filters` у qadam'а** и, если диапазон там работает,
   ничего не менять в схеме.

Схему W1 **не меняли**: добавлять `*_ms` до проверки (3) — это заложить дубль,
который потом никто не решится убрать. До первого флоу с выборкой по времени
(W10/W12) идём по варианту (1), он не требует схемы вообще.

Решать в W2 — там появится первый флоу, где `tables-find-records` настраивается
через `ap_add_step`, и форма `filters` станет видна.

### Закрыт 2026-09-08 (W2): вариант 3 отпадает

Форма `filters` у qadam'а выяснена — это **DYNAMIC-проп с вложенным массивом**,
и поле задаётся объектом, а не именем:

```json
{"filters": {"filters": [
  {"field": {"id": "<externalId поля>", "type": "DATE", "name": "starts_at"},
   "operator": "lt", "value": "2026-09-11T00:00:00Z"}
]}}
```

С правильной формой прогнали сам qadam через `ap_run_action` на строке
`events` с `starts_at = 2026-09-10T09:00:00Z`:

| Фильтр | Результат |
| --- | --- |
| `starts_at eq 2026-09-10T09:00:00Z` | ✅ строка найдена — форма фильтра верна |
| `starts_at lt 2026-09-11T00:00:00Z` | ❌ пусто |
| `overbook_pct gt 10` (NUMBER) | ✅ строка найдена |

Проверка воспроизводится одним вызовом `ap_run_action` над
`@aiqadam/qadam-tables / tables-find-records` с формой фильтра выше, на строке
`events` с `starts_at = 2026-09-10T09:00:00Z` и `overbook_pct = 40`.
Id тех прогонов здесь **не приводятся сознательно**: `ap_run_action` не сохраняется
как flow run, `ap_get_run` на такой id отвечает «Flow run not found», а ссылка,
которую следующий агент не может открыть, доказательством не является.

`eq` по тому же полю работает, значит фильтр **не игнорируется**, а именно
диапазонное сравнение по `DATE` не срабатывает. Поведение qadam'а совпадает
с MCP до буквы: догадка про приведение к числу подтверждается.

**Решение:** идём вариантом (1) — тянем строки фильтром `eq` по `status`/`event_id`
и **сравниваем даты в Code step**. Числовых дублей `*_ms` (вариант 2) в схему
не добавляем: это два поля с одним смыслом, которые обязаны обновляться вместе.
Вариант 2 остаётся резервом на случай, если `registrations` или `events` вырастут
настолько, что скан станет дорогим, — и тогда это будет отдельный ADR, а не
тихая правка схемы.

Заодно видно то, чего в вопросе не было: `find-records` возвращает **все** колонки
строки, проекции нет ([Q17](#q17)).

**Статус:** ✅ закрыт 2026-09-08 в W2. Схема W1 не менялась. W10/W12 разблокированы
вариантом (1).

## Q16. Как проверить `initData` от живого клиента Telegram

Всплыло на ревью W2 (2026-09-08).

Чек-лист W2 требует: «`fn-verify-init-data` проверён на **реальном** `initData`».
Агент такой строки достать не может — `initData` выдаёт клиент Telegram при
открытии Mini App, и синтезировать её без bot token невозможно (а токен лежит
в connection платформы и наружу не читается).

Что **уже** проверено без живого клиента и перепроверять не нужно:

- цепочка двух HMAC пересчитана вне платформы (`openssl`) и сошлась побайтово,
  включая трактовку hex-ключа второго шага как двоичного — то есть алгоритм
  телеграмовский, а не «похожий»;
- семантика аргументов `crypto / hmac-signature` проверена вызовом
  `ap_run_action` — воспроизводится любым внешним HMAC, id прогона намеренно
  не приводится (`ap_run_action` не сохраняется как flow run, `ap_get_run` его
  не открывает). Условия и контрольные значения:
  `secretKey = "WebAppData"`, `secretKeyEncoding = utf-8`, `method = sha256`,
  `text = "PROBE-W2"`, `outputEncoding = hex` →
  `5a2b099b41154ee663ad6753f999940b02ae5fba122a8592adef108769343e8b`,
  что равно HMAC(key=`WebAppData`, msg=`PROBE-W2`) и **не** равно обратной
  ориентации `4469d2c2e3e24b893b41b726a09bb3d7b3b6391f85de813060a11a88207367cc`.
  Значит `secretKey` — это ключ, а `text` — сообщение. Тот же вывод независимо
  получил ревьюер третьего круга на своём тексте (`PROBE-REVIEW2`);
- отказы проверены прогонами: подделанный `hash`, подменённый `user`,
  просроченный `auth_date`, переставленный порядок полей, мусор.

**Закрыто 2026-09-08, часть про ориентацию.** Конфигурация шага была слепым
пятном: MCP не отдаёт inputs PIECE-шагов, а при зеркальной ориентации аргументов
цепочка осталась бы самосогласованной для собственноручно посчитанного `hash` —
все прогоны прошли бы точно так же. Read-only REST-экспорт
([ADR-0006](adr/0006-rest-read-only-for-review.md), снимал ревьюер) показал
фактическую конфигурацию: у `step_2` `secretKey: "WebAppData"`,
`text: "{{connections['TZTlXaCEO2hEvimUowbSA']}}"`, `secretKeyEncoding: "utf-8"`;
у `step_3` `secretKey: "{{step_2['output']}}"`, `secretKeyEncoding: "hex"`.
Токен подставлен именно в `text`, ориентация верна, hex-ключ второго шага
на месте.

**Что остаётся:** собственно `initData`, выданный живым клиентом Telegram.
Ни экспорт, ни пробники его не заменяют — они подтверждают наш конец цепочки,
а не то, что Telegram считает подпись так же.

Кто может закрыть:

1. **человек** — открыть Mini App у `@aiqadam_events_dev_bot`, скопировать
   `Telegram.WebApp.initData` и прогнать `fn-verify-init-data`. Пять минут;
2. **W7** — сканер всё равно будет присылать `initData` в `checkin-api`, так что
   первый же сквозной прогон W7/W8 закрывает вопрос сам собой;
3. глазами в UI — открыть шаг и посмотреть, что стоит в `secretKey` и `text`.
   Закрывает ориентацию, но не «реальный `initData`».

До закрытия соответствующий пункт чек-листа W2 **не отмечен**, а формулировка
критерия в [BACKLOG](BACKLOG.md#w2-subflow-функции) уточнена отдельным коммитом:
пункт разделён на «алгоритм сверен независимо» (сделано в W2) и «проверено на
живом `initData`» (переезжает в W7/W8).

**Статус:** открыт частично. Ориентация аргументов и конфигурация цепочки —
закрыты экспортом (ADR-0006). Остался прогон на живом `initData`: нужен человек
или W7. Не блокирует W4/W5, **блокирует приёмку STF-2 в W8**.

**W8 (2026-09-09), первый прогон:** флоу `checkin-api` собран и полностью проверен
сквозными прогонами с настоящей криптографией (все исходы STF-4 плюс `401`/`403`),
но на синтетическом `initData`, посчитанном тем же алгоритмом, а не выданном
клиентом Telegram.

**Закрыт 2026-09-09.** Владелец бота открыл Mini App в Telegram и дважды передал
настоящий `initData` (второй раз — прямым `fetch()` из самого Mini App, без
ручного копирования) — оба раза `fn-verify-init-data` вернул `hashValid: false`.
Это оказался не недостаток прогона, а **реальный баг**: `{{connections['<id>']}}`,
подставленный в `text` шага `crypto : hmac-signature` как данные (не как `auth`),
не даёт тот же байт-в-байт токен бота, что использует внутренняя авторизация
того же connection для настоящих вызовов Bot API (`getMe` через ту же connection
подтвердил правильный токен). Решающая проверка: владелец бота посчитал
`HMAC("WebAppData", bot_token)` **локально, у себя**, с реальным токеном из
BotFather — значение не совпало с тем, что вычислял шаг через connection.

Токен продублирован в project Variable `BOT_TOKEN`, `fn-verify-init-data / step_2`
переключён на `{{variables['BOT_TOKEN']}}` — тот же `initData`, на котором до
этого было `hashValid: false`, дал `hashValid: true` тем же прогоном
(`zVsliGe9MlO6cfXpjcwbT`), без других изменений в цепочке.

Находка задокументирована как [ADR-0008](adr/0008-bot-token-as-variable-not-connection-template.md) —
исправление применяется ко **всем** вызывающим `fn-verify-init-data`
(`registration`, `my-qr-api`, `checkin-api`), не только к W8. Пакет W8 разблокирован
этим закрытием — [W08](work/W08-checkin-api.md).

## Q17. ПД в логах прогонов: у `tables` нет проекции колонок

Всплыло на ревью W2 (2026-09-08), связано с
[ADR-0005](adr/0005-secrets-visible-in-run-logs.md).

`tables-find-records` возвращает **все** поля найденных строк — выбрать три
колонки из двенадцати нельзя. Входы и выходы шагов логируются целиком, поэтому
любое чтение `users` кладёт в лог прогона `phone` (DAT-2), имена и `username`
тех строк, которые попали в выборку. Читает лог любой, у кого есть доступ
к проекту.

Что сделано в W2: `fn-resolve-segment` перестал выгружать таблицу `users`
целиком. Вместо одного чтения без фильтров — два фильтрованных
(`blocked_bot eq true` и `consent_marketing eq true`), то есть в лог попадают
только те, кто заблокирован или дал согласие, а не все пользователи бота.
Множества при этом ровно те же, что давала прежняя проверка `=== 'true'` в коде.

Что **не** решается: у найденных строк всё равно логируются все колонки.
Варианты на будущее, ни один не бесплатный:

1. **Ничего не менять**, ограничиваться фильтрами и дисциплиной доступа
   (текущий выбор, ADR-0005).
2. **Вынести `phone` в отдельную таблицу** `user_phones` и читать её только там,
   где телефон действительно нужен (экспорт OWN-8). Цена: ещё одна связь,
   которую держит только флоу, и +1 чтение в регистрации.
3. Свой сервис-прокси к данным — прямой отказ от ADR-0001.

Кого касается дальше: **W13** (экспорт с ПД), **W14** (рассылки читают `users`),
**W12b** (`dedup-sweep` ходит по всем таблицам).

**Статус:** открыт как **принятый риск**. Решать вариантом (2) стоит не раньше,
чем телефон реально начнут собирать (DAT-2 делает его опциональным).

> **Апдейт 2026-09-12 (W19).** Посылка вопроса — «у `tables` нет проекции
> колонок» — **устарела**: она появилась
> ([qadam-flow#407](https://github.com/aiqadam/qadam-flow/pull/407)). На
> инстансе это проп **`columns`** у `tables-find-records` (а не `fieldIds`, как
> сказано в тексте апстримного PR), `MULTI_SELECT_DROPDOWN`, значения —
> **externalId** полей, не `field id` из `cells`. Описание пропа называет ровно
> нашу причину: «Step outputs are recorded verbatim in the run log, so reading
> only the columns you need is also what keeps the rest out of it».
>
> **Проекция применяется, риск сужается.** Существующие шаги `tables` нельзя
> править напрямую — они пришпилены к версии qadam'а, которой после обновления
> образа нет ([qadam-flow#411](https://github.com/aiqadam/qadam-flow/issues/411)),
> и перепривязать их не удаётся даже явным `qadamName`. Но пересозданный шаг
> правится штатно и **получает то же имя**, поэтому ссылки вниз по флоу не
> ломаются, а `ap_update_step` **мержит** `input` — `filters` при добавлении
> `columns` не теряются (проверено). То есть обход дешевле, чем казалось.
>
> Сделано на 2026-09-12: `tg-router/step_7` — сквозной прогон
> `BywBIqJvv6bjW06R6qYBC` подтверждает, что в логе остались только пять
> потребляемых колонок, фильтр цел, регресса в `step_8` нет. Остальные пять
> чтений — в работе.
>
> Доказательство, что риск реален, а не теоретичен: прогон `tg-router`
> `jAb16tiE4Zm5PyQ3IqSri` (2026-09-12) содержит в выводе `step_7` строку
> `users` целиком — `phone`, оба consent-флага, имена, `username`.
>
> Два ограничения, которые проекция колонок **не** снимает:
>
> - **`phone` из лога `tg-router` не уйдёт** — `step_8` вычисляет из него булев
>   `phoneKnown`. Чтобы убрать и его, нужна колонка-флаг в `users`, то есть
>   изменение схемы, смежное с вариантом (2).
> - **`tables-update-record` возвращает строку целиком**, и проекции колонок у
>   этого действия нет — только у `tables-find-records`. Поэтому `tg-router/step_10`
>   (апдейт `users`) по-прежнему кладёт в лог все двенадцать колонок, включая
>   `phone`. Проверено прогоном `BywBIqJvv6bjW06R6qYBC`. То есть для `tg-router`
>   утечка **уменьшена, но не устранена**, и вариант (2) остаётся на столе.
>
> Кандидаты на сужение, отобранные по фактическому потреблению (прочитан код

## Q18. Как мы узнаём, что фоновый флоу не сделал работу

Поднято ревью пакета W3 (замечание 8).

`i18n-sync` спроектирован **fail-safe**: язык, файл которого не скачался или
выглядит обрезанным, не трогается, а прогон завершается **успешно** и пишет
причину в `report.skipped_langs`. Это правильное поведение — альтернатива
(упасть или стереть строки) хуже. Но у него есть слепая зона: **отчёт видит
только тот, кто откроет лог прогона.**

При суточном расписании это значит, что словарь может неограниченно долго
оставаться устаревшим или неполным, и никто не узнает: в UI флоу зелёный.
Тот же класс проблемы ждёт `reminders`, `lifecycle` и `broadcast-runner` —
любой фоновый флоу, который сознательно «ничего не делает» вместо падения.

Вопрос шире W3, поэтому и вынесен сюда: **своего канала уведомлений
у проекта нет.** Варианты, ни один пока не выбран:

1. **Сообщение owner'у в Telegram** из самого флоу, когда `skipped_langs`
   непуст. Дёшево, но требует знать, кому писать, — списка админов нет,
   а `events.owner_id` к i18n отношения не имеет.
2. **Уронить прогон намеренно** (`throw` в Code step), когда пропущен язык:
   тогда флоу краснеет в списке и виден без чтения логов. Цена — ложная
   тревога при разовом сетевом сбое и, что хуже, привычка к красным прогонам.
3. **Отдельный флоу-сторож** по расписанию: читает `strings`, сверяет число
   строк по языкам с ожидаемым и пишет владельцу. Ещё один артефакт
   и ещё одно место, где надо помнить ожидаемое число.
4. **Ничего не делать** и проверять руками на приёмке (W15). Честный вариант,
   пока проект не в бою.

Решать не позднее W14: рассылка — то место, где молчаливое «ничего не сделал»
стоит дороже всего.

**Статус:** открыт, не блокирует W3 (поведение fail-safe уже реализовано
и проверено), решать до W14.

> Q16/Q17 своими вопросами, его PR влит первым.

Значит, правило I18N-2 «ни одной пользовательской строки литералом» к этой

Варианты:

1. **`checkin-api` возвращает готовый текст.** Исходы чекина уже приходят
   с сервера — пусть приходят строкой, а не кодом. Тогда четыре исхода

   Остаются надписи самой страницы (камера, подсказки).
2. **Маленький словарь внутри `index.html`** на три языка, язык — из

   зато без сети. Расхождение с `i18n/*.json` — вопрос времени.
3. **Страница тянет `i18n/*.json` с того же GitHub Pages** при загрузке.
   Источник правды один, лишнего бэкенда нет; цена — один запрос на старте
   и необходимость держать файлы в артефакте Pages, а не только в репозитории.
4. **Только пиктограммы и цвет** для исходов, текста на странице почти нет.

Предпочтение автора W3 — комбинация (1) для исходов и (3) для надписей
страницы, но решение за W7: там будет видно, во что это обходится по вёрстке.

**Решено при старте W7, 2026-09-09: комбинация (1)+(3).** `checkin-api`
(и `my-qr-api` для `ticket.html`) отдаёт уже локализованный текст исхода —
язык берётся из `users.lang` по `initData`, так же как везде в проекте
(DAT-1, `telegram_id` — ключ, `lang` — атрибут пользователя). Обе статические
страницы (`index.html` сканера и `ticket.html`) при загрузке одним `fetch`
тянут `i18n/<lang>.json` с того же GitHub Pages (тот же артефакт, значит без

«переоткройте Mini App» и т. п.) по ключам из `i18n/*.json`; язык страницы —
`WebApp.initDataUnsafe.user.language_code` с фолбэком на `ru` для
неподдерживаемых значений. Источник правды остаётся один — `i18n/*.json` —
никакого встроенного словаря в HTML.

**Статус:** ✅ решено и реализовано в W7 (2026-09-09): `checkin-api` и `my-qr-api`
отдают локализованный `text` во всех исходах/ошибках (язык из `users.lang`;
для непроверенного `initData` — `ru`), обе страницы (`index.html`, `ticket.html`)
тянут `i18n/<lang>.json` с того же GitHub Pages (артефакт Pages теперь включает

## Q20. `callFlow` с динамическими данными не настраивается через MCP

Поднято пакетом W4, 2026-09-09. Полное описание находки —
[ARCHITECTURE](ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2)
(пункт 4, дописан W4).

Шаг `callFlow` (`@aiqadam/qadam-subflows`), которому нужно передать callee
**данные из предыдущих шагов** (а не пустой вызов), не удаётся сохранить через
MCP: сам subflow выбирается нормально (`flow: {"externalId": ...}` работает),
но `flowProps` — сам платёж данных — не долетает ни в одной из шести проверенных
форм. Проверено и на реальном шаге, и на изолированном пробном флоу через
`ap_build_flow` в одну команду (чтобы исключить артефакт инкрементальных
`ap_update_step`). Результат одинаковый: `trigger['output']` у callee не содержит
ключа `data` вовсе.

Это не мешает W4 (у `tg-router` пока нет подходящего обработчика, которому
нужно передавать разобранный payload), но заблокирует **W5, W10, W11** — все
три вызывают subflow'ы (`fn-event-card`, `fn-find-registration`, `fn-sign-qr`,
`fn-verify-qr`, `fn-parse-start`...) с данными, специфичными для конкретного
запроса. W2 такие вызовы строил (`fn-event-card` → `fn-fmt-time`/`fn-t`
с данными), но неизвестно, как именно — журнал W2 не фиксирует точную форму
`flowProps`, а MCP не отдаёт inputs PIECE-шагов задним числом, так что
воспроизвести конфигурацию чтения нельзя.

Варианты:

1. **Переоткрыть вопрос на момент W5** — платформа могла поменяться; не тратить
   время на статью, если факт уже неверен.
2. **UI-эскейп**: тот же приём, что ARCHITECTURE.md уже фиксировал для выбора
   флоу (пункт 3) — шаг донастраивается вручную в UI, разово. Требует
   человека с доступом в UI (агент им не наделён).
3. **Обойтись без `callFlow` с данными** там, где это возможно: продублировать
   маленькую чистую логику Code step'ом вместо вызова subflow (цена — расход
   с «0 кода» и дублирование, годится только для совсем небольших функций).

**Закрыт 2026-09-09, переоткрыт по варианту 1 перед началом W5.** Дело было не
в платформе, а в способе, которым W4 резолвил схему `flowProps`: шесть форм из
таблицы в ARCHITECTURE.md проверялись с `input.flow` = строкой-`externalId`.
Если передать `ap_get_piece_props` полный объект `flow` — тот же, что отдаёт
`ap_resolve_property_options` (`{"externalId": "...", "exampleData": {"sampleData": {...}}}`),
а не строку, — схема резолвится верно и обнажает настоящее подполе:
`flowProps.payload` (JSON), а не `data`. С `payload` данные доезжают до callee
и лежат под `trigger['output'].data`, как и задокументировано в разделе
«Subflow'ы на практике». Тем же путём резолвится и `returnResponse.response`
(подполе `response.response`). Проверено на изолированной паре тестовых флоу
(`ap_build_flow` → `ap_test_flow`, оба флоу удалены после проверки) и на живом
`fn-t` — реальный вызов `callFlow` вернул настоящий перевод, а не пустой ответ.
Подробности и рабочий JSON конфигурации — [ARCHITECTURE](ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2),
блок «Опровергнуто». **W5, W10, W11 разблокированы**: subflow-вызовы с данными
собираются целиком через MCP, UI-эскейп не нужен. Пакет W5 подтвердил это на
практике — `registration` и правка `tg-router` собраны полностью через
`callFlow` с данными (`docs/work/W05-registration.md`).

## Q21. Доставка файлов (QR-изображения) участнику не работает через MCP

Поднято пакетом W5, 2026-09-09. Подпись и генерация QR работают штатно
(`fn-sign-qr` → `@aiqadam/qadam-qrcode` `text_to_qrcode`), но **отправка готовой
картинки в Telegram падает во всех проверенных формах**, собранных через MCP.

Проверено два независимых пути, оба на изолированной паре тестовых флоу
(создана, проверена, удалена) и повторены на реальном шаге `registration`:

1. **`@aiqadam/qadam-telegram-bot / send_media`, FILE-проп `media.photo`.**
   Значение — URL из вывода `qrcode`-qadam'а (`https://app.flow.aiqadam.org/api/v1/files/...`).
   Перепробованы: голая строка, `{"url": ...}`, `{"url": ..., "filename": ...}` —
   во всех случаях `"No media defined. Provide either a file or an id."`.
   В `custom_api_call` с `body_type: form_data` и `fieldType: file` та же строка
   не роняет шаг, но `_valueLength` в теле запроса совпадает с длиной
   URL-строки, а не с размером PNG — значит платформа не резолвит ссылку
   на файл предыдущего шага в реальные байты, а пишет саму строку как
   содержимое файла.
2. **`custom_api_call` (`/sendPhoto`, `/sendDocument`) с тем же URL в JSON-теле** —
   запрос реально уходит в Bot API (в отличие от пункта 1), но Telegram отвечает
   `"Bad Request: failed to get HTTP URL content"` **одинаково для фото и для
   документа** — их сервер не может скачать файл по этому URL. Заголовки ответа
   (`content-type: application/octet-stream`, `content-disposition: attachment`)
   и происхождение TLS-сертификата инстанса (внутренний CA, похоже на
   MITM-прокси в сети, откуда работает агент) наводят на след, но подтвердить
   его нельзя: агент не может воспроизвести запрос с серверов Telegram, только
   со своей стороны.

**Не проверено и не исключено (на момент постановки):** что `app.flow.aiqadam.org`
в принципе недоступен внешним серверам (не только Telegram) из публичного
интернета — если так, это шире одной картинки QR и касается любого будущего
сценария, которому нужно, чтобы **внешний сервис** (не сам агент, не UI)
забрал файл по ссылке этого инстанса.

### Дополнение 2026-09-09: доступность извне подтверждена, найдена настоящая причина

Пункт «не проверено» — проверен. `curl` с независимой машины (не из сети
агента, не через инструменты платформы) забрал тот же файл по URL из вывода
`qrcode`-qadam'а: `HTTP 200`, `1025` байт, валидный PNG-заголовок. Значит
**`app.flow.aiqadam.org` внешним серверам доступен** — вариант 2 из списка ниже
закрыт с ответом «доступен», и версия про MITM-сертификат как причину отпадает.

Значит дело не в сетевой доступности инстанса, а в **самой возможности передать
реальные бинарные байты через MCP-настроенный шаг** — это проверено отдельно,
без Telegram и без внешнего стораджа вовсе, двумя независимыми путями на
изолированной паре тестовых флоу (`ap_build_flow` → `ap_test_flow`, оба флоу
удалены после проверки):

1. **`http`-qadam, `body_type: raw`.** Ожидание: строка (в т.ч. base64) уходит
   как есть. Факт: тело реально отправленного запроса — **JSON-сериализованная
   строка в кавычках** (`Content-Type: application/json`, `Content-Length` на
   ~2 байта больше длины самой base64-строки — ровно на кавычки), а не сырые
   байты. Подтверждено эхом `httpbin.org/put`: `data` в ответе — та же
   base64-строка, обёрнутая в кавычки как JSON. То есть **`raw` в этом
   `http`-qadam'е не сырой** — это `json`-режим, переименованный.
2. **`http`-qadam, `body_type: form_data`, поле `fieldType: file`.** Та же
   ошибка, что и с `send_media.media.photo` в пункте 1 выше, но уже на
   **другом qadam'е** — то есть это не особенность `telegram-bot`, а общая
   проблема FILE-проп'ов. `fileFieldValue` = data-URI со base64 (`data:image/png;base64,...`)
   не резолвится в файл: `httpbin.org/post` эхом показал `"form":{"file":"undefined"}`,
   `Content-Length` тела — 168 байт (у настоящего файла размером 1025 байт
   такое тело физически невозможно). Значит **FILE-тип пропа не понимает
   base64/data-URI, переданный через `input` в обход UI-пикера**, ни на одном
   из проверенных qadam'ов.

**Вывод: смена внешнего хранилища (S3/R2/что угодно) эту проблему не решает.**
Она не в Telegram и не в конкретном сервисе — она в том, что **MCP не может
сконфигурировать шаг так, чтобы он передал реальные бинарные байты куда бы то
ни было**: ни в `send_media`, ни в `custom_api_call` с form-data, ни в общий
`http`-qadam с `raw`-телом. Вариант с внешним объектным хранилищем (R2 и
подобные) закрыт как нежизнеспособный через MCP по этой же причине — не дошли
даже до вопроса заведения бакета и секретов.

Варианты, оставшиеся в силе:

1. **UI-эскейп**: перенастроить проблемный FILE-проп (`send_media.media.photo`
   или аналогичный) в UI, руками через штатный пикер — вероятно, он умеет то,
   что не умеет голый JSON через MCP (пикер, в отличие от `input`, кладёт в
   конфиг что-то помимо строки/data-URI — что именно, agent увидеть не может,
   MCP не отдаёт `settings.input` PIECE-шагов). Требует человека с доступом
   в UI и повторной проверки: точно ли после ручной настройки шаг рабочий,
   не просто «не падает».
2. ~~Проверить сетевую доступность инстанса извне~~ — сделано, инстанс доступен,
   причина не в этом.
3. **Обойтись без изображения** там, где это возможно уже сейчас: отправлять
   участнику подписанный `payload` текстом (не то же самое, что «QR выдан» из
   BACKLOG.md, но не блокирует остальной диалог) — временная деградация, не
   решение.

**Статус:** решение принято 2026-09-09 — [ADR-0007](adr/0007-qr-rendered-in-miniapp.md):
QR не отправляется файлом вовсе, а рендерится клиентским JS в Mini App из
текстового `payload`. Сам вопрос (нельзя передать бинарные байты через
MCP-собранный шаг) остаётся открытым и общим для платформы — актуален для W7
(Mini App может захотеть отдавать/принимать похожие ссылки), W12 (вложения
в напоминаниях) и любого будущего сценария с файлом во внешнем сервисе; W5
он больше не блокирует.

лечится ещё воркерами). Единичного before/after недостаточно для разделения —

подтверждённый рычаг), но остаётся BLOCKER для решений по `checkin-api`, где
доминирует другой, ещё не изолированный источник остатка.

**Проверено 2026-09-09, после W16** ([ADR-0010](adr/0010-unsandboxed-code-step-for-crypto.md) —
`fn-verify-qr` перестал вызывать `fn-sign-qr` как subflow, инлайнил ту же подпись
через `node:crypto`, убрав один слой вложенного `callFlow` из цепочки `checkin-api`).
Тёплый прогон одного скана (тем же методом): шаги в сумме ≈4,9 с, прогон 22,8 с,
остаток ≈17,9 с (`cCXetqX6VPVmPpe3s1p5G`) — против ≈19,9 с в прошлой строке таблицы
(`EFIxi7F09xHzQEmQRKsl0`). Эффект в ожидаемую сторону (снят целый вложенный
flow-run, гипотеза «доминирует стоимость дочернего прогона» подтверждается тем же
знаком), но на одном прогоне это не разделяет накопленную и общую очередь — вопрос
остаётся открытым в той же формулировке, что выше.

**Ответ платформы 2026-09-10 (команда qadam-flow, разбор по коду engine/worker/api).**
Атрибуция закрыта по существу: пауза между `callFlow`-хопами — **не** настраиваемый
интервал очереди, а фиксированная архитектурная стоимость. Один синхронный
`callFlow`-хоп = до 3 полных циклов «BullMQ-джоба → воркер → engine» строго
последовательно (`EXECUTE_WEBHOOK` → создание run ребёнка → `EXECUTE_FLOW` →
resume родителя) + полный снапшот состояния родителя на паузе и download+replay
на resume. Inline-исполнения ребёнка в процессе родителя в движке нет; concurrency
лечит только очередь ожидания параллельных прогонов, а не последовательную цепь
зависимых джоб (отсюда эффект T-0161 на `registration`/`tg-router` и его отсутствие
на `checkin-api`). `EXECUTE_WEBHOOK` — отдельный проход воркера до создания run
ребёнка, в нашей методике он тоже прятался в «паузу».

**Статус (было):** частично закрыт ответом платформы (гипотеза подтверждена: рычаг — только
сокращение хопов), оставался **открытым как ожидание upstream**: запрошен настоящий
синхронный subflow (исполнение дочернего flow в engine-процессе родителя без
очереди/снапшота) — [aiqadam/qadam-flow#363](https://github.com/aiqadam/qadam-flow/issues/363),
milestone v2.0.0.

**Закрыт 2026-09-11, W17.** Апстрим починил #363 и раскатал `executionMode:
"inline"` на `callFlow` (issue закрыт с прямым подтверждением от команды
платформы: inline исполняет ребёнка в engine-процессе родителя, без

## Q23. Умеет ли платформа исполнять независимые ветки/шаги параллельно

**Открыт 2026-09-09.** Нужен для [ADR-0009](adr/0009-hot-path-latency-budget-and-order.md)
(кандидат «независимые чтения/подписи считать конкурентно»).

Вопрос: если после некоторого шага есть два независимых подграфа (например, две
ветки ROUTER или два последовательных чтения таблиц, чьи результаты не зависят
друг от друга), исполняет ли платформа их конкурентно или строго последовательно?
У ROUTER ветки взаимоисключающие (выполняется одна), так что вопрос про шаги,
которые в ActivePieces-моделях обычно можно развести в параллельные ветки
(split) — умеет ли Qadam Flow такое и как это настраивается через MCP.

**Гипотеза:** не умеет (всё строго последовательно). Проверяется прогоном-пробником:
шаг A и шаг B с известной задержкой после общего предка, сравнение суммы длительностей
со временем прогона. Если параллельности нет — кандидат закрывается, остаётся только
сокращение числа слоёв.

### Закрыт 2026-09-11: не умеет, подтверждено разбором по коду

Прогон-пробник не понадобился — ответ есть в апстриме, с точностью до файлов
([qadam-flow#374](https://github.com/aiqadam/qadam-flow/issues/374)):

- `flow-executor.ts` — цикл `while (!isNil(currentAction)) { …; currentAction = currentAction.nextAction }`,
  ни одного `Promise.all` в исполнителе;
- `LOOP_ON_ITEMS` (`loop-executor.ts`) — обычный `for` с `await` на каждой итерации;
- `ROUTER` (`router-executor.ts`) — перебор веток и исполнение первой подошедшей,
  то есть условный селектор, а не конкурентный fan-out;
- `callFlow` в queue-режиме с `waitForResponse: true` останавливает **весь**
  родительский прогон на waitpoint — двух `callFlow` в полёте одновременно
  у одного прогона быть не может.

**Гипотеза подтверждена: параллельности нет вообще.** Кандидат ADR-0009 п.3
«независимые чтения/подписи считать конкурентно» закрывается как неисполнимый
на текущей платформе. Fan-out/fan-in запрошен апстриму (#374, milestone v2.0.0),
и после закрытия #363 это **единственный оставшийся рычаг латентности**: пауза
между хопами убита, всё оставшееся время горячего пути — тела шагов
(`checkin-api`: 9,95 с из 10,0 с).

**Статус:** ✅ закрыт 2026-09-11. Ждём #374; до него порядок шагов на горячем
пути оптимизируется только их количеством.

## Q24. Разовый провал доставки вебхука Telegram → инстанс (~5 мин)

**Обнаружено 2026-09-10**, живым прогоном W17 (`return_void_0` регистрируется
через `/start`). Несколько тапов подряд не доходили до `tg-router` заметное
время, а потом прилетели разом одним пакетом.

**Факты:**

- Telegram Bot API (`getWebhookInfo`) отдал `last_error_message: "Connection
  timed out"` и `last_error_date`, укладывающийся в это же окно; следом —
  успешная доставка, после которой `pending_update_count: 0`.
- На стороне инстанса за то же окно — **ничего**: ни ошибок в логах
  приложения/reverse proxy, ни рестартов контейнеров или веб-сервера, ни
  всплеска CPU steal/нагрузки, ни сетевых ошибок на интерфейсах (проверено
  штатными системными метриками с разрешением 10 мин).
- Вывод: точка отказа — не наш процесс/контейнер/приложение, а что-то на
  сетевом пути между Telegram и инстансом (или на стороне Telegram), не
  наблюдаемое изнутри самого инстанса.

**Не связано с W17/ADR-0009**: латентность `callFlow` внутри уже дошедшего
апдейта тут ни при чём — апдейт просто не долетал до триггера `tg-router`.

**Рассмотрели и отклонили:** переход `@aiqadam/qadam-telegram-bot` с вебхука
на polling. У пропа платформы нет триггера-polling вообще — есть только
вебхук (`new_telegram_message`, один на бот-токен). Написать свой polling-сервис
в обход платформы противоречит [ADR-0001](adr/0001-qadam-flow-as-carrier-stack.md).
К тому же polling не застрахован от того же класса сбоя — исходящий запрос идёт
по той же сети.

**Статус:** открыт, эпизод разовый и не воспроизведён. Действие: не менять
архитектуру по одному инциденту; если повторится — тогда предметно разбираться
(вопрос к хостинг-провайдеру/сети, не к платформе qadam-flow).

## Q25. Два дефекта платформы, отказывающие **в открытую**

**Открыт 2026-09-11**, по итогам аудита платформы с нашей стороны. Оба заведены
апстриму, оба относятся к классу «платформа молча делает не то вместо ошибки»,
и оба отказывают в сторону **предоставления доступа**, а не отказа в нём.
Поэтому они вынесены отдельным вопросом, а не растворены в списке пожеланий.

### 1. Снятый фильтр прав — [qadam-flow#382](https://github.com/aiqadam/qadam-flow/issues/382) (P0)

`tables-find-records` **молча игнорирует `filters`, форму которого не распознал,
и возвращает все строки таблицы.** Не ошибка, не пустой результат — полная
выборка, которая выглядит как «фильтр совпал со всем».

Что это значит у нас. `checkin-api` решает права так:

```
step_5: tables-find-records event_staff
        filters: (event_id, telegram_id контролёра, revoked_at not_exists)
step_6: CODE   isStaff = records.length > 0
```

Постфильтра в коде нет, и в
[catalog/flows/checkin-api.md](../catalog/flows/checkin-api.md) его отсутствие
записано как **гарантия**: «„пользователь вообще где-то staff“ тут физически
невозможно получить, потому что `event_id` — обязательный член фильтра, а не
постфильтр в коде». С учётом #382 это утверждение **неверно**: если форма
фильтра перестанет распознаваться, вернётся вся `event_staff`, `records.length > 0`
станет истиной, и **любой пользователь с валидным `initData` окажется
контролёром любого ивента** — ровно инвариант №1 из AGENTS.md, «участник
отметит соседа».

Достаточно ли этого, чтобы считать дыру открытой сегодня? Нет: сейчас форма
фильтра верна и права проверяются правильно (доказано различающими прогонами
W8). Но единственное, что отделяет нас от обхода прав, — неизменность
недокументированной формы DYNAMIC-пропа, которую платформа не проверяет.
Это не тот фундамент, на котором должна стоять авторизация.

> **Проверка W19, 2026-09-12.** Апстримный фикс #382 подтверждён **по
> документации действия на живом инстансе**, а не только по коммиту: описание
> пропа `filters` у `tables-find-records` теперь прямо заявляет обратное
> прежнему поведению — «A filters value that cannot be read raises an error —
> it is never ignored, because ignoring it would return every row in the table».
>
> Это **не закрывает** пункт 1 и **не отменяет** [W18](BACKLOG.md#w18-страховка-от-fail-open-дефектов-платформы-382-392):
> постфильтр в `checkin-api/step_6` остаётся как defense-in-depth, и
> `catalog/flows/checkin-api.md` по-прежнему должен перестать утверждать
> несуществующую гарантию. На 2026-09-12 W18 **не начат**, журнала
> `docs/work/W18-*.md` нет — то есть противоречащих утверждений в нём не
> содержится просто потому, что его не существует. Когда W18 будет сделан,
> сверку надо повторить по его журналу.
>
> Отдельно, чтобы не возникло ложной тревоги: блокер
> [#411](https://github.com/aiqadam/qadam-flow/issues/411) (существующие шаги
> `tables`/`store` не редактируются) **W18 не задевает**. Постфильтр живёт в
> `checkin-api/step_6`, а это **CODE**-шаг — такие правятся штатно; аудит
> `{{VAR}}` вообще на чтение. Затронуты только правки самих шагов `tables`,
> то есть проекция колонок из [Q17](#q17) и миграция из [Q27](#q27).

### 2. Пустой ключ подписи — [qadam-flow#392](https://github.com/aiqadam/qadam-flow/issues/392) (P1)

`{{VAR}}` вместо `{{variables['VAR']}}` резолвится в **пустую строку**, а не
падает (это уже записано в
[ARCHITECTURE](ARCHITECTURE.md#переменные-проекта-в-шаблонах--проверено-на-инстансе-2026-09-08),
но как ошибка автора, а не как дефект безопасности).

Цена конкретно для нас: если так написан `QR_SIGNING_KEY` или `BOT_TOKEN`,
HMAC считается **с пустым ключом**. Подпись и проверка деградируют
**согласованно** — QR, подписанный пустым ключом, пустым ключом же и
проверяется. Поэтому все позитивные тесты проходят, прогон зелёный, ответ
`200`, в логе штатное исполнение. При этом секрета больше нет: формат payload
у нас задокументирован, и подделать QR или `initData` может кто угодно.

Негативного теста, который это ловит, не существует в принципе — обе стороны
ломаются вместе и остаются взаимно согласованными. Ловится только чтением
конфигурации шага, то есть глазами.

### Что делаем

Не ждём апстрим: оба дефекта митигируются на нашей стороне дёшево, и обе
митигации полезны сами по себе — [W18](BACKLOG.md#w18-страховка-от-fail-open-дефектов-платформы-382-392).
Постфильтр по `event_id` в `step_6` и аудит `{{VAR}}` + пункт в чек-лист
ревьюера. Апстрим-исправления снимут необходимость первой, но не второй:
привычка ссылаться на переменные полной формой нужна независимо.

**Статус:** открыт. Закрывается не ответом платформы, а выполнением W18 —
до тех пор приёмка (W15) не должна считаться пройденной.

> **Апдейт 2026-09-12** ([Q26](#q26)): #382 закрыт апстримом коммитом
> `6b4d5a0839` (PR [#404](https://github.com/aiqadam/qadam-flow/pull/404)) —
> `tables-find-records` теперь отклоняет нераспознанный `filters` вместо
> полной выдачи. #392 **остаётся открытым** — вторая митигация W18 (аудит
> `{{VAR}}`) не снимается. Само по себе закрытие issue не отменяет
> постфильтр в `checkin-api`: нужно сперва подтвердить, что **инстанс**
> обновлён до этого коммита или новее (см. [Q26](#q26)).

## Q27. Пересматривать ли ADR-0003 после появления атомарных примитивов

**Открыт 2026-09-12** пакетом [W19](BACKLOG.md#w19-ревизия-после-обновления-образа-qadam-flow).
Владелец проекта в тот же день **заказал** пересмотр отдельным пакетом
([W20](BACKLOG.md#w20-пересмотр-adr-0003-идемпотентность-на-атомарных-примитивах)),
поэтому вопрос заводится не как «стоит ли обсуждать», а как «чем именно
кончится пересмотр».

### Почему вопрос вообще возник

[ADR-0003](adr/0003-idempotency-without-atomicity.md) написан из посылки
«атомарных примитивов у платформы нет вообще», и вся идемпотентность проекта
(IDM-1…IDM-4) построена на find-then-write с детерминированным разрешением
дублей. С [qadam-flow#410](https://github.com/aiqadam/qadam-flow/pull/410)
посылка перестала быть верной. Проверено на инстансе 2026-09-12:

| Примитив | Что даёт | На какой инвариант ложится |
|----------|----------|----------------------------|
| `tables-update-record` → проп `only_if` | условный апдейт, при непопадании — `RECORD_PRECONDITION_FAILED`, а **не** тихий no-op. Описание прямо говорит: «Use "Does not exist" to mean "only if this column is still empty" — that is how you write "record it only the first time"» | **IDM-2**: `checked_in_at` пишется только при первом чекине, повтор показывает исходное время |
| `store : put_if_absent` + `ttl_seconds` | «report whether this run is the one that took it», плюс истечение ключа | **IDM-4**: дедуп `update_id`; TTL заодно снимает нужду в `dedup-sweep` (W12b) |
| `tables-upsert-records` | матчинг по ключу вместо find-then-write | апсерт `users` в `tg-router` (`step_7`→`step_9`→`step_10`/`step_11`) |

### Что важно не потерять при пересмотре

- **`upsert` — не уникальный индекс.** Описание действия честно оговаривает:
  «The key is matched here, **not enforced by the table** — another write path
  can still insert one». То есть гонка двух одновременных апсертов по-прежнему
  способна создать дубль, и детерминированный выбор канонической строки
  (`tg-router/step_8`) убирать нельзя. Из трёх примитивов этот — самый слабый.
- **`only_if` и `put_if_absent` — качественно другое дело**: это настоящие
  CAS/put-if-absent, они дают то, чего у нас не было, и на них IDM-2 и IDM-4
  перестают зависеть от «повтор безвреден по построению».
- **Exactly-once по-прежнему обещать нельзя** — между шагами флоу транзакции
  нет, и ADR-0003 в этой части не отменяется, а сужается.

### Цена

Миграция существующих таблиц, перепись четырёх мест (`fn-register`,
`checkin-api`, `reminders`, `dedup-sweep`) и **повторная проверка трёх
сценариев идемпотентности** из CLAUDE.md. Плюс — на 2026-09-12 существующие
шаги `tables`/`store` вообще нельзя править через MCP
([#411](https://github.com/aiqadam/qadam-flow/issues/411)), так что до
починки апстримом пересмотр технически неисполним.

**Статус:** **ОТВЕЧЕН 2026-09-12.** Решение принято — [ADR-0011](adr/0011-idempotency-on-atomic-primitives.md),
реализовано в W20: IDM-4 на `put_if_absent` + TTL, IDM-2 на `only_if` (CAS).
ADR-0003 сужен, но не отменён: атомарность появилась у двух операций, а не
у платформы вообще; exactly-once по-прежнему не обещается. W19 вопрос только
ставит; тихо переписывать идемпотентность внутри ревизии было нельзя.

## Q28. Что осталось в горячем пути после того, как `inline` исчерпан

**Открыт 2026-09-12**, по замерам живого сквозного прогона в
[W20](work/W20-idempotency-on-atomic-primitives.md). Это **продолжение**
[ADR-0009](adr/0009-hot-path-latency-budget-and-order.md) и [Q22](#q22),
а не новая тема: ADR-0009 уже назвал «сократить число последовательных
`callFlow`» кандидатом №1 и уже указал на `fn-parse-start` поимённо.
Новое здесь — **число**, которого тогда не было.

### Замер 2026-09-12 (живой путь, чистая база)

Тот же метод, что в эталоне ADR-0009: длительность прогона против суммы
длительностей шагов.

| Флоу | Эталон 2026-09-09 | После W17 | **2026-09-12 (W20)** |
|---|---|---|---|
| `registration` `/start` | 34,2 с (пауза ≈26,4) | 17,1 с (пауза ≈0,2) | **17,9 с** (шаги 17,89, пауза ≈0) |
| `checkin-api`, скан | 23,3 с (пауза ≈17,9 после W16) | 10,0 с (пауза ≈0,05) | **10,2 с** (шаги 10,15, пауза ≈0,05) |
| `my-qr-api`, открытие тикета | не мерился | не мерился | **5,3 с** (шаги 5,31, пауза ≈0) |
| `tg-router`, апдейт | 7,8 / 7,0 с | — | **2,1–3,8 с** |

Прогоны: `Nt8LUIMayzZfRKF4NtqtI`, `UeuIK7RgT7LaJNSqp84y3`,
`aMRe0pueWhTN1III9dApF`. Бюджеты п.1 ADR-0009 выдержаны все три, включая
`my-qr-api` ≤ 10 с, который до сих пор не проверялся ни разу.
`tg-router` ускорился вдвое-втрое — это эффект W20 (дедуп свёрнут с трёх
шагов до двух), а не `inline`.

### Что здесь нового

ADR-0009 объяснял остаток **межшаговой диспетчеризацией** и считал, что
цена вызова — это цена отдельного флоу-прогона. Рычаг `inline` эту цену
должен был снять полностью. Замер показывает, что **не снял**:

| Тип шага | Стоимость |
|---|---|
| CODE-шаг | ~0,06 с |
| `tables-find-records` | 0,3–0,4 с |
| **`callFlow` в режиме `inline`** | **1,2–1,9 с** |

Решающее наблюдение: `fn-parse-start` — чистая функция без ввода-вывода,
внутренняя работа ~0,1 с, а вызов стоит **1,15 с** (`checkin-api/step_8`).
Диспетчеризации больше нет, отдельного прогона нет — значит ~1 с это
накладной расход **самого вызова inline**, факт, которого в ADR-0009 быть
не могло.

Доля вызовов subflow в прогоне: `my-qr-api` — 89 %, `checkin-api` — 76 %,
`registration` `/start` — 76 %. Худший одиночный шаг системы —
`registration/step_19` → `fn-event-card`: **8,06 с**, 45 % прогона (W17
мерил сам `fn-event-card` изолированно — 6,7 с).

### Что с этим делать

ADR-0009 в обновлении W17 **снял** запасной план «дублировать `fn-*`-логику
вместо `callFlow`» — на том основании, что upstream-рычаг закрыл вопрос
дешевле. Эти замеры — основание **пересмотреть снятие**, но не повод
молча вернуть план: он размывает subflow-функции из
[ADR-0001](adr/0001-qadam-flow-as-carrier-stack.md) и каталог ADR-0004.

Варианты, ни один не выбран:

1. **Инлайнить чистые функции в CODE-шаг вызывающего** — `fn-parse-start`,
   `fn-fmt-time`. Ровно кандидат №1 из ADR-0009 п.3. Цена — дублирование
   логики между флоу; требует своего ADR.
2. **Разобрать `fn-event-card`** (8,06 с, 45 % `/start`) — четыре
   собственных вызова; посмотреть, сколько из них нужны. Это ADR-0009 п.3
   «уплостить `fn-event-card`», и он ничего не размывает.
3. **Проверить батчинг `fn-t`** — ADR-0009 п.3, до сих пор не сделано.
4. **Завести апстриму** стоимость `inline`-вызова: 1 с на вызов чистой
   функции в том же процессе выглядит как то, что чинится на их стороне.
   Дешевле всех наших вариантов и никаких ADR не трогает.

**Статус:** открыт. Порядок предлагается обратный номерам: сначала (4) и (3),
потом (2), и только если не хватит — (1) с отдельным ADR.

## Q29. `registration/step_38` получает пустой вход — реактивация не работает (IDM-1)

**Открыт 2026-09-12**, найден случайно при оптимизации [Q28](#q28) в
[W20](work/W20-idempotency-on-atomic-primitives.md). Это **дефект, а не вопрос
проектирования**, и он заведён здесь только потому, что чинить его должен
владелец W5, а не W20.

### Что наблюдается

В ветке `pdn_yes` шаг `step_38` («существующая регистрация? для реактивации»,
`callFlow → fn-find-registration`) стабильно возвращает:

```json
{"found":false,"inputOk":false,"eventId":"","telegramId":"","duplicates":0,...}
```

`inputOk: false` — это сам `fn-find-registration` сообщает, что ему **не
передали** `eventId`/`telegramId`. Дальше `step_39` вычисляет
`reactivate: false`, роутер `step_40` уходит в ветку `Otherwise`, и `step_42`
**создаёт новую строку** `registrations` вместо реактивации существующей.

### Почему это не артефакт теста

Сначала выглядело как следствие синтетических данных. Перепроверено на
**настоящем боевом прогоне владельца** `wOV2cCyvBUZ4eN8NQuoIy` (PRODUCTION,
2026-09-12 14:13:41, `SUCCEEDED`, живой тап по кнопке «I agree» с настоящим
`callbackQueryId`): `step_38` там даёт ровно тот же пустой вход. При этом
соседний `step_4` в ветке `start` работает правильно (`inputOk: true`), то есть
дело в конфигурации именно `step_38`, а не в subflow'е.

Подтверждение в данных: два срабатывания `pdn_yes` подряд оставили в таблице
**две** строки `registrations` на одну пару (`demo`, `322876545`) —
`CupLVok0YdzVFECk6noID` и `VEN5YQNHCZf5n3KCY8nkI`, обе `status: registered`.

### Чем это грозит

- **IDM-1** (идемпотентность регистрации) на этом пути не выполняется:
  повторное согласие создаёт дубль, а не находит существующую запись.
- **Реактивация после отмены** (`status: cancelled` → снова `registered`)
  не срабатывает никогда — вместо неё появляется вторая строка.
- Овербукинг считается по `registered`-строкам (`step_6`), поэтому дубли
  **завышают занятость** и могут закрыть регистрацию раньше времени.
- Ниже по течению дубли частично гасятся: `fn-find-registration` отдаёт
  `duplicates`, а `fn-resolve-segment` дедуплицирует по `telegram_id`. То есть
  участник не получит два сообщения, но данные всё равно грязные.

### Чего не хватает для починки

Конкретной причины. `settings.input` PIECE-шагов MCP не отдаёт
([#102](https://github.com/aiqadam/qadam-flow/issues/102)), поэтому увидеть,
на что именно ссылается `step_38`, сейчас нельзя — только пересобрать шаг
заново по контракту. Правка относится к области W5, а не к ревизии или
оптимизации, поэтому вынесена в отдельный вопрос.

**Статус:** открыт. Нужен пакет-исправление; до него дубли в `registrations`
на dev будут появляться при каждом повторном прохождении визарда.

## Q30

**Очистить DATE-поле через `tables-update-record` больше нечем.**

Заведено 2026-09-12 (W21), найдено прогоном `nk7ET4kibX4N2YWUqJqtX`.

Шаг реактивации регистрации в `registration` писал в `cancelled_at` значение,
которое qadam `tables` теперь отвергает:

```
Invalid date for field "cancelled_at"
```

Пустая строка больше не проходит валидацию DATE, а «оставить значение пустым»
у пропа `values` означает **не менять поле**, а не очистить его. Обходного пути
внутри qadam'а нет: `ap_update_record` (MCP) пустую строку принимает и поле
очищает — то есть умеет это БД, но не qadam.

**Что сделано сейчас:** `cancelled_at` убран из записи. У реактивированной
строки он остаётся от прошлой отмены, и это **противоречие в данных**:
`status = registered` при непустом `cancelled_at`. Потребители обязаны
смотреть на `status`.

**Чего не хватает:** либо у qadam'а должен появиться способ очистить DATE
(отдельное значение-сентинел или флаг), либо `''` должен снова означать
«очистить». Заводить тикет в апстрим.

**Связано:** [Q29](#q29) — этот дефект был им замаскирован: пока `step_38`
получал пустой вход, ветка реактивации не исполнялась ни разу.

**Где ещё это должно быть записано (по ревью W21):** требование «потребители
смотрят на `status`, а не на `cancelled_at`» продублировано в
[DATA-MODEL.md](DATA-MODEL.md) и [catalog/tables/registrations.md](../catalog/tables/registrations.md) —
иначе его не увидит тот, кто будет делать список участников owner'а и экспорт OWN-8.
