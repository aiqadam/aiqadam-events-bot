<a id="q2"></a>

## Q2. Уникальность и атомарность в Tables

**Проверено 2026-09-08 на живом инстансе. Ответ: ничего этого нет.**

| Проверка | Результат |
| --- | --- |
| Три записи с одинаковым ключом в таблице-пробе | вставились все три, ошибки нет |
| Уникальные индексы при создании таблицы | не поддерживаются |
| Типы полей | только `TEXT`, `NUMBER`, `DATE`, `STATIC_DROPDOWN` — ни boolean, ни JSON |
| Upsert в `tables` qadam | отсутствует: create / update / get / find / delete / clear |
| `store put` «только если нет» | отсутствует |
| TTL у `store` | отсутствует |
| Условный update (обновить, если поле пусто) | отсутствует, `update-record` работает по `id` |

Атомарного примитива на платформе нет вообще. Идемпотентность переписана
на «повтор безвреден + свёртка дублей при чтении + `dedup-sweep`» —
[ADR-0003](adr/0003-idempotency-without-atomicity.md).

Строгой exactly-once гарантии у нас не будет, и это записано прямо.

**Статус:** закрыт 2026-09-08.

<a id="q4"></a>

## Q4. Отношение к существующему `aiqadam/aiqadam-telegram-bot`

В организации уже есть бот на aiogram (`aiqadam/aiqadam-telegram-bot`, «AI Qadam
Telegram bot + outbound notifier, long-poll + Redis Streams», компаньон
`ai-qadam-platform` по ADR-0034).

Вопросы:

- это **тот же бот-аккаунт** или новый? Один токен не может одновременно висеть
  на long-poll в одном сервисе и на webhook в Qadam Flow — они будут отбирать
  апдейты друг у друга;
- если бот один, кто владеет `setWebhook` и как события событийного модуля
  доезжают до Qadam Flow;
- не дублируем ли мы существующий outbound notifier своей рассылкой.

**Решено: отдельный бот-аккаунт под ивенты.** Конфликт за апдейты снимается целиком:
существующий бот остаётся на long-poll, новый работает по webhook в Qadam Flow.

Следствия:
- `setWebhook` нового бота ставит **только** флоу `tg-router`;
- у пользователя будет два бота AI Qadam — стоит развести их по назначению в описаниях
  и перелинковать друг на друга;
- `QR_SIGNING_KEY` и токен нового бота заводятся как отдельные connections
  в проектах `events-dev` и `events-prod`.

**Статус:** закрыт 2026-09-08.

## Q6. Возможности Code step

**Проверено 2026-09-08 прогоном пробного флоу.** Песочница — чистый ECMAScript плюс
полный `Intl`, и ничего больше:

| Что | Результат |
| --- | --- |
| `Intl` + `Asia/Tashkent` | ✅ `2026-09-08T14:00:00Z` → `8 сент. 2026 г., 19:00` |
| Локаль `uz-UZ` | ✅ `Sentabr` |
| `node:crypto` | ❌ `Not supported` |
| `fetch` | ❌ `undefined` |
| `Buffer`, `btoa`, `TextEncoder`, `crypto.subtle` | ❌ отсутствуют |
| npm через `packageJson` | ❌ `require is not defined` |
| `process` | ❌ отсутствует; таймзона песочницы UTC |

Следствия разнесены по документам:

- `fn-fmt-time` делается штатно, ручной расчёт UTC+5 не нужен (OWN-3);
- HMAC — только через `crypto` qadam, альтернативы физически нет;
- base64url — строковое преобразование base64-вывода qadam'а;
- случайные токены — `crypto / generate-password`;
- правило «Code step — чистая функция» обеспечено песочницей, а не дисциплиной.

**Статус:** закрыт 2026-09-08.

<a id="q7"></a>

## Q7. Экспорт и версионирование флоу

**Решено по окружениям: два проекта в одном инстансе** — `events-dev` и `events-prod`,
с разными ботами, таблицами и connections. Правки обкатываются в dev, в prod едет
экспортированный флоу. Для рассылок это не формальность: ошибка в боевом флоу
уходит людям и не отзывается.

**Решено: агентский каталог, REST API не используем.**

Сначала я нашёл в исходниках рабочий экспорт
(`GET /api/v1/flows/<flowId>/template`, `flow.controller.ts:153`, принимает
платформенный API-ключ) и предложил скриптовать выгрузку в `flows/*.json`.
Владелец указал на `qadam-flow-project-template` — домашнюю практику,
обкатанную на BPM Hero, где принята модель **только MCP + UI**, а источник правды
в git — **агентский каталог** `catalog/*.md`.

Приняли практику. Найденный REST-эндпоинт остаётся неиспользованным сознательно —
[ADR-0004](adr/0004-catalog-instead-of-flow-export.md) фиксирует и его существование,
и причину отказа, чтобы через полгода это не выглядело упущением.

Цена решения — синхронизация каталога держится на дисциплине агента, а не на
автоматическом diff'е. Поэтому «каталог обновлён» входит в чек-лист готовности
каждого пакета работ.

### Дополнение 2026-09-08: что REST-экспорт умеет на самом деле

Отказ от REST в силе, но одно его свойство проверено прогоном, потому что упёрлись
в него трижды. Ревьюеры W2 и W3 независимо обнаружили, что **MCP не отдаёт входы
PIECE-шагов**: `ap_read_step_code` работает только для CODE, `ap_get_run` — только
для выводов. Из-за этого через MCP нельзя проверить ни URL и расписание
`i18n-sync`, ни ориентацию аргументов `hmac-signature` в `fn-verify-init-data` —
то есть ровно те места, где ошибка тихая и дорогая.

`GET /api/v1/flows/<flowId>/template` с платформенным API-ключом
(обязателен `?projectId=`) отдаёт `settings.input` каждого шага целиком. Проверено
на двух флоу:

- `i18n-sync` — `cronExpression: "0 4 * * *"`, `timezone: "Asia/Tashkent"`,
  три URL на `main`, `failureMode: "continue_all"`;
- `fn-verify-init-data / step_2` — `secretKey: "WebAppData"`,
  `text: "{{connections['<id>']}}"`, `secretKeyEncoding: "utf-8"`;
  у `step_3` ключ — `{{step_2['output']}}` с `secretKeyEncoding: "hex"`.

Секретов в экспорте нет: bot token присутствует **ссылкой на connection**, а не
значением. Для git это безопасно.

**Решено 2026-09-08: read-only REST разрешён ревьюеру** —
[ADR-0006](adr/0006-rest-read-only-for-review.md). Только `GET`, только то, чего не
отдаёт MCP, и только проверяющему: владельцу пакета REST не разрешён ни для чего,
`flows/*.json` в репозиторий не выгружаются, каталог остаётся источником правды.
ADR-0004 задним числом не правится — граница проведена новым решением.

Соблазн «выгружать флоу скриптом» закрыт по-прежнему. Разница в роли: у ревьюера
нет права ничего менять, поэтому чтение конфигурации не открывает дорогу к
скрипту заливки и своему деплою — тому, от чего защищает ADR-0004.

Цена названа в ADR-0006: конвенция «только MCP + UI» перестала быть однострочной,
и в обороте появился третий секрет — платформенный API-ключ, чья область шире
одного проекта. Ключ не коммитится, передаётся переменной окружения.

**Статус:** закрыт 2026-09-08. Основная часть — агентский каталог как источник
правды; слепое пятно ревью — ADR-0006.

## Q8. Второй чаптер

ТЗ прямо говорит: «скоро появится второй чаптер», и из-за этого роли моделируются
таблицами (DAT-3). Но не сказано, что именно чаптер значит для данных:

- у ивента появляется `chapter_id`?
- owner становится owner'ом чаптера, а не отдельных ивентов?
- сегменты рассылок режутся по чаптеру?

**Решено: `chapter_id` заводим сразу, логики пока нет.** В модель добавлены таблица
`chapters` и поле `events.chapter_id`. Права, сегменты рассылок и видимость по чаптеру
**не режутся** — это отдельное требование, когда появится.

Так второй чаптер не потребует миграции данных, а мы не выдумываем семантику
разграничения раньше, чем узнаем реальные правила.

**Осталось открытым:** что чаптер значит для прав (owner чаптера vs owner ивента)
и для сегментов рассылок.

**Подтверждено 2026-09-08: оставляем отложенным сознательно.** Решаем, когда второй
чаптер появится реально. Модель к этому готова в главном — права привязаны к ивенту,
а не к пользователю (ADR-0002), поэтому миграции не потребуется. Выдумывать семантику
разграничения раньше реальных требований — верный способ угадать неправильно.

**Статус:** частично закрыт 2026-09-08; остаток отложен намеренно.

> **Дополнение 2026-09-15:** часть «что чаптер значит для прав» отвечена —
> [ADR-0024](adr/0024-staff-by-chapter-event-staff-checkin.md): глобальный `staff`
> ограничен чаптером (`staff.chapter_id` = `'' ` — все чаптеры, иначе должен
> совпасть с `event.chapter_id`). Заведён общий чаптер `id=1`; выбор чаптера в форме
> не появляется. Сегменты рассылок по чаптеру **по-прежнему не режутся** — эта часть
> Q8 остаётся открытой до W14/первого реального второго чаптера.

## Q11. CORS между GitHub Pages и вебхуком

**Проверено 2026-09-08 боем** — поднял временный webhook-флоу и постучался с
`Origin: https://aiqadam.github.io`. Работает полностью:

```
OPTIONS /api/v1/webhooks/<flowId>/sync   → 204
  access-control-allow-origin: *
  access-control-allow-methods: *
  access-control-allow-headers: content-type

POST    /api/v1/webhooks/<flowId>/sync   → 200  {"ok":true}
  access-control-allow-origin: *
  + заголовки, которые вернул сам флоу
```

Важные детали:

- **preflight обрабатывает платформа**, а не флоу — прогон на `OPTIONS` не тратится;
- ответ синхронный при суффиксе **`/sync`** — это и есть адрес для `checkin-api`;
- `webhook / return_response` умеет отдавать произвольные `headers` и `status`,
  так что коды `401`/`403` из [FLOWS.md](FLOWS.md#checkin-api--основной-путь-чекина-mini-app)
  реализуемы штатно;
- подгонять запрос под «простой» не требуется: `Content-Type: application/json` проходит.

Проверка шла с `Origin: https://aiqadam.github.io`, но платформа отвечает
`access-control-allow-origin: *`, поэтому переезд страницы на собственный домен
`miniapp.events.aiqadam.org` ([Q3](#q3)) на CORS не влияет — перепроверять не нужно.

**Статус:** закрыт 2026-09-08.

## Q13. Темп рассылки и `retry_after` — **BLOCKER для W14**

Всплыло после разведки W0: в песочнице Code step нет `fetch`, поэтому отправлять
из кода нельзя. Рассылка становится циклом платформы (`LOOP_ON_ITEMS` + шаг
`telegram send_text_message` + `delay`), а не пачкой внутри одного шага.

Отсюда два неизвестных, и оба упираются в требования ТЗ:

1. **Достижимы ли 25 msg/s (OWN-11)?** У каждой итерации цикла есть накладные
   расходы платформы — запись состояния шага, переход по дереву. Если итерация
   стоит дороже 40 мс, потолок окажется ниже требуемого, и рассылка на 3000 человек
   не уложится ни в один прогон по `FLOW_TIMEOUT_SECONDS = 600`.
2. **Доступен ли `retry_after` из ответа Telegram** в объекте ошибки шага
   (`{{step['error']}}`) при `continueOnFailure`? Требование OWN-12 говорит «пауза
   ровно на `retry_after`». Если в ошибке лежит только текст без структуры, придётся
   парсить строку, а при неудаче — брать фиксированную паузу, что уже не «ровно».

**Как проверить:** временный флоу с циклом на 50 итераций и `delay 40ms`, замер
фактического времени прогона; отдельно — шаг с заведомо неверным `chat_id`,
чтобы посмотреть форму ошибки. Обе пробы дешёвые, делать до сборки W14.

**Решено заранее, что делать при отрицательном результате** (2026-09-08):
**снижаем темп до реального и правим OWN-11** отдельным коммитом в
[SPEC.md](SPEC.md), с честной записью, какой потолок даёт платформа.

Параллельные прогоны по чанкам отклонены: они дают нужный суммарный темп, но
общий лимит Telegram при этом не контролирует никто, и вместо одной управляемой
очереди получаем лавину `429`. Оставить требование невыполненным «на бумаге»
тоже нельзя — документ, расходящийся с реальностью, хуже отсутствующего.

Для митапа это малая потеря: рассылка на 500 человек при 10 msg/s — минута.

**Уточнение 2026-09-14 (пересмотр беклога).** Часть первого неизвестного уже
отвечена замерами, не ждущими W14: отправка сообщения Bot API стоит
**0,7–0,9 с** на вызов, итерация цикла — единицы мс ([ADR-0009](adr/0009-hot-path-latency-budget-and-order.md),
замер 2026-09-13; параллельности нет — [Q23](#q23)). Арифметика
последовательного цикла даёт потолок порядка **1–1,4 msg/s**, то есть
25 msg/s (OWN-11) недостижимы по арифметике, а не только накладными
расходами итераций. Это оценка по цене одной операции, а не прогон рассылки
— замер W14 подтверждает число или опровергает; при подтверждении
срабатывает заранее принятое решение: снизить темп и править OWN-11
отдельным коммитом. Второе неизвестное (`retry_after` в `{{step['error']}}`)
этим фактом не затронуто и остаётся на замер.

**Статус:** открыт (нужен замер), но решение по результату уже принято.
С 2026-09-16 W14 — v0.1: замер входит в пакет.

## Q14. Как одна страница сканера адресует два окружения

Всплыло при заведении `events-prod` (шаг 0.6, 2026-09-08).

`checkin-api` адресуется как `/api/v1/webhooks/<flowId>/sync`
([ARCHITECTURE.md](ARCHITECTURE.md)), и `flowId` у `events-dev` и `events-prod`
**разный**: флоу пересобирается по каталогу, а не переносится файлом
([ADR-0004](adr/0004-catalog-instead-of-flow-export.md)). При этом страница
сканера — одна, на одном домене `miniapp.events.aiqadam.org` ([Q3](#q3)),
и в ТЗ нигде не сказано, откуда она берёт адрес своего окружения.

Цена ошибки несимметрична: боевой сканер, стучащий в dev-проект, отмечает людей
в пустой таблице и рапортует успех. Молча захардкодить один `flowId` нельзя.

Варианты, все в рамках «0 кода»:

1. **Два пути в артефакте** — `/` (prod) и `/dev/`, у каждого бота в BotFather
   свой Mini App URL. Адрес окружения виден в URL, перепутать труднее всего.
2. **Query-параметр** — `?env=dev` в Mini App URL у dev-бота, карта
   `env → flowId` внутри страницы. Один файл, но параметр легко потерять.
3. **Отдельный поддомен для dev** — чище всех, но это ещё одна DNS-запись
   и второй сертификат.

Склоняюсь к (1): цена — копия файла в `miniapp/`, зато окружение видно глазами,
и prod остаётся адресом по умолчанию, который уже прописан.

**Отложен на старте W7, 2026-09-09.** `events-prod` (шаг 0.6) на момент W7
ещё не существует — он сам сдвинут в BACKLOG на волну 6 (после W15), решено
2026-09-08. Адресовать два окружения, второе из которых физически не
развёрнуто, преждевременно: `flowId` `events-prod` сегодня взять неоткуда,
любое решение будет гаданием. W7 строится на один `flowId` — `checkin-api`
в `events-dev` — зашитый обычной константой в `miniapp/index.html` (не через
переменные проекта, их в статике нет). Вопрос, как различать окружения
(варианты 1–3 выше), переоткрывается **к моменту фактического создания
`events-prod`**, а не раньше; тогда же учитывать найденное по ходу W7
ограничение GitHub Pages — автоматический TLS-сертификат выдаётся на один
кастомный домен на репозиторий, поэтому вариант 3 («отдельный поддомен»)
на практике требует **второго репозитория**, а не только DNS-записи.

**Решение владельца 2026-09-17 (перед W15):** вариант — **раздельные
инсталляции**. Каждое окружение (`events-dev`/`events-prod`) получает
собственный полноценный деплой `miniapp/`, с зашитым на момент деплоя
`flowId` `checkin-api` своего окружения — без runtime-переключения по
`env`-параметру или общему артефакту с двумя путями. Это ближе к варианту 3,
но проще: не отдельный поддомен ради одного файла, а осознанно раздельные
сборки/деплои на своих адресах, как и весь остальной состав `events-prod`
(свой бот, свой connection, свой `QR_SIGNING_KEY`).

**Статус:** решение принято 2026-09-17; реализация (второй деплой,
`flowId` `events-prod`) — часть шага 0.6 внутри [W15](../BACKLOG.md#w15-приёмка),
поскольку `events-prod` физически ещё не создан.

<a id="q15"></a>

## Q15. Как выбирать строки по диапазону дат

Всплыло при заведении таблиц (W1, 2026-09-08).

Через MCP `ap_find_records` операторы `gt`/`lt` **работают только по `NUMBER`**:

| Фильтр | Результат |
| --- | --- |
| `overbook_pct gt 10` (NUMBER, значение 40) | ✅ строка найдена |
| `starts_at lt 2026-09-11T00:00:00Z` (DATE, значение 2026-09-10T09:00:00Z) | ❌ пусто |
| то же со значением `2026-09-01` и с epoch-ms | ❌ пусто |
| `title gt A` (TEXT) | ❌ пусто |
| `starts_at eq 2026-09-10T09:00:00Z` | ✅ строка найдена |

Похоже, диапазонное сравнение приводит значение к числу, и всё нечисловое
превращается в `NaN`. Проверить то же на **qadam'е** `tables-find-records`
(а флоу ходят именно через него) в W1 не удалось: `filters` — DYNAMIC-проп,
и обе угаданные формы (`fieldName`/`field_id`) были молча проигнорированы —
действие вернуло все строки. Молчаливое игнорирование неизвестной формы фильтра
опаснее ошибки, и это само по себе стоит запомнить.

Кого касается:

- **W12** (lifecycle) — «ивенты, у которых `ends_at` уже прошёл»;
- **W12** (напоминания) — «ивенты в окне ближайших N часов»;
- **W10** — «инвайт не просрочен» (`expires_at`);
- **W6/W13** — «предстоящие» против «прошедших» ивентов.

Варианты:

1. **Фильтровать в Code step.** Тянем строки по `status`/`event_id` (`eq` работает)
   и сравниваем даты в шаге. Ивентов десятки — объём не проблема. Цена: сканы
   растут вместе с историей, для `registrations` так делать уже нельзя.
2. **Числовой дубль поля** — `starts_at_ms`, `ends_at_ms`, `expires_at_ms` типа
   `NUMBER`, по ним диапазонные фильтры точно работают. Цена: два поля с одним
   смыслом, которые обязаны обновляться вместе, — классический источник расхождения.
3. **Разобраться с формой `filters` у qadam'а** и, если диапазон там работает,
   ничего не менять в схеме.

Схему W1 **не меняли**: добавлять `*_ms` до проверки (3) — это заложить дубль,
который потом никто не решится убрать. До первого флоу с выборкой по времени
(W10/W12) идём по варианту (1), он не требует схемы вообще.

Решать в W2 — там появится первый флоу, где `tables-find-records` настраивается
через `ap_add_step`, и форма `filters` станет видна.

### Закрыт 2026-09-08 (W2): вариант 3 отпадает

Форма `filters` у qadam'а выяснена — это **DYNAMIC-проп с вложенным массивом**,
и поле задаётся объектом, а не именем:

```json
{"filters": {"filters": [
  {"field": {"id": "<externalId поля>", "type": "DATE", "name": "starts_at"},
   "operator": "lt", "value": "2026-09-11T00:00:00Z"}
]}}
```

С правильной формой прогнали сам qadam через `ap_run_action` на строке
`events` с `starts_at = 2026-09-10T09:00:00Z`:

| Фильтр | Результат |
| --- | --- |
| `starts_at eq 2026-09-10T09:00:00Z` | ✅ строка найдена — форма фильтра верна |
| `starts_at lt 2026-09-11T00:00:00Z` | ❌ пусто |
| `overbook_pct gt 10` (NUMBER) | ✅ строка найдена |

Проверка воспроизводится одним вызовом `ap_run_action` над
`@aiqadam/qadam-tables / tables-find-records` с формой фильтра выше, на строке
`events` с `starts_at = 2026-09-10T09:00:00Z` и `overbook_pct = 40`.
Id тех прогонов здесь **не приводятся сознательно**: `ap_run_action` не сохраняется
как flow run, `ap_get_run` на такой id отвечает «Flow run not found», а ссылка,
которую следующий агент не может открыть, доказательством не является.

`eq` по тому же полю работает, значит фильтр **не игнорируется**, а именно
диапазонное сравнение по `DATE` не срабатывает. Поведение qadam'а совпадает
с MCP до буквы: догадка про приведение к числу подтверждается.

**Решение:** идём вариантом (1) — тянем строки фильтром `eq` по `status`/`event_id`
и **сравниваем даты в Code step**. Числовых дублей `*_ms` (вариант 2) в схему
не добавляем: это два поля с одним смыслом, которые обязаны обновляться вместе.
Вариант 2 остаётся резервом на случай, если `registrations` или `events` вырастут
настолько, что скан станет дорогим, — и тогда это будет отдельный ADR, а не
тихая правка схемы.

Заодно видно то, чего в вопросе не было: `find-records` возвращает **все** колонки
строки, проекции нет ([Q17](#q17)).

**Статус:** ✅ закрыт 2026-09-08 в W2. Схема W1 не менялась. W10/W12 разблокированы
вариантом (1).

## Q16. Как проверить `initData` от живого клиента Telegram

Всплыло на ревью W2 (2026-09-08).

Чек-лист W2 требует: «`fn-verify-init-data` проверён на **реальном** `initData`».
Агент такой строки достать не может — `initData` выдаёт клиент Telegram при
открытии Mini App, и синтезировать её без bot token невозможно (а токен лежит
в connection платформы и наружу не читается).

Что **уже** проверено без живого клиента и перепроверять не нужно:

- цепочка двух HMAC пересчитана вне платформы (`openssl`) и сошлась побайтово,
  включая трактовку hex-ключа второго шага как двоичного — то есть алгоритм
  телеграмовский, а не «похожий»;
- семантика аргументов `crypto / hmac-signature` проверена вызовом
  `ap_run_action` — воспроизводится любым внешним HMAC, id прогона намеренно
  не приводится (`ap_run_action` не сохраняется как flow run, `ap_get_run` его
  не открывает). Условия и контрольные значения:
  `secretKey = "WebAppData"`, `secretKeyEncoding = utf-8`, `method = sha256`,
  `text = "PROBE-W2"`, `outputEncoding = hex` →
  `5a2b099b41154ee663ad6753f999940b02ae5fba122a8592adef108769343e8b`,
  что равно HMAC(key=`WebAppData`, msg=`PROBE-W2`) и **не** равно обратной
  ориентации `4469d2c2e3e24b893b41b726a09bb3d7b3b6391f85de813060a11a88207367cc`.
  Значит `secretKey` — это ключ, а `text` — сообщение. Тот же вывод независимо
  получил ревьюер третьего круга на своём тексте (`PROBE-REVIEW2`);
- отказы проверены прогонами: подделанный `hash`, подменённый `user`,
  просроченный `auth_date`, переставленный порядок полей, мусор.

**Закрыто 2026-09-08, часть про ориентацию.** Конфигурация шага была слепым
пятном: MCP не отдаёт inputs PIECE-шагов, а при зеркальной ориентации аргументов
цепочка осталась бы самосогласованной для собственноручно посчитанного `hash` —
все прогоны прошли бы точно так же. Read-only REST-экспорт
([ADR-0006](adr/0006-rest-read-only-for-review.md), снимал ревьюер) показал
фактическую конфигурацию: у `step_2` `secretKey: "WebAppData"`,
`text: "{{connections['TZTlXaCEO2hEvimUowbSA']}}"`, `secretKeyEncoding: "utf-8"`;
у `step_3` `secretKey: "{{step_2['output']}}"`, `secretKeyEncoding: "hex"`.
Токен подставлен именно в `text`, ориентация верна, hex-ключ второго шага
на месте.

**Что остаётся:** собственно `initData`, выданный живым клиентом Telegram.
Ни экспорт, ни пробники его не заменяют — они подтверждают наш конец цепочки,
а не то, что Telegram считает подпись так же.

Кто может закрыть:

1. **человек** — открыть Mini App у `@aiqadam_events_dev_bot`, скопировать
   `Telegram.WebApp.initData` и прогнать `fn-verify-init-data`. Пять минут;
2. **W7** — сканер всё равно будет присылать `initData` в `checkin-api`, так что
   первый же сквозной прогон W7/W8 закрывает вопрос сам собой;
3. глазами в UI — открыть шаг и посмотреть, что стоит в `secretKey` и `text`.
   Закрывает ориентацию, но не «реальный `initData`».

До закрытия соответствующий пункт чек-листа W2 **не отмечен**, а формулировка
критерия в [BACKLOG](BACKLOG.md#w2-subflow-функции) уточнена отдельным коммитом:
пункт разделён на «алгоритм сверен независимо» (сделано в W2) и «проверено на
живом `initData`» (переезжает в W7/W8).

**Статус:** открыт частично. Ориентация аргументов и конфигурация цепочки —
закрыты экспортом (ADR-0006). Остался прогон на живом `initData`: нужен человек
или W7. Не блокирует W4/W5, **блокирует приёмку STF-2 в W8**.

**W8 (2026-09-09), первый прогон:** флоу `checkin-api` собран и полностью проверен
сквозными прогонами с настоящей криптографией (все исходы STF-4 плюс `401`/`403`),
но на синтетическом `initData`, посчитанном тем же алгоритмом, а не выданном
клиентом Telegram.

**Закрыт 2026-09-09.** Владелец бота открыл Mini App в Telegram и дважды передал
настоящий `initData` (второй раз — прямым `fetch()` из самого Mini App, без
ручного копирования) — оба раза `fn-verify-init-data` вернул `hashValid: false`.
Это оказался не недостаток прогона, а **реальный баг**: `{{connections['<id>']}}`,
подставленный в `text` шага `crypto : hmac-signature` как данные (не как `auth`),
не даёт тот же байт-в-байт токен бота, что использует внутренняя авторизация
того же connection для настоящих вызовов Bot API (`getMe` через ту же connection
подтвердил правильный токен). Решающая проверка: владелец бота посчитал
`HMAC("WebAppData", bot_token)` **локально, у себя**, с реальным токеном из
BotFather — значение не совпало с тем, что вычислял шаг через connection.

Токен продублирован в project Variable `BOT_TOKEN`, `fn-verify-init-data / step_2`
переключён на `{{variables['BOT_TOKEN']}}` — тот же `initData`, на котором до
этого было `hashValid: false`, дал `hashValid: true` тем же прогоном
(`zVsliGe9MlO6cfXpjcwbT`), без других изменений в цепочке.

Находка задокументирована как [ADR-0008](adr/0008-bot-token-as-variable-not-connection-template.md) —
исправление применяется ко **всем** вызывающим `fn-verify-init-data`
(`registration`, `my-qr-api`, `checkin-api`), не только к W8. Пакет W8 разблокирован
этим закрытием — [W08](work/W08-checkin-api.md).

## Q17. ПД в логах прогонов: у `tables` нет проекции колонок

Всплыло на ревью W2 (2026-09-08), связано с
[ADR-0005](adr/0005-secrets-visible-in-run-logs.md).

`tables-find-records` возвращает **все** поля найденных строк — выбрать три
колонки из двенадцати нельзя. Входы и выходы шагов логируются целиком, поэтому
любое чтение `users` кладёт в лог прогона `phone` (DAT-2), имена и `username`
тех строк, которые попали в выборку. Читает лог любой, у кого есть доступ
к проекту.

Что сделано в W2: `fn-resolve-segment` перестал выгружать таблицу `users`
целиком. Вместо одного чтения без фильтров — два фильтрованных
(`blocked_bot eq true` и `consent_marketing eq true`), то есть в лог попадают
только те, кто заблокирован или дал согласие, а не все пользователи бота.
Множества при этом ровно те же, что давала прежняя проверка `=== 'true'` в коде.

Что **не** решается: у найденных строк всё равно логируются все колонки.
Варианты на будущее, ни один не бесплатный:

1. **Ничего не менять**, ограничиваться фильтрами и дисциплиной доступа
   (текущий выбор, ADR-0005).
2. **Вынести `phone` в отдельную таблицу** `user_phones` и читать её только там,
   где телефон действительно нужен (экспорт OWN-8). Цена: ещё одна связь,
   которую держит только флоу, и +1 чтение в регистрации.
3. Свой сервис-прокси к данным — прямой отказ от ADR-0001.

Кого касается дальше: **W13** (экспорт с ПД), **W14** (рассылки читают `users`),
**W12b** (`dedup-sweep` ходит по всем таблицам).

**Статус:** открыт как **принятый риск**. Решать вариантом (2) стоит не раньше,
чем телефон реально начнут собирать (DAT-2 делает его опциональным).

> **Апдейт 2026-09-12 (W19).** Посылка вопроса — «у `tables` нет проекции
> колонок» — **устарела**: она появилась
> ([qadam-flow#407](https://github.com/aiqadam/qadam-flow/pull/407)). На
> инстансе это проп **`columns`** у `tables-find-records` (а не `fieldIds`, как
> сказано в тексте апстримного PR), `MULTI_SELECT_DROPDOWN`, значения —
> **externalId** полей, не `field id` из `cells`. Описание пропа называет ровно
> нашу причину: «Step outputs are recorded verbatim in the run log, so reading
> only the columns you need is also what keeps the rest out of it».
>
> **Проекция применяется, риск сужается.** Существующие шаги `tables` нельзя
> править напрямую — они пришпилены к версии qadam'а, которой после обновления
> образа нет ([qadam-flow#411](https://github.com/aiqadam/qadam-flow/issues/411)),
> и перепривязать их не удаётся даже явным `qadamName`. Но пересозданный шаг
> правится штатно и **получает то же имя**, поэтому ссылки вниз по флоу не
> ломаются, а `ap_update_step` **мержит** `input` — `filters` при добавлении
> `columns` не теряются (проверено). То есть обход дешевле, чем казалось.
>
> Сделано на 2026-09-12: `tg-router/step_7` — сквозной прогон
> `BywBIqJvv6bjW06R6qYBC` подтверждает, что в логе остались только пять
> потребляемых колонок, фильтр цел, регресса в `step_8` нет. Остальные пять
> чтений — в работе.
>
> Доказательство, что риск реален, а не теоретичен: прогон `tg-router`
> `jAb16tiE4Zm5PyQ3IqSri` (2026-09-12) содержит в выводе `step_7` строку
> `users` целиком — `phone`, оба consent-флага, имена, `username`.
>
> Два ограничения, которые проекция колонок **не** снимает:
>
> - **`phone` из лога `tg-router` не уйдёт** — `step_8` вычисляет из него булев
>   `phoneKnown`. Чтобы убрать и его, нужна колонка-флаг в `users`, то есть
>   изменение схемы, смежное с вариантом (2).
> - **`tables-update-record` возвращает строку целиком**, и проекции колонок у
>   этого действия нет — только у `tables-find-records`. Поэтому `tg-router/step_10`
>   (апдейт `users`) по-прежнему кладёт в лог все двенадцать колонок, включая
>   `phone`. Проверено прогоном `BywBIqJvv6bjW06R6qYBC`. То есть для `tg-router`
>   утечка **уменьшена, но не устранена**, и вариант (2) остаётся на столе.
>
> Кандидаты на сужение, отобранные по фактическому потреблению (прочитан код
> шагов, а не угадано): `tg-router/step_7` (нужны только `created_at`, `lang`,
> `consent_pdn`, `consent_marketing`, `phone` из двенадцати колонок),
> `checkin-api/step_28` и `my-qr-api/step_15` (нужен только `lang`),
> `checkin-api/step_12` (нужно только имя), `fn-resolve-segment/step_4` и
> `step_7` (нужен только `telegram_id`).

## Q18. Как мы узнаём, что фоновый флоу не сделал работу

Поднято ревью пакета W3 (замечание 8).

`i18n-sync` спроектирован **fail-safe**: язык, файл которого не скачался или
выглядит обрезанным, не трогается, а прогон завершается **успешно** и пишет
причину в `report.skipped_langs`. Это правильное поведение — альтернатива
(упасть или стереть строки) хуже. Но у него есть слепая зона: **отчёт видит
только тот, кто откроет лог прогона.**

При суточном расписании это значит, что словарь может неограниченно долго
оставаться устаревшим или неполным, и никто не узнает: в UI флоу зелёный.
Тот же класс проблемы ждёт `reminders`, `lifecycle` и `broadcast-runner` —
любой фоновый флоу, который сознательно «ничего не делает» вместо падения.

Вопрос шире W3, поэтому и вынесен сюда: **своего канала уведомлений
у проекта нет.** Варианты, ни один пока не выбран:

1. **Сообщение owner'у в Telegram** из самого флоу, когда `skipped_langs`
   непуст. Дёшево, но требует знать, кому писать, — списка админов нет,
   а `events.owner_id` к i18n отношения не имеет.
2. **Уронить прогон намеренно** (`throw` в Code step), когда пропущен язык:
   тогда флоу краснеет в списке и виден без чтения логов. Цена — ложная
   тревога при разовом сетевом сбое и, что хуже, привычка к красным прогонам.
3. **Отдельный флоу-сторож** по расписанию: читает `strings`, сверяет число
   строк по языкам с ожидаемым и пишет владельцу. Ещё один артефакт
   и ещё одно место, где надо помнить ожидаемое число.
4. **Ничего не делать** и проверять руками на приёмке (W15). Честный вариант,
   пока проект не в бою.

Решать не позднее W14: рассылка — то место, где молчаливое «ничего не сделал»
стоит дороже всего.

**Статус:** открыт, не блокирует W3 (поведение fail-safe уже реализовано
и проверено), решать до W14 (v0.1 с 2026-09-16).

> Заведён как Q16, перенумерован в Q18 при мерже: пакет W2 занял номера
> Q16/Q17 своими вопросами, его PR влит первым.

## Q19. Локализация страниц Mini App

Поднято ревью пакета W3 (замечание 10). **Расширено ревью пакета W5,
2026-09-09**: вторая страница Mini App, `miniapp/ticket.html` (выдача QR
участнику, [ADR-0007](adr/0007-qr-rendered-in-miniapp.md)), собрана с теми
же литеральными русскими строками (заголовок, статусы загрузки, тексты
ошибок), что и страница сканера ниже — тот же класс проблемы, тот же вывод:
не блокер, но входит в тот же вопрос и то же решение по W7, а не отдельная
находка. Ключей под интерфейс `ticket.html` в словаре тоже нет.

Страница сканера (`miniapp/`, сейчас заглушка) показывает пользователю текст:
запрос разрешения на камеру, подсказку «наведите камеру на QR», четыре исхода
чекина (STF-4), сообщение «переоткройте Mini App» на просроченном `initData`.
При этом она:

- **не может читать `strings`** — это статическая страница на GitHub Pages
  без бэкенда, а Tables доступны только изнутри флоу;
- **не вызывает `fn-t`** и не должна: лишний round-trip на каждой надписи.

Значит, правило I18N-2 «ни одной пользовательской строки литералом» к этой
странице в текущем виде **неприменимо**, и это надо решить явно, а не обнаружить
в W7. Ключей под интерфейс сканера в словаре сейчас тоже нет.

Варианты:

1. **`checkin-api` возвращает готовый текст.** Исходы чекина уже приходят
   с сервера — пусть приходят строкой, а не кодом. Тогда четыре исхода
   локализованы бесплатно, `lang` берётся из `users.lang` по `initData`.
   Остаются надписи самой страницы (камера, подсказки).
2. **Маленький словарь внутри `index.html`** на три языка, язык — из
   `WebApp.initDataUnsafe.user.language_code`. Дублирует источник правды,
   зато без сети. Расхождение с `i18n/*.json` — вопрос времени.
3. **Страница тянет `i18n/*.json` с того же GitHub Pages** при загрузке.
   Источник правды один, лишнего бэкенда нет; цена — один запрос на старте
   и необходимость держать файлы в артефакте Pages, а не только в репозитории.
4. **Только пиктограммы и цвет** для исходов, текста на странице почти нет.
   Заманчиво, но «нет регистрации» и «другой ивент» иконкой не различить.

Предпочтение автора W3 — комбинация (1) для исходов и (3) для надписей
страницы, но решение за W7: там будет видно, во что это обходится по вёрстке.

**Решено при старте W7, 2026-09-09: комбинация (1)+(3).** `checkin-api`
(и `my-qr-api` для `ticket.html`) отдаёт уже локализованный текст исхода —
язык берётся из `users.lang` по `initData`, так же как везде в проекте
(DAT-1, `telegram_id` — ключ, `lang` — атрибут пользователя). Обе статические
страницы (`index.html` сканера и `ticket.html`) при загрузке одним `fetch`
тянут `i18n/<lang>.json` с того же GitHub Pages (тот же артефакт, значит без
CORS) и берут оттуда собственные надписи (запрос камеры, подсказка,
«переоткройте Mini App» и т. п.) по ключам из `i18n/*.json`; язык страницы —
`WebApp.initDataUnsafe.user.language_code` с фолбэком на `ru` для
неподдерживаемых значений. Источник правды остаётся один — `i18n/*.json` —
никакого встроенного словаря в HTML.

**Статус:** ✅ решено и реализовано в W7 (2026-09-09): `checkin-api` и `my-qr-api`
отдают локализованный `text` во всех исходах/ошибках (язык из `users.lang`;
для непроверенного `initData` — `ru`), обе страницы (`index.html`, `ticket.html`)
тянут `i18n/<lang>.json` с того же GitHub Pages (артефакт Pages теперь включает
`i18n/*.json`). Прогоны на опубликованных версиях и e2e — [журнал W07](work/W07-miniapp-scanner.md).

## Q20. `callFlow` с динамическими данными не настраивается через MCP

Поднято пакетом W4, 2026-09-09. Полное описание находки —
[ARCHITECTURE](ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2)
(пункт 4, дописан W4).

Шаг `callFlow` (`@aiqadam/qadam-subflows`), которому нужно передать callee
**данные из предыдущих шагов** (а не пустой вызов), не удаётся сохранить через
MCP: сам subflow выбирается нормально (`flow: {"externalId": ...}` работает),
но `flowProps` — сам платёж данных — не долетает ни в одной из шести проверенных
форм. Проверено и на реальном шаге, и на изолированном пробном флоу через
`ap_build_flow` в одну команду (чтобы исключить артефакт инкрементальных
`ap_update_step`). Результат одинаковый: `trigger['output']` у callee не содержит
ключа `data` вовсе.

Это не мешает W4 (у `tg-router` пока нет подходящего обработчика, которому
нужно передавать разобранный payload), но заблокирует **W5, W10, W11** — все
три вызывают subflow'ы (`fn-event-card`, `fn-find-registration`, `fn-sign-qr`,
`fn-verify-qr`, `fn-parse-start`...) с данными, специфичными для конкретного
запроса. W2 такие вызовы строил (`fn-event-card` → `fn-fmt-time`/`fn-t`
с данными), но неизвестно, как именно — журнал W2 не фиксирует точную форму
`flowProps`, а MCP не отдаёт inputs PIECE-шагов задним числом, так что
воспроизвести конфигурацию чтения нельзя.

Варианты:

1. **Переоткрыть вопрос на момент W5** — платформа могла поменяться; не тратить
   время на статью, если факт уже неверен.
2. **UI-эскейп**: тот же приём, что ARCHITECTURE.md уже фиксировал для выбора
   флоу (пункт 3) — шаг донастраивается вручную в UI, разово. Требует
   человека с доступом в UI (агент им не наделён).
3. **Обойтись без `callFlow` с данными** там, где это возможно: продублировать
   маленькую чистую логику Code step'ом вместо вызова subflow (цена — расход
   с «0 кода» и дублирование, годится только для совсем небольших функций).

**Закрыт 2026-09-09, переоткрыт по варианту 1 перед началом W5.** Дело было не
в платформе, а в способе, которым W4 резолвил схему `flowProps`: шесть форм из
таблицы в ARCHITECTURE.md проверялись с `input.flow` = строкой-`externalId`.
Если передать `ap_get_piece_props` полный объект `flow` — тот же, что отдаёт
`ap_resolve_property_options` (`{"externalId": "...", "exampleData": {"sampleData": {...}}}`),
а не строку, — схема резолвится верно и обнажает настоящее подполе:
`flowProps.payload` (JSON), а не `data`. С `payload` данные доезжают до callee
и лежат под `trigger['output'].data`, как и задокументировано в разделе
«Subflow'ы на практике». Тем же путём резолвится и `returnResponse.response`
(подполе `response.response`). Проверено на изолированной паре тестовых флоу
(`ap_build_flow` → `ap_test_flow`, оба флоу удалены после проверки) и на живом
`fn-t` — реальный вызов `callFlow` вернул настоящий перевод, а не пустой ответ.
Подробности и рабочий JSON конфигурации — [ARCHITECTURE](ARCHITECTURE.md#subflowы-на-практике--проверено-на-инстансе-2026-09-08-w2),
блок «Опровергнуто». **W5, W10, W11 разблокированы**: subflow-вызовы с данными
собираются целиком через MCP, UI-эскейп не нужен. Пакет W5 подтвердил это на
практике — `registration` и правка `tg-router` собраны полностью через
`callFlow` с данными (`docs/work/W05-registration.md`).

## Q21. Доставка файлов (QR-изображения) участнику не работает через MCP

Поднято пакетом W5, 2026-09-09. Подпись и генерация QR работают штатно
(`fn-sign-qr` → `@aiqadam/qadam-qrcode` `text_to_qrcode`), но **отправка готовой
картинки в Telegram падает во всех проверенных формах**, собранных через MCP.

Проверено два независимых пути, оба на изолированной паре тестовых флоу
(создана, проверена, удалена) и повторены на реальном шаге `registration`:

1. **`@aiqadam/qadam-telegram-bot / send_media`, FILE-проп `media.photo`.**
   Значение — URL из вывода `qrcode`-qadam'а (`https://app.flow.aiqadam.org/api/v1/files/...`).
   Перепробованы: голая строка, `{"url": ...}`, `{"url": ..., "filename": ...}` —
   во всех случаях `"No media defined. Provide either a file or an id."`.
   В `custom_api_call` с `body_type: form_data` и `fieldType: file` та же строка
   не роняет шаг, но `_valueLength` в теле запроса совпадает с длиной
   URL-строки, а не с размером PNG — значит платформа не резолвит ссылку
   на файл предыдущего шага в реальные байты, а пишет саму строку как
   содержимое файла.
2. **`custom_api_call` (`/sendPhoto`, `/sendDocument`) с тем же URL в JSON-теле** —
   запрос реально уходит в Bot API (в отличие от пункта 1), но Telegram отвечает
   `"Bad Request: failed to get HTTP URL content"` **одинаково для фото и для
   документа** — их сервер не может скачать файл по этому URL. Заголовки ответа
   (`content-type: application/octet-stream`, `content-disposition: attachment`)
   и происхождение TLS-сертификата инстанса (внутренний CA, похоже на
   MITM-прокси в сети, откуда работает агент) наводят на след, но подтвердить
   его нельзя: агент не может воспроизвести запрос с серверов Telegram, только
   со своей стороны.

**Не проверено и не исключено (на момент постановки):** что `app.flow.aiqadam.org`
в принципе недоступен внешним серверам (не только Telegram) из публичного
интернета — если так, это шире одной картинки QR и касается любого будущего
сценария, которому нужно, чтобы **внешний сервис** (не сам агент, не UI)
забрал файл по ссылке этого инстанса.

### Дополнение 2026-09-09: доступность извне подтверждена, найдена настоящая причина

Пункт «не проверено» — проверен. `curl` с независимой машины (не из сети
агента, не через инструменты платформы) забрал тот же файл по URL из вывода
`qrcode`-qadam'а: `HTTP 200`, `1025` байт, валидный PNG-заголовок. Значит
**`app.flow.aiqadam.org` внешним серверам доступен** — вариант 2 из списка ниже
закрыт с ответом «доступен», и версия про MITM-сертификат как причину отпадает.

Значит дело не в сетевой доступности инстанса, а в **самой возможности передать
реальные бинарные байты через MCP-настроенный шаг** — это проверено отдельно,
без Telegram и без внешнего стораджа вовсе, двумя независимыми путями на
изолированной паре тестовых флоу (`ap_build_flow` → `ap_test_flow`, оба флоу
удалены после проверки):

1. **`http`-qadam, `body_type: raw`.** Ожидание: строка (в т.ч. base64) уходит
   как есть. Факт: тело реально отправленного запроса — **JSON-сериализованная
   строка в кавычках** (`Content-Type: application/json`, `Content-Length` на
   ~2 байта больше длины самой base64-строки — ровно на кавычки), а не сырые
   байты. Подтверждено эхом `httpbin.org/put`: `data` в ответе — та же
   base64-строка, обёрнутая в кавычки как JSON. То есть **`raw` в этом
   `http`-qadam'е не сырой** — это `json`-режим, переименованный.
2. **`http`-qadam, `body_type: form_data`, поле `fieldType: file`.** Та же
   ошибка, что и с `send_media.media.photo` в пункте 1 выше, но уже на
   **другом qadam'е** — то есть это не особенность `telegram-bot`, а общая
   проблема FILE-проп'ов. `fileFieldValue` = data-URI со base64 (`data:image/png;base64,...`)
   не резолвится в файл: `httpbin.org/post` эхом показал `"form":{"file":"undefined"}`,
   `Content-Length` тела — 168 байт (у настоящего файла размером 1025 байт
   такое тело физически невозможно). Значит **FILE-тип пропа не понимает
   base64/data-URI, переданный через `input` в обход UI-пикера**, ни на одном
   из проверенных qadam'ов.

**Вывод: смена внешнего хранилища (S3/R2/что угодно) эту проблему не решает.**
Она не в Telegram и не в конкретном сервисе — она в том, что **MCP не может
сконфигурировать шаг так, чтобы он передал реальные бинарные байты куда бы то
ни было**: ни в `send_media`, ни в `custom_api_call` с form-data, ни в общий
`http`-qadam с `raw`-телом. Вариант с внешним объектным хранилищем (R2 и
подобные) закрыт как нежизнеспособный через MCP по этой же причине — не дошли
даже до вопроса заведения бакета и секретов.

Варианты, оставшиеся в силе:

1. **UI-эскейп**: перенастроить проблемный FILE-проп (`send_media.media.photo`
   или аналогичный) в UI, руками через штатный пикер — вероятно, он умеет то,
   что не умеет голый JSON через MCP (пикер, в отличие от `input`, кладёт в
   конфиг что-то помимо строки/data-URI — что именно, agent увидеть не может,
   MCP не отдаёт `settings.input` PIECE-шагов). Требует человека с доступом
   в UI и повторной проверки: точно ли после ручной настройки шаг рабочий,
   не просто «не падает».
2. ~~Проверить сетевую доступность инстанса извне~~ — сделано, инстанс доступен,
   причина не в этом.
3. **Обойтись без изображения** там, где это возможно уже сейчас: отправлять
   участнику подписанный `payload` текстом (не то же самое, что «QR выдан» из
   BACKLOG.md, но не блокирует остальной диалог) — временная деградация, не
   решение.

**Статус:** решение принято 2026-09-09 — [ADR-0007](adr/0007-qr-rendered-in-miniapp.md):
QR не отправляется файлом вовсе, а рендерится клиентским JS в Mini App из
текстового `payload`. Сам вопрос (нельзя передать бинарные байты через
MCP-собранный шаг) остаётся открытым и общим для платформы — актуален для W7
(Mini App может захотеть отдавать/принимать похожие ссылки), W12 (вложения
в напоминаниях) и любого будущего сценария с файлом во внешнем сервисе; W5
он больше не блокирует.

## Q22. Куда уходят секунды между шагами прогона; почему PRODUCTION медленнее TESTING

**Открыт 2026-09-09.** Поставлен живым демо-прогоном (участник → чекин) и
[ADR-0009](adr/0009-hot-path-latency-budget-and-order.md): без ответа структуру
горячего пути не пересобираем — сначала атрибуция.

**Факты (измерено, `events-dev`, 2026-09-09):**

- Длительность прогона ≫ суммы длительностей его шагов. `registration` `/start`
  (`JYWkDu2jBXX9BDd3kHna3`): шаги в сумме ≈ 8 с, прогон 34,2 с — остаток ≈ 26 с
  прогон проводит в паузах между шагами. Длительность шага `callFlow` **не
  включает** ожидание возврата вложенного флоу (считается своим прогоном:
  `fn-event-card` внутри — отдельные 13,9 с, `PR9hsQxEpyJMBXj4TPb6l`).
- `checkin-api`: изолированные TESTING-прогоны 4–9 с (запись в каталоге), те же
  графы в PRODUCTION — стабильно 21–27 с. Ранние отказы (401/403, до бизнес-цепочки)
  короткие: 6,5–8,4 с; дорогая часть — цепочка из ~5 последовательных `callFlow`
  + чтения `users` после авторизации.

**Гипотеза (не подтверждена):** остаток — платформенная меж-шаговая диспетчеризация
и очередь общего dev-инстанса (прогон ставится на паузу между шагами и резюмируется
по слоту), а не сеть и не тело шагов. Прямых инструментов платформы для проверки
у нас нет — нужен либо доступ к логам/метрикам диспетчера, либо эксперимент с
нагрузкой (сколько параллельных прогонов ухудшает время), либо ответ владельцев
платформы.

**Что нужно, чтобы закрыть:** разложить один PRODUCTION-прогон `checkin-api` и один
`registration` на составляющие (время исполнения шага / ожидание вложенного флоу /
пауза между шагами) и объяснить разницу TESTING vs PRODUCTION. Ответ меняет набор
кандидатов ADR-0009: если остаток — диспетчеризация, выигрыш даст только
сокращение числа шагов и слоёв, а не параллелизм; если параллельность существует
(Q23) — часть цепочки можно считать конкурентно.

**Проверено 2026-09-09, после инфра-тюнинга `pro-data-tech-qa` (T-0161: `AP_WORKER_CONCURRENCY`
1→5 закреплено явно, реплики воркера 1→5).** Пересчитаны step-sum vs полная длительность
на тех же графах, тем же методом, что дал эталон:

| Прогон | Флоу | Шаги (сумма) | Прогон (факт) | Остаток («пауза») |
|---|---|---|---|---|
| `JYWkDu2jBXX9BDd3kHna3` (эталон, до/во время тюнинга) | `registration` `/start` | ≈7,8 с | 34,2 с | ≈26,4 с |
| `EZR9h29YdjhAsyppMpKD1` (после) | `registration`, клик-шаг визарда | ≈4,2 с | 15,7 с | ≈11,5 с |
| `EFIxi7F09xHzQEmQRKsl0` (после) | `checkin-api`, один скан | ≈4,1 с | 24,0 с | ≈19,9 с |

Остаток на `registration` сократился примерно в 2,3 раза (26,4 с → 11,5 с) — это
согласуется с гипотезой «остаток — очередь диспетчера воркеров»: пяти воркерам
не нужно так долго ждать освобождения слота между шагами. Но на `checkin-api`
остаток **не изменился** (19,9 с после, вписывается в разброс 21–27 с эталона) —
тот же тюнинг не дал того же эффекта на графе с более длинной цепочкой вложенных
`callFlow` (авторизация → `fn-parse-start` → `fn-verify-qr` → `fn-find-registration` →
`fn-fmt-time` → отправка).

**Вывод:** гипотеза о диспетчеризации/очереди воркеров подтверждена частично —
она объясняет часть остатка (`registration`, `tg-router`: тот же прогон показывает
падение с 7,0–7,8 с до 2,2–3,4 с), но не весь и не везде. У `checkin-api` есть
второй, независимый источник остатка, который увеличение числа воркеров не лечит —
скорее всего, фиксированная накладная стоимость самого вложенного `callFlow`
(диспетчеризация *дочернего* прогона, а не ожидание слота в общей очереди), что
согласуется с длиной его цепочки. Открытым остаётся, сколько из ≈4 с на каждый
`callFlow`-переход — это диспетчеризация конкретно дочернего прогона (тогда лечится
только сокращением числа слоёв, ADR-0009 п.3) и сколько — общая очередь (тогда
лечится ещё воркерами). Единичного before/after недостаточно для разделения —
нужен контролируемый прогон с фиксированным числом одновременных флоу.

**Статус:** открыт, частично сужен. Дальше **не BLOCKER** для `registration`/`tg-router`
(тюнинг воркеров даёт измеримый выигрыш, можно фиксировать в ADR-0009 как
подтверждённый рычаг), но остаётся BLOCKER для решений по `checkin-api`, где
доминирует другой, ещё не изолированный источник остатка.

**Проверено 2026-09-09, после W16** ([ADR-0010](adr/0010-unsandboxed-code-step-for-crypto.md) —
`fn-verify-qr` перестал вызывать `fn-sign-qr` как subflow, инлайнил ту же подпись
через `node:crypto`, убрав один слой вложенного `callFlow` из цепочки `checkin-api`).
Тёплый прогон одного скана (тем же методом): шаги в сумме ≈4,9 с, прогон 22,8 с,
остаток ≈17,9 с (`cCXetqX6VPVmPpe3s1p5G`) — против ≈19,9 с в прошлой строке таблицы
(`EFIxi7F09xHzQEmQRKsl0`). Эффект в ожидаемую сторону (снят целый вложенный
flow-run, гипотеза «доминирует стоимость дочернего прогона» подтверждается тем же
знаком), но на одном прогоне это не разделяет накопленную и общую очередь — вопрос
остаётся открытым в той же формулировке, что выше.

**Ответ платформы 2026-09-10 (команда qadam-flow, разбор по коду engine/worker/api).**
Атрибуция закрыта по существу: пауза между `callFlow`-хопами — **не** настраиваемый
интервал очереди, а фиксированная архитектурная стоимость. Один синхронный
`callFlow`-хоп = до 3 полных циклов «BullMQ-джоба → воркер → engine» строго
последовательно (`EXECUTE_WEBHOOK` → создание run ребёнка → `EXECUTE_FLOW` →
resume родителя) + полный снапшот состояния родителя на паузе и download+replay
на resume. Inline-исполнения ребёнка в процессе родителя в движке нет; concurrency
лечит только очередь ожидания параллельных прогонов, а не последовательную цепь
зависимых джоб (отсюда эффект T-0161 на `registration`/`tg-router` и его отсутствие
на `checkin-api`). `EXECUTE_WEBHOOK` — отдельный проход воркера до создания run
ребёнка, в нашей методике он тоже прятался в «паузу».

**Статус (было):** частично закрыт ответом платформы (гипотеза подтверждена: рычаг — только
сокращение хопов), оставался **открытым как ожидание upstream**: запрошен настоящий
синхронный subflow (исполнение дочернего flow в engine-процессе родителя без
очереди/снапшота) — [aiqadam/qadam-flow#363](https://github.com/aiqadam/qadam-flow/issues/363),
milestone v2.0.0.

платформы: inline исполняет ребёнка в engine-процессе родителя, без
BullMQ-джобы/снапшота/waitpoint-резюма — именно тот механизм, которого не
хватало). W17 перевёл все синхронные (`waitForResponse: true`) `callFlow`
горячего пути на `inline` и перемерил тем же методом:

| Прогон | Флоу | Шаги (сумма) | Прогон (факт) | Остаток («пауза») | Было (эталон) |
|---|---|---|---|---|---|

## Q23. Умеет ли платформа исполнять независимые ветки/шаги параллельно

**Открыт 2026-09-09.** Нужен для [ADR-0009](adr/0009-hot-path-latency-budget-and-order.md)
(кандидат «независимые чтения/подписи считать конкурентно»).

Вопрос: если после некоторого шага есть два независимых подграфа (например, две
ветки ROUTER или два последовательных чтения таблиц, чьи результаты не зависят
друг от друга), исполняет ли платформа их конкурентно или строго последовательно?
У ROUTER ветки взаимоисключающие (выполняется одна), так что вопрос про шаги,
которые в ActivePieces-моделях обычно можно развести в параллельные ветки
(split) — умеет ли Qadam Flow такое и как это настраивается через MCP.

**Гипотеза:** не умеет (всё строго последовательно). Проверяется прогоном-пробником:
шаг A и шаг B с известной задержкой после общего предка, сравнение суммы длительностей
со временем прогона. Если параллельности нет — кандидат закрывается, остаётся только
сокращение числа слоёв.

### Закрыт 2026-09-11: не умеет, подтверждено разбором по коду

Прогон-пробник не понадобился — ответ есть в апстриме, с точностью до файлов
([qadam-flow#374](https://github.com/aiqadam/qadam-flow/issues/374)):

- `flow-executor.ts` — цикл `while (!isNil(currentAction)) { …; currentAction = currentAction.nextAction }`,
  ни одного `Promise.all` в исполнителе;
- `LOOP_ON_ITEMS` (`loop-executor.ts`) — обычный `for` с `await` на каждой итерации;
- `ROUTER` (`router-executor.ts`) — перебор веток и исполнение первой подошедшей,
  то есть условный селектор, а не конкурентный fan-out;
- `callFlow` в queue-режиме с `waitForResponse: true` останавливает **весь**
  родительский прогон на waitpoint — двух `callFlow` в полёте одновременно
  у одного прогона быть не может.

**Гипотеза подтверждена: параллельности нет вообще.** Кандидат ADR-0009 п.3
«независимые чтения/подписи считать конкурентно» закрывается как неисполнимый
на текущей платформе. Fan-out/fan-in запрошен апстриму (#374, milestone v2.0.0),
и после закрытия #363 это **единственный оставшийся рычаг латентности**: пауза
между хопами убита, всё оставшееся время горячего пути — тела шагов
(`checkin-api`: 9,95 с из 10,0 с).

**Статус:** ✅ закрыт 2026-09-11. Ждём #374; до него порядок шагов на горячем
пути оптимизируется только их количеством.

## Q25. Два дефекта платформы, отказывающие **в открытую**

**Открыт 2026-09-11**, по итогам аудита платформы с нашей стороны. Оба заведены
апстриму, оба относятся к классу «платформа молча делает не то вместо ошибки»,
и оба отказывают в сторону **предоставления доступа**, а не отказа в нём.
Поэтому они вынесены отдельным вопросом, а не растворены в списке пожеланий.

### 1. Снятый фильтр прав — [qadam-flow#382](https://github.com/aiqadam/qadam-flow/issues/382) (P0)

`tables-find-records` **молча игнорирует `filters`, форму которого не распознал,
и возвращает все строки таблицы.** Не ошибка, не пустой результат — полная
выборка, которая выглядит как «фильтр совпал со всем».

Что это значит у нас. `checkin-api` решает права так:

```
step_5: tables-find-records event_staff
        filters: (event_id, telegram_id контролёра, revoked_at not_exists)
step_6: CODE   isStaff = records.length > 0
```

Постфильтра в коде нет, и в
[catalog/flows/checkin-api.md](../catalog/flows/checkin-api.md) его отсутствие
записано как **гарантия**: «„пользователь вообще где-то staff“ тут физически
невозможно получить, потому что `event_id` — обязательный член фильтра, а не
постфильтр в коде». С учётом #382 это утверждение **неверно**: если форма
фильтра перестанет распознаваться, вернётся вся `event_staff`, `records.length > 0`
станет истиной, и **любой пользователь с валидным `initData` окажется
контролёром любого ивента** — ровно инвариант №1 из AGENTS.md, «участник
отметит соседа».

Достаточно ли этого, чтобы считать дыру открытой сегодня? Нет: сейчас форма
фильтра верна и права проверяются правильно (доказано различающими прогонами
W8). Но единственное, что отделяет нас от обхода прав, — неизменность
недокументированной формы DYNAMIC-пропа, которую платформа не проверяет.
Это не тот фундамент, на котором должна стоять авторизация.

> **Проверка W19, 2026-09-12.** Апстримный фикс #382 подтверждён **по
> документации действия на живом инстансе**, а не только по коммиту: описание
> пропа `filters` у `tables-find-records` теперь прямо заявляет обратное
> прежнему поведению — «A filters value that cannot be read raises an error —
> it is never ignored, because ignoring it would return every row in the table».
>
> Это **не закрывает** пункт 1 и **не отменяет** [W18](BACKLOG.md#w18-страховка-от-fail-open-дефектов-платформы-382-392):
> постфильтр в `checkin-api/step_6` остаётся как defense-in-depth, и
> `catalog/flows/checkin-api.md` по-прежнему должен перестать утверждать
> несуществующую гарантию. На 2026-09-12 W18 **не начат**, журнала
> `docs/work/W18-*.md` нет — то есть противоречащих утверждений в нём не
> содержится просто потому, что его не существует. Когда W18 будет сделан,
> сверку надо повторить по его журналу.
>
> **Сверка выполнена 2026-09-13, после закрытия W18.** Журнал
> [W18](work/W18-fail-open-mitigation.md) обратного не утверждает: постфильтр
> в `checkin-api/step_6` поставлен и отдельно записан как defense-in-depth,
> который апстрим-фикс #382 **не отменяет**; `catalog/flows/checkin-api.md`
> несуществующую гарантию больше не заявляет. Действие закрыто, повторять
> не нужно.
>
> Отдельно, чтобы не возникло ложной тревоги: блокер
> [#411](https://github.com/aiqadam/qadam-flow/issues/411) (существующие шаги
> `tables`/`store` не редактируются) **W18 не задевает**. Постфильтр живёт в
> `checkin-api/step_6`, а это **CODE**-шаг — такие правятся штатно; аудит
> `{{VAR}}` вообще на чтение. Затронуты только правки самих шагов `tables`,
> то есть проекция колонок из [Q17](#q17) и миграция из [Q27](#q27).

### 2. Пустой ключ подписи — [qadam-flow#392](https://github.com/aiqadam/qadam-flow/issues/392) (P1)

`{{VAR}}` вместо `{{variables['VAR']}}` резолвится в **пустую строку**, а не
падает (это уже записано в
[ARCHITECTURE](ARCHITECTURE.md#переменные-проекта-в-шаблонах--проверено-на-инстансе-2026-09-08),
но как ошибка автора, а не как дефект безопасности).

Цена конкретно для нас: если так написан `QR_SIGNING_KEY` или `BOT_TOKEN`,
HMAC считается **с пустым ключом**. Подпись и проверка деградируют
**согласованно** — QR, подписанный пустым ключом, пустым ключом же и
проверяется. Поэтому все позитивные тесты проходят, прогон зелёный, ответ
`200`, в логе штатное исполнение. При этом секрета больше нет: формат payload
у нас задокументирован, и подделать QR или `initData` может кто угодно.

Негативного теста, который это ловит, не существует в принципе — обе стороны
ломаются вместе и остаются взаимно согласованными. Ловится только чтением
конфигурации шага, то есть глазами.

### Что делаем

Не ждём апстрим: оба дефекта митигируются на нашей стороне дёшево, и обе
митигации полезны сами по себе — [W18](BACKLOG.md#w18-страховка-от-fail-open-дефектов-платформы-382-392).
Постфильтр по `event_id` в `step_6` и аудит `{{VAR}}` + пункт в чек-лист
ревьюера. Апстрим-исправления снимут необходимость первой, но не второй:
привычка ссылаться на переменные полной формой нужна независимо.

**Статус: закрыт 2026-09-13 выполнением W18** — как и было сказано, не ответом
платформы, а своей митигацией. Блокер приёмки (W15) снят.

- **Пункт 1 (снятый фильтр прав).** `checkin-api/step_6` больше не решает по
  `records.length > 0`: он ищет среди выдачи строку с `event_id` запроса,
  `telegram_id` контролёра и пустым `revoked_at`, а без валидных ключей
  отказывает (fail-closed). Доказано **дифференцирующим** прогоном, а не
  зелёными позитивными: шагу намеренно скормили всю таблицу `event_staff` —
  сценарий #382 — и не-контролёр получил `403` (`OifLDzW11SoSVAXP283Wf`,
  `rowsRead: 5`, `rowsMatched: 0`), контролёр чужого ивента и отозванный
  контролёр тоже `403`, а настоящий контролёр `demo` — `200`. На старом коде
  все четыре получили бы права. **Второй круг ревью** нашёл, что fail-closed
  отсекал пустой ключ, но не сентинел `-`: `step_3` отдаёт
  `String(data.telegramId || '-')`, поэтому проверенный Telegram'ом `initData`
  **без** `user.id` давал `initDataValid: true` и `staffTelegramId = '-'`.
  Строка `event_staff` с `telegram_id = '-'` при этом совпадала бы — и,
  в отличие от #382, **фильтр чтения её тоже отдавал**, то есть обход не
  требовал никакого дефекта платформы. Закрыто проверкой ключей **на форму**
  (`^[A-Za-z0-9_]{1,12}$` / `^[0-9]{1,16}$`), доказано прогоном
  `INqiGWE9ryivvoZEkfPdZ`: `step_5` вернул строку с `-`, `step_6` дал
  `keysOk: false` → `403`. Подробности и остальные прогоны —
  [catalog/flows/checkin-api.md](../catalog/flows/checkin-api.md).
- **Пункт 2 (пустой ключ подписи).** Аудит пяти флоу **проекта**: **ни одного**
  вхождения короткой формы `{{VAR}}` (шестой флоу в `events-dev` к проекту не
  относится — [Q34](#q34); проверен отдельно, ссылок на переменные нет). Инцидент не объявлялся, `QR_SIGNING_KEY`
  не ротировался. Попутно снято предположение BACKLOG, что для PIECE-шагов
  понадобится read-only REST: `ap_validate_flow` ловит короткую форму и в
  CODE-, и в PIECE-шагах — проверено пробным флоу, а не выведено из документации
  ([catalog/variables.md](../catalog/variables.md)).
  Ревью усомнилось, видна ли короткая форма, если в **том же** значении стоит и
  длинная. Проверено вторым пробным флоу: видна — обе ссылки печатаются
  отдельными строками. Ревьюеру всё равно назван штатным инструментом экспорт:
  он отдаёт опубликованную версию и полные имена, то есть строго сильнее.
  #392 у апстрима **остаётся открытым**, и именно поэтому пункт про `{{VAR}}`
  добавлен в блок AppSec [чек-листа ревьюера](work/REVIEW-CHECKLIST.md):
  одноразовый аудит защищает только сегодняшнее состояние.

**Что осталось верным после закрытия.** Обе митигации не отменяются
апстрим-исправлениями: постфильтр — это defense-in-depth, а привычка писать
переменные полной формой нужна независимо от того, починят ли #392.

> **Апдейт 2026-09-12** ([Q26](#q26)): #382 закрыт апстримом коммитом
> `6b4d5a0839` (PR [#404](https://github.com/aiqadam/qadam-flow/pull/404)) —
> `tables-find-records` теперь отклоняет нераспознанный `filters` вместо
> полной выдачи. #392 **остаётся открытым** — вторая митигация W18 (аудит
> `{{VAR}}`) не снимается. Само по себе закрытие issue не отменяет
> постфильтр в `checkin-api`: нужно сперва подтвердить, что **инстанс**
> обновлён до этого коммита или новее (см. [Q26](#q26)).

## Q27. Пересматривать ли ADR-0003 после появления атомарных примитивов

**Открыт 2026-09-12** пакетом [W19](BACKLOG.md#w19-ревизия-после-обновления-образа-qadam-flow).
Владелец проекта в тот же день **заказал** пересмотр отдельным пакетом
([W20](BACKLOG.md#w20-пересмотр-adr-0003-идемпотентность-на-атомарных-примитивах)),
поэтому вопрос заводится не как «стоит ли обсуждать», а как «чем именно
кончится пересмотр».

### Почему вопрос вообще возник

[ADR-0003](adr/0003-idempotency-without-atomicity.md) написан из посылки
«атомарных примитивов у платформы нет вообще», и вся идемпотентность проекта
(IDM-1…IDM-4) построена на find-then-write с детерминированным разрешением
дублей. С [qadam-flow#410](https://github.com/aiqadam/qadam-flow/pull/410)
посылка перестала быть верной. Проверено на инстансе 2026-09-12:

| Примитив | Что даёт | На какой инвариант ложится |
|----------|----------|----------------------------|
| `tables-update-record` → проп `only_if` | условный апдейт, при непопадании — `RECORD_PRECONDITION_FAILED`, а **не** тихий no-op. Описание прямо говорит: «Use "Does not exist" to mean "only if this column is still empty" — that is how you write "record it only the first time"» | **IDM-2**: `checked_in_at` пишется только при первом чекине, повтор показывает исходное время |
| `store : put_if_absent` + `ttl_seconds` | «report whether this run is the one that took it», плюс истечение ключа | **IDM-4**: дедуп `update_id`; TTL заодно снимает нужду в `dedup-sweep` (W12b) |
| `tables-upsert-records` | матчинг по ключу вместо find-then-write | апсерт `users` в `tg-router` (`step_7`→`step_9`→`step_10`/`step_11`) |

### Что важно не потерять при пересмотре

- **`upsert` — не уникальный индекс.** Описание действия честно оговаривает:
  «The key is matched here, **not enforced by the table** — another write path
  can still insert one». То есть гонка двух одновременных апсертов по-прежнему
  способна создать дубль, и детерминированный выбор канонической строки
  (`tg-router/step_8`) убирать нельзя. Из трёх примитивов этот — самый слабый.
- **`only_if` и `put_if_absent` — качественно другое дело**: это настоящие
  CAS/put-if-absent, они дают то, чего у нас не было, и на них IDM-2 и IDM-4
  перестают зависеть от «повтор безвреден по построению».
- **Exactly-once по-прежнему обещать нельзя** — между шагами флоу транзакции
  нет, и ADR-0003 в этой части не отменяется, а сужается.

### Цена

Миграция существующих таблиц, перепись четырёх мест (`fn-register`,
`checkin-api`, `reminders`, `dedup-sweep`) и **повторная проверка трёх
сценариев идемпотентности** из CLAUDE.md. Плюс — на 2026-09-12 существующие
шаги `tables`/`store` вообще нельзя править через MCP
([#411](https://github.com/aiqadam/qadam-flow/issues/411)), так что до
починки апстримом пересмотр технически неисполним.

**Статус:** **ОТВЕЧЕН 2026-09-12.** Решение принято — [ADR-0011](adr/0011-idempotency-on-atomic-primitives.md),
реализовано в W20: IDM-4 на `put_if_absent` + TTL, IDM-2 на `only_if` (CAS).
ADR-0003 сужен, но не отменён: атомарность появилась у двух операций, а не
у платформы вообще; exactly-once по-прежнему не обещается. W19 вопрос только
ставит; тихо переписывать идемпотентность внутри ревизии было нельзя.

## Q28. Что осталось в горячем пути после того, как `inline` исчерпан

**Открыт 2026-09-12**, по замерам живого сквозного прогона в
[W20](work/W20-idempotency-on-atomic-primitives.md). Это **продолжение**
[ADR-0009](adr/0009-hot-path-latency-budget-and-order.md) и [Q22](#q22),
а не новая тема: ADR-0009 уже назвал «сократить число последовательных
`callFlow`» кандидатом №1 и уже указал на `fn-parse-start` поимённо.
Новое здесь — **число**, которого тогда не было.

### Замер 2026-09-12 (живой путь, чистая база)

Тот же метод, что в эталоне ADR-0009: длительность прогона против суммы
длительностей шагов.

| Флоу | Эталон 2026-09-09 | После W17 | **2026-09-12 (W20)** |
|---|---|---|---|
| `registration` `/start` | 34,2 с (пауза ≈26,4) | 17,1 с (пауза ≈0,2) | **17,9 с** (шаги 17,89, пауза ≈0) |
| `checkin-api`, скан | 23,3 с (пауза ≈17,9 после W16) | 10,0 с (пауза ≈0,05) | **10,2 с** (шаги 10,15, пауза ≈0,05) |
| `my-qr-api`, открытие тикета | не мерился | не мерился | **5,3 с** (шаги 5,31, пауза ≈0) |
| `tg-router`, апдейт | 7,8 / 7,0 с | — | **2,1–3,8 с** |

Прогоны: `Nt8LUIMayzZfRKF4NtqtI`, `UeuIK7RgT7LaJNSqp84y3`,
`aMRe0pueWhTN1III9dApF`. Бюджеты п.1 ADR-0009 выдержаны все три, включая
`my-qr-api` ≤ 10 с, который до сих пор не проверялся ни разу.
`tg-router` ускорился вдвое-втрое — это эффект W20 (дедуп свёрнут с трёх
шагов до двух), а не `inline`.

### Что здесь нового

ADR-0009 объяснял остаток **межшаговой диспетчеризацией** и считал, что
цена вызова — это цена отдельного флоу-прогона. Рычаг `inline` эту цену
должен был снять полностью. Замер показывает, что **не снял**:

| Тип шага | Стоимость |
|---|---|
| CODE-шаг | ~0,06 с |
| `tables-find-records` | 0,3–0,4 с |
| **`callFlow` в режиме `inline`** | **1,2–1,9 с** |

Решающее наблюдение: `fn-parse-start` — чистая функция без ввода-вывода,
внутренняя работа ~0,1 с, а вызов стоит **1,15 с** (`checkin-api/step_8`).
Диспетчеризации больше нет, отдельного прогона нет — значит ~1 с это
накладной расход **самого вызова inline**, факт, которого в ADR-0009 быть
не могло.

Доля вызовов subflow в прогоне: `my-qr-api` — 89 %, `checkin-api` — 76 %,
`registration` `/start` — 76 %. Худший одиночный шаг системы —
`registration/step_19` → `fn-event-card`: **8,06 с**, 45 % прогона (W17
мерил сам `fn-event-card` изолированно — 6,7 с).

### Что с этим делать

ADR-0009 в обновлении W17 **снял** запасной план «дублировать `fn-*`-логику
вместо `callFlow`» — на том основании, что upstream-рычаг закрыл вопрос
дешевле. Эти замеры — основание **пересмотреть снятие**, но не повод
молча вернуть план: он размывает subflow-функции из
[ADR-0001](adr/0001-qadam-flow-as-carrier-stack.md) и каталог ADR-0004.

Варианты, ни один не выбран:

1. **Инлайнить чистые функции в CODE-шаг вызывающего** — `fn-parse-start`,
   `fn-fmt-time`. Ровно кандидат №1 из ADR-0009 п.3. Цена — дублирование
   логики между флоу; требует своего ADR.
2. **Разобрать `fn-event-card`** (8,06 с, 45 % `/start`) — четыре
   собственных вызова; посмотреть, сколько из них нужны. Это ADR-0009 п.3
   «уплостить `fn-event-card`», и он ничего не размывает.
3. **Проверить батчинг `fn-t`** — ADR-0009 п.3, до сих пор не сделано.
4. **Завести апстриму** стоимость `inline`-вызова: 1 с на вызов чистой
   функции в том же процессе выглядит как то, что чинится на их стороне.
   Дешевле всех наших вариантов и никаких ADR не трогает.

### Ответ 2026-09-13 (W22): дело было не в вызовах

Порядок «сначала (4) и (3), потом (2)» оказался неверным, потому что неверна
была сама модель. Q28 считал, что горячий путь состоит из вызовов subflow, и
искал, как их удешевить. К моменту замера W22 вызовов на горячем пути уже не
было (W21 их убрал), а время никуда не делось — оно просто перераспределилось
и стало видно:

| Флоу | CODE | Таблицы/store | Telegram HTTP |
|---|---|---|---|
| `tg-router` (2,28 с своей работы) | 0,31 с | **1,96 с** | — |
| `registration` `/start` (7,7 с) | 0,75 с | **3,42 с** | **2,98 с** |
| `checkin-api` (4,3 с) | **1,25 с** | **2,63 с** | 0,38 с |

Два измерения переставили приоритеты:

1. **Цена чтения `tables` почти не зависит от объёма** (30 строк — 472 мс,
   3 строки — 531 мс). Значит дорого не «много данных», а **сам поход**.
   Рычаг — не сокращать выборки, а не ходить дважды за одним и тем же.
2. **CODE-шаг дёшев поштучно (~72 мс) и дорог в количестве** — 17 штук в
   `checkin-api` дают 1,25 с, 29 % прогона. Пункт «CODE-шаг ~0,06 с, значит
   бесплатно» из формулировки выше — верный факт с неверным выводом.

Пункт (1) вопроса («инлайнить чистые функции») **снимается как неактуальный**:
W21 уже встроил всё, а оставшийся вызов ровно один (`tg-router` →
`registration`) и он архитектурный (ADR-0012), а не дублируемый.

Пункт (4) — вопрос апстриму — остаётся, но с уточнёнными числами: inline-хоп
теперь ~0,5 с (а не 1,0–1,2 с), и к нему добавляется CODE-шаг ~70 мс.

Что сделано и что осталось — [ADR-0009](adr/0009-hot-path-latency-budget-and-order.md#обновление-2026-09-13-w22-дешёвые-пункты-взяты-модель-стоимости-уточнена)
и [W22](work/W22-latency-and-cleanup.md).

**Статус:** закрыт 2026-09-13. Оставшиеся кандидаты перечислены в ADR-0009 и не
требуют отдельного вопроса: они не про непонятое, а про несделанное.

## Q29. `registration/step_38` получает пустой вход — реактивация не работает (IDM-1)

**Открыт 2026-09-12**, найден случайно при оптимизации [Q28](#q28) в
[W20](work/W20-idempotency-on-atomic-primitives.md). Это **дефект, а не вопрос
проектирования**, и он заведён здесь только потому, что чинить его должен
владелец W5, а не W20.

### Что наблюдается

В ветке `pdn_yes` шаг `step_38` («существующая регистрация? для реактивации»,
`callFlow → fn-find-registration`) стабильно возвращает:

```json
{"found":false,"inputOk":false,"eventId":"","telegramId":"","duplicates":0,...}
```

`inputOk: false` — это сам `fn-find-registration` сообщает, что ему **не
передали** `eventId`/`telegramId`. Дальше `step_39` вычисляет
`reactivate: false`, роутер `step_40` уходит в ветку `Otherwise`, и `step_42`
**создаёт новую строку** `registrations` вместо реактивации существующей.

### Почему это не артефакт теста

Сначала выглядело как следствие синтетических данных. Перепроверено на
**настоящем боевом прогоне владельца** `wOV2cCyvBUZ4eN8NQuoIy` (PRODUCTION,
2026-09-12 14:13:41, `SUCCEEDED`, живой тап по кнопке «I agree» с настоящим
`callbackQueryId`): `step_38` там даёт ровно тот же пустой вход. При этом
соседний `step_4` в ветке `start` работает правильно (`inputOk: true`), то есть
дело в конфигурации именно `step_38`, а не в subflow'е.

Подтверждение в данных: два срабатывания `pdn_yes` подряд оставили в таблице
**две** строки `registrations` на одну пару (`demo`, `322876545`) —
`CupLVok0YdzVFECk6noID` и `VEN5YQNHCZf5n3KCY8nkI`, обе `status: registered`.

### Чем это грозит

- **IDM-1** (идемпотентность регистрации) на этом пути не выполняется:
  повторное согласие создаёт дубль, а не находит существующую запись.
- **Реактивация после отмены** (`status: cancelled` → снова `registered`)
  не срабатывает никогда — вместо неё появляется вторая строка.
- Овербукинг считается по `registered`-строкам (`step_6`), поэтому дубли
  **завышают занятость** и могут закрыть регистрацию раньше времени.
- Ниже по течению дубли частично гасятся: `fn-find-registration` отдаёт
  `duplicates`, а `fn-resolve-segment` дедуплицирует по `telegram_id`. То есть
  участник не получит два сообщения, но данные всё равно грязные.

### Чего не хватает для починки

Конкретной причины. `settings.input` PIECE-шагов MCP не отдаёт
([#102](https://github.com/aiqadam/qadam-flow/issues/102)), поэтому увидеть,
на что именно ссылается `step_38`, сейчас нельзя — только пересобрать шаг
заново по контракту. Правка относится к области W5, а не к ревизии или
оптимизации, поэтому вынесена в отдельный вопрос.

**Статус:** ⚠️ предмет вопроса исчез, поведение требует подтверждения.
Флоу `registration` на инстансе больше нет — проверено `ap_list_flows`
2026-09-13; после очистки и пересборки по [ADR-0015](adr/0015-one-touch-one-flow.md)
цепочка регистрации разложена на `reg-start` / `reg-consent-pdn` /
`reg-consent-mkt` / `reg-phone`, а реактивацию отменённой регистрации делает
один шаг `tables-upsert-records registrations` в `reg-consent-pdn` (ключ
`event_id + telegram_id`) — конструкции «`step_38` с пустым входом» там нет
в принципе.

**Почему не закрыт полностью:** исчез флоу, а не доказательство. Что
`reg:pdn:yes` на **ранее отменённую** регистрацию действительно её
реактивирует, а не создаёт дубль, должно быть подтверждено различающим
прогоном (отменить регистрацию → зарегистрироваться снова → в
`registrations` одна строка с тем же `record id`, `status = registered`).
До этого прогона вопрос остаётся как напоминание, а не как известный дефект.

**Дополнение 2026-09-14:** `reg-phone` удалён (телефон из регистрации убран),
цепочка теперь заканчивается на `reg-consent-mkt` — терминальном касании.
На предмет вопроса это не влияет: реактивацию по-прежнему делает upsert
в `reg-consent-pdn`, различающий прогон всё ещё нужен.

**Прежний статус (до пересборки):** открыт, нужен пакет-исправление; до него дубли в `registrations`
на dev будут появляться при каждом повторном прохождении визарда.

## Q30

**Очистить DATE-поле через `tables-update-record` больше нечем.**

Заведено 2026-09-12 (W21), найдено прогоном `nk7ET4kibX4N2YWUqJqtX`.

Шаг реактивации регистрации в `registration` писал в `cancelled_at` значение,
которое qadam `tables` теперь отвергает:

```
Invalid date for field "cancelled_at"
```

Пустая строка больше не проходит валидацию DATE, а «оставить значение пустым»
у пропа `values` означает **не менять поле**, а не очистить его. Обходного пути
внутри qadam'а нет: `ap_update_record` (MCP) пустую строку принимает и поле
очищает — то есть умеет это БД, но не qadam.

**Что сделано сейчас:** `cancelled_at` убран из записи. У реактивированной
строки он остаётся от прошлой отмены, и это **противоречие в данных**:
`status = registered` при непустом `cancelled_at`. Потребители обязаны
смотреть на `status`.

**Чего не хватает:** либо у qadam'а должен появиться способ очистить DATE
(отдельное значение-сентинел или флаг), либо `''` должен снова означать
«очистить». Заводить тикет в апстрим.

**Связано:** [Q29](#q29) — этот дефект был им замаскирован: пока `step_38`
получал пустой вход, ветка реактивации не исполнялась ни разу.

**Где ещё это должно быть записано (по ревью W21):** требование «потребители
смотрят на `status`, а не на `cancelled_at`» продублировано в
[DATA-MODEL.md](DATA-MODEL.md) и [catalog/tables/registrations.md](../catalog/tables/registrations.md) —
иначе его не увидит тот, кто будет делать список участников owner'а и экспорт OWN-8.

## Q31. Широкое чтение `registrations` на `/start`: где порог

**Открыт 2026-09-13**, по замечанию ревью [W22](work/W22-latency-and-cleanup.md).

W22 слил два чтения `registrations` в одно широкое (`registration/step_22`,
фильтр только `event_id eq`, без `limit` и без `columns`) — это дало −0,41 с
и попутно закрыло старую ловушку «выборка молча обрезалась на `limit 500`».
Но размен назван не полностью.

**Уточнение 2026-09-13 (после того, как [#417](https://github.com/aiqadam/qadam-flow/issues/417)
починили): скорость больше не мотив вообще.** Чтение `tables` теперь стоит
25–70 мс целиком, и объём выборки на это почти не влияет. `columns` нужен
**только как защита логов от ПД** — и в этом качестве нужен ровно так же, как
был. Ниже речь только об этом; ускорения от проекции ждать не надо.

**Что не так.** Всё прочитанное пишется в лог прогона дословно
([ADR-0005](adr/0005-secrets-visible-in-run-logs.md), [Q17](#q17)). Значит:

- на каждый `/start` в лог уезжают `telegram_id` **всех** участников ивента;
- `/start` — публичный deep link, дёрнуть его может кто угодно, сколько угодно
  раз. То есть объём логов растёт от действий постороннего, а не только своих;
- при достаточно большом ивенте прогон упрётся в `LOG_SIZE_EXCEEDED` либо
  вывод шага заменится файлом (факт 13 в
  [catalog/flows/README.md](../catalog/flows/README.md)) — второе не ломает
  исполнение, но ломает читаемость логов.

**Чего не хватает, чтобы закрыть.** Числа: при скольких строках `registrations`
прогон начинает деградировать. И решения — что делать дальше:

1. задать `columns` — снимает объём в разы, ничего не ломает.
   **Самый дешёвый шаг, скорее всего его и надо сделать первым.**
   Для `registration/step_22` достаточно `telegram_id`, `status`, `event_id`,
   `registered_at`, `checked_in_at`. **Этот список привязан именно к `step_22`
   и не переносится на другие чтения** (замечание ревью W22, круг 2): эталон
   `find-registration` собирает из строки ещё `checked_in_by`, `cancelled_at`,
   `source` и `id`. Сегодня их ниже по течению никто не читает, но если тот же
   список применить к узким чтениям (`checkin-api/step_41`, `checkin-api/step_19`,
   `my-qr-api/step_22`), эти поля молча станут пустыми строками — а `checked_in_by`
   и `cancelled_at` участвуют в IDM-2 и в статусе регистрации;
2. вернуть `limit` с явной проверкой «выборка не обрезалась» — возвращает
   старую ловушку, но с сигнализацией;
3. считать занятость отдельным дешёвым способом, если у платформы появится
   агрегат (сейчас его нет).

**Закрыт 2026-09-17 ([W46](../work/W46-pre-acceptance-tails.md)), вариант 1.**
Старый флоу `registration` из формулировки вопроса не существует — пересобран
в W26/W28. Живой эквивалент — `reg-api/step_7` (каталог `#/events`, действие
`register`/`cancel`): читал все поля всех регистраций ивента без `columns`,
доступно любому пользователю с валидным `initData` на произвольный `eventId`.
Сужен до `event_id`+`telegram_id`+`status` — ровно то, что использует
`step_9` (`decide`). `reg-api/step_6` («мои билеты») сужен до
`telegram_id`+`status`+`registered_at`+`checked_in_at`+`event_id` тем же
приёмом, хотя риск там ниже (только свои данные). `reg-start/step_2` уже
был сужен в W28 — не трогали. Числовой порог деградации не определён и не
нужен — уточнение самого вопроса от 2026-09-13 верно: чтение `tables` стоит
25–70 мс почти независимо от объёма, `columns` — защита логов, а не
латентности.

**Связано:** [Q17](#q17) (ПД в логах — принятый риск), ADR-0009 (правило
«читать надмножество один раз» и его цена).

## Q32. При `inline` упавший обработчик теряет тап пользователя молча

**Открыт 2026-09-13**, при закрытии [W17](work/W17-inline-callflow.md)
(замечание 7 его ревью). Заметка об этом была в каталоге; вопросу здесь место,
потому что это пробел надёжности, а не особенность шага.

### Что происходит

Порядок шагов в `tg-router` на любом апдейте:

1. `step_2` — `store put_if_absent` по ключу `upd:<update_id>`: апдейт
   **заклеймён как обработанный** (IDM-4);
2. …дальше классификация и `step_18`/`step_20` — `callFlow` в `registration`.

С переходом на `executionMode: inline` (W17, распространено на роутер в W20)
ребёнок исполняется в процессе родителя, поэтому **падение `registration`
роняет прогон `tg-router`**. Но клеймо уже поставлено на шаге 2. Telegram
повторной доставки не сделает (long-polling подтверждает получение), а даже
если бы сделал — дедуп отбросил бы апдейт как уже виденный.

**Итог: нажатие кнопки пользователем пропадает, и никто об этом не узнаёт.**
Пользователь видит, что бот «не ответил», и обычно жмёт ещё раз — но если он
жал не кнопку, а отправлял контакт, повторить это без подсказки он не догадается.

Побочно: `waitForResponse: false` при `inline` **больше не означает
fire-and-forget** — длительность прогона роутера включает ребёнка (видно
в замерах W21 и W22).

### Чего не хватает, чтобы закрыть

Решения, какой ценой это лечить. Варианты, ни один не выбран:

1. **Ставить клеймо после успеха, а не до.** Ломает IDM-4 в другую сторону:
   два одновременных апдейта с одним `update_id` пройдут оба.
2. **Снимать клеймо при падении** — но снимать его некому: прогон уже упал.
   Нужна ветка `continueOnFailure` вокруг вызова обработчика, которая
   и удалит ключ, и сообщит пользователю «попробуйте ещё раз». Это выглядит
   самым честным вариантом и стоит один PIECE-шаг только на пути отказа.
3. **Ничего не делать, но заметить.** Сейчас о потере не узнаёт никто:
   [Q18](#q18) («как узнаём, что фоновый флоу не сделал работу») — тот же
   вопрос с другой стороны, и закрывать их стоит вместе.

**Закрыт 2026-09-17 ([W46](../work/W46-pre-acceptance-tails.md)), с
переформулировкой.** Постановка вопроса описывала архитектуру, которой уже
нет: с W26 все делегирования `tg-router` идут через `executionMode: queue,
waitForResponse: false` (задокументировано в `catalog/flows/tg-router.md`),
а не `inline` — падение ребёнка не видно родителю вообще, ни синхронно, ни
через `continueOnFailure` на стороне `tg-router`. Снимать клеймо
`upd:<update_id>` не нужно ни в каком виде: Telegram не переотправляет
обновления, а повторное нажатие пользователя — это новый `update_id` с
чистым клеймом.

Владелец решил: страховка живёт **внутри** каждого вызываемого флоу, а не
в `tg-router`, и покрывает три флоу гостевой цепочки регистрации
(`reg-start`, `reg-consent-pdn`, `reg-consent-mkt`) — не `menu`/`bcast-*`.
На каждом `tables`-шаге без обработки ошибки — `continueOnFailure: true`;
где ниже по потоку уже есть CODE-шаг, формирующий ответ пользователю
(`reg-start/step_3`, `reg-consent-pdn/step_7`, `reg-consent-mkt/step_5`),
он читает `{{stepName['error']}}` упавших шагов и отдаёт `common.err.generic`
вместо текста, построенного на неполных данных — **одна** ветка отказа на
несколько шагов, а не по одной на каждый (первая версия страховки дублировала
сообщение с тем, что решает общий потребитель, — исправлено до публикации).
На листовых шагах без общего потребителя (`reg-start/step_11`,
`reg-consent-pdn/step_12`) — своя ветка `continueOnFailure`, либо без
уведомления там, где текст следующего шага не зависит от результата
(`step_12`). Различающие прогоны на все три флоу — в журнале W46.

**Связано:** [Q18](#q18) (наблюдаемость фоновых флоу), IDM-4,
[ADR-0011](adr/0011-idempotency-on-atomic-primitives.md).

## Q33. Прогон продиспетчеризован с задержкой в десятки секунд

**Открыт 2026-09-13**, замечен на сквозном прогоне W24.
**Переписан в тот же день по замечанию ревью:** первая редакция утверждала, что
прогон «содержит только вывод триггера» и «провисел в `RUNNING` двадцать минут».
На момент ревью тот же прогон уже был `SUCCEEDED` с 26 шагами за 1,7 с —
то есть формулировка не переживала перепроверки по своему же id, и следующий
читатель списал бы вопрос как выдумку. Ниже — только то, что проверяемо.

### Что наблюдалось

Прогон `checkin-api` `o33YAvyWrVnPggSQOBErB`, PRODUCTION, **создан
2026-09-12T22:04:36Z**.

- В 22:26 (двадцать минут спустя) он был в статусе `RUNNING` и содержал
  **только вывод триггера** — ни одного шага. Это наблюдение зафиксировано
  выводом `ap_get_run` в сессии W24, но по самому прогону сейчас уже не
  воспроизводится.
- **Что проверяемо по id сегодня:** прогон `SUCCEEDED`, шаги суммарно 1,7 с, а
  `step_41` прочитал строку с `checked_in_at = 2026-09-12T22:05:23Z`. Записал
  это время **другой** прогон. Значит шаги начали исполняться **не раньше чем
  через 47 секунд** после создания прогона, при собственной работе в 1,7 с.

Итого: задержка между приёмом вебхука и началом исполнения — десятки секунд
минимум, а по живому наблюдению — до двадцати минут. Тело шагов ни при чём.

### Почему это важнее, чем кажется

`TRIGGER_TIMEOUT_SECONDS = 60`
([ARCHITECTURE](ARCHITECTURE.md#известные-лимиты-платформы-проверены-по-исходникам))
должен был убить такой прогон. Он этого не сделал: прогон дождался своей
очереди и **успешно отработал** через существенно большее время. То есть лимит
либо не покрывает стадию до начала исполнения, либо не применяется вовсе.

Для контролёра это выглядит так: скан не отвечает, он жмёт ещё раз. Повторный
скан прошёл штатно за 2,0 с (`8Gkv59hzhZiCtUF9W19NI`). На входе с очередью это
стоит времени, а при `already`-семантике второй скан ещё и безопасен — но
полагаться на это нельзя.

### Чего не хватает, чтобы закрыть

**Воспроизведения.** Один случай на два сквозных прогона; во втором заходе
(девять прогонов) не повторился. Не установлено, связано ли это с нагрузкой,
с публикацией флоу незадолго до (см. факт про холодный кэш после публикации)
или это разовый сбой инстанса.

Что стоит сделать: поискать в истории прогоны, у которых разрыв между
`created` и началом первого шага велик, — если такие есть у других флоу,
завести апстриму отдельно от
[#417](https://github.com/aiqadam/qadam-flow/issues/417): это не про
латентность исполнения, а про задержку диспетчеризации и неработающий таймаут.

**Связано:** [Q32](#q32) (молчаливая потеря апдейта при `inline`) — другой
механизм, тот же наблюдаемый эффект: действие пропало, и никто не узнал.
Закрывать вместе с [Q18](#q18) (наблюдаемость).

**Почему спрашиваем.** Вся числовая база [ADR-0012](adr/0012-end-to-end-flows-instead-of-subflow-functions.md)

subflow — снята **12.09.2026**. На следующий день апстрим починил

## Q36

**Куда девать рассылку по списку: она не касание и не разрешённая функция.**

Заведён 2026-09-13 челленджем каталога под
[ADR-0015](adr/0015-one-touch-one-flow.md). Дефект найден **в самом ADR-0015**,
а не в каталоге.

**В чём дыра.** ADR-0015 п. 5 разрешает subflow-функции `fn-*` для
«криптографии и общих чтений». Уведомление регистрантов при публикации или
отмене ивента (`find registrations → собрать telegram_id → LOOP → send → delay`)
не подходит ни под одно:

- это **не касание** — никто в систему не входит, это следствие чужого касания,
  поэтому собственным флоу по п. 1 оно стать не может;
- это **не чтение и не крипта** — оно шлёт сообщения, поэтому в список п. 5
  не попадает;
- значит по букве ADR-0015 оно обязано быть **скопировано в каждый флоу,
  который может его вызвать**.

Ровно этим болел удалённый `event-wizard`: блок уведомления был построен
в нём **трижды подряд** (15 шагов на одну логику, различались только веткой
ROUTER'а, из которой пришли). Пересборка по новому правилу воспроизведёт эту
копипасту, если вопрос не закрыть до неё.

**Варианты, между которыми выбирать:**

1. **Расширить п. 5 ADR-0015 на «отправку по списку»** — отдельным ADR, не
   правкой задним числом. Дёшево, но размывает критерий: следующий кандидат
   на исключение будет ссылаться на этот прецедент.
2. **Увести уведомления в механику рассылок [W14](BACKLOG.md#w14-рассылки)** —
   запись в `broadcasts` + `broadcast_targets`, отправка отдельным флоу
   с курсором. Честнее по архитектуре (25 msg/s, `retry_after`, `blocked_bot`,
   «отписаться» — OWN-10…OWN-13 всё равно обязательны), но делает W11
   зависимым от W14, а W14 сам заблокирован [Q13](#q13).
3. **Считать «событие в системе» отдельным видом входа** и дать ему флоу
   наравне с касанием. Самый общий вариант; требует решить, чем такой вход
   триггерится, — платформенных событий у `tables` нет, значит всё равно
   понадобится явный вызов, то есть п. 1 в другой обёртке.

**Почему нельзя отложить до сборки.** Это решение меняет границы пакетов:
при варианте 2 W11 (визард ивента) не может быть закрыт раньше W14. Узнать
об этом в середине сборки — значит переделывать.

**Закрыт 2026-09-13** решением владельца при слиянии W11 в W26 —
[ADR-0016](adr/0016-shared-flow-for-same-shaped-touches.md). Выбран узкий
вариант, не входящий в перечисленные три буквально: уведомление OWN-5 —
**прямой нетроттленый цикл** по регистрациям **своего** ивента внутри
`event-wizard-publish`, без `broadcasts`/`broadcast_targets` и без OWN-11/12
(троттлинг, ретраи). Это сознательно не расширение ADR-0015 п. 5 (вариант 1
размыл бы критерий) и не полноценная интеграция с W14 (вариант 2 сделал бы
W11 зависимым от заблокированного Q13) — узкая мера для объёма «одно
уведомление своим регистрантам», не для сегментированной рассылки. Когда
W14 построит `broadcasts`/`broadcast-runner`, `event-wizard-publish`
переключается на запись в `broadcasts` — это правка одного шага, не пересмотр.

**Статус:** закрыт. Не блокирует W11 (теперь часть W26).

## Q37

**Какой `parse_mode` реально стоит в действующих шагах отправки сообщений.**

Заведён 2026-09-13 при подготовке
[ADR-0017](adr/0017-screen-not-message.md).

**В чём риск.** Проверено через `ap_get_piece_props` по
`@aiqadam/qadam-telegram-bot`: у `send_text_message` и у `edit_message_text`
проп `format` необязательный и имеет **`defaultValue: "MarkdownV2"`**. Шаг,
собранный без явного `format`, отправляет текст как MarkdownV2.

MarkdownV2 требует экранирования восемнадцати символов —
``_ * [ ] ( ) ~ ` > # + - = | { } . !`` — в **любом** месте текста, включая
данные пользователя. Неэкранированный символ даёт от Telegram `400
Bad Request: can't parse entities`, то есть **сообщение не уходит вовсе**.

Через наши тексты проходят: `{title}` и `{description}` ивента (вводит
организатор), `{name}` участника (из профиля Telegram), `{address}`, `{url}`
регистрационной ссылки, тело рассылки. Точка в конце названия, дефис в дате,
скобка в описании, восклицательный знак — обычные символы, а не экзотика.

**Почему не проверено здесь.** MCP не отдаёт `settings.input` PIECE-шагов
([ADR-0006](adr/0006-rest-read-only-for-review.md)) — что именно стоит
в `format` у построенных шагов, владельцу пакета через MCP не видно.
Проверяется либо ревьюером через `GET /api/v1/flows/<id>/template`, либо
прогоном с заведомо «ядовитым» названием ивента (например `AI Qadam. Meetup
#3 (важно!)`).

**Три возможных исхода:**

1. **`format` везде задан явно как `None`** — риска нет, но тогда и разметки
   в сообщениях нет; ADR-0017 п. 4 остаётся обязательным при переходе
   на форматирование.
2. **`format` не задан (MarkdownV2 по умолчанию), экранирования нет** — баг
   уже в продукте, и он чинится независимо от судьбы ADR-0017: «ядовитое»
   название ивента ломает и карточку, и напоминания, и уведомления об
   изменениях.
3. **`format` не задан, но тексты случайно безопасны** — работает, пока
   организатор не введёт точку в названии. Отличается от (2) только удачей.

### Что уже проверено (2026-09-13)

**MCP этот вопрос закрыть не может — подтверждено, а не предположено.**
`ap_flow_structure` на `reg-phone` (`Cx7U4wKXLwmBCtb4FR5AW`) возвращает по
каждому шагу только `name`, `type`, `displayName`, `parentName`,
`relationship`, `valid`, `configStatus`. Ни `settings`, ни `input` — то есть
значение пропа `format` у шагов `send confirmation + QR button` (`step_4`)
и подобных владельцу пакета через MCP не видно вообще.

Остаются два пути, оба вне MCP:

1. **UI** — открыть любой шаг отправки и посмотреть поле Format. Десять секунд,
   даёт ответ по одному шагу; чтобы закрыть вопрос, нужен обход всех шагов
   отправки во всех флоу.
2. **REST-экспорт** — `GET /api/v1/flows/<id>/template?projectId=<id>` даёт
   `settings.input` всех шагов разом и закрывает вопрос целиком за один проход.
   **С 2026-09-13 доступен всем** ([ADR-0018](adr/0018-rest-read-for-everyone.md),
   отменяет ADR-0006) — ограничение «только ревьюер», из-за которого этот
   вопрос и завис, снято. Нужен ключ платформы из keychain.

**Живой прогон как третий путь** — отправить сообщение с «ядовитым» текстом
через `ap_run_action` — упирается в то, что нужен реальный `chat_id`, а ответ
`400` от Telegram на несуществующий чат неотличим от `400` на неразобранные
entities. Тест имеет смысл только в настоящий чат и проверяет поведение
**умолчания qadam'а**, а не конфигурацию действующих шагов, — то есть даже
при успехе не заменяет пп. 1–2.

### Ответ (2026-09-13): исход (1), бага нет

Проверено REST-экспортом всех 21 флоу проекта
(`GET /flows/<id>/template`, [ADR-0018](adr/0018-rest-read-for-everyone.md)).

**Во всех 31 шаге `send_text_message` проп `format` задан явно как `"None"`
(Plain Text). Шагов с `MarkdownV2`, `HTML` или пропущенным `format` — ноль.**
Пофайловая сверка сходится: в каждом из 13 флоу, где есть отправка, число
шагов `send_text_message` равно числу `"format":"None"`, иных значений
`format` не встречается вовсе. Шагов `edit_message_text` в проекте пока нет.

Умолчание qadam'а (`MarkdownV2`) в наших флоу **не срабатывает** — его
всюду перекрывает явное значение. «Ядовитое» название ивента
(`AI Qadam. Meetup #3 (важно!)`) отправится как есть и ничего не сломает.

**Что из этого следует для [ADR-0017](adr/0017-screen-not-message.md).**
Пункт 4 ADR («`format` задаётся явно, пользовательские данные экранируются»)
остаётся обязательным, но меняет характер: это не починка существующего
дефекта, а **условие входа в разметку**. Сейчас безопасность держится на
том, что разметки нет вообще; в момент, когда первый шаг получит `HTML`
или `MarkdownV2`, экранирование обязано появиться в том же шаге, а не
«потом» — иначе исход (2) из списка выше возникнет уже по-настоящему.

**Статус:** ✅ закрыт 2026-09-13. Исход (1) из трёх возможных. Бага в продукте
нет; риск перенесён в ADR-0017 п. 4 как условие перехода на разметку.

## Q38

**Резолвит ли `GET /flows/:id/template` значения Variables и connections —
то есть не коммитим ли мы секреты в git.**

Заведён 2026-09-13 вместе с [ADR-0018](adr/0018-rest-read-for-everyone.md).
**Блокирует пункт 3 ADR-0018** (выгрузку `flows/*.json` в репозиторий).
Пункты 1–2 (чтение разрешено, запись запрещена) действуют независимо.

**В чём риск.** Шаблон флоу содержит `settings.input` всех шагов. У нас туда
подставлены `{{variables['BOT_TOKEN']}}` (HMAC `initData`, ADR-0008),
`{{variables['QR_SIGNING_KEY']}}` (подпись QR), `{{variables['MINIAPP_URL']}}`,
`{{variables['BOT_USERNAME']}}` и `auth` по `externalId` connection'а.

Два исхода:

1. **Платформа отдаёт шаблон как написано** — строками `{{variables['...']}}`,
   без подстановки. Тогда экспорт безопасен, п. 3 ADR-0018 разблокирован.
2. **Платформа где-то резолвит значение** — и мы коммитим боевой токен бота
   и ключ подписи QR в историю репозитория. Удаление файла это не откатывает:
   потребуется ротация обоих секретов и чистка истории.

Достаточно **одного** места с исходом (2), чтобы экспорт был запрещён
в текущем виде; частичный ответ («в большинстве шагов ссылкой») не годится.

**Почему это не то же самое, что [ADR-0005](adr/0005-secrets-visible-in-run-logs.md).**
Там признано, что секреты видны в логах прогонов, и это принято как цена
ADR-0001. Логи живут на инстансе и стираются. История git — нет, и она
уезжает на GitHub.

**Как проверять.** `GET /api/v1/flows/<flowId>/template?projectId=<id>` на
флоу, заведомо содержащем секрет в инпутах — `checkin-api`
(`{{variables['BOT_TOKEN']}}` в `step_1`) или `my-qr-api`
(`QR_SIGNING_KEY`). Грепать вывод на фактические значения, а не на имена
переменных. **Вывод команды не сохранять в файл и не печатать целиком**
до того, как исход известен.

### Ответ (2026-09-13): исход (1), экспорт безопасен

Проверено на всех 21 флоу проекта (196 КБ выгрузки):

| Проверка | Результат |
| --- | --- |
| `{{variables['...']}}` в `settings.input` | остаются **строками**: `BOT_TOKEN` ×2, `QR_SIGNING_KEY` ×2, `MINIAPP_URL` ×3, `BOT_USERNAME` ×1 |
| Паттерн токена Telegram (`\d{8,10}:[A-Za-z0-9_-]{35}`) | **0 совпадений** |
| Hex-строки длиной ≥32 (кандидат в `QR_SIGNING_KEY`) | **0 совпадений** |
| `auth` у шагов | **41 раз** ссылкой `{{connections['TZTlXaCEO2hEvimUowbSA']...}}`, значения нет |

Платформа отдаёт шаблон **как написано**, ничего не резолвя. Коммит
`flows/*.json` не унесёт в историю git ни `BOT_TOKEN`, ни `QR_SIGNING_KEY`,
ни данные connection'а.

**Оговорка, которая остаётся.** Проверено **текущее** поведение платформы
на образе, работающем 2026-09-13. Это не гарантия на будущее: смена версии
может изменить сериализацию шаблона. Поэтому проверка «в экспорте нет
фактических значений секретов» должна стоять не разово здесь, а **в чек-листе
перед коммитом экспорта** — как и любая проверка, защищающая от необратимого.

**Статус:** ✅ закрыт 2026-09-13. Исход (1). **Блокировка с п. 3
[ADR-0018](adr/0018-rest-read-for-everyone.md) снята** — выгрузка
`flows/*.json` в репозиторий разрешена.

## Q39

**Нужна ли нормализация экспорта флоу перед коммитом.**

Заведён 2026-09-13 вместе с [ADR-0018](adr/0018-rest-read-for-everyone.md).
Не блокирует ничего; решается на первом же реальном диффе.

**В чём вопрос.** Шаблон флоу содержит идентификаторы, версии qadam'ов и
служебные поля, меняющиеся без смысловых изменений. Если коммитить сырой
вывод, дифф в PR будет большим и наполовину бессмысленным — и ровно в нём
потеряется та единственная строка `format`, ради видимости которой экспорт
и возвращён ([Q37](#q37)).

**Варианты:**

1. **Коммитить сырой вывод.** Честно и без инструментов; цена — шум и риск,
   что дифы перестанут читать.
2. **Нормализовать** (стабильный порядок ключей, отбрасывание изменчивых
   служебных полей, фиксированный отступ). Скрипт выгрузки — инструмент
   репозитория, не часть продукта, ADR-0001 он не нарушает. Цена — сам
   скрипт надо поддерживать, а отброшенное поле однажды окажется важным.
3. **Коммитить срез, а не весь шаблон** — только `settings.input` шагов.
   Минимальный шум, но снимок перестаёт быть снимком, и восстановить по нему
   структуру нельзя.

### Промежуточное (2026-09-13, [W29](BACKLOG.md#w29-экспорт-flowsjson-в-репозиторий)): не закрыт, измерить нечем

Скрипт выгрузки (`tools/export-flows.sh`) собран, но **ни одного реального
диффа ещё не снято**: у агента нет доступа к ключу платформы (шаг 0.7
ROADMAP), и `flows/*.json` пока пусты. Закрывать вопрос рассуждением прямо
запрещено условием самого вопроса, поэтому он остаётся открытым.

Что сделано заранее и вариантом ответа **не является**: экспорт пишется
детерминированно — стабильный порядок ключей (`jq -S`) и фиксированный
отступ в два пробела. Без этого дифф шумит на ровном месте и **измерить**
шум нельзя вовсе; это предусловие замера, а не выбор между вариантами
1–3. Что именно отбрасывать (и отбрасывать ли) — по-прежнему открыто.

**Как закрывать.** Снять экспорт, внести одно осмысленное изменение в один
флоу (например, `format` у `send_text_message`), снять экспорт снова,
посчитать `git diff --numstat`: сколько строк изменилось всего и сколько
из них относятся к делу. Отношение и есть то число, с которым Q39
записывается.

### Первый ответ (2026-09-14) был неверен — замер сделан не в том режиме

Сначала в W29 записали «вариант (1), нормализация не нужна, 1 строка шума
на 1 осмысленную». Число получили правкой одного поля **без публикации
флоу**. В реальном процессе изменение всегда проходит `ap_lock_and_publish`
([ADR-0018](adr/0018-rest-read-for-everyone.md) п. 5 — экспорт обновляется
тем же коммитом, что и правка), а публикация создаёт **новую версию** и
перештамповывает `lastUpdatedDate` у **всех** шагов разом. Ошибку нашло
независимое ревью пакета.

### Ответ (2026-09-14, после пересчёта): вариант (2), нормализация нужна

Замер на реальных парах версий, между которыми **нет ни одной смысловой
правки** — сравнивается опубликованная версия со следующей за ней:

| Флоу | Сырой дифф | После нормализации |
| --- | --- | --- |
| `checkin-api` | **36 строк** | 2 |
| `fn-hmac-init-data` | **24 строки** | 3 |
| `events-list` | **22 строки** | 2 |

**Содержательных изменений в этих диффах — ноль.** Из 36 строк
`checkin-api` двадцать шесть — `lastUpdatedDate`. Шум масштабируется числом
шагов: чем крупнее флоу, тем полнее он тонет. Именно то, чего опасался ADR
(«ровно в них потеряется та единственная строка `format`»).

Остаток после нормализации — `state` (в экспорте всегда `LOCKED`, потому что
снимается только опубликованная версия) и структурное появление
`sampleData`. То есть на практике дифф двух публикаций без правок ≈ **0
строк вместо 22–36**.

**Что выбрасывается** (`tools/export-flows.sh`, переменная `NORMALIZE`) —
только отметки времени и идентификаторы, которые платформа переписывает
сама:

- `lastUpdatedDate` — публикация переписывает у всех шагов разом;
- `lastTestDate`, `sampleDataFileId` — меняются от прогонов теста;
- `created` / `updated` / `id` / `flowId` / `updatedBy` версии — новые при
  каждой публикации.

**`state` сохранён намеренно** и нормализацией не выбрасывается: это
доказательство, что снят `LOCKED`, а не черновик, — файл свидетельствует
о себе сам.

**Цена, названная в варианте (2), принимается:** нормализатор надо
поддерживать, а отброшенное поле однажды окажется важным. Смягчение —
список выбрасываемого короткий, лежит в одном месте и весь состоит из
машинных меток времени; `settings.input`, ради которого всё затевалось,
не трогается вовсе.

Вариант (3), срез, по-прежнему отвергнут: снимок перестаёт быть снимком.

**Побочный замер:** две выгрузки подряд без единой правки дают **побайтово
одинаковый** результат (`diff -rq` пуст) — сериализация сама по себе не
«дышит», весь шум приходил от версионирования.

**Статус:** ✅ закрыт 2026-09-14 в [W29](BACKLOG.md#w29-экспорт-flowsjson-в-репозиторий).
Исход — **вариант (2), нормализация**, узкая и документированная.

## Q40

**Как Mini App подключает брендовый CSS: ссылкой на `brand.aiqadam.org`
или вендорингом копии.**

Заведён 2026-09-13 вместе с [ADR-0019](adr/0019-design-system-from-brand-repo.md).
Не блокирует решение; блокирует первую брендированную страницу.

**Почему это не вопрос вкуса.** `ticket` и `scan` открываются **на площадке
ивента**: гость показывает QR на входе, контролёр сканирует очередь. Связь
там обычно плохая — это худший момент из всех возможных, чтобы тянуть
внешний CSS и три шрифтовых семейства (Geist, Inter, JetBrains Mono).
Отказ загрузки внешнего стиля на входе означает нечитаемый билет у человека,
который уже стоит в дверях.

**Варианты:**

1. **Внешняя ссылка на `brand.aiqadam.org`.** Всегда актуально, ноль
   дисциплины обновления. Цена — сторонний домен в горячем пути показа QR
   и чужой деплой, способный сломать наш вход.
2. **Вендоринг копии в `miniapp/`** с зафиксированной версией и пометкой,
   откуда взято. Наш деплой ни от кого не зависит, вес контролируем,
   можно взять подмножество токенов. Цена — копия устаревает, нужна
   дисциплина обновления и строка в чек-листе.
3. **Гибрид:** вендорится критический минимум (токены + то, что нужно
   `ticket`/`scan`), остальное — ссылкой на страницу `manage`, которая
   открывается организатором в спокойной обстановке, а не в дверях зала.

**Связано:** [ADR-0019](adr/0019-design-system-from-brand-repo.md) п. 2 и 5,
[ADR-0007](adr/0007-qr-rendered-in-miniapp.md) (QR рендерится в Mini App,
то есть страница обязана открыться при плохой связи),
[ADR-0017](adr/0017-screen-not-message.md) п. 3.

### Ответ (2026-09-13, W30): вариант (3), и решает его не CSS, а шрифты

Замерено на бренде, коммит `8ef4a80`.

**Вес самого CSS ничтожен, вес шрифтов — нет:**

| Что | Сырой | gzip |
| --- | --- | --- |
| `tokens.css` целиком | 16 995 Б | 4 002 Б |
| `components.css` целиком | 24 797 Б | 4 961 Б |
| **наше подмножество** `vendor/aiqadam-brand-subset.css` | **10 413 Б** | **3 649 Б** |
| Geist 400/500/600, `cyrillic` + `latin` | 132 564 Б | — (woff2 уже сжат) |
| Inter 400/500/600, `cyrillic` + `latin` | 201 528 Б | — |
| JetBrains Mono 400/500/600, `cyrillic` + `latin` | 120 696 Б | — |
| **шрифты, три семейства** | **454 788 Б (444 КиБ)** | — |

Метод: `wc -c` и `gzip -9 -c < <файл>` (потоком, без имени файла в заголовке —
иначе цифра пляшет от длины имени). Доля шрифтов в общем весе — 97,8 %.

Числа по шрифтам — `content-length` фактических `woff2`, на которые указывает
`fonts.googleapis.com/css2?...` из `index.html` бренда; взяты только подмножества
`cyrillic` и `latin` (страницы русские). Все подмножества сразу — 1 083 000 Б (1 058 КиБ).

**Отсюда решение, и оно распадается надвое:**

1. **CSS вендорится** — `miniapp/vendor/aiqadam-brand-subset.css`, дословные
   блоки бренда с зафиксированным коммитом в шапке. 3,6 КиБ gzip в пути показа
   QR дешевле, чем сторонний домен в нём же: `brand.aiqadam.org` — ещё одно
   TCP+TLS-рукопожатие на связи, где RTT 400 мс, и чужой деплой, способный
   сломать нам вход.
2. **Шрифты не грузятся вовсе** — ни ссылкой, ни копией. 444 КиБ против 10,2 КиБ:
   это **97,8 %** брендового веса, и покупается на них начертание в ту минуту,
   когда человек стоит в дверях. Токены `--font-display` / `--font-sans` /
   `--font-mono` взяты у бренда **как есть**, вместе с их же системными
   фолбэками (`system-ui`, `-apple-system`) — это и есть то, чем страница
   набирается. Своего шрифта не заведено: не загрузить веб-шрифт и завести
   свою типографику — разные вещи.

**Один сторонний домен в горячем пути остаётся, и убрать его нельзя.**
`telegram.org/js/telegram-web-app.js` подключён блокирующим `<script>` на обеих
страницах: без него нет `initData`, то есть нет ни билета, ни чекина. Он не
взвешен здесь потому, что выбора по нему нет — в отличие от бренда и шрифтов,
где выбор был. «Ещё одно рукопожатие» выше сказано про `brand.aiqadam.org`
именно в этом смысле: второе сверх неустранимого, а не первое.

`display=swap` эту цену не отменяет: он защищает отрисовку, а не канал.
Гость на плохой связи платит 444 КиБ трафика ради того, чтобы подпись под QR
была набрана Inter, а не системным гротеском.

**Что это стоит.** Копия устаревает молча — за это платим строкой в чек-листе
ревьюера и инструкцией обновления в шапке файла. И `manage` (когда появится,
[Q43](#q43)) — та самая «спокойная обстановка» из варианта (3): организатор
открывает её не в дверях, там шрифты и полный `components.css` уместны.
Это не наследуется автоматически: страница решает сама и обосновывает замером.

**Что это сужает в ADR-0019.** Пункт 2 решения читается как «страницы
берут семейства Geist / Inter / JetBrains Mono как есть», а пункт 5
делегировал сюда только *способ подключения CSS*. Ответ выше выходит за
эту делегацию: он говорит и про шрифты. Формально это сужение пункта 2 —
**на двух страницах, `ticket` и `scan`**, и по той самой причине, которую
сам ADR назвал ценой («три шрифтовых семейства недёшевы… вес — не
абстрактная оптимизация, а Q40»). ADR задним числом не правится, поэтому
запись живёт здесь; если владелец захочет закрепить это на уровне решения,
а не вопроса, — это новый ADR, а не редактирование старого.

**Статус:** ✅ закрыт 2026-09-13 пакетом
[W30](BACKLOG.md#w30-бренд-mini-app-и-docsvoicemd). Решение принято весом.

**Закреплено на уровне решения 2026-09-14** —
[ADR-0020](adr/0020-no-web-fonts-on-venue-pages.md): расхождение с ADR-0019
п. 2, названное абзацем выше, снято новым ADR, а не осталось пометкой
в вопросе. Для `manage` — п. 3 того же ADR: решает сама, замером.

## Q41

**Нужен ли fallback-чекин по deep link (пакет W9).**

Заведён 2026-09-13 при ревизии плана работ. Блокирует
[W9](BACKLOG.md#w9-checkin-deeplink-fallback--не-будет-сделан) — пакет не берётся, пока
вопрос открыт.

**В чём вопрос.** STF-3 требует второй путь чекина: контролёр открывает
`/start`-payload в чате, если Mini App недоступен. Это означает **второй
экземпляр** проверки прав STF-2 и **вторую копию** проверки подписи QR
в другом канале — ровно тот дрейф копий, ради которого заведён
[catalog/snippets/](../catalog/snippets/) и ради которого
[ADR-0012](adr/0012-end-to-end-flows-instead-of-subflow-functions.md)
принимал риск дублирования осознанно.

Одновременно [ADR-0017](adr/0017-screen-not-message.md) п. 5 назвал сканер
**нормальным интерфейсом роли контролёра** — единственным из трёх, который
и так устроен правильно.

**Что говорит за.** Mini App может не открыться: старый клиент Telegram,
корпоративная сборка, отвалившийся GitHub Pages, плохая связь на площадке.
В этот момент очередь стоит в дверях, и «попробуйте позже» — не ответ.

**Что говорит против.** Критичная проверка прав, размноженная по двум
каналам, расходится молча: копии кода не падают при расхождении, они
начинают по-разному отвечать. Цена ошибки — посторонний отмечает людей.

**Варианты:**

1. **Делать W9** как задумано, с обязательной побайтовой сверкой копий
   с эталонами в ревью.
2. **Не делать**, признав сканер единственным путём, и записать это правкой
   SPEC (STF-3) со ссылкой на это решение — а не молчаливым невыполнением.
3. **Отложить до W15**: проверить на приёмке, насколько реально сканер
   не открывается, и решать по факту, а не по опасению.

**Статус:** ✅ закрыт 2026-09-14 решением владельца — **вариант (2), не делать.**
Записанная склонность (отложить до W15) отклонена: владелец решил не держать
требование открытым до приёмки, а снять его сейчас. Сканер Mini App —
единственный путь чекина. Что сделано этим решением:

- SPEC STF-3 помечен снятым со ссылкой сюда (не удалён — история требований);
- [W9](BACKLOG.md#w9-checkin-deeplink-fallback--не-будет-сделан) закрыт как «не будет сделан»;
- в `docs/FLOWS.md` секция `checkin-deeplink` переписана: payload `c…` в чате
  уходит в `Otherwise` роутера без обработчика, и это теперь состояние
  по замыслу, а не «пока не построено».

Что это стоит: если у контролёра на площадке Mini App не откроется, второго
канала нет — очередь ждёт, пока сканер откроется у другого контролёра. Это
цена названа в вопросе и принята. Наблюдения «сканер не открылся» собираются
на приёмке W15; вернуть требование может только новое решение с ними на руках.

## Q42

**Нужен ли `dedup-sweep` (пакет W12b).**

Заведён 2026-09-13 при ревизии плана работ. Блокирует
[W12b](BACKLOG.md#w12b-dedup-report--диагностика-дублей).

**В чём вопрос.** После сужения 2026-09-12 (ключи `upd:*` закрыты TTL)
в пакете осталась уборка дублей строк в `registrations`, `event_staff`,
`broadcast_targets`. Но [ADR-0011](adr/0011-idempotency-on-atomic-primitives.md)
оставляет появление дублей **данностью**: `tables-upsert-records` — не
уникальный индекс, дубли схлопываются **при чтении** детерминированным
выбором самой ранней строки.

То есть уборка не чинит корректность — она косметическая. А фоновый флоу,
удаляющий записи по расписанию, — это механизм, способный удалить лишнее,
и с ним придётся жить.

**Варианты:**

1. **Закрыть пакет как ненужный** со ссылкой сюда — как закрыт
   [W23](BACKLOG.md#w23-слияние-code-цепочек-и-остатки-латентности--закрыт-как-неактуальный),
   объяснением, а не молча.
2. **Сузить до диагностики:** флоу по расписанию не удаляет ничего,
   а считает дубли и сообщает владельцу. Даёт наблюдаемость без риска
   удаления — смежно с [Q18](#q18).
3. **Делать как есть**, с удалением, приняв риск.

**Статус:** ✅ закрыт 2026-09-14 решением владельца — **вариант (2), сузить
до диагностики.** [W12b](BACKLOG.md#w12b-dedup-report--диагностика-дублей)
переписан: флоу по расписанию **считает** дубли по ключевым парам в
`registrations`, `event_staff`, `broadcast_targets` и сообщает владельцу
проекта числом; **не удаляет ничего**. Решение об уборке (вариант 3) — только
после того, как число известно, и это будет новый вопрос, а не переоткрытие
этого. Смежно с [Q18](#q18): тот же механизм «фоновый флоу отчитывается»
годится и для наблюдаемости.

## Q43

**Переезжает ли визард ивента в Mini App (`manage`), раз он только что
собран в чате.**

Заведён 2026-09-13 при ревизии плана работ.

**В чём вопрос.** [ADR-0017](adr/0017-screen-not-message.md) п. 3 говорит:
длинный структурированный ввод — форма в Mini App, а не анкета в чате;
создание и правка ивента переезжают на страницу `manage`. При этом
[W26](BACKLOG.md#w26-пересборка-events-dev-по-adr-0015) только что собрал
шесть флоу `event-wizard-*` именно как чат-анкету, и они приняты ревью.

Формально противоречия нет: ADR-0017 п. 8 применяется **пилотом**, а
решение о переносе лекала на визард принимается **по результату пилота**.
Фактически в документах это нигде не записано, и следующий агент, увидев
ADR-0017, может начать переписывать визард, которого никто не просил
трогать.

**Что решать после [W28](BACKLOG.md#w28-пилот-adr-0017--гостевой-срез-одной-карточкой):**

1. **Переносить** — заводится пакет на страницу `manage` (четвёртая
   поверхность Mini App уже разрешена ADR-0017 п. 3 как одна из трёх),
   шесть флоу визарда сокращаются до одного webhook-флоу валидации и записи.
   Цена: самая сложная страница проекта оказывается в самой слабо
   проверяемой его части, и это названо в «Цене» ADR-0017.
2. **Не переносить** — визард остаётся в чате, но пересобирается по лекалу
   карточки-экрана (одно редактируемое сообщение вместо одиннадцати вопросов).
   Дешевле, покрывается ревью флоу, но не убирает главную боль: нет «назад»,
   нет обзора всех полей сразу, дата вводится текстом.
3. **Не трогать вовсе** — визард работает, принят, стоит ноль. Допустимый
   исход, который надо назвать вслух, а не получить по умолчанию.

**Пока вопрос открыт — визард не трогает никто.** Это и есть его главная
функция сегодня.

**Статус:** ✅ закрыт 2026-09-14 решением владельца, после закрытия W28 —
**вариант (1), переносить в Mini App `manage`.** Заведён пакет
[W31](BACKLOG.md#w31-страница-manage-визард-ивента-в-mini-app): третья
страница Mini App из трёх, разрешённых [ADR-0017](adr/0017-screen-not-message.md)
п. 3 (новый ADR не нужен — решение уже принято там, здесь выбран момент), плюс
один webhook-флоу валидации и записи вместо шести `event-wizard-*`.

Цена принята с открытыми глазами: самая сложная страница проекта оказывается
в самой слабо проверяемой его части (статический HTML без тестов, проверка —
только ревью и headless-прогон). Что это требует от пакета, записано в его
чек-листе: авторизация owner'а по `initData` + `events.owner_id` на сервере,
а не на странице; ввод дат — как Asia/Tashkent, запись в UTC (OWN-3);
уведомление зарегистрированным при правке полей `notify-on-change` (OWN-5) —
всё то, что визард в чате уже делает и что нельзя потерять при переезде.

**Шесть флоу `event-wizard-*` живут, пока `manage` не принят ревью.**

**Статус 2026-09-14:** `manage` принят (W31, ревью «замечаний нет»), шесть
флоу удалены, `/newevent` и `/editevent` открывают форму.
Удаляются последним шагом W31, с отражением в каталоге и экспорте
(`flows/`), а не по факту появления страницы. До этого правило «визард не
трогает никто» остаётся в силе — теперь потому, что его заменяют, а не
потому, что решают.

## Q44

**Чем выгружать флоу после qadam-flow PR #439: REST-скриптом или
`ap_export_flow`.**

Заведён 2026-09-14 в ходе [W29](BACKLOG.md#w29-экспорт-flowsjson-в-репозиторий).
Не блокирует работающий экспорт; решение владельца, потому что затрагивает
посылку принятого ADR.

**Факт.** 2026-09-13 в qadam-flow влит и накачен **PR #439**
(`feat(api,web,shared): MCP tools for flow/table export-import and variable
rotation`). Он добавляет в MCP семь инструментов, из них по нашей части:

- **`ap_export_flow` / `ap_import_flow`** — флоу как `SharedTemplate`,
  **той же формы, что `GET /v1/flows/:id/template`**;
- `ap_export_table` / `ap_import_table`;
- `ap_list_variables` / `ap_upsert_variable` / `ap_delete_variable`
  (значения переменных никогда не возвращаются).

**Почему это вопрос, а не выбор исполнителя.**
[ADR-0018](adr/0018-rest-read-for-everyone.md) обоснован ровно тем, что
«`ap_flow_structure` не отдаёт `settings.input` PIECE-шагов, и владелец
пакета не может проверить собственную работу». `ap_export_flow` выбивает
эту посылку: то же самое становится доступно **штатным** MCP-путём, без
REST и без ключа платформы у человека (шаг 0.7 ROADMAP перестаёт быть
зависимостью). Менять способ выгрузки молча нельзя — это правка решения.

**Варианты:**

1. **Остаться на REST-скрипте** (`tools/export-flows.sh`). Работает,
   измерен, ключ у владельца уже есть. Цена — шаг 0.7 остаётся
   зависимостью, а REST-путь живёт параллельно штатному.
2. **Перейти на `ap_export_flow`.** Ключ платформы перестаёт быть нужен
   вообще, выгрузка встаёт в тот же MCP-процесс, что и сборка. Цена —
   инструмент новый и в проекте не проверен; форма ответа заявлена
   совпадающей с `/template`, но это надо подтвердить сверкой, а не
   принять на слово.
3. **Держать оба.** MCP — основной путь, REST-скрипт — запасной на случай
   отката PR. Цена — два пути к одному артефакту и обязанность следить,
   чтобы они давали побайтово одно и то же.

**Практическая оговорка.** Список инструментов MCP фиксируется при старте
сессии. В сессии W29 `ap_export_flow` **не резолвится** — сессия старше PR.
Это не значит, что инструмента нет на инстансе; это значит, что для
проверки варианта (2) нужна переподключённая сессия (`/mcp`).

**Связанный факт, уже повлиявший на нас.** В том же PR починен
`removeConnectionsFromInput`: до фикса экспорт оставлял реальные ссылки на
connections трёх форм, включая `{{connections['x']}}`, хотя заявлял, что
вычищает их. Наблюдаемое следствие: [Q38](#q38) видел `auth` **41 раз**
ссылкой, а экспорт от 2026-09-14 не содержит **ни одной** ссылки на
connections и ни одного поля `auth`. Для безопасности это улучшение,
но оно меняет форму выгрузки, и позитивный контроль в
`tools/check-export-secrets.sh` пришлось переписать: наличие
`{{connections[...]}}` больше не признак здоровья, теперь признак —
их **отсутствие**, а появление означает откат фикса.

**Что выяснилось после того, как вопрос был заведён — и это меняет цену
варианта (2).** `ap_export_flow` отдаёт флоу как `SharedTemplate`, то есть
**ту же форму, что `GET /flows/:id/template`**. А этот эндпоинт, как
выяснилось в том же пакете, **молча игнорирует `versionId` и всегда отдаёт
последнюю версию**, а не опубликованную (проверено: ответ побайтово
одинаков при `versionId` published, draft, отсутствующем и заведомо
несуществующем). На 2026-09-14 у 14 из 22 флоу проекта последняя версия не
совпадала с опубликованной.

Отсюда конкретный вопрос к варианту (2), на который нужен ответ **до**
перехода: умеет ли `ap_export_flow` брать **опубликованную** версию — и
доказуемо ли это, а не по названию параметра. Если он наследует поведение
`/template`, то переход на него означает снимок черновика под видом
опубликованного, то есть ровно тот дефект, от которого экспорт должен
защищать. Наш REST-путь этой проблемы не имеет: он ходит в
`GET /flows/:id?versionId=`, сверяет `version.id` и `version.state == LOCKED`
в ответе и пропускает флоу, если не сошлось.

### Ответ (2026-09-14): проверено — `ap_export_flow` отдаёт черновик

Владелец распорядился сначала проверить, потом решать. Проверено в сессии,
где инструмент резолвится, на `fn-parse-start` (`9iKpekYS4tRUOsmYZaXZg`):

| Что | `ap_export_flow` | `flows/_manifest.json` (опубликованная) |
| --- | --- | --- |
| id версии (`flows[0].id`) | `oG1KA0SNUzlEeyBSHHlpf` | `kFNxo90Y8u65ncLzBiVku` |
| `state` | **`DRAFT`** | `LOCKED` |
| параметр версии у инструмента | **нет** (только `flowId`) | — |

То есть он наследует поведение `/template`: отдаёт **последнюю** версию, не
опубликованную, и попросить другую нечем. Снимок с него описывал бы то,
чего пользователь не видит — ровно дефект, от которого экспорт должен
защищать. Побочно подтверждено заявленное в PR #439: `auth` в шагах вычищен,
`connectionIds` на уровне флоу сохранён, значений секретов нет.

**Решение: вариант (1), остаёмся на REST-скрипте.** `ap_export_flow`
годится для быстрого взгляда на `settings.input` черновика через MCP, но
не для `flows/`. Пересматривать — когда у инструмента появится выбор версии,
и это будет доказано различающей проверкой (draft ≠ published на одном
флоу), а не названием параметра. Шаг 0.7 ROADMAP (ключ платформы у
человека) остаётся зависимостью экспорта. Посылка ADR-0018 («MCP не отдаёт
`settings.input`») ослаблена — для черновика теперь отдаёт, — но решение
ADR-0018 стоит на другом: снимок нужен с **опубликованной** версии, и это
по-прежнему умеет только REST.

**Статус:** ✅ закрыт 2026-09-14. Записано в `flows/README.md`,
`CLAUDE.md`, чек-листе ревьюера п. 1a.

**Дополнено 2026-09-14 решением владельца
([ADR-0021](adr/0021-repo-is-source-of-truth-migrations-table.md)):** источник
правды — репозиторий, поэтому снимок через `ap_export_flow` **допустим**, если
снят сразу после `ap_lock_and_publish` и до правок черновика (черновик равен
опубликованной версии); в `_manifest.json` он помечается `source: "mcp"`, а
факт синхронности инстанса записывается в таблицу `migrations`. REST-скрипт
остаётся предпочтительным при наличии ключа — его снимок полнее (`auth`,
пустые строки `exampleData`).

## Q45

**Уровень коррекции QR на билете: H (как сейчас) или Q (как бренд требует
для печатных стендов).**

Заведён 2026-09-14 из «Хвостов» [W30](work/W30-brand-and-voice.md): пакет
нашёл расхождение и не стал менять умолчание `qrcode.js` без владельца.

**В чём вопрос.** Бренд в разделе «Event stands → QR codes» требует уровень Q
и зону покоя четыре модуля. У нас H. Это **размен, а не запас**: H покупает
больше избыточности ценой более мелкого модуля. Замер на границах нашего
payload: Q даёт 25 модулей против 29 у H на самом коротком, модуль 8,96 px,
и зона покоя при `padding: 32px` падает до **3,57 модуля** — ниже того же
брендового правила «четыре всегда». Переход на Q не бесплатен: он требует
увеличить padding плиты и перепроверить декодирование.

**Варианты:**

1. **Оставить H.** Раздел бренда написан про печатные стенды, а не про экран
   телефона; на экране враг — блик и грязное стекло, против них избыточность H
   полезнее крупного модуля. Зона покоя ≥ 4 модуля сегодня выполняется
   (худший случай 4,14).
2. **Перейти на Q, увеличить padding.** Следовать бренду буквально; правка
   `ticket.html` и повторный прогон декодирования `jsQR` на всех границах
   payload.

**Статус:** ✅ закрыт 2026-09-14 решением владельца — **вариант (1), H
остаётся.** Правило бренда про Q применяется к печати; для экрана билета
действующие требования — зона покоя ≥ 4 модуля (соблюдена) и декодируемость
(доказана прогоном в W30). Если бренд когда-нибудь опишет QR на экране
отдельно — пересмотреть по его тексту.

## Q46

**Как форма `manage` получает фото афиши, если Mini App не умеет отдавать
Telegram `file_id`.**

Заведён 2026-09-14 пакетом [W31](BACKLOG.md#w31-страница-manage-визард-ивента-в-mini-app)
как объявленная в нём точка остановки: «гео и фото — либо решены внутри
страницы, либо вынесены владельцу явным вопросом, не урезаны молча».

**В чём вопрос.** OWN-1 включает фото в поля ивента. Визард в чате получал
его фото-сообщением и хранил `photo_file_id` — идентификатор файла на
серверах Telegram, которым потом отправляется афиша (`send_photo`). У Mini App
такого канала нет: `<input type=file>` даёт байты в браузере, а не `file_id`;
чтобы получить `file_id`, файл должен пройти через Bot API от имени бота, то
есть быть загружен куда-то и отправлен `sendPhoto` по URL. Обе половины этого
пути — не платформа: хранилища у проекта нет (ADR-0001), а `http` qadam
с multipart из браузерных байтов — это тот самый «небольшой сервис», которого
ADR-0001 запрещает.

**Гео решено внутри страницы**: координаты вводятся руками или берутся
кнопкой через `Telegram.WebApp.LocationManager` (фолбэк —
`navigator.geolocation`); ссылка на карту строится из `lat`/`lon`, как и
раньше. Вопрос только про фото.

**Что сделано пока:** форма `manage` фото **не трогает**. У ивента с афишей
из визарда `photo_file_id` сохраняется при любой правке (upsert не пишет это
поле); страница показывает подсказку «Афиша остаётся в чате». Новый ивент,
созданный формой, афиши не имеет. Это временное состояние, названное здесь,
а не молчаливое сужение OWN-1.

**Варианты:**

1. **Афиша — ссылкой (URL).** Поле «ссылка на картинку» в форме; в таблице
   хранится URL, `send_photo` Bot API принимает HTTP-URL напрямую. Цена:
   семантика `photo_file_id` меняется (URL, не `file_id`; либо новое поле
   `photo_url`), и нужно место, где картинка лежит — у организатора, не у нас.
2. **Фото — отдельным касанием в чате.** После сохранения формы бот
   предлагает «пришлите афишу» одним сообщением; фото-сообщение обрабатывает
   узкий флоу, пишущий `photo_file_id` по `event_id` владельца. Цена: одно
   касание вне экрана — ровно то, от чего уходит ADR-0017, но только для
   поля, у которого нет экранного аналога.
3. **Убрать фото из OWN-1.** Афиша не показывается в карточке (ADR-0013
   уже убрал отдельное фото-сообщение из `/start` ради латентности; W28
   отправляет афишу «отдельным сообщением один раз»). Если она не нужна и
   там — поле можно снять правкой SPEC.

**Рекомендация пакета — вариант (2):** не меняет модель данных, не требует
хранилища, а касание одно и опциональное.

**Статус:** ✅ закрыт 2026-09-14 — владелец выбрал **вариант (3)**: фото
убрано из OWN-1 (правка SPEC отдельным коммитом со ссылкой сюда). Следствия
для системы — пакет [W32](BACKLOG.md#w32-owner-ы-по-списку-initdata-5-минут-афиша-снята):
`reg-start/step_12` (`send_media`) убирается, подсказка `manage.hint.photo`
снимается со страницы, `photo_file_id` остаётся в таблице как неиспользуемое
поле у прежних ивентов (удалять поле нечем без потери данных — не удаляем).

> **Дополнение 2026-09-15: вывод фото — временный.** Решением владельца афиша
> **возвращается** ([Q50](#q50); с 2026-09-16 — v0.1, пакет
> [W39](BACKLOG.md#w39-возврат-афиши-в-mini-app-форма-и-доставка)), поэтому
> W32 вычищает ровно минимум
> (`reg-start/step_12` + подсказка `manage.hint.photo`), а мёртвый пока код —
> `photoFileId` в `reg-start/step_3`, `hasPhoto` в `manage-api`/SPA, разбор
> фото в `tg-router`, строки в `event-card.md` — **сохраняется намеренно**.
> `photo_file_id` в `events` не «не используется», а «временно не используется». Путь возврата и правка SPEC — [Q50](#q50).

## Q47

**Кто вправе создавать ивенты, и сколько живёт `initData` в логах прогонов.**

Заведён 2026-09-14 из ревью [W31](BACKLOG.md#w31-страница-manage-визард-ивента-в-mini-app)
(замечания 6 и 13 круга 1). Два вопроса в одном, потому что оба — про
границу «любой пользователь бота» / «организатор» и оба не закрываются
пакетом про форму.

**1. Allow-list owner'ов.** Сегодня создать ивент может любой валидный
`initData`: `/newevent` у визарда и `save` с пустым `eventId` у `manage-api`
не проверяют ничего, кроме HMAC. Для dev-бота это удобно, для `events-prod`
значит, что любой человек, нашедший бота, публикует ивент с deep link'ом
регистрации от имени AI Qadam. SPEC п. 0 говорит «роли берутся из конфига» —
где этот конфиг (таблица `owners`? переменная со списком `telegram_id`?
`chapters`?) не решено. Варианты: (а) таблица `owners`/поле в `users`,
проверка в `manage-api` перед `isNew`; (б) переменная проекта со списком;
(в) оставить открытым до W15 и решить там.

**2. `initData` в логах прогонов.** Тело запроса webhook-флоу (`checkin-api`,
`my-qr-api`, `manage-api`) целиком лежит в выводе триггера в логе прогона,
и `fn-hmac-init-data` принимает его 24 ч. Читающий прогоны проекта может в
это окно действовать от имени пользователя во всех трёх флоу — в W31 это и
позволило прогнать различающий тест без живого WebView. Варианты: сократить
потолок свежести (Telegram рекомендует минуты, не сутки); резать `initData`
в логе нечем — платформа пишет тело триггера как есть; принять как цену
«кто читает прогоны — тот админ проекта» и записать в SECURITY.md.

**Статус:** ✅ закрыт 2026-09-14 решением владельца.
1. **Вариант (а): таблица `owners`** (`telegram_id`, `note`), проверка в

## Q48. Safe Area: перекрывает ли системный UI Telegram контент SPA

**Открыт 2026-09-14**, из пересмотра платформенных ограничений Mini App
([MINIAPP-UX.md](MINIAPP-UX.md) п. 5).

Контент Telegram WebView может заходить под системную шапку (три точки,
название приложения), под вырезы экрана («брови») и жестовую зону. Платформа
отдаёт инсеты через `contentSafeAreaInset` / `safeAreaInset` (конец 2024) —
SPA их нигде не читает (grep по `miniapp/src` пуст), страницы живут на
собственных паддингах.

**Чем грозит.** Главные артефакты проекта работают в дверях зала: плита QR
на `ticket` (главный путь гостя) и вердикт чекина на `scan` (главный путь
контролёра). Если на узком экране с вырезом шапка срезает верх страницы,
страдает именно то, ради чего Mini App открыт. Проверки на устройстве с
вырезом не было ни одной — только desktop-прогоны headless.

**Что нужно для закрытия:**

1. визуальная проверка на устройстве с вырезом (шаг человека, не агента):
   `ticket` и `scan` при раскрытом приложении, светлая и тёмная темы;
2. если перекрытие есть — применить инсеты в одном месте layout (App),
   а не по роутам, и записать решение в [MINIAPP-UX.md](MINIAPP-UX.md) п. 5
   как соблюдённое;
3. если перекрытия нет — записать факт и критерий (какие экраны считались),
   чтобы вопрос не переоткрывался.

**2026-09-18 (W48): пункт 2 сделан заранее, не дожидаясь проверки.**
Заявленное перекрытие — не только гипотеза для конкретного устройства, а
код-уровневый факт: `<meta name="viewport">` не имел `viewport-fit=cover`,
без которого браузерные `env(safe-area-inset-*)` **всегда** резолвятся в 0
(спецификация), — то есть уже существовавшие `env()` в `.sticky-actions` и
`.app-sheet-panel` были мёртвым кодом независимо от устройства. Добавлены
`viewport-fit=cover` и переменные `--safe-top`/`--safe-bottom`
(`max(env(...), var(--tg-content-safe-area-inset-*, 0px))` — учитывают и
вырез устройства, и собственную шапку Telegram, Bot API 8.0+, с нулевым
фолбэком на старых клиентах); применены в одном месте — `#root` сверху,
`.sticky-actions`/`.app-sheet-panel` снизу (там же, где раньше был мёртвый
`env()`). На инсеты `0` (нет выреза, старый клиент) поведение не меняется.
**Пункт 1 не сделан** — живая проверка на устройстве с вырезом всё ещё нужна
владельцу: агент не может подтвердить, что после правки перекрытия
действительно нет, только что сама механика теперь работает, а не молчит.

**Статус:** код готов (W48), закрыть до приёмки W15 (боевой ивент — телефоны
в дверях) после живой проверки владельцем. Не BLOCKER для сборки: не меняет
структуру флоу и таблиц, это правка одного layout-места SPA.

## Q49. Окно свежести `initData` по флоу и долгоживущая scan-сессия

**Открыт 2026-09-15** при подготовке [W32](BACKLOG.md#w32-owner-ы-по-списку-initdata-5-минут-афиша-снята):
[Q47](#q47) п. 2 закрыт решением «потолок `initData` — 300 c, для всех трёх
webhook-флоу». Для `manage` и `ticket` это верно (страница делает запрос один
раз при открытии), но **неверно для `scan`**.

**Два факта, оба проверены по коду.**

1. **`Telegram.WebApp.initData` — статичный снимок на момент открытия WebView**
   и внутри сессии не обновляется. `scan` — долгоживущая страница: контролёр
   стоит в дверях дольше пяти минут, а `checkin-api` он дёргает на каждый скан.
   С окном 300 c **все** чекины после пятой минуты уходят в `invalid_init_data`,
   `Scan.tsx` вызывает `stopAll` → сканер встаёт до переоткрытия приложения.
   Это главный путь v0.1 (контролёр). `Ticket.tsx`/`Manage.tsx` читают
   `initData` один раз при монтировании — им короткого окна достаточно.
2. **Потолок в `fn-hmac-init-data/step_3` (`MAX_AGE_CAP`) обрезает вызов
   сверху.** Просто поменять его на 300 значило бы обрезать и `checkin-api`
   до 300 c — окна по флоу одним этим числом не выражаются.

**Решение владельца 2026-09-15** (ответы на вопросы Q1/Q2/Q6 при подготовке W32):

- окна **по флоу**: `manage-api` = 300 c, `my-qr-api` = 300 c,
  `checkin-api` = **43200 c (12 ч)**;
- `MAX_AGE_CAP` = **43200**: 12 ч становится общим максимумом, свойство
  «завысить окно вызовом нельзя» сохраняется, значение выбирает флоу.

**Цена названа и принята.** Окно replay для чекина — 12 ч вместо суток:
читатель логов прогонов может до 12 ч действовать от имени контролёра. Размер
ущерба ограничен: чекин помечает посещение ивента, где этот `telegram_id` и так
staff (STF-2/IDOR), а `manage` (создание данных) остался на 300 c.

**Статус:** ✅ закрыт решением 2026-09-15. Реализация — [W32](BACKLOG.md#w32-owner-ы-по-списку-initdata-5-минут-афиша-снята).

## Q52. Чем рисуется карта в визарде ивента

**Открыт 2026-09-16** вердиктом владельца по прототипу
([W41](work/W41-prototypes-e2e.md#вердикт-владельца), [OWN-1](SPEC.md)):
точка задаётся вставкой ссылки Яндекс.Карт или выбором на карте.

**Что не решено.** Вставка ссылки не требует провайдера: координаты
разбираются из `pt`/`ll`/`@lat,lon`/`q` на клиенте. «Указать на карте» —
требует карты: Yandex Maps (ключ и условия), OSM-тайлы (лицензия и стиль),
либо отказ от карты в пользу ссылки и недавних мест. У проекта нет ни ключа,
ни картографической зависимости, и ADR-0001 требует обосновывать каждый
внешний элемент.

**Решение владельца 2026-09-16:** «Тупо ссылка на Яндекс карту» —
**интерактивной карты в продукте нет**. В визарде остаются: адрес,
«Вставить ссылку Яндекс.Карт» (разбор `pt`/`ll`/`@lat,lon`/`q`), «Взять моё
местоположение», недавние места и ссылка на карту для превью точки.
«Указать на карте» из прототипа снимается. Причина: ни ключа, ни
картографической зависимости, а ADR-0001 требует обосновывать каждый внешний
элемент; для точки в карточке достаточно ссылки.

**Что это меняет:** [SPEC](SPEC.md) OWN-1 поправлен отдельным коммитом
(формулировка «выбором на карте» отменена); «Недавние места» собираются
из собственных ивентов овнера (список `#/manage`), хранилища им не нужно.

**Статус:** ✅ закрыт 2026-09-16 решением владельца. W42 (v0.1) берётся
целиком, карта из объёма исключена.

## Q55. Чем разбирается орг-ссылка Яндекс.Карт («Поделиться» из приложения)

**Открыт 2026-09-16** живым тестом W42 ([журнал](work/W42-event-wizard.md#журнал)):
кнопка «Поделиться» в Яндекс.Картах отдаёт ссылку вида
`https://yandex.com/maps/org/beelab/34279609643?si=…` — координат в ней нет,
и разбор `pt`/`ll`/`@lat,lon`/`q` ([SPEC](SPEC.md) OWN-1) её отвергает.

**Что рассмотрено** (подробнее — в журнале W42):

1. серверный разбор публичной страницы организации: HTML с координатами
   отдаётся без ключа (проверено), но разметка недокументирована, возможны
   капча и блокировка по IP (nakarte в 2024 снял поддержку коротких ссылок
   Яндекс.Карт по этой причине);
2. **Геокодер Яндекс.Карт по `uri=ymapsbm1://org?oid=…`** — координаты
   структурно, официальным API; бесплатный лимит — 1000 запросов/сутки;
3. ручной путь: скопировать координаты в приложении и вставить их
   (визард голые пары уже принимает);
4. геокодинг адреса из share-текста (OSM Nominatim и др.).

**Решение владельца 2026-09-16 — вариант 2.** Координаты орг-ссылки достаёт
Геокодер Яндекс.Карт, `oid` вырезается из ссылки (только цифры); ключ —
проектная Variable `YANDEX_GEOCODER_API_KEY`, заводится в UI и в репозиторий
не попадает ([ADR-0008](adr/0008-bot-token-as-variable-not-connection-template.md)).
Отказ Геокодера деградирует в понятную подсказку «скопируйте координаты» —
вариант 3 остаётся фолбэком.

**Цена, принятая владельцем осознанно.** Условия бесплатного использования
[API Яндекс.Карт](https://yandex.ru/legal/maps_api/ru/) не допускают:
п. 5.1.5 — постоянного хранения результатов Геокодера (разрешено только
кэширование до 30 дней), п. 6.6.1 — использования Геокодера вне
сайтов/приложений с JavaScript API Яндекс.Карт. Продукт хранит `lat`/`lon`
в `events` бессрочно, карты в нём нет ([Q52](#q52)); полностью по условиям
это расширенная коммерческая лицензия (в тарифах ~195–226 тыс ₽/год).
Владелец принял риск свободного тарифа с открытыми глазами: блокировка ключа
по п. 6.7 возможна, это осознанное отступление, а не недосмотр. Если ключ
заблокируют — фолбэк (вариант 3) сохраняется, решение пересматривается.

**Что это меняет:** [SPEC](SPEC.md) OWN-1 — к формам ссылки добавлена
орг-ссылка; `manage-api` получает действие `resolve_geo`. Короткие ссылки
`yandex.ru/maps/-/…` (в них нет `oid`) не поддержаны — отдельный вопрос,
если понадобятся живьём.

**Статус:** ✅ закрыт 2026-09-16 решением владельца. Реализация — W42
(переоткрыт тем же днём).

## Q56. Каталог `#/events` и `status = finished`: буква ADR-0023 против W12

**Заведён 2026-09-16** при сборке W38. [ADR-0023](adr/0023-fourth-miniapp-page-event-catalog.md)
п. 3 говорит «чтение только `status = published`», а п. 1 — «опубликованные
ивенты, будущие и прошедшие раздельно». Прошедшие ивенты с [W12](BACKLOG.md#w12-жизненный-цикл-и-напоминания)
(OWN-4) получают из таблицы статус `finished` (автопереход по `ends_at`) —
при буквальном фильтре такой ивент исчез бы из вкладки «Прошедшие» на
следующем прогоне lifecycle.

**Решение — читать `published` + `finished`** (фильтр `in` в шаге плюс
постфильтр в CODE, defense in depth Q25). `draft` и `cancelled` не видны
ни в одной вкладке; завершённый ивент был опубликован и обязан остаться
в афише. Буква ADR-0023 п. 3 — неточность формулировки, а не другое решение:
ADR не редактируется задним числом, эта запись — его уточнение.

**Статус:** ✅ решён 2026-09-16. Реализация — W38 (`events-api`).

## Q57. Отмена регистрации «из чата» после вывода карточки `myreg`

**Заведён 2026-09-16** при взятии W43: SPEC PAR-5 («отмена — до `starts_at`,
**из чата** и с экрана билета») против BACKLOG W43 («чат-карточка `myreg`
выводится из эксплуатации»). Единственный вход в `my-reg-cancel` — кнопки
карточки `my-regs`, так что вывод карточки убирает и чат-отмену.

**Решение владельца 2026-09-16 (спрошен при взятии): отмена — только
в Mini App** (экран «Мои билеты» и `#/ticket`, новый `reg-api`); `my-regs`
и `my-reg-cancel` удаляются; PAR-5 поправлен со ссылкой на ADR-0017.

**Статус:** ✅ закрыт 2026-09-16. Реализация — W43.

## Q58. Должность + компания — одним сообщением или двумя

**Заведён 2026-09-18** при принятии [ADR-0032](adr/0032-onboarding-first-touch-profile.md):
прототип рисует одну строку («ML-инженер, Payme», разбор запятой, при мусоре —
экран «разбили верно?»), альтернатива — два отдельных вопроса в чате (проще,
но длиннее на тап).

Один или два вопроса — решает **пакет реализации онбординга** (ещё не нарезан);
до решения брать нечего. В тот же пакет входит таб «Профиль» в `#/events`
(правка имени/должности/компании/города, согласие залочено) — размещение
четвёртым табом каталога подтверждает владелец вердиктом по прототипу.

**Статус:** открыт.
