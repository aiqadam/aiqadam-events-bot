# 0017. Единица интерфейса — экран, а не сообщение

**Статус:** принято, 2026-09-13. Решение владельца проекта — принято целиком,
включая расширение исключения Mini App до трёх страниц (п. 3).

**Не отменяет** [ADR-0015](0015-one-touch-one-flow.md) и
[ADR-0016](0016-shared-flow-for-same-shaped-touches.md): «касание = флоу»
остаётся правилом разбиения **внутренней** структуры. Здесь решается, **чем
флоу отвечает пользователю**, а не на сколько флоу режется сценарий.

**Расширяет** исключение [ADR-0001](0001-qadam-flow-as-carrier-stack.md) про
Mini App — с одной статической страницы до трёх. Это главная цена решения.

**Усиливает** [ADR-0013](0013-fewer-messages-on-start.md): «меньше сообщений»
превращается из рекомендации в механику.

## Контекст

### Три роли, один нормальный интерфейс

У продукта три пользователя. У одного из них — **контролёра** — интерфейс
устроен правильно: одноэкранный Mini App-сканер. Открыл, навёл, увидел
результат, навёл на следующего. Ни команд, ни состояния в голове, ни ленты.

Гость и организатор живут в другой парадигме — **чат-анкета с состоянием
в таблице**: `sessions.step`, маршрутизация по шагу, один вопрос = одно
сообщение.

**Гость**, регистрируясь по deep link, получает девять сообщений подряд:
карточка → вопрос ПД → подтверждение → вопрос рассылки → подтверждение →
вопрос телефона → подтверждение с QR. Каждое — отдельная отправка
(0,7–0,9 с, самая дорогая операция в системе по
[ADR-0009](0009-hot-path-latency-budget-and-order.md)). Через неделю гость
листает этот чат в поисках своего QR.

**Организатор** проходит одиннадцать вопросов подряд
(`event-wizard-start` → `event-wizard-field` ×6 → `photo` → `geo` →
`capacity`/`overbook`/`utm`): назад нельзя, вперёд нельзя, ошибка на девятом
поле возвращает к тому же вопросу, правка — тот же визард заново. Пропуск
поля объясняется через собственную реализацию: «пришлите `-`» — сентинел,
появившийся потому, что платформа не пишет пустую строку поверх значения
(CLAUDE.md, «Лимиты платформы»), а не потому, что так удобно человеку.

### Дело не в текстах

Разбор `i18n/ru.json` (240 строк — это и есть весь видимый продукт) даёт
четыре независимых дефекта, и только первые два лечатся копирайтом:

1. **Нет визуальной иерархии.** Ни эмодзи, ни жирного, ни разделителей.
   Карточка ивента — `Когда: {when}` / `Где: {address}` / `Статус: {status}`;
   списки — `{title} — {when} — {status}`, три факта равного веса в строку.
2. **Тон непоследователен.** «Недостаточно прав для этого действия» и
   «В этом срезе никого нет» соседствуют с живыми «Договорились, будем
   присылать анонсы» и «Листа ожидания у нас нет — следите за анонсами».
   Голос найден, но применён примерно к 15 % строк.
3. **Кульминации не отмечены.** `reg.done` — «Вы зарегистрированы на «{title}»»
   без даты, адреса и «что дальше», после воронки из согласия, телефона и QR.
   `checkin.ok` — «{name} — отмечен» в единственной точке физического контакта
   человека с продуктом.
4. **Нет жизненного цикла.** Исходящих касаний после регистрации ровно три:
   `remind.24h`, `remind.2h`, `notify.changed`. После чекина — ничего. Продукт
   заканчивается там, где начинается лояльность.

Пункты 3 и 4 — не про слова: их нечем починить, не меняя структуру касаний.

### Экономика сместилась, а интерфейс — нет

После апстрим-фиксов [#412](https://github.com/aiqadam/qadam-flow/issues/412)
и [#417](https://github.com/aiqadam/qadam-flow/issues/417) CODE-шаг стоит
2–5 мс, ROUTER — 0,03 мс, чтение таблицы — 25–70 мс, а отправка сообщения —
0,7–0,9 с. Из «меньше сообщений» (ADR-0013) есть два выхода: **меньше текста**
или **богаче каждое сообщение**. Проект выбрал первый, хотя рендер насыщенной
карточки со всеми фактами и полным набором кнопок — это тот же один `send`,
что и «Ивент не найден.».

Место под качественный интерфейс уже оплачено латентностью. Оно не занято.

### Что подтверждено на инстансе, а что нет

Проверено 2026-09-13 через `ap_research_pieces` / `ap_get_piece_props` по
`@aiqadam/qadam-telegram-bot`:

| Факт | Значение для решения |
| --- | --- |
| `edit_message_text` **есть**: `chat_id` + `message_id` + `text` + `format` + `reply_markup` | редактирование текстовой карточки на месте возможно штатным действием |
| `edit_message_caption` / `edit_message_media` / `edit_message_reply_markup` — **нет** | карточку с **фото** штатно не отредактировать; варианты — в «Цене» |
| `delete_message` есть | есть чем убирать мусор, если карточку решено пересоздавать |
| У `send_text_message` и `edit_message_text` проп `format` **по умолчанию `MarkdownV2`** | экранирование перестаёт быть пожеланием — см. [Q37](../OPEN-QUESTIONS.md#q37) |

**Не проверено:** отдаёт ли `send_text_message` в `output` `message_id`
присланного сообщения. Telegram Bot API возвращает объект `Message`, так что
ожидание обоснованно, но это ожидание, а не факт — подтверждается прогоном
на пилоте до сборки остального.

## Решение

**Единица интерфейса — экран, а не сообщение.**

1. **Многошаговый диалог ведётся одной карточкой, которая редактируется
   на месте.** `send_text_message` один раз, дальше `edit_message_text`
   с новым `text` и новым `reply_markup`. `message_id` карточки хранится
   в `sessions`.

2. **Что остаётся отдельным сообщением.** Правило: **состояние диалога
   редактируется, факт, к которому вернутся, — отправляется.** Отправляются
   билет, напоминания, уведомление об изменении ивента, рассылка. Всё
   остальное — редактирование карточки.

3. **Длинный структурированный ввод — форма в Mini App, а не анкета в чате.**
   Создание и правка ивента переезжают на страницу `manage`: все поля видны
   сразу, дата — нативный picker (вместе с ним исчезает весь класс
   `wizard.err.datetime`), гео — карта, фото — file picker, «без ограничений» —
   пустое поле вместо сентинела `-`. Отправка — один POST в webhook-флоу,
   который валидирует и пишет. Чат остаётся каналом уведомлений и быстрых
   действий.

4. **`format` задаётся явно в каждом шаге отправки и редактирования, а
   пользовательские данные экранируются в CODE-шаге, который рендерит текст.**
   Ни один шаг не полагается на умолчание qadam'а. Экранирование — часть
   эталона рендера в `catalog/snippets/`, а не решение автора флоу.

5. **У каждой роли есть своя главная точка входа, и это не команда.**
   Гость — карточка ивента. Организатор — экран ивента со счётчиками
   («зарегистрировано / пришло / мест»). Контролёр — сканер. Команды остаются
   как ускоритель для тех, кто их знает, но ни один сценарий не требует их
   помнить.

6. **Голос кодифицируется.** Отдельный документ `docs/VOICE.md`: правила тона
   (короткое человеческое утверждение; успех называется успехом; отказ
   объясняет причину и даёт следующий шаг) плюс образцы четырёх классов —
   карточка, список, успех, отказ. На него ссылается чек-лист ревьюера;
   без него следующий флоу соберут в старом тоне, и это уже происходило.

7. **Жизненный цикл гостя — пять касаний, а не два.** Билет → напоминание
   за сутки → напоминание за два часа → чекин → **послесловие** («спасибо,
   что были» + ближайший следующий ивент). Послесловие — единственная новая
   функция во всём решении; оно же — прямой канал в `consent_marketing`.

8. **Применяется пилотом, а не фронтом.** Первым пересобирается гостевой срез
   целиком — от deep link до билета. Решение о переносе лекала на визард
   и на экран организатора принимается по результату пилота, а не заранее.

## Цена

Названа прямо, потому что решение принимается с ней, а не вопреки ей.

- **Ни одной новой функции, кроме послесловия.** Пересобираются `reg-start`,
  `reg-consent-pdn`, `reg-consent-mkt`, `reg-phone`, пять флоу визарда и
  правила маршрутизации `tg-router` — ради ощущения. Это законная причина,
  но при первом же сорванном сроке прозвучит «зачем мы это трогали»,
  и ответ должен лежать здесь, а не собираться задним числом.

- **Карточка с фото афиши на месте не редактируется.** `edit_message_caption`
  и `edit_message_media` в qadam'е отсутствуют. Три выхода, выбор — за пилотом:
  (а) карточка текстовая, фото отправляется отдельным сообщением один раз;
  (б) `custom_api_call` к Bot API — ADR-0001 это не нарушает (HTTP делает
  qadam), но выводит горячий путь из типизированных действий, теряя валидацию
  пропов; (в) `delete_message` + новая карточка — дешёво в сборке, но именно
  тот мусор в ленте, от которого уходим. Ни один вариант не бесплатен, и
  делать вид, что «просто отредактируем», нельзя.

- **Экранирование становится обязательным и опасным.** MarkdownV2 требует
  экранировать 18 символов; неэкранированный `{title}` с точкой или дефисом
  даёт `400` от Telegram, то есть **молча потерянное касание**, а не видимую
  ошибку. Риск существует уже сейчас, до всякой пересборки — дефолт пропа
  `MarkdownV2`, и что стоит в действующих шагах, MCP не показывает
  ([ADR-0006](0006-rest-read-only-for-review.md): `settings.input`
  PIECE-шагов доступен только ревьюеру через REST). Заведено как
  [Q37](../OPEN-QUESTIONS.md#q37) и проверяется **до** пилота.

- **`sessions` растёт полем под `card_message_id`,** а редактирование
  устаревшего или чужого `message_id` даёт `400`. Значит `edit_message_text`
  идёт с `continueOnFailure` и фолбэком на новое сообщение — иначе первая же
  рассинхронизация обрывает диалог насмерть. Плюс гонка: две карточки одного
  ивента (гость открыл deep link дважды) — редактируется последняя, прежняя
  остаётся в ленте с живыми кнопками. Кнопки обязаны быть идемпотентными
  по [ADR-0011](0011-idempotency-on-atomic-primitives.md); это уже так, но
  теперь на это опирается интерфейс.

- **Mini App растёт с одной страницы до трёх.** Клиентский код не покрыт ни
  ревью флоу, ни прогонами на инстансе — единственная замена тестам
  (свежий контекст ревьюера) на него распространяется хуже всего. Форма
  создания ивента — самая сложная страница проекта, и она окажется в самой
  слабо проверяемой его части.

- **Долг i18n удваивается.** `uz` и `en` уже отстают от `ru` на 19 ключей;
  пересборка добавит ключей примерно вдвое. [ADR-0014](0014-russian-only-until-platform-i18n.md)
  разрешает жить на русском, но решение о том, догоняем ли переводы в пилоте
  или фиксируем долг явно, принимается сейчас, а не когда ключей станет 400.

## Что остаётся в силе

- **ADR-0001** целиком: свой сервис нельзя, Code step — чистая функция. Mini App
  остаётся **именованным** исключением: три страницы (`ticket`, `scan`,
  `manage`), четвёртая — новым ADR.
- **ADR-0015 и ADR-0016 не меняются.** Экран ≠ флоу. Карточка, меняющаяся
  три раза, — это по-прежнему три касания и три флоу; меняется только действие,
  которым флоу отвечает (`edit` вместо `send`).
- **ADR-0007**: QR по-прежнему рендерится в Mini App и не отправляется файлом.
- **ADR-0009**: бюджеты горячего пути не отменяются. Редактирование стоит
  примерно столько же, сколько отправка, — выигрыш здесь в чистоте ленты,
  а не в латентности, и выдавать одно за другое нельзя.
- **Инварианты SPEC.** **PAR-1/PAR-2 — два отдельных согласия, а не два
  отдельных экрана**: два явных тапа по одной карточке остаются двумя
  раздельными актами, `consent_marketing` по-прежнему не проставляется
  побочным эффектом и по умолчанию `false`. STF-2 (права по конкретному
  `event_id`), DAT-1 (`telegram_id` — единственный ключ), OWN-3 (UTC в базе,
  Ташкент в показе), IDM-1…IDM-4 — без изменений.

## Альтернативы

- **Косметика: эмодзи и жирный в существующие строки.** Отвергнуто как
  недостаточное: лечит дефекты 1 и 2 из разбора, не трогает ни ленту из девяти
  сообщений, ни анкету из одиннадцати вопросов, ни отсутствие послесловия.
  Самое дешёвое из возможного и единственное, что можно сделать **вместо**
  этого ADR, если пересборку решено не начинать.
- **Всё в Mini App, бот — только канал уведомлений.** Отвергнуто: deep link
  остаётся главным каналом привлечения, гость обязан регистрироваться без
  установки и открытия чего бы то ни было лишнего, а перенос всего UX
  в клиентский код выводит его из-под единственной работающей в проекте формы
  проверки.
- **Ждать, пока в qadam появятся `edit_message_caption`/`edit_message_media`.**
  Отвергнуто: срок чужой, а обходной путь есть (см. «Цену»).
- **Оставить как есть.** Работает, оттестировано, стоит ноль. Именно это
  и произойдёт, если владелец не примет решение — и это допустимый исход,
  который надо назвать вслух, а не получить по умолчанию.

## Решения владельца, принятые вместе с ADR (2026-09-13)

1. **Объём — целиком**, включая п. 3. Исключение ADR-0001 расширяется
   с одной страницы Mini App до трёх: `ticket`, `scan`, `manage`.
   Четвёртая страница по-прежнему требует нового ADR.
2. **`uz`/`en` — долг фиксируется явно, а не догоняется по ходу.** Пилот
   и последующие пакеты пишутся на `ru` по
   [ADR-0014](0014-russian-only-until-platform-i18n.md); отдельный пакет
   на догон переводов заводится в [BACKLOG](../BACKLOG.md) с посчитанным
   числом ключей. Причина — не растворить величину долга в десяти пакетах,
   где её никто не увидит целиком.
3. **Способ редактирования карточки с фото выбирается на пилоте**, из трёх
   вариантов в разделе «Цена». Заранее не фиксируется: разница между ними
   ощущается только на живом экране.
4. **Порядок работ: сначала [Q37](../OPEN-QUESTIONS.md#q37), потом пилот.**
   Проверка дешёвая, а её исход может обязать чинить продукт независимо
   от этого ADR.

Что именно пересобирается и в каком порядке — предмет отдельного пакета
работ; здесь фиксируется только правило и его цена.
