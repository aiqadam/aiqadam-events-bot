# 0058. Перенос `users` в AI Qadam ID — флоу `id-migrate` в `events-dev`

**Статус:** принято, 2026-11-24, решением владельца. Исполняет на стороне бота
[ID ADR-0030](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0030-users-migration-mechanics.md)
(принят владельцем) и [ID ADR-0031](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0031-events-dev-is-qa-rehearsal-on-its-data.md).
Расширяет [ADR-0010](0010-unsandboxed-code-step-for-crypto.md): ещё одно узкое место для `node:crypto`.

## Контекст

AI Qadam ID — единый профиль участника для всех модулей. ID ADR-0030 решил, как люди из `users` бота
переезжают в ID: подписанный импорт, который запускается внутри платформы, без выгрузки данных наружу и без
агента посередине. Сторона ID — вебхуки `migrate-import`, `migrate-verify` и ручной `migrate-undo` — построена
и проверена на QA (ID, пакет W06). ID ADR-0030 §2 прямо говорит, что флоу-отправитель `id-migrate` — изменение
бота и записывается ADR бота. Это он.

ID ADR-0031: `events-dev` — QA-среда (переход на `events-prod` выполнен, в dev остались тестировщики), и
репетиция на его данных разрешена до публикации политики — только в паре QA `events-dev` ↔ ID QA. Пара prod
(`events-prod` ↔ ID prod) переносится отдельно и своим ключом.

## Решение

1. **Флоу `id-migrate` в `events-dev`, ручной запуск**, логирование выключено на каждом шаге, который несёт
   людей или ключ (включая вывод триггера). Шаги:
   - блокировка прогона `mig:lock` (`put_if_absent`, TTL 1 ч); второй прогон отказывается;
   - чтение `users` без `limit` и без `phone` и второе чтение с фильтром `consent_pdn = true` — сверка
     (RT-9); то же — для выдуманной таблицы `mig_test_users`;
   - `preflight` (эталон [id-migrate-preflight](../../catalog/snippets/id-migrate-preflight.md)): гистограммы,
     дубли, даты, диапазон id; любая аномалия останавливает прогон до первой отправки; совпадающие дубли
     сливаются; люди без `consent_pdn = true` остаются (`left_behind`);
   - отчёт `preflight` — только числа; это и есть ожидаемые числа, которые пишутся в журнал **до** реального
     прогона;
   - цикл по батчам из 10 ([id-migrate-send](../../catalog/snippets/id-migrate-send.md)): подпись и отправка
     в `migrate-import`, до трёх попыток со свежим `request_id`; неудача батча останавливает прогон;
   - сверка ([id-migrate-verify](../../catalog/snippets/id-migrate-verify.md)): ключевой digest и суммы в
     `migrate-verify`; итог `pass` — только флаги и числа;
   - снятие блокировки.
2. **Режим — переменная `migration_mode`:** `dry-test` / `dry-real` только считают; `test` отправляет
   выдуманных людей из `mig_test_users` (id `9000000000000000`+); `real` — людей из `users`. Значение покоя —
   `off` (отказ `bad_mode`). Прогон помечается `migration_run`.
3. **Окно — переменная `migration_open_until`** в обоих проектах (как в ID): `test`/`real` не отправляют
   ничего вне окна не длиннее 4 ч.
4. **`node:crypto` в Code step** — четвёртое узкое место после ADR-0010: HMAC подписи и ключевые хэши digest.
   `crypto`-qadam не используется: он логирует вход с ключом (ID RT-6c). Отправка — `fetch` внутри того же
   шага, а не HTTP-qadam: подпись, тело и ключ живут в одном нелогируемом шаге, и повтор подписывается
   заново со свежим `request_id` (повтор старого `request_id` ID отклонит как replay).
5. **Ключ `migration_key`** — отдельная переменная, равная ID-шной, не модульный ключ. В паре QA он
   сгенерирован в сессии агента (риск принят владельцем, ID ADR-0031 §3); ключ prod задаёт владелец.
6. **Бот ничего не пишет в `users` и не меняет свои флоу.** Переключение бота на ID API — отдельный ADR
   (ворота RT-12, RT-16 в ID ADR-0030 §4).

## Следствия

- Реальный прогон — по отдельной команде владельца, с ожидаемыми числами в журнале W144.
- `mig_test_users` — выдуманные люди тестового диапазона; удаляется вместе с тестовыми строками в ID после
  приёмки.
- Ошибка батча видна в прогоне как `batch_failed: <статус> <код>` — без id и без тела.
- Повтор прогона безопасен: импорт ID идемпотентен (существующие люди считаются `existing`, пропущенные —
  `skipped_*`). Освежить данные перед переключением — `migrate-undo` + новый прогон (ID ADR-0030 §4).
