# 0008. Bot token для HMAC читается из Variable, а не из `{{connections[...]}}`

**Статус:** принято, 2026-09-09. Обнаружено пакетом W8 на живом `initData`.

## Контекст

`fn-verify-init-data` (W2) считает секретный ключ Telegram по предписанному
алгоритму — `HMAC-SHA256("WebAppData", bot_token)` — и токен бота
подставлялся в `text` шага `crypto : hmac-signature` шаблоном
`{{connections['TZTlXaCEO2hEvimUowbSA']}}`. На ревью W2 это было признано
рабочим: цепочка воспроизводилась на синтетических пробниках
(`PROBE-W2`, `PROBE-REVIEW2`) и совпадала с независимым пересчётом через
`openssl`. Единственное, что оставалось непроверенным — [Q16](../OPEN-QUESTIONS.md#q16):
подпись `initData`, выданная **настоящим** клиентом Telegram, а не
собранная агентом.

Пакет W8 закрыл Q16 и обнаружил, что синтетическая проверка была слепым
пятном другого рода: она подтверждала **механику** шага `crypto`
(что `secretKey` — это ключ, а `text` — сообщение), но не проверяла,
**действительно ли `{{connections['<externalId>']}}` даёт байт-в-байт тот же
токен**, что использует сам бот. Ни один пробник этого не мог показать —
для этого нужен `hash`, реально посчитанный Telegram-сервером на настоящем
токене, и сравнение результата.

## Находка

Два независимых захвата `initData` от живого клиента Telegram (второй — отправлен
напрямую `fetch()` из самого Mini App, без единого ручного копирования) дали
`hashValid: false` на опубликованной версии `fn-verify-init-data`, при том что:

- бот `@aiqadam_events_dev_bot` в connection подтверждён как раз тот, что нужен —
  `custom_api_call GET /getMe` вернул `username: "aiqadam_events_dev_bot"`,
  токен рабочий и текущий (иначе Telegram отдал бы `401`);
- алгоритм сверен построчно с официальной документацией Telegram
  (`core.telegram.org/bots/webapps`): в строку идут все поля кроме `hash`
  (включая `signature` — это отдельно проверено, версия с исключением
  `signature` тоже не даёт совпадения; исключение `hash` **и** `signature`
  вместе — это другой, Ed25519-алгоритм, к нашему случаю не относится);
- перебраны все комбинации полей и вариантов экранирования — ни один не
  воспроизводит присланный Telegram `hash`.

**Решающий тест: владелец бота посчитал `HMAC-SHA256("WebAppData", bot_token)`
локально, у себя, с реальным токеном из BotFather (`/mybots` → API Token,
без ротации) — результат не совпал с тем, что вычислял шаг `fn-verify-init-data`
через `{{connections['TZTlXaCEO2hEvimUowbSA']}}`.** Это подтверждает: сам
токен в connection рабочий (иначе `getMe` бы не прошёл), но шаблон
`{{connections['<externalId>']}}`, использованный как **данные** (в `text`
PIECE-шага, не как выделенный параметр `auth`), не отдаёт то же самое
значение, что и внутренняя авторизация того же коннекшна для реальных
API-вызовов (`getMe`, `send_text_message`, …).

## Решение

**Токен бота дублируется в project Variable `BOT_TOKEN`** (тот же приём, что уже
применён к `QR_SIGNING_KEY`, W2) и читается шаблоном `{{variables['BOT_TOKEN']}}`.
После правки `fn-verify-init-data / step_2` тот же самый `initData`,
на котором до этого был `hashValid: false`, дал `hashValid: true` — тем же
прогоном, без каких-либо других изменений в цепочке.

- **`{{connections['<id>']}}` остаётся** для мест, где токен используется как
  `auth` PIECE-шага (`send_text_message`, `getMe` и другие реальные вызовы
  Telegram Bot API) — там подстановка проверена рабочей (`getMe` возвращает
  верный `username`).
- **`{{connections['<id>']}}`, использованный как обычные данные** (в `text`,
  `body` и т.п. любого шага, не в параметре `auth`) — считается ненадёжным до
  отдельной проверки поведением (не только конфигурацией). Правило
  `fn-*`-соглашений (README, «Code step — чистая функция») дополняется:
  **если секрету нужно попасть в шаг именно как данные — он живёт в Variable,
  не в connection**.
- Поскольку `fn-verify-init-data` — общий subflow, правка чинит проверку
  `initData` сразу во всех вызывающих (`registration`, `my-qr-api`,
  `checkin-api`, будущие `tg-router`-обработчики W10/W11) одним шагом,
  без правки каждого из них.

## Следствия

- **[Q16](../OPEN-QUESTIONS.md#q16) закрыт полностью**, а не частично: STF-2
  теперь проверен на настоящей подписи Telegram, а не только на синтетике.
  Без этого прогона баг остался бы невидимым до первого реального контролёра
  в проде — `checkin-api` отклонял бы **всех**, включая легитимных.
- Цена секрета в двух местах вместо одного (connection + Variable) — принята
  сознательно: связность (`{{connections[...]}}` работает для реальных API,
  `{{variables[...]}}` — для данных) важнее экономии одной копии токена.
  Оба места по-прежнему настраиваются только в UI, репозиторий секретов
  не содержит.
- [ADR-0005](0005-secrets-visible-in-run-logs.md) не меняется: токен и
  производный ключ по-прежнему видны в логах прогонов вне зависимости от
  источника (connection или Variable) — риск тот же, просто теперь хотя бы
  сама проверка **работает**.
- **Общий урок для будущих пакетов**: утверждение о конфигурации PIECE-шага,
  подтверждённое только конфигом или синтетическим пробником, недостаточно
  для секретов, которые платформа резолвит по нескольким разным путям —
  нужен прогон на данных, которые эту развилку различают (здесь — реальная
  подпись Telegram, которую подделать нельзя). Ровно та же логика, что уже
  зафиксирована в [flows/README.md](../../catalog/flows/README.md) про
  `limit: 50` в W2: конфигурация, «которая просто выглядит правильно»,
  не обязана быть правильной.
