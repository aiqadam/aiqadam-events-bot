# 0003. Идемпотентность без атомарных примитивов

**Статус:** принято, 2026-09-08. Основано на проверке живого инстанса (W0).

## Контекст

ТЗ требует идемпотентности в четырёх местах (IDM-1…IDM-4): регистрация, чекин,
напоминания, обработка `update_id`. Модель данных изначально предполагала, что
её обеспечит база: уникальный индекс по паре колонок и атомарный upsert.

Проверка на <https://app.flow.aiqadam.org> показала, что **ни одного атомарного
примитива платформа не даёт**:

| Проверка | Результат |
| --- | --- |
| Три записи с одинаковым ключом в Tables | вставились все три, ошибки нет |
| Уникальные индексы при создании таблицы | не поддерживаются (`TEXT`/`NUMBER`/`DATE`/`STATIC_DROPDOWN`, и всё) |
| Upsert-действие в `tables` qadam | отсутствует: только create / update / get / find / delete / clear |
| `store put` с режимом «только если нет» | отсутствует; TTL тоже нет |
| Условный `update` (обновить, если поле пусто) | отсутствует: `tables-update-record` работает по `id` записи |

Значит, любая наша проверка — это «прочитать → решить → записать» двумя разными
шагами флоу, между которыми есть окно. Воркеры платформы горизонтальны, так что
окно реально.

## Решение

Идемпотентность строится **не на блокировках, а на форме данных и на уборке**.
Три уровня, по убыванию надёжности:

### 1. Сделать повтор безвредным (основной приём)

Где можно — операция пишется так, что второй проход не меняет результат:

- **Чекин (IDM-2).** Пишем `checked_in_at` только если поле пусто, и **никогда**
  не перезаписываем. Даже если два контролёра просканировали человека одновременно
  и обе записи прошли, значения различаются на миллисекунды, а показываем мы
  всегда минимальное. Практический эффект гонки — ноль.
- **Регистрация (IDM-1).** Подтверждение отправляется только при фактическом
  переходе `нет строки → registered`. Дубль строки не порождает второго сообщения,
  потому что решение принимается по состоянию до записи.

### 2. Схлопывать дубли сверткой при чтении

Все чтения `registrations` идут через `fn-find-registration`, который при нескольких
строках на `(event_id, telegram_id)` берёт **самую раннюю** и считает её канонической.
Так дубль перестаёт быть логической ошибкой ещё до того, как его уберут.

Счётчики owner'а (OWN-7) и сегменты рассылок (OWN-9) считают **уникальные
`telegram_id`**, а не строки. Иначе один задвоенный участник превращается в двух.

### 3. Периодическая уборка

Флоу `dedup-sweep` по расписанию находит дубли по ключевым парам
(`registrations`, `event_staff`, `broadcast_targets`) и удаляет все, кроме самой ранней
записи. Уборка — не оправдание для пункта 1, а страховка: она чинит следствие,
а не причину.

### Отдельно: `update_id` (IDM-4)

`store get` → `store put` с окном между ними. Telegram переотправляет апдейт
через секунды, а не через миллисекунды, поэтому окно практически не срабатывает.
Дополнительно: обработчики пишутся так, чтобы повтор был безвреден по пункту 1.

TTL у `store` нет, поэтому ключи `upd:*` копятся. Их подчищает тот же `dedup-sweep`.

### Отдельно: рассылка (OWN-11…OWN-13)

Здесь цена ошибки выше всего — дубль виден человеку. Поэтому защита не на ключах,
а на курсоре: `broadcast_targets.state` переводится в `sent` **сразу после каждой
успешной отправки**, до перехода к следующему адресату, а прогон возобновляется
по `broadcasts.cursor`. Список получателей материализуется один раз на старте.

## Следствия

- Мы честно принимаем: **строгой exactly-once гарантии нет**. Есть «повтор ничего
  не портит» плюс уборка. Для регистрации на митап этого достаточно; для платежей
  такой схемы не хватило бы.
- Каждая проверка «есть ли уже такая строка» — это отдельный шаг `find-records`
  перед записью. Флоу становятся длиннее; это цена, а не недосмотр.
- Boolean-полей в Tables нет: флаги (`consent_pdn`, `consent_marketing`, `blocked_bot`)
  хранятся как `STATIC_DROPDOWN` со значениями `true`/`false`, JSON (`sessions.draft`) —
  как `TEXT` со строкой JSON.
- Если в Qadam Flow появятся уникальные индексы или условный update — это первый
  кандидат на upstream-вклад от нас в платформу, и тогда ADR пересматривается.
