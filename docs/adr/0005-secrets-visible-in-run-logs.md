# 0005. Секреты и персональные данные видны в логах прогонов

**Статус:** принято, 2026-09-08. Обнаружено на ревью W2, подтверждено на живом инстансе.

## Контекст

[ADR-0001](0001-qadam-flow-as-carrier-stack.md) выбрал Qadam Flow несущим стеком:
секреты живут в платформе (connection, Variables), а не в `.env` репозитория,
и это записано как выигрыш. Пакет W2 показал, что у этого выигрыша есть цена,
которую до сих пор нигде не назвали.

**Платформа логирует входы и выходы каждого шага прогона целиком.** Прочитать их
может любой, у кого есть доступ к проекту (UI или MCP `ap_get_run`). Значит,
всё, что проходит через шаг, — не только в памяти воркера, но и в логе.

Проверено на `events-dev` 2026-09-08 (ревьюер W2 прочитал и **воспроизвёл** это,
а не предположил):

| Что | Где именно | Что из этого следует |
| --- | --- | --- |
| Производный секретный ключ Telegram = `HMAC("WebAppData", bot_token)` | `fn-verify-init-data / step_2`, вывод шага; одинаков во всех прогонах | этим ключом подделывается `hash` для **любого** `telegram_id` — полный обход STF-2 мимо `event_staff` |
| Сам bot token | inputs того же шага (`text` = `{{connections['…']}}`) | доступ к боту целиком |
| `phone`, `first_name`, `last_name`, `username` пользователей | вывод любого `tables-find-records` по `users` | персональные данные (DAT-2) в логах шагов, которым они не нужны |

Обойти это внутри платформы **нечем**:

- цепочка двух HMAC для `initData` — предписанный Telegram алгоритм, и ключ
  второго шага физически обязан быть выходом первого
  ([SECURITY.md](../SECURITY.md#валидация-initdata-stf-2));
- считать HMAC в Code step невозможно: в песочнице нет ни `node:crypto`,
  ни `crypto.subtle`, ни `Buffer`
  ([ARCHITECTURE.md](../ARCHITECTURE.md#песочница-code-step--проверено-на-инстансе-2026-09-08));
- проекции колонок у `tables` qadam нет: `find-records` возвращает **все** поля
  строки, выбрать три из двенадцати нельзя.

Единственная альтернатива — свой сервис, который держал бы токен и считал HMAC
у себя. Это прямой отказ от ADR-0001 ради одного шага.

## Решение

**Принимаем и называем прямо: в этом проекте доступ к проекту Qadam Flow
равносилен доступу к bot token и к персональным данным участников.**
Логи прогонов — такой же секретный артефакт, как сам токен.

Отсюда правила, а не пожелания:

1. **Доступ к проектам `events-dev` / `events-prod` выдаётся как доступ к секретам**,
   а не как доступ «посмотреть флоу». Отдельная роль «только чтение» здесь ничего
   не защищает: чтения логов достаточно.
2. **Логи прогонов не выносятся из платформы**: ни в тикеты, ни в чаты, ни в issue.
   Прогон, приложенный к баг-репорту, — это утёкший токен.
3. **`events-prod` получает собственного бота и собственный `QR_SIGNING_KEY`**
   (уже требование W15). Утечка dev-логов не должна давать доступ к бою.
4. **Компрометация логов = ротация bot token через BotFather.** Ротация ломает
   `initData` до переоткрытия Mini App, и это дешевле подделанных чекинов.
5. **Шаг не читает больше данных, чем ему нужно.** Проекции колонок нет, но фильтр
   есть: выборка сужается фильтром до тех строк, которые шагу действительно нужны.
   Так сделано в `fn-resolve-segment` (два фильтрованных чтения `users` вместо
   полной выгрузки таблицы). Полная выгрузка `users` в шаг — дефект, а не
   особенность реализации.

## Следствия

- Модель угроз проекта честнее: «секреты в платформе» больше не читается как
  «секреты защищены». Защищён только репозиторий — в нём секретов действительно нет.
- Требование к процессу, а не к коду: у пакетов W7/W8/W14 нет способа это исправить
  флоу, зато есть способ ухудшить — вытащив в шаг лишние поля.
- Остаточный риск, который **не** снимается этим решением: персональные данные
  найденных строк всё равно попадают в лог, потому что проекции колонок нет
  ([Q17](../OPEN-QUESTIONS.md#q17)). Уменьшать его можно только фильтрами.
- Если однажды появится критерий «логи не содержат секретов», он потребует
  пересмотра ADR-0001, а не правки флоу. Это и есть настоящая цена «0 кода»,
  и теперь она записана.
