# 0016. Одинаковые по устройству касания делят один флоу

**Статус:** принято, 2026-09-13. Решение владельца проекта.

**Уточняет** [ADR-0015](0015-one-touch-one-flow.md) п. 2–3: не отменяет «одно
касание = один флоу», а даёт второй критерий для границы флоу там, где
буквальное чтение ADR-0015 плодит копии без пользы для ревью.

## Контекст

W11 (визард ивента: создание и правка, OWN-1…OWN-5) взят в работу как часть
W26 решением владельца 2026-09-13 — инстанс всё равно пуст, откладывать
пересборку до отдельного пакета смысла не было.

Визард — это **последовательность из шести структурно одинаковых вопросов**
(название → описание → адрес → начало → конец → дедлайн регистрации) плюс
два вопроса с другой механикой ответа (фото, гео-точка) плюс превью и
публикация. У шести «одинаковых» вопросов код различается только: какое
поле черновика пишем, каким правилом валидируем ответ, какой текст следующего
вопроса. Буквальное применение ADR-0015 п. 3 («смена стадии диалога — смена
флоу») даёт шесть почти идентичных флоу — как `reg-consent-pdn`/`reg-consent-mkt`
в W26, но там ветвление было по **смыслу ответа** (да/нет меняет, что
записывается и как), а здесь — по **тому, какое поле спрашивается**, при
одном и том же алгоритме обработки. Это другое основание для границы, и оно
не обязано давать тот же результат.

Множить файлы, которые отличаются только данными (какое поле, какой валидатор,
какой текст), не покупает читаемость — ревьюер должен сверить шесть копий
одного и того же кода, а не шесть разных решений. Это ровно та цена, которую
ADR-0015 называло у `event-wizard`: «одна логика, скопированная трижды».
Здесь копий было бы не три, а шесть, и мотив к копированию тот же.

## Решение

**Критерий границы флоу — не только «какой вопрос», но и «отличается ли
обработка ответа по существу».**

1. Если N последовательных вопросов обрабатываются **одним и тем же алгоритмом**,
   различаясь только тем, какое поле черновика пишется, каким правилом
   проверяется ответ и какой текст следующего вопроса — они делят один флоу.
   Текущий вопрос и правило перехода к следующему читаются из `session.step`
   и небольшой таблицы соответствий **в коде** (не в БД — это код, а не данные
   проекта), а не из ветвления ROUTER'а.
2. Если вопрос требует другой **механики ответа** (медиа-сообщение вместо
   текста, гео-точка вместо строки, callback вместо свободного текста с другим
   набором валидаций) — это разные флоу, как и раньше по ADR-0015 п. 2–3.
3. Итоговая структура визарда (create+edit, OWN-1…OWN-5):

   | Флоу | Касание |
   |---|---|
   | `event-wizard-start` | `/newevent` — открывает сессию, первый вопрос |
   | `event-wizard-field` | шесть простых полей (title/description/address/starts_at/ends_at/deadline) — один флоу, ветвление по `session.step` в коде |
   | `event-wizard-photo` | ответ фото — другая механика (Telegram `file_id`) |
   | `event-wizard-geo` | ответ гео-точкой — другая механика (`location`) |
   | `event-wizard-preview` | показ карточки-черновика + кнопка публикации |
   | `event-wizard-publish` | публикация; при правке — diff по `notify-on-change` и уведомление (см. ниже) |

   Шесть флоу вместо десяти-двенадцати почти одинаковых.

## Q36 — уведомление при правке (OWN-5) решено тем же пакетом

**Дыра, которую [Q36](../OPEN-QUESTIONS.md#q36) описал:** рассылка по списку —
не касание и не разрешённая ADR-0015 п. 5 функция (не крипто, не чтение).

**Решение, узкое, только для OWN-5:** уведомление о правке ивента — **прямой
цикл по `registrations` этого ивента** (`LOOP_ON_ITEMS`, `continueOnFailure`,
`send_text_message` каждому), без `broadcasts`/`broadcast_targets`, без
троттлинга 25 msg/s и без ретраев на `429` (OWN-11/OWN-12). Это сознательно
**не** система рассылок: у одного ивента реалистично десятки-сотни
регистраций, не тысячи, а редактирование — не частое действие, поэтому
разовый нетроттленый цикл в пределах `FLOW_TIMEOUT_SECONDS = 600` терпим.

Когда W14 построит `broadcasts`/`broadcast_targets`/`broadcast-runner` по
OWN-9…OWN-13, `event-wizard-publish` можно будет переключить на запись в
`broadcasts` вместо прямого цикла — это правка одного шага, не архитектурный
пересмотр. До тех пор дублирования логики нет: узкий цикл здесь и будущий
рассыльщик в W14 решают разные по объёму задачи (уведомление своих
регистрантов об одном ивенте vs сегментированная рассылка с троттлингом).

**Q36 закрыт этим решением** — см. запись в OPEN-QUESTIONS.md.

## Цена

- **Критерий границы флоу стал двумя правилами вместо одного** — «какой
  вопрос» и «отличается ли алгоритм». Это больше суждения при разбиении
  будущих флоу, не механическое правило. Смягчение — оба правила явно
  описаны здесь, и любое новое разбиение сверяется с этим ADR, а не
  придумывается заново.
- **`event-wizard-field` — единственный флоу в проекте с ROUTER-подобной
  логикой внутри одного CODE-шага** (маленькая таблица `{step: {field,
  validator, nextStep, promptKey}}`), а не ROUTER-шагом платформы. Это
  осознанное отличие от остального проекта, где ветвление — через ROUTER;
  здесь веток шесть с одинаковым скелетом, и ROUTER на шесть почти одинаковых
  веток был бы ровно той дупликацией, которую этот ADR устраняет.
- **Уведомление OWN-5 не troттлится и не ретраится** — при очень крупном
  ивенте (сотни регистраций) есть риск упереться в `FLOW_TIMEOUT_SECONDS`
  или в лимиты Bot API без бэкоффа на `429`. Принято как временный узкий
  охват; W14 снимет это ограничение, когда будет построен.

## Что остаётся в силе

ADR-0015 целиком, включая критерий «одно касание = один флоу» для вопросов
с РАЗНОЙ обработкой ответа (это большинство касаний в проекте — регистрация,
чекин, всё, что уже построено в W26 до этого решения). Это уточнение касается
только последовательностей структурно одинаковых вопросов, которых до сих пор
в проекте не было.
