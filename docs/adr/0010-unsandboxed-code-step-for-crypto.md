# 0010. UNSANDBOXED Code step: разрешаем `node:crypto` для трёх HMAC-цепочек

**Статус:** принято, 2026-09-09. Решение владельца проекта, после подтверждённого
прогоном факта и явной оценки цены.

## Контекст

Инфра-тикет `T-0161` на `pro-data-tech-qa` (тот же инстанс, что использует
`aiqadam-events-bot`) поменял, помимо прочего, `AP_EXECUTION_MODE` с `SANDBOXED`
на `UNSANDBOXED` и включил `ALLOW_NPM_PACKAGES_IN_CODE_STEP`. Это сделано ради
профилирования латентности горячего пути ([ADR-0009](0009-hot-path-latency-budget-and-order.md)),
но фактически меняет и то, что задокументировано в
[ARCHITECTURE.md](../ARCHITECTURE.md#песочница-code-step--проверено-на-инстансе-2026-09-08)
как факт от 2026-09-08: «нет `node:crypto`, `fetch`, `Buffer`, `crypto.subtle`, npm».

Проверено прогоном пробного флоу 2026-09-09 (создан и удалён тем же прогоном,
без изменений в реальных флоу): `require('node:crypto')` считает HMAC-SHA256 за
6 мс, `Buffer`, `TextEncoder`, `crypto.subtle`, `process`, `require` — все
определены. `packageJson` с реальной npm-зависимостью не проверялся: агент,
проводивший тест, не имеет права выполнять код, скачанный из внешнего реестра,
даже с разрешения владельца проекта — это ограничение агента, а не платформы.

Это прямо касается [ADR-0005](0005-secrets-visible-in-run-logs.md), который
принял как факт «считать HMAC в Code step невозможно» и на этом основании
смирился с тем, что производный секретный ключ Telegram
(`HMAC("WebAppData", BOT_TOKEN)`) виден в логе **каждого** прогона
`fn-verify-init-data` — открытым текстом, одинаковый на каждом прогоне, что
равносильно полному обходу STF-2 для того, у кого есть доступ к проекту/логам.
Тот факт был верен на момент принятия ADR-0005 и перестал быть верным здесь и
сейчас.

Третье место нашлось не из ADR-0005, а из вопроса «а что ещё можно менять,
кроме этих двух флоу»: `fn-verify-qr` (проверка подписи QR на каждом скане
контролёра) сегодня **не считает HMAC сам** — он вызывает `fn-sign-qr` как
subflow (`step_2: callFlow`), чтобы получить «ожидаемую» подпись, и сравнивает.
Секрета в логах это не добавляет (`fn-sign-qr` и так не отдаёт полный дайджест
наружу), но это лишний вложенный flow-run на **каждый** чекин — отдельная
диспетчеризация сверх той, что уже посчитана в [Q22](../OPEN-QUESTIONS.md#q22).
Мотив здесь другой (латентность, не секьюрити), но техническая возможность та
же самая — `node:crypto` внутри Code step.

## Решение

1. **Разрешаем `node:crypto` и другие builtin-возможности Node внутри Code step**
   для трёх конкретных мест, каждое — по отдельному, явно названному мотиву,
   не ради самого разрешения:
   - `fn-verify-init-data` (`step_2`+`step_3` → один CODE-шаг) — **мотив: секрет
     в логах.** Производный ключ Telegram перестаёт быть *выводом* какого-либо
     шага;
   - `fn-sign-qr` (`step_2`+`step_3` → один CODE-шаг) — **мотив: секрет в логах.**
     Полный HMAC-дайджест перестаёт быть *выводом* шага, наружу — только
     10-символьный `sig`, как и сегодня, но без промежуточного полного значения
     в логе;
   - `fn-verify-qr` (`step_2` `callFlow → fn-sign-qr` → инлайн той же логики
     подписи через `node:crypto`, без вызова subflow'а) — **мотив: латентность,
     не секьюрити.** Убирается целый вложенный flow-run на каждый скан, а не
     шаг внутри одного флоу — по масштабу это ближе к эффекту тюнинга воркеров
     (Q22), чем к ~9% от инлайна `fn-parse-start`, потому что снимается не хоп
     внутри графа, а весь дочерний прогон целиком. Логика подписи (`msg`,
     ключ, срез до 10 символов) дублируется из `fn-sign-qr` — в модели «0 кода»
     без общих JS-модулей это ожидаемая цена, не новый костыль.
2. **Это узкое исключение, не отмена ADR-0001.** «0 кода» остаётся правилом:
   по-прежнему нельзя писать сетевые вызовы, запись в БД или бизнес-логику в
   Code step в обход core-qadam'ов. Единственное снятое ограничение — крипто-
   примитив, который раньше был физически недоступен и поэтому обязан был жить
   в отдельном `crypto` qadam; теперь недоступности нет, и решение о том, где
   жить HMAC, — архитектурный выбор, а не вынужденная мера.
3. **npm-пакеты не разрешаем без отдельного решения.** `ALLOW_NPM_PACKAGES_IN_CODE_STEP`
   включён на инстансе, но ни один пакет не проверен и не согласован. Builtin
   Node (`node:crypto`, `Buffer`, `TextEncoder`) достаточен для всех трёх HMAC-цепочек;
   заводить внешнюю зависимость ради того же результата — не наш случай.
4. **Что это НЕ чинит** (важно не спутать с полным закрытием ADR-0005):
   - `BOT_TOKEN` всё равно должен попасть в объединённый CODE-шаг как *вход*,
     а входы шагов логируются платформой так же, как выходы — токен бота
     остаётся в логе каждого прогона `fn-verify-init-data`, ровно как сегодня;
   - утечка персональных данных из `tables-find-records` без проекции колонок
     ([Q17](../OPEN-QUESTIONS.md#q17)) не связана с песочницей Code step вовсе;
   - смена архитектуры не влияет на STF-2-права по `event_id` (ADR/DATA-MODEL
     не трогаются) — это отдельная гарантия, слияние шагов её не касается;
   - `fn-verify-qr` не убирает секрет из логов — там его и не было; это не
     регресс п.1/п.2, просто другой мотив для того же технического разрешения.

## Следствия

- Реализация — отдельный пакет работ (см. [BACKLOG.md](../BACKLOG.md), W16), не
  эта правка ADR: меняется код на критическом пути авторизации (STF-2/PAR-6),
  обязательно независимое AppSec-ревью до статуса «готов»
  ([REVIEW-CHECKLIST.md](../work/REVIEW-CHECKLIST.md#4-appsec)), с проверкой,
  что HMAC внутри объединённых/инлайненных шагов даёт тот же результат
  побайтово, что старые цепочки (регресс здесь стоит дороже выигрыша) — это
  касается всех трёх флоу, включая `fn-verify-qr`.
- **Обратимость.** `UNSANDBOXED`/`ALLOW_NPM_PACKAGES_IN_CODE_STEP` — настройка
  инфры на уровне инстанса (`.env` воркеров), не проектная. Если инфра откатит
  `T-0161`, изменённые CODE-шаги начнут падать на `require('node:crypto')` —
  привязка к настройке должна быть явной в каталоге (`catalog/flows/fn-verify-init-data.md`,
  `catalog/flows/fn-sign-qr.md`, `catalog/flows/fn-verify-qr.md`), чтобы будущий
  агент не тратил цикл ревью на разгадывание, почему рабочий флоу вдруг не проходит.
- ADR-0005 **не переписывается и не закрывается** этим решением — его вывод
  «доступ к проекту = доступ к секретам» остаётся верным по двум оставшимся
  пунктам (bot token во входах, ПД без проекции колонок). ADR-0005 получает
  ссылку сюда как на частичное, а не полное снятие цены. `fn-verify-qr` к
  ADR-0005 отношения не имеет вовсе — упомянут здесь только потому, что
  использует то же техническое разрешение.
- Латентность: у `fn-verify-init-data`/`fn-sign-qr` это побочный эффект (не
  основная причина решения) — по тому же принципу, что дал ~9% на эксперименте
  с `fn-parse-start` ([Q22](../OPEN-QUESTIONS.md#q22)), один `callFlow`-хоп
  меньше на каждый. У `fn-verify-qr` это **основная причина** — убирается не
  хоп, а целый вложенный flow-run (вызов `fn-sign-qr`) на каждый скан; ожидаемый
  эффект больше, но не заявляется числом заранее — измеряется после реализации,
  тем же методом (`ap_get_run`, step-sum vs полная длительность, тёплый прогон).
