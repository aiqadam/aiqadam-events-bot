# 0060. Переключение бота на AI Qadam ID API: вызовы ID, экраны согласий, дневное обновление профиля, отказ при сбое ID

**Статус:** черновик, на принятие владельцем. Исполняет на стороне бота шаг 3 порядка
[ID ADR-0032](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0032-events-bot-switch-to-id-api.md) §7
(принят владельцем 2026-11-24). Опирается на [ADR-0059](0059-id-switch-prep-deletion-and-delivery-state.md)
(`fn-delete-person`, `bot_contacts`, приёмник `id-member-deleted`). Уточняет [ADR-0043](0043-shorter-onboarding.md)
(карточка согласия) и [ADR-0039](0039-account-self-deletion-gdpr.md) (самоудаление). Расширяет
[ADR-0010](0010-unsandboxed-code-step-for-crypto.md): шестое узкое место для `node:crypto`, подпись запросов в ID.
Три вопроса ниже ID ADR-0032 не решил. Они ждут выбора владельца: «Выбор владельца» 1–3.

## Контекст

ID ADR-0032 принят. Сторона ID готова на QA (ID W10, W11). Подготовка бота тоже готова (W145). Осталось
перевести на ID API 11 флоу, которые сейчас читают или пишут `users`:

- горячий путь, каждый апдейт: `tg-router`;
- регистрация: `reg-start`, `reg-profile`, `reg-consent-pdn`, `reg-consent-mkt`, `reg-api`, `menu`;
- чекин: `checkin-api`;
- массовые: `manage-api`, `bcast-step`, `bcast-run`.

**Что требует ID API сейчас** (источник — документы ID, по ссылкам):

- Каждый запрос подписан ключом модуля, с `ts` и одноразовым `request_id`
  ([ID ADR-0012](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0012-module-signing-keys-payload-replay.md)).
  Ключ на QA уже есть в `events-dev`: `id_module_key` (ADR-0059 §5).
- `profile-get` (API-1) отвечает `found:false` одинаково для неизвестного человека и для человека без
  согласий `base`/`id` и `module`/`events`
  ([ID ADR-0025](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0025-profile-get-requires-module-consent.md)).
  Поле без значения приходит как `null`.
- `profile-upsert` (API-2) пишет, только пока действуют оба согласия. Без них ответ `403 no_consent`, а с
  `update_only: true` ответ `200 {written:false}`
  ([ID ADR-0033](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0033-profile-upsert-requires-consents-batch-pages-250.md) §1).
  - `created_at` и `last_seen_at` ставит сам ID.
  - Отсутствующее поле или `null` сохраняет значение. Очистить поле можно, только назвав его в `clear`
    ([ID ADR-0034](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0034-profile-upsert-explicit-clear-list.md)).
- `consent-set` (API-3): модуль ставит согласие `base`/`id` и свои `module`/`mailing`. Ответы `409 base_required`,
  `module_required`, `withdraw_pending`
  ([ID ADR-0026](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0026-no-module-grant-while-deletion-outstanding.md)).
  - `text_version` имеет вид `<purpose>.<module>.v<N>.<lang>`
    ([ID docs/legal/ru/consents.md](https://github.com/aiqadam/aiqadam-id/blob/main/docs/legal/ru/consents.md)).
- `profile-batch` (API-5): режимы `mailing` и `by_ids`, не больше 250 человек на запрос (ID ADR-0033 §2).
- `account-delete` (API-4): ID удаляет у себя и шлёт боту `id.member-deleted.v1` (ADR-0059 §3).

**Три вопроса, которые ID ADR-0032 не решил:**

1. **Одна кнопка — два согласия.** Сейчас одна карточка «Согласен» (ADR-0043) ставит `users.consent_pdn`.
   ID ADR-0032 §4 переводит её на `consent-set` `base`/`id`, затем `module`/`events`. Но инвариант 4 ID
   («ни одно согласие не ставится побочным эффектом другого») и правило текстов согласий ID («одна кнопка
   никогда не даёт двух согласий») так не позволяют. Базовое согласие идёт вместе с вопросом «мне 18 лет» и
   принятием условий (ID consents.md §1).
2. **Текущее согласие на рассылку не прочитать.** Таб «Профиль» показывает переключатель рассылки по
   `users.consent_marketing` (`reg-api` `step_17`). В ID нет чтения этого состояния:
   - `profile-get` отдаёт профиль, но не согласия;
   - `profile-batch` `mailing` отдаёт всю аудиторию, а не одного человека.

   Отзыв рассылки на странице ID боту не приходит: событие шлётся только при отзыве модульного согласия
   ([ID ADR-0020](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0020-module-withdrawal-deletes-module-records.md)).
   Значит, своя копия в боте устаревает молча.
3. **Чем подписывать и отправлять.** `crypto`-qadam логирует вход вместе с ключом (ID RT-6c), поэтому он не
   подходит (ADR-0058 §4). `id-migrate` подписывает и отправляет `fetch` внутри одного Code step (ADR-0058
   §4). Но это ручной редкий флоу, а здесь 11 флоу и горячий путь. Главное правило ADR-0001 — HTTP делает
   `http`-qadam, а не Code step.

## Выбор владельца

### Выбор 1. Экраны согласий в боте

- **(а) Отдельные экраны в боте** (рекомендация). Человек без профиля в ID видит по очереди: «Мне 18 лет»,
  карточку базового согласия ID, карточку согласия модуля `events`. У каждой свои кнопки. Тексты и
  версии берутся из ID. На QA тексты — черновики ID с пометкой «ЧЕРНОВИК, тестовая среда», как на QA-странице
  ID: исключение владельца от 2026-11-19 сейчас покрывает только её, а не бота. Онбординг становится
  длиннее ADR-0043 на два экрана.
- **(б) Базовое согласие — на странице ID.** Новичка бот отправляет на `id.aiqadam.org`, а возвращается он за
  модульным согласием. Экранов в боте меньше, но появляется уход из Telegram и возврат. Возврат из ID в
  модуль для бота не построен.
- **(в) Одна карточка, два вызова.** Отвергается: нарушает инвариант 4 ID и правило текстов согласий.

### Выбор 2. Как бот узнаёт текущее согласие на рассылку

- **(а) `profile-get` отдаёт и согласие на рассылку подписавшего модуля** (рекомендация): в ответе
  `mailing: true|false`. Это не поле профиля, а состояние согласия самого модуля. Нужен ADR в ID и небольшой
  пакет ID. Пакет переключения ждёт его.
- **(б) Копия в `bot_contacts`, которую обновляет сам бот.** Устаревает молча после отзыва на странице ID. Сама
  рассылка при этом верна (аудитория — из API-5), неверен только переключатель.
- **(в) Таб не показывает состояние.** Две кнопки «Подписаться» / «Отписаться» без отметки текущего.
  Ничего не устаревает, но человек не видит, подписан ли он.

### Выбор 3. Подпись и отправка

- **(а) Подфлоу `fn-id-call`: Code step подписывает, `http`-qadam отправляет** (рекомендация). Ключ и
  подпись живут в Code step с `node:crypto`, у которого выключены ввод и вывод. Запрос шлёт `http`-qadam,
  тоже без логов. Главное правило ADR-0001 соблюдено: сети в Code step нет. Повторов нет (выбор 4 ID
  ADR-0032: сбой — отказ), поэтому переподпись при повторе не нужна.
- **(б) Code step подписывает и отправляет `fetch`, как `id-migrate`.** Один шаг вместо двух, но исключение
  ADR-0058 распространяется на горячий путь 11 флоу.
- **(в) `crypto`-qadam.** Отвергается: логирует ключ.

## Решение

Ниже — при рекомендованных вариантах: 1(а), 2(а), 3(а). При другом выборе меняются §2, §3 и §1 соответственно.

### 1. Подфлоу `fn-id-call`

Все вызовы ID идут через один подфлоу. Его вызывают inline с ожиданием ответа (ADR-0040).

- **Вход:** `api` (`profile-get` | `profile-upsert` | `profile-batch` | `consent-set` | `account-delete`) и
  `body`.
- **Шаги:**
  1. Code step `sign` (`node:crypto`): `ts` — текущее время, `request_id` — случайный, `signature = HMAC-SHA256(
     id_module_key, "events\n<ts>\n<request_id>\n<sha256(canon(body))>")` (ID ADR-0012). Ввод и вывод
     выключены.
  2. `http` `send_request` POST на адрес из переменной `id_url_<api>`, таймаут 10 с, `continueOnFailure`. Ввод
     и вывод выключены.
  3. Code step `result`: `{ok, status, body}`. Сеть, таймаут и ответ не в JSON дают `ok:false, status:0`. В
     лог попадает только `status`.
- **Переменные `events-dev`:** `id_url_profile_get`, `id_url_profile_upsert`, `id_url_profile_batch`,
  `id_url_consent_set`, `id_url_account_delete` — полные адреса вебхуков ID QA. Они не секретны. Адреса prod
  задаёт владелец.
- Подфлоу ничего не повторяет. Решение об ответе человеку принимает вызывающий флоу (§6).

### 2. Экраны согласий

Человек без профиля в ID (`profile-get` → `found:false`) на первом касании проходит:

1. **«Мне 18 лет»** (`[Да, мне есть 18] [Нет]`). На «Нет» — текст ID «AI Qadam ID доступен с 18 лет. Профиль не
   создан, данные не сохранены.» Ответ «Нет» нигде не записывается.
2. **Базовое согласие** (ID consents.md §1, с принятием условий). «Согласен» → `consent-set` `base`/`id` `grant`,
   `text_version = base.id.v1.<lang>`.
3. **Согласие модуля `events`** (§2). «Согласен» → `consent-set` `module`/`events` `grant`,
   `text_version = module.events.v1.<lang>`.
4. **Вопросы профиля**, как сейчас (ADR-0043). В конце `profile-upsert`: профиль и `profile_completed_at`.
5. **Рассылка**, как сейчас. «Да» → `consent-set` `mailing`/`events` `grant`, `text_version = mailing.events.v1.<lang>`.
   На «Нет» вызова нет.

Правила:

- `<lang>` — язык интерфейса бота (`bot_contacts.lang`). Тексты экранов — ключи `i18n` бота, скопированные из
  `i18n/*.json` ID (`age.*`, `base.*`, `module.*`, `mailing.*`, номера версий `_v.*`). Офлайн-проверку
  совпадения с ID пакет добавляет в `tools/`.
- Отказ на шаге 2 или 3 («Не согласен»): ничего не пишется, человек видит, что без согласия регистрация
  невозможна. Как сейчас при отказе от `consent_pdn`.
- Перенесённые люди (согласия с `text_version = events-bot-pre-id`) получают `found:true` и экранов не видят.
- У кого базовое согласие уже есть (дано на странице ID), а модульного нет, тот тоже получает `found:false` (ID
  ADR-0025) и видит шаги 1–2 снова. Повторное `grant` базового согласия ID принимает: это
  upsert строки согласия. Это цена того, что
  `profile-get` не раскрывает, есть ли человек.
- **Prod:** экраны показываются только после юриста и публикации текстов (ID ADR-0030, ворота RT-15 и Q-014).

### 3. Согласие на рассылку в табе «Профиль»

`reg-api` берёт текущее значение переключателя из `profile-get` (`mailing`, выбор 2(а)). Переключение
вызывает `consent-set` `mailing`/`events` `grant` или `withdraw` с версией `mailing.events.v1.<lang>` или
`withdraw.mailing.v1.<lang>`. `continueOnFailure` у записи согласия убирается (ID ADR-0032 §4).

### 4. Что меняется во флоу

| Флоу | Было (`users`) | Станет |
|---|---|---|
| `tg-router` | `step_6` апсерт `users`, `step_27` язык из `users.lang` | апсерт `bot_contacts` (`last_contact_at`, `blocked_bot = false`); язык из `bot_contacts.lang`; запуск дневного обновления (§5) |
| `reg-start`, `menu` | гейт `users.profile_completed_at`, `lang` | `profile-get`: `found` и `profile_completed_at`; `lang` из `bot_contacts` |
| `reg-consent-pdn` | `consent_pdn = true` | экраны §2, шаги 1–3 |
| `reg-profile` | апсерт `users` (профиль) | `profile-upsert` после согласий; `lang` в `bot_contacts` |
| `reg-consent-mkt` | `consent_marketing` с `continueOnFailure` | `consent-set` `mailing`/`events`, без `continueOnFailure` |
| `reg-api` | чтение и апсерт `users`, `set_lang`, самоудаление через `fn-delete-person` | `profile-get` / `profile-upsert` / `consent-set` (§3); `set_lang` в `bot_contacts`; самоудаление — проверка автора (ADR-0059 §4), затем `account-delete` |
| `checkin-api` | имя из `users` | `profile-get` с полем `first_name`; сбой ID — отказ чекина, контролёр повторяет |
| `manage-api` | имена `users in <csv>`; «есть ли в `users`»; счётчик `consent_marketing = true` | имена — API-5 `by_ids` страницами по 250; «бот видел этого человека» — `bot_contacts`; счётчик — API-5 `mailing` минус `blocked_bot` |
| `bcast-step`, `bcast-run` | база `consent_marketing`, `users in <csv>`, `blocked_bot` в `users` | аудитория — API-5 `mailing` (страницы по 250) ∩ сегмент, минус `bot_contacts.blocked_bot`; на 403 Telegram `blocked_bot` ставится в `bot_contacts` |

- `profile-get` с пустым ответом (`found:false`) — не сбой, а «не зарегистрирован». Для `checkin-api` это значит:
  чекин проходит без имени. Регистрация человека без модульного согласия к этому моменту уже удалена
  приёмником; остаётся только гонка.
- Каждый флоу читает только поля, которые ему нужны (`fields` в запросе).

### 5. Дневное обновление профиля

- После апсерта `bot_contacts` `tg-router` делает `put_if_absent` ключа Store `idr:<telegram_id>`. TTL — до
  ближайшей полуночи UTC, не меньше 60 с.
- Если ключ новый, `tg-router` запускает подфлоу `fn-id-refresh` с `waitForResponse: false`. Ответ человеку его
  не ждёт.
- `fn-id-refresh` вызывает `profile-upsert` с `update_only: true`: `first_name` из Telegram и те из `last_name`,
  `username`, которые есть в апдейте. Отсутствующие идут в `clear` (ID ADR-0034 §4).
- Сбой не повторяется до завтра: ключ живёт до полуночи. От обновления ничего больше не зависит.
- Ключ `idr:<telegram_id>` удаляет `fn-delete-person` (ADR-0059 §1 п. 4 оставил его имя этому ADR).

### 6. Ответы ID и что видит человек

| Ответ | Где | Что делает бот |
|---|---|---|
| `ok:false` (сеть, таймаут, `5xx`), `401`, `409` повтор | везде | отказ с текстом «Сервис временно недоступен, попробуйте позже»; в боте ничего не пишется |
| `403 no_consent` | `profile-upsert` на регистрации | отказ с тем же текстом; это дефект порядка вызовов, видный в логе по `status` |
| `200 {written:false}` | дневное обновление | ничего |
| `409 base_required`, `module_required`, `withdraw_pending` | `consent-set` | свои тексты (ID ADR-0026) |
| `400` | везде | отказ с текстом «попробуйте позже»; дефект бота, видный в логе |
| отказ чекина | `checkin-api` | контролёр видит «ID недоступен, повторите скан» |

Новые тексты — в трёх языках, ключами `i18n` (I18N-2).

### 7. `bot_contacts` и `users`

- Перед переключением один прогон переносит в `bot_contacts` из `users` поля `lang`, `blocked_bot` и
  `last_contact_at` (из `users.created_at`, это «последний контакт»). Отчёт — только числа (ADR-0059 §2).
- После переключения `users` не читается и не пишется ни одним флоу. `fn-delete-person` удаляет из неё, пока она
  существует.
- `users`, `id-migrate` и `mig_test_users` удаляются после приёмки QA владельцем (ID ADR-0032 §7 шаг 6).

## Порядок и ворота

1. **ID:** ADR и пакет для выбора 2(а). До этого пакет переключения не публикует `reg-api`.
2. **`fn-id-call`, `fn-id-refresh`, переменные адресов.** Проверка подписанными вызовами на выдуманных людях
   тестового диапазона: каждый `api`, неверный ключ (`401`), таймаут.
3. **Переключение флоу в черновиках** по таблице §4, с офлайн-тестами эталонов. Перед публикацией
   экспортируются опубликованные версии всех 11 флоу. Это откат на QA.
4. **Освежить данные** (ID ADR-0032 §7 шаг 4): `migrate-undo` прогона `qa-real-2026-11-24`, новый прогон
   `id-migrate`, перенос `bot_contacts` (§7). Сразу после — публикация всех 11 флоу одним окном.
5. **Сквозная проверка на QA** с выдуманными людьми (ID ADR-0032 §7 шаг 5):
   - регистрация;
   - чекин;
   - рассылка;
   - отзыв модуля на странице ID;
   - удаление аккаунта.

   Замер задержки горячих путей против бюджетов [ADR-0009](0009-hot-path-latency-budget-and-order.md):
   `checkin-api` p50 ≤ 10 с.
6. **Откат на QA:** публикация экспортированных версий. То, что тестировщики сделали через ID после
   переключения, для бота теряется (выбор владельца 1 в ID ADR-0032).

## Следствия

- **Бот зависит от ID в регистрации, чекине и рассылках.** Сбой ID останавливает все три (выбор 4 ID ADR-0032).
  Каждый вызов ID стоит около 0,6 с: подфлоу около 0,2 с, ID около 0,4 с p50, 2–7 с в 3–4 % вызовов (ID W05).
  На пути регистрации их три-четыре.
- **Онбординг длиннее** на экраны «18 лет» и базового согласия (выбор 1(а)).
- **Тексты согласий живут в ID,** бот хранит их копию. Изменение текста в ID требует новой версии и копии в
  боте. Офлайн-проверка ловит расхождение.
- **Шестое узкое место `node:crypto`** — `fn-id-call` `sign`. Новых мест это не открывает.
- **Новое касание с `telegram_id`** — ключ Store `idr:<telegram_id>`. Он добавлен в `fn-delete-person`
  (правило ADR-0039).
- **Контролёр без согласий `events`** в списках `manage-api` виден без имени, только по id. Это верно по ID
  ADR-0025.
- **Prod** — после всего остального, со своим планом отката и воротами prod ID ADR-0030 и ID W06.

## Альтернативы

- **Читать профиль из своей копии, а писать в ID.** Отвергнуто в ID ADR-0032: выбор 4, ничего из устаревшей
  копии.
- **Оставить `users` как кэш ID.** Отвергнуто: два источника правды, и копия устаревает после изменений на
  странице ID.
- **Звать ID прямо из каждого флоу, без подфлоу.** Отвергнуто: ключ и подпись в 11 местах.
