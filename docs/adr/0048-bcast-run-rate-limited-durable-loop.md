# 0048. `bcast-run`: перевод на rate-limited durable цикл

**Статус:** предложение — на принятие владельцем (заведён пакетом
[W111](../work/W111-bcast-loop-eval.md), 2026-09-28). Уточняет способ
рассылки; не отменяет OWN-10…OWN-13, [ADR-0013](0013-fewer-messages-on-start.md)
и [ADR-0003](0003-idempotency-without-atomicity.md).

## Контекст

`bcast-run` рассылает чанками: `limit 30` по `state = pending`, пауза **1 с на
получателя**, `callFlow` queue для следующего чанка, поля `sent`/`failed`/
`cursor` в `broadcasts` ([ADR-0044](0044-platform-novelties-sep-2026.md)
п. 3.3). Механизм работает и прошёл ревью, но пейсинг 1 с/получателя — это
≈1 msg/s при платформенном лимите **25 msg/s** (OWN-10): рассылка идёт на
порядок медленнее, чем позволяет Telegram, а чанкование и самовызов
существуют, чтобы уложиться в 600-секундный бюджет флоу.

`#546` дал `LOOP_ON_ITEMS` с `rateLimit {count, perSeconds}`,
`onRateLimited: WAIT_AND_RETRY`, collector (`collected`/`failures`), durable
(чекпоинт на границе элемента) и structured errors
(`description`/`status`/`retryAfterSeconds`).

## Замер (W111, живой `events-dev`)

Временная таблица (100 строк) и временный флоу (после — удалены):

- `LOOP_ON_ITEMS` с `rateLimit {count:25, perSeconds:1}` и collector,
  тело без сети: **4,0 с** на 100 итераций (три прогона: 4,1 с флоу, шаг
  4,0 с), `collected` длиной 100, `failures: []` — rate limit держит ровно
  25/s.
- **Находка:** значение строки Tables в collector берётся как
  `{{loop['output'].item.cells.<внутренний fieldId>.value}}`; плоский
  `{{loop['output'].item.<имя поля>}}` резолвится только для `id` (как в
  `reg-api`) и для остальных полей молча даёт пустую строку — collector
  честно собирает `""`, поэтому проверять надо значения, а не длину.

## Решение (предлагается владельцу)

Перевести `bcast-run` на **один durable rate-limited цикл**:

1. список получателей — `tables-find-records` по сегменту (проекция только
   нужных колонок) → `LOOP_ON_ITEMS` c
   `rateLimit {count:25, perSeconds:1}`, `onRateLimited: WAIT_AND_RETRY`,
   `durable: true` (переживает 600-с бюджет — заменяет cursor-резюме);
2. отправка в теле цикла — `telegram-bot send_message`; `403` (`blocked_bot`)
   и `429` (`retryAfterSeconds`) — через `continueOnFailure` и structured
   errors, без ручного разбора сырого `error` в CODE;
3. `collected`/`failures` — вместо CODE-счётчиков `sent`/`failed`;
4. следующий чанк/самовызов `callFlow` и поля `cursor` — убрать.

**Что не меняется:** расчёт сегмента, `test_sent_at` до боевой отправки
(OWN-10), кнопка «отписаться» (OWN-12), `broadcast_targets.state`
(`pending`/`sent`/`blocked`/`failed`), обязательный тест себе.

**Почему не делается этим пакетом.** `bcast-run` — самый чувствительный флоу
(пишет живым людям, шлёт сообщения), а переписывание меняет способ рассылки
целиком. Это отдельный пакет с независимым ревью, различающими прогонами на
тестовом сегменте и живым тестом себе — как и требует OWN-10. W111 дал замер,
решение и план; реализация — **W111b**.

## Следствия

- Ожидаемый выигрыш — до ~25× по пропускной способности (с ~1 до 25 msg/s);
  цена — миграция самого опасного флоу.
- `durable` в замере не проверялся (нужен прогон дольше бюджета) — проверить
  в W111b различающим прогоном.
- Пока не принято — действует cursor-механизм; менять `bcast-run` не нужно.

## Альтернативы

- **Оставить cursor+callFlow** — рабочий вариант; цена — 25× медленнее и
  ручной разбор ошибок.
- **Переписать `bcast-run` сразу этим пакетом** — отклонено: живой флоу
  массовой отправки без отдельного ревью и теста себе не переписываем.
