# 0059. Подготовка к переключению на AI Qadam ID: полное удаление человека, таблица доставки, приёмник удалений ID

**Статус:** предложено, 2026-11-25. Исполняет на стороне бота шаг 2 порядка
[ID ADR-0032](https://github.com/aiqadam/aiqadam-id/blob/main/docs/adr/0032-events-bot-switch-to-id-api.md) §7
(принят владельцем 2026-11-24). Закрывает Part 2 [ADR-0039](0039-account-self-deletion.md) решениями
владельца от 2026-11-25. Расширяет [ADR-0010](0010-unsandboxed-code-step-for-crypto.md): ещё одно узкое
место для `node:crypto`, проверка подписи ID. Само переключение флоу на ID API в этот ADR не входит,
у него будет свой ADR (ID ADR-0032 §7, шаг 3).

## Контекст

ID ADR-0032 принят. После переключения людьми владеет ID, а бот хранит только данные модуля. Удаление
идёт одним путём. ID удаляет свои строки и шлёт боту подписанное событие `id.member-deleted.v1`
(ID ADR-0017, ADR-0018). Бот удаляет всё, что знает о человеке, и отвечает `200 {done: true}`. То же
событие приходит при отзыве модульного согласия на странице ID (ID ADR-0020).

Перед переключением в боте не хватает трёх вещей.

1. **Полного списка удаления.** Сейчас `reg-api` удаляет строки человека в `registrations`, `feedback`,
   `broadcast_targets`, `sessions`, `quiz_answers`, `quiz_attempts` и `users`. Не покрыты:
   - `reports`: сообщения человека;
   - `event_staff`, `staff`, `staff_invites`: Part 2 ADR-0039, отложенная;
   - чужие строки, где id человека записан исполнителем действия: `registrations.checked_in_by`,
     `event_staff.granted_by`, `staff_invites.created_by` / `used_by`, `broadcasts.created_by`;
   - `events.staff_id`, автор события;
   - Store-ключи напоминаний `rm:<event_id>:<kind>:<telegram_id>` (живут 48 ч).
2. **Места для состояния доставки.** `lang`, `blocked_bot` и «последний контакт» сейчас лежат в `users`,
   а `users` уходит (ID ADR-0032 §1).
3. **Приёмника события ID.** Его нет. В ID QA `module_delete_url_events` указывает на заглушку.

## Решения владельца (2026-11-25)

1. **Автор событий не удаляется, пока за ним числятся события.** Строка `events` с его `staff_id` не
   обезличивается и не удаляется каскадом.
2. **В чужих строках поле с id человека обезличивается.** Строка остаётся, в поле больше нет id.
3. **QA-ключ для проверки подписи ID ставит агент через MCP.** Ключ prod задаёт владелец, и он
   отличается от QA.

## Решение

### 1. Один список удаления, один исполнитель: подфлоу `fn-delete-person`

Всё, что бот знает о человеке, удаляет один подфлоу. Он получает `telegram_id` и возвращает
`{done, reason}`. Его вызывают:

- `reg-api` при самоудалении, до переключения;
- приёмник событий ID (§3), всегда.

После переключения `reg-api` вызывает `account-delete` ID, а удаление в боте приходит через приёмник
(ID ADR-0032 §5). Так список живёт в одном месте. Правило ADR-0039 остаётся в силе: пакет, который
заводит новое касание с `telegram_id`, обязан добавить его в этот подфлоу.

Порядок внутри подфлоу:

1. **Проверка автора.** Ищется `events` по `staff_id = telegram_id`. Если найдена хоть одна строка
   (любой `status`), подфлоу делает всё остальное по списку, но `events` не трогает и возвращает
   `done: false, reason: author_of_events`.
2. **Удаление своих строк:**
   - `registrations`, `feedback`, `broadcast_targets`, `sessions`, `quiz_answers`, `quiz_attempts`;
   - `reports` (новое);
   - `event_staff` по `telegram_id` (новое, права контролёра);
   - `staff` (новое, права организатора);
   - таблица доставки §2 (новое);
   - `users`, пока таблица существует.
3. **Обезличивание чужих строк.** Поле очищается в строках, где id человека записан исполнителем:
   - `registrations.checked_in_by`;
   - `event_staff.granted_by`;
   - `staff_invites.created_by` и `staff_invites.used_by`;
   - `broadcasts.created_by`.

   Очистка идёт через `tables-update-records` с «Clear Columns». Если на сборке очистка окажется
   недоступной для поля, ставится сентинел `-`, как в остальном боте. Чекин, права и история рассылок
   других людей не меняются.
4. **Store.** До удаления `registrations` из неё берутся `event_id` человека. По ним удаляются ключи
   `rm:<event_id>:24h:<id>` и `rm:<event_id>:2h:<id>`, а также ключ дневного обновления профиля
   (ID ADR-0032 §3; его имя задаёт ADR переключения).
5. `done: true` возвращается только после всех шагов и только без автора событий.

Требования к сборке:

- **Отказ при ошибке (fail closed).** Ошибка любого удаления или очистки валит подфлоу. Ответ
  `done: true` при оставшихся строках невозможен.
- **Пустой список — не ошибка.** `tables-delete-record` с пустым `records_ids` падает с `400`
  (W98). Поэтому удаление либо идёт циклом, где пустой список даёт ноль итераций, либо идёт одним
  шагом на таблицу с `continueOnFailure` и следующим шагом-проверкой. Проверка валит прогон, если список
  был непустым, а шаг упал. Маршрутизатор не годится: ветки не сходятся.
- **Укладывается в 15 с.** ID ждёт ответа приёмника не дольше 15 с (ID ADR-0017). Время замеряется на
  QA на человеке с регистрациями, рассылками и правами. Если подфлоу не уложился, ID повторит запрос
  через 5 минут. Повтор безопасен: удаление идемпотентно, второй проход находит пустые списки.
- **Логи.** Ввод и вывод выключены на каждом шаге, который несёт строки людей (ADR-0005). В логе
  остаются только счётчики и `reason`.

### 2. Таблица доставки `bot_contacts`

| Поле | Тип | Примечание |
|---|---|---|
| `telegram_id` | text, ключ (`keyFields`) | DAT-1 |
| `lang` | text | `ru` \| `uz` \| `en`, язык интерфейса бота |
| `blocked_bot` | boolean | ставит `bcast-run` на ответ Telegram 403 |
| `last_contact_at` | timestamp | последний апдейт от человека, UTC |

- Это данные модуля, как `registrations`. В ID они не уходят.
- Удаляется подфлоу `fn-delete-person`.
- Таблица создаётся в этом пакете. Писать в неё начинает пакет переключения: `tg-router` вместо
  `users`, `bcast-run` для `blocked_bot`. Начальные значения переносятся из `users` одним прогоном перед
  переключением, с отчётом только из чисел.

### 3. Приёмник `id-member-deleted`

Вебхук в `events-dev`. Шаги:

1. **Проверка подписи ID** (ID ADR-0018). Тип в конверте должен быть `id.member-deleted.v1`, модуль —
   `events`.
   - Подписанная строка: `"id.member-deleted.v1"\nevents\n<ts>\n<request_id>\n<sha256(canon(body))>`,
     HMAC-SHA256 ключом `id_module_key`.
   - Окно `ts` — 300 с, перекос — 60 с, как в ID `fn-verify-sig`.
   - Защита от повтора: Store `put_if_absent` `idrq:<request_id>`, TTL 360 с.
   - Это Code step с `node:crypto`, пятое узкое место после ADR-0010 и ADR-0058. Ввод и вывод выключены.

   Неверная подпись — ответ `401`, повтор — `409`. Удаления в этих случаях нет.
2. **Проверка тела.** `telegram_id` — строка `^[1-9][0-9]{0,15}$`, иначе `400`.
3. **Удаление.** `fn-delete-person` вызывается inline с ожиданием ответа.
4. **Ответ:**
   - `200 {done: true}` — только при `done: true`;
   - `200 {done: false, reason: "author_of_events"}` — если человек автор событий. ID это не засчитывает;
   - `500` — при любой ошибке.

Приёмник никогда не вызывает ID, поэтому петли нет (ID ADR-0032 §5).

### 4. Автор событий

- **Самоудаление в боте.** До удаления `reg-api` проверяет `events.staff_id`. Если человек автор
  событий, удаления нет: ответ `409 author_of_events` и текст `profile.delete.author` в трёх языках.
  Текст говорит, что сначала события нужно передать другому организатору. После переключения проверка
  остаётся в `reg-api` до вызова `account-delete`, поэтому ID удаление не запускает.
- **Удаление, пришедшее из ID** (страница ID, отзыв модуля, ручное удаление по ID ADR-0021, неактивные
  по ID ADR-0022). Отказать ему нельзя. Приёмник удаляет всё остальное и не подтверждает удаление. В ID
  строка `deletion_log` остаётся открытой: `pending`, затем `failed`, а через 7 дней `stopped`.
  Владелец получает алерт (ID ADR-0027, ADR-0028).
- **Что делает владелец по алерту:**
  1. Переназначает `staff_id` событий человека на другого организатора в UI платформы.
  2. Запускает повторную отправку в ID (ID ADR-0027).
  3. Приёмник подтверждает удаление.

  Срок ручного удаления — 3 рабочих дня (ID ADR-0021).

### 5. Ключ и адреса

- **`id_module_key`** — секретная переменная `events-dev`, равная `module_key_events` в ID QA.
  - На QA её ставит агент через MCP и не выводит значение (решение владельца 3; риск QA-ключей принят,
    ID ADR-0031 §3).
  - Ключ prod задаёт владелец, отдельно и с другим значением.
- **`module_delete_url_events`** в ID QA меняется с заглушки на адрес приёмника только после пункта
  «Ворота» ниже.
- Адреса API ID для чтения и записи профиля в этом пакете не нужны. Их заводит пакет переключения.

## Порядок и ворота

1. **`fn-delete-person`**, список §1 целиком. `reg-api` переходит на него с проверкой автора §4.
   Проверка: выдуманные люди тестового диапазона в каждой таблице, включая автора событий,
   контролёра, отметившего чужой чекин, и автора инвайта. Пустые таблицы. Повторный запуск.
2. **`bot_contacts`**: таблица создана, пустая.
3. **`id-member-deleted`**: подпись, повтор, окно, тело, ответы, время ≤ 15 с. Подписанные запросы с
   выдуманными id.
4. **Ворота:** пункты 1–3 приняты владельцем. Только после этого `module_delete_url_events` в ID QA
   указывает на приёмник, и выполняется сквозная проверка: `account-delete` ID → приёмник → `deletion_log`
   `done`. Инвариант 6 ID и политика обещают удаление во всех модулях. До этих ворот приёмник не
   подключается.

## Следствия

- **Part 2 ADR-0039 закрыта.** Аккаунт staff удаляется полностью, кроме автора событий: он ждёт
  владельца, и это видно в алерте ID, а не теряется молча.
- **История чекинов, прав и рассылок у других людей остаётся,** без имени исполнителя. Кто отметил
  чекин или выдал права, после удаления не узнать. Это цена удаления.
- **Организатор, который ни разу не создавал событий,** удаляется сразу и теряет права. Вернуть права
  может только владелец, новой строкой в `staff`.
- **Подфлоу удаления становится обязательной точкой.** Новое касание с `telegram_id` без строки в
  `fn-delete-person` — дефект удаления.
- **Время ответа приёмника растёт с числом строк человека.** Если оно подойдёт к 15 с, это решается
  отдельно: параллельные шаги или асинхронный ответ с подтверждением позже. Для асинхронного ответа
  нужен новый ADR в ID.

## Альтернативы

- **Обезличить `events.staff_id`** (рекомендация агента). Отвергнуто владельцем: автор события должен
  быть передан явно, а не потерян.
- **Удалять события автора каскадом.** Отвергнуто: удаляет регистрации, отзывы и рассылки других людей.
- **Удалять чужие строки целиком.** Отвергнуто: у участника пропадает отметка о приходе, у контролёров —
  права.
- **Два списка: в `reg-api` и в приёмнике.** Отвергнуто: списки разойдутся. Пропуск `reports` в
  нынешнем списке — пример того, как это происходит.
