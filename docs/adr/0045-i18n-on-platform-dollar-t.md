# 0045. Возврат i18n на платформенном `$t`

**Статус:** принято, 2026-09-27. Снимает приостановку I18N-1/I18N-2, введённую
[ADR-0014](0014-russian-only-until-platform-i18n.md); реализует решение
[ADR-0044](0044-platform-novelties-sep-2026.md) п. 3.2 «берём, путь W25».

## Контекст

ADR-0014 приостановил I18N-1/I18N-2 до появления платформенного i18n
([qadam-flow#420](https://github.com/aiqadam/qadam-flow/issues/420)) и записал
порядок возврата: если #420 закрыт «как задумано» — строки уезжают bulk-импортом,
входы `texts` заменяются платформенной подстановкой, `i18n-sync` не воскрешается,
эталон `i18n-resolve` не возвращается.

2026-09-26 #420 закрыт (PR #550/#553). Платформа дала:

- синтаксис `{{$t['ключ']}}` (и динамическую скобку `{{$t['ключ'][expr]}}`);
- цепочку локали: явная скобка → **локаль прогона** (`FlowVersion.localeSource`)
  → `project.defaultLocale`; каждое звено ещё и базовая языка (`ru-RU` → `ru`);
- наследование локали вызванным subflow (inline — в процессе, queue — заголовком);
- MCP-ручки `ap_list/upsert/delete_translations`, `localeSource` в
  `ap_build_flow`/`ap_import_flow`;
- отсутствующий ключ **валит шаг** (`TranslationKeyNotFoundError`), а не отдаёт
  ключ-заглушку, как наш `t(key)`; пустое значение `''` — «перевода нет»,
  цепочка идёт дальше.

## Решение

**Строки флоу живут в платформенных переводах; вход `texts` CODE-шага хранит
ссылку `{{$t['ключ']}}`, а не литерал.**

1. **Импорт.** Все ключи, на которые ссылаются флоу (198), импортированы в
   платформенные переводы из `i18n/*.json`; репозиторий остаётся источником
   правды. Значения `ru` полны; `uz`/`en` заполнены (см. «Цена»).
2. **Вход `texts`.** Каждое значение — `{{$t['тот-же-ключ']}}`; `t()` внутри
   CODE-шага не изменился (подставляет `{name}`/`{title}`/…). Расхождения
   ловит `tools/check-texts.py` офлайн: значение обязано быть ссылкой на
   существующий ключ `i18n/ru.json`.
3. **Локаль прогона — только у входа.**
   - `tg-router` (единственный Telegram-триггер) несёт
     `localeSource = {{step_1['output'].languageCode}}` — шаг нормализации уже
     достаёт `message.from.language_code` и `callback_query.from.language_code`.
     Все вызываемые им флоу наследуют локаль.
   - Вебхук-флоу Mini App (`checkin-*`, `manage-api`, `events-api`, `reg-api`,
     `feedback-api`, `my-qr-api`, `staff-events-api`, `staff-invite`) **своего
     `localeSource` не имеют намеренно**: свой перебил бы наследование. Локаль
     приходит заголовком `ap-parent-run-locale`, который SPA ставит из
     `Telegram.WebApp.initDataUnsafe.user.language_code` (значение санитизируется
     платформой, это лишь предпочтение поиска).
   - Флоу без контекста (расписания `lifecycle`/`reminders`/`dedup-report`)
     падают на **`project.defaultLocale = ru`**.
4. **`project.defaultLocale = ru` — обязательное условие.** Без него цепочка
   локали пуста (в ней нет `ru`), и любой `$t` валит шаг. Это разовая настройка
   UI (Settings → General → Default locale).
5. **Mini App.** `pick()` по `user.language_code` (ru/uz/en, иначе ru) вернулся;
   русский словарь грузится всегда как основа, словарь языка — поверх
   (**фолбэк по каждому ключу**: неполный `uz`/`en` показывает русскую строку, а
   не сырой ключ). Даты — `Intl` на языке пользователя, таймзона по-прежнему
   `Asia/Tashkent` (OWN-3).
6. **`i18n-sync` не воскрешается, таблица `strings` не читается и остаётся
   пустой**; `i18n-resolve` не возвращается.
7. **I18N-1/I18N-2 в SPEC сняты с паузы:** языка три, строк во входах шагов нет —
   только ключи.

## Цена

- **Полные `uz`/`en` ещё не вычитаны носителем.** W25 заполнил все flow-ключи,
  но вычитка — работа человека; Mini App-ключи (246, в `texts` не входят)
  догоняются пакетом [W27](../BACKLOG.md#w27-догон-переводов-uz--en). До этого
  недостающие ключи падают на `ru` (фолбэк платформы и per-key фолбэк SPA).
- **Мульти-адресатные рассылки расписаний** (`reminders`, `reg-afterword`,
  `bcast-run`) получают локаль `ru` по дефолту проекта: один прогон шлёт многим,
  а локаль прогона одна. Локализация по получателю — динамическая скобка
  `{{$t['ключ'][получатель.lang]}}` с чтением `users.lang` — осознанно оставлена
  хвостом, а не сделана вслепую.
- **Отсутствующий ключ валит шаг.** Поэтому порядок обязателен: сначала импорт
  переводов, потом публикация флоу с `$t`. Офлайн-проверка ловит только ссылку
  на существующий ключ `ru.json`; наличие значения для локали проверяет
  `ap_validate_flow` и падение на `ru`.
- **`localeSource` на существующем флоу задаётся только UI или импортом**
  (`ap_import_flow` несёт поле, отдельной MCP-ручки `UPDATE_LOCALE_SOURCE` нет).

## Что не изменилось

- Сырой ключ на экране вместо пустоты, «ни одной строки литералом в шагах
  отправки», подстановка `{…}` без повторного прохода, даты через `Intl` — всё
  в силе. Никакой разметки Telegram в строках.
- Хранение дат — UTC, показ — `Asia/Tashkent` (OWN-3); на язык это не влияет.

## Альтернативы

- **Вторая ветка ADR-0014** (воскресить `i18n-sync` + `i18n-resolve`) —
  отвергнуто: #420 закрыт как задумано, обвес не нужен.
- **`localeSource` на каждом вебхук-флоу из тела запроса** — отвергнуто: свой
  `localeSource` перебивает наследование, а заголовок даёт то же без правки
  контракта тел.
- **Хранить строки литералами, как в ADR-0014** — отвергнуто: ради этого W25 и
  возвращался; два источника текста снимаются.
