# 0013. Меньше сообщений на `/start`: карточка вместо четырёх сообщений

**Статус:** принято, 2026-09-13. Решение владельца проекта по замерам
[W22](../work/W22-latency-and-cleanup.md). **Меняет OWN-2** в [SPEC.md](../SPEC.md).

## Контекст

Разложение живого прогона `registration` `/start` (`vAVCNJuF1SedAdEPBhQzh`,
7,7 с) показало, что **отправка сообщений в Telegram — 2,98 с, 39 % прогона**,
и это самая дорогая категория после чтений таблиц:

| Сообщение | Шаг | Цена |
|---|---|---|
| карточка ивента (текст, адрес, ссылка на карту) | `step_20` | 860 мс |
| `sendVenue` — нативный пин | `step_22` | 727 мс |
| «точка на карте — сообщением выше» + ссылка | `step_24` | 723 мс |
| вопрос про согласие на ПД (кнопки) | `step_32` | 667 мс |

Плюс отдельное чтение `strings` ради одной строки `reg.venue.hint` — 531 мс.

Цена отправки одного сообщения (670–860 мс) — это Bot API, внутри платформы
она не лечится ничем. Единственный рычаг — не слать лишнего.

Содержательно три из четырёх сообщений говорят об одном и том же месте:
карточка уже содержит адрес текстом и ссылку на Яндекс.Карты, а третье
сообщение — подпись к пину плюс та же ссылка второй раз.

## Решение

**`/start` отправляет два сообщения: карточку ивента и вопрос о согласии.**

1. `sendVenue` с горячего пути убирается. Нативный пин на карте не отправляется.
2. Сообщение-подсказка «точка на карте — сообщением выше» вместе со второй
   копией ссылки убирается: без пина оно бессмысленно.
3. Адрес текстом и ссылка на Яндекс.Карты остаются **в карточке** — они там
   и были, ключи `event.card.where` и `event.card.map_link` не трогаются.
4. Ключ `reg.venue.hint` остаётся в `i18n/*.json` неиспользованным: его
   удаление — отдельная уборка, а не часть этого решения.

## Цена

- **Участник больше не получает нативный пин Telegram.** Тап по пину открывал
  карту в приложении Telegram; теперь открывается Яндекс.Карты по ссылке.
  Это ухудшение для того, кто нажимал именно на пин.
- **OWN-2 переписывается**, а не обходится молча: требование «точка
  отправляется через `sendVenue`» больше не выполняется и не должно
  проверяться на приёмке.
- Если пин понадобится вернуть — он возвращается одним шагом и стоит
  ровно те же ~0,7 с; решение обратимо.

## Что остаётся в силе

- OWN-2 в части «ссылка на Яндекс.Карты генерируется из точки, не хранится
  отдельным полем и не вводится руками» — не меняется.
- Ни одной пользовательской строки литералом (I18N-2): удаляются шаги,
  а не заменяются текстом.
- PAR-1/PAR-2: порядок согласий не меняется, вопрос о ПД по-прежнему
  отдельным сообщением с кнопками.

## Альтернативы

- **Слать пин, но убрать только подсказку.** Экономит 1,25 с из 1,45 с и
  сохраняет пин. Отвергнуто: пин без подписи в потоке из трёх сообщений
  подряд читается как случайный, а выигрыш почти тот же.
- **Слать всё одним сообщением с медиа.** Упирается в [Q21](../OPEN-QUESTIONS.md#q21)
  (FILE-пропы не резолвятся через MCP).
