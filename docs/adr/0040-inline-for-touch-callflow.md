# 0040. Касания из `tg-router` — `inline`, кроме `bcast-*`

**Статус:** принят 2026-09-24 владельцем (прямой запрос в чате, без пакета
BACKLOG). Дополняет и в части fire-and-forget **отменяет**
[W17](../BACKLOG.md#w17-inline-execution-mode-для-callflow-на-горячем-пути):
там `inline` предписывался только синхронным (`waitForResponse: true`)
вызовам, а fire-and-forget (`waitForResponse: false`) сознательно оставлялись
в `queue`.

## Контекст

`tg-router` — единственная точка входа бота (ADR-0015 п. 4). Из веток
`step_11` он делегирует касания обработчикам (`reg-start`, `reg-consent-pdn`,
`reg-consent-mkt`, `reg-profile`, `staff-accept`, `menu`, `bcast-*`). W17 и
конвенция каталога держали все эти вызовы в `queue` — «передал и не жду
ответа»: `inline` синхронен независимо от `waitForResponse`, родитель ждёт
всю длительность callee, включая отправку сообщений Bot API (~0,7–0,9 с
каждое).

Владелец решил перевести касания на `inline`, кроме рассылочных.

Единственное жёсткое ограничение фичи названо платформой: `inline` для
subflow запрещён, если тот делает паузу — `Delay`, Human Input/Approval или
собственный `callFlow` в режиме `queue`. На это ограничение и опирается
исключение для рассылок.

## Решение

1. **Касания из `tg-router` (ветки `step_11`) — `inline` при
   `waitForResponse: false`.** Это `step_12`→`reg-start`, `step_13`→
   `reg-consent-pdn`, `step_14`→`reg-consent-mkt`, `step_20`→`reg-profile`,
   `step_21`→`staff-accept`, `step_15`→`menu`. Результат вызова роутером не
   читается (как и раньше) — меняется только транспорт: родитель ждёт
   завершения callee, а не отдаёт его в очередь.
2. **`bcast-*` остаются `queue`** — `step_17`→`bcast-draft`, `step_18`→
   `bcast-step`, `step_19`→`bcast-unsub`. Не по стилю, а по запрету:
   `bcast-step` содержит `callFlow bcast-run`, а `bcast-run` делает `Delay`
   и самовызов `callFlow bcast-run` в `queue`. `inline` сломал бы продолжение
   рассылки чанками в рантайме.
3. **`lifecycle → reg-afterword` (`step_8`) — тоже `inline`.** Тот же класс
   (касание без пауз внутри), родитель — тик крона раз в 15 мин, а не
   апдейт пользователя.
4. **`fn-*` — `inline` как было** (`fn-parse-start` на `tg-router/step_9`
   синхронен и обязателен для маршрутизации; остальные `fn-*` — из W17).

## Цена

Названа прямо, решение принято с ней.

- **Fire-and-forget теряется.** Роутер ждёт весь вызванный тач, включая
  отправку сообщений Bot API (`~0,7–0,9 с` на сообщение). Апдейт, который
  раньше ставил задачу в очередь и сразу завершался, теперь занимает время
  касания. Латентности пользователь не видит (роутер молчит), но прогон
  `tg-router` удлиняется, и при деградации Bot API очередь апдейтов может
  копиться. `lifecycle` при `inline` отправляет послесловия
  последовательно, а не параллельно.
- **Инвариант, который теперь надо держать руками.** Если внутрь любого
  инлайнутого callee (`reg-*`, `menu`, `staff-accept`, `reg-afterword`)
  добавится `Delay`, Human Input/Approval или `queue`-`callFlow` — `inline`
  сломается в рантайме. Проверять при каждой правке структуры этих флоу.
- **Дрейф с W17.** W17 писал «не трогаем `tg-router → registration`,
  fire-and-forget, inline не применим». Формально вызывать `inline` при
  `waitForResponse: false` по-прежнему «не к чему», но решение владельца —
  применять его ко всем касаниям, кроме `bcast-*`.
