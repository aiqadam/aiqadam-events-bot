# 0032. Онбординг первого касания: профиль гостя, вариант C

**Статус:** предложен 2026-09-18 — на принятие владельцем. **Не меняет**
ни один ADR задним числом; при принятии потребует отдельной правки
[SPEC](../SPEC.md) (PAR-раздел: поля профиля) и
[DATA-MODEL](../DATA-MODEL.md) (`users`: новые поля) — таков порядок:
сначала решение, потом ТЗ со ссылкой на него.

## Контекст

До сих пор регистрация знала о госте только `telegram_id` и два согласия
(PAR-1, PAR-2): имя подтягивалось из апдейта справочно. Владелец решил:
участие в жизни сообщества AI Qadam — поимённое, поэтому первое касание
собирает профиль (имя, фамилия, должность, компания, город), а все
следующие касания — чистая регистрация без consent и без профиля.
Шторм вариантов — `prototypes/onboard.html` (A — чат по шагам,
B — форма в Mini App, C — гибрид с предзаполнением).

Ограничения, в которых выбирали:

- PAR-1: регистрация без согласия на обработку данных недействительна;
  спрашивать ПД до согласия — нарушение по духу, даже если текст согласия
  показывается позже;
- PAR-2: согласие на рассылку — отдельное, необязательное, не по умолчанию;
- DAT-1: ключ — только `telegram_id`; имя из Telegram — справочная подпись,
  в нём бывает мусор (`Crypto King 👑`, пустая фамилия);
- ADR-0017/ADR-0025: единица интерфейса — экран, вход — только `/start`;
  шестой роут Mini App — только новым ADR, поэтому вариант без зависимости
  от Mini App дешевле;
- `users.first_name/last_name` перезаписываются каждым апдейтом из Telegram —
  профиль в них хранить нельзя.

## Решение

1. **Два сценария.** Первое касание: объяснение «зачем данные» → согласие
   на ПД → профиль (5 полей) → создание регистрации → отдельный вопрос
   про рассылку. Повторные касания: карточка ивента → «Зарегистрироваться» →
   готово; consent и профиль не спрашиваются, профиль тихо показывается
   строкой «Дилшод · ML-инженер · изменить».
2. **Базовый вариант — C (гибрид).** Порядок шагов первого касания:
   согласие (`Согласен / Подробнее`) → имя из Telegram **только** через
   эвристику (п. 4): чисто → «Вы — Дилшод Азимов? [Это я / Поправить имя]»,
   подозрительно → кнопки «Это я» нет, только ручной ввод →
   «должность и компания одним сообщением» → город кнопками
   (Ташкент / Алматы / написать свой) → экран «Всё верно?» (регистрация
   до него не создаётся) → регистрация → маркетинг отдельно.
3. **Полный текст согласия — за кнопкой «Подробнее».** Лёгкий абзац в
   карточке называет состав данных (имя, фамилия, должность, компания,
   город, `telegram_id`), хранение у себя и отсутствие передачи третьим
   лицам; «Подробнее» раскрывает полный текст без ухода со сценария.
4. **Эвристика «подозрительное имя» — CODE-шаг, только роутинг, не запрет.**
   Вход — `first_name`/`last_name` из апдейта; выход — `suspicious + reason`.
   Проверки: короче 2 букв (включая пустую фамилию — профиль без неё всё
   равно не годится) → цифра → эмодзи → символ вне
   `/[^\p{L}\s\-'’‘ʼʻ`]/u` (буквы любого алфавита, пробел, дефис, апострофы
   включая U+02BB — `Oʻzbek` проходит, `xX_Dark_Xx` нет) → длиннее 40 знаков.
   Словарных блок-листов нет: обходятся, бьют по реальным фамилиям, требуют
   ведения. Настройка — в сторону придирчивости: ложное срабатывание стоит
   один лишний вопрос, пропуск — мусор в экспорте участников.
5. **Данные.** В `users` добавляются `position`, `company`, `city`
   (TEXT) и `profile_completed_at` (DATE); `first_name/last_name/username` —
   как были, справочно из апдейта. Недозаполненный профиль — это сессия
   (`sessions.draft`), не регистрация: PAR-1 держится тем, что строка
   в `registrations` появляется только после «Всё верно?».
6. **Город — кнопками, компания — с правом пропуска.** Ташкент / Алматы
   покрывают большинство и держат справочник чистым без ведения городов;
   компания необязательна (фриланс/студент), остальные четыре поля —
   обязательны.

## Следствия

- Реализация — отдельным пакетом BACKLOG (ещё не нарезан): расширение
  `reg-start` (эвристика + ветка), шагов профиля в `reg-consent-pdn`
  или новым касанием по ADR-0015, `reg-api` для каталога; правка SPEC
  (поля профиля, два сценария) и DATA-MODEL (`users`) отдельными коммитами
  со ссылкой сюда; ключи текстов — в `i18n/ru.json` (сегодня — во входах
  CODE-шагов по ADR-0014).
- Цена CODE-шага эвристики — 2–5 мс; поведение при мусоре — ручной ввод,
  а не отказ: отказ здесь не за что давать, человек настоящий.
- Различающие примеры (регресс пакета): `Дилшод / Азимов` → чисто;
  `Oʻzbek / Qodirov` → чисто; `Crypto King 👑` → `has_emoji`;
  `xX_Dark_Xx` → `bad_chars`; пустая фамилия → `no_surname`.

## Альтернативы

- **A (чат по шагам, 5 отдельных вопросов).** Отвергнут как базовый:
  длиннее C на два-три тапа при том же качестве данных; остаётся
  запасным — C схлопывается в A удалением предзаполнения имени, если
  приёмка покажет мусор в фамилиях.
- **B (форма в Mini App).** Отложен, не отвергнут: быстрее всего и чище
  данные, но полная зависимость от Mini App (нет приложения — нет
  регистрации) и вопрос шестого роута; доделывается вторым шагом внутри
  каталога `#/events`.
