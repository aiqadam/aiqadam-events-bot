# Flow: dedup-report

- **Статус**: ENABLED (published)
- **Триггер**: cron `0 3 * * *`, `Asia/Tashkent` (`@aiqadam/qadam-schedule : cron_expression`)
- **Назначение**: диагностика дублей строк — раз в сутки считает дубли по
  ключевой паре в `registrations`, `event_staff`, `broadcast_targets` и одним
  сообщением отдаёт счётчики организаторам; **ничего не удаляет** (Q42, W12b).
- **Flow ID (MCP)**: `zOjCtJKlvYqmvthgITW4L` · **externalId**: `2WPDkudf495YfCyJWS6ti`

## Заметки

- **Ни одной записи и ни одного удаления.** Все четыре `tables`-шага —
  `tables-find-records`, отчёт уходит сообщением; это и есть цель пакета
  (Q42, вариант 2: считать и сообщать). Проверяется `ap_flow_structure`,
  а не журналом.
- **«Лишние строки» = сумма `n−1` по ключам, встретившимся больше одного
  раза.** Так «число дублей» — это число строк сверх первой на каждую пару.
  Строка с пустой половиной ключа не судится (считать нечего). ADR-0011
  оставляет появление дублей данностью: `tables-upsert-records` — не
  уникальный индекс.
- **Метрика считает все повторы пары, включая ожидаемые.** В `event_staff`
  это revoked+active после возврата прав и вторая активная строка после
  повторного принятия инвайта; и то, и другое — штатное состояние
  ([event_staff](../../catalog/tables/event_staff.md),
  [manage-api](manage-api.md), [staff-accept](staff-accept.md)). Поэтому число
  отвечает на вопрос «сколько строк сверх первой на пару», а **не** «сколько
  мусора»: будущей уборке нельзя удалять строки, не различив активные и
  отозванные, — это сломает права контролёра.
- **Отчёт агрегатный, без `event_id`.** Цель пакета — знать число
  ([Q42](../../docs/OPEN-QUESTIONS.md#q42)); разбивка по событиям в него
  намеренно не входит. Когда встанет вопрос уборки (Q42, вариант 3), ей
  понадобится отдельный пакет — этот флоу адресов дублей не отдаёт.
- **`events` вне охвата.** Ключ `events` — одно поле `id` (уникально по
  замыслу, `manage-api` пишет upsert по нему), пары для счёта дублей у
  таблицы нет; пакет читает ровно три пары из BACKLOG.
- **Читаются только ключевые колонки** (`columns`), чтобы остальные поля не
  попадали в лог прогона. `telegram_id` в логе есть — он и есть половина
  ключа, без него счёт невозможен; в **сообщении** персональных данных нет,
  только имена таблиц и счётчики.
- **Получатели — строки `staff`** (глобальный список организаторов,
  [ADR-0024](../../docs/adr/0024-staff-by-chapter-event-staff-checkin.md)).
  Отдельного канала админов в проекте нет ([Q18](../../docs/OPEN-QUESTIONS.md#q18)),
  а `staff` — единственный список, который ведёт человек; сейчас это ровно
  одна строка — владелец проекта. Получатели дедуплицируются; пустой `staff`
  даёт ноль итераций цикла и молчание (отправлять некому).
- **Сообщение уходит и при нуле дублей.** Молчание неотличимо от несработавшего
  флоу, поэтому суточный отчёт — всегда; при нуле он показывает нули.
- **`continueOnFailure` на отправке** не даёт недоставке одному получателю
  оборвать остальных.
- **Пустой `staff`/таблица — не ошибка.** `arr()` нормализует и массив, и
  `{records:[…]}`, и `null`/`undefined` в `[]`; пустая таблица даёт `rows: 0`.
- **Чтение без `limit`** — таблицы читаются целиком (проверено: `limit` не
  обязателен, дефолт «no limit»). Это цена полноты счёта: проекция `columns`
  держит в логе только ключевые поля, но при росте `registrations` полный дамп
  может упереться в потолок размера лога и уронить прогон **до** отправки —
  тогда диагностика замолчит. При перерастании разумного размера потолок
  вводится осознанно, вместе с пометкой в тексте «счёт неполный».
- **Дата — Asia/Tashkent** (`Intl`, `ru-RU`, `DD.MM.YYYY`), как и везде в
  проекте (OWN-3): прогон 03:00 по Ташкенту не должен показывать вчерашнюю UTC-дату.
- **Тексты — из `i18n/ru.json`** (ключи `dedup.*`), сверяются
  `tools/check-texts.py`; новых литералов в шагах нет (ADR-0014, W24).
- **Один отчёт в сутки, время 03:00.** Ночью по Ташкенту, вне часов работы:
  диагностическое сообщение не конкурирует с боевыми.
